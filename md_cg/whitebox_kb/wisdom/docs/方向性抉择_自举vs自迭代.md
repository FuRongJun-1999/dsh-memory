# 方向性抉择：自举测试 vs 持续自迭代（2026-09）

**背景**：白箱代码能力已有 WB-SPEC 自评标尺（0.9851），现在面临方向选择。

## 一、事实核查（自举的可行性前提）

**protocol-compiler v0.3 现状**：
- 输出目标：**Python 代码 + 智能论字节码 VM**（零外部运行时依赖）
- condition_vm 25 条指令：PUSH/LOAD/STORE/JUMP/条件跳转/算术/比较/
  CALL/RETURN（调用栈帧）+ 条件空间原语（DAO 压入/DE 信任累积/ZIRAN 弹栈）
- **图灵完备基础已具备**（有循环跳转、条件、算术、函数调用、栈帧）

**中文 OS 现状**：os 域 112 单元是「迷你 Linux」**复现**（页置换/调度/文件系统
模拟单元）——不是可独立引导的操作系统，是条件单元库。

**关键约束**：编译器本身是 **Python 写的**（lexer/parser/codegen），
输出 Python——「自举」在这里的确切含义是：**用 protocol-compiler 编译一个
能编译 protocol-compiler 自身的中文程序**（编译器自举），而非 OS 引导。

## 二、两条路的分析

### 路线 1：自举测试（立即）

**做什么**：用中文编译器 + 中文编程语言，编译一个「能处理编译器逻辑」的
中文程序（如实现一个中文版的词法/语法简化器），跑在 condition_vm 上，
验证「我们的语言能表达计算逻辑」的闭环。

**收益**：
- 验证图灵完备的**真实落地**（VM 真能跑我们写的程序）
- 暴露 VM 缺陷（缺什么指令/栈帧问题/边界）——**最高价值的测试**
- 建立「我们的语言能自我表达」的证据（自举的种子）

**风险**：
- 编译器语法是「道德经助记符 + 九章算术结构」——**表达力受限**（VM 指令
  是定制的，缺高级特性如字符串/列表/闭包）
- 自举完整编译器（lexer+parser）工作量巨大（我们的 parser 41163 字节，
  需用中文语言重写）——**立即全自举不现实**，需分阶段
- 中文 OS 不是可引导系统——**「使用中文操作系统」当前不可行**（只有单元库）

### 路线 2：持续自迭代（渐进）

**做什么**：继续八步闭环——感知/吸收/简化（W6 效率/W7 可读短板）、
外部吸纳、频率条件反射固化。评分 0.9851 → 更高。

**收益**：
- 低风险，验证过的路径（自迭代机制已 26 套测试全绿）
- 补 W6/W7 短板（真实可改进：状态机简化、短名改善）
- 条件反射频率积累 → 高频路径固化

**风险**：
- **不验证核心命题**：我们的语言到底能不能真正自举？持续迭代只优化
  Python 实现，不证明「中文语言本身可用」
- 局部最优风险：0.9851 已高，继续优化收益递减

## 三、我的建议：两阶段（路线 2 现在，路线 1 验证后）

**理性路径**：不是二选一，而是**条件化选择**——

1. **现在（路线 2 为主）**：继续自迭代，但**补一块「自举预研」**——
   用中文语言 + VM 写一个**最小自举探针**（mini 计算器/小编译器片段），
   验证 VM 图灵完备真实落地。这是低成本的路线 1 探测。
2. **探针通过后（路线 1）**：扩为「中文编译器自举」——用中文语言重写
   protocol-compiler 的词法分析器（lexer 16440 字节，是自举的最小完整
   组件），跑在 VM 上编译自己。这是真正的自举第一步。
3. **中文 OS**：暂不作为自举目标（当前是单元库非引导系统）——可
   先验证「OS 单元能否在 VM 上运行」（如页置换算法用中文重写跑 VM）。

**为什么这样选**：
- 自举是**终局验证**（证明语言可用），持续迭代是**过程优化**（证明
  实现质量）——两者不冲突，是同一主线的前后半段
- 最小自举探针风险小、信息价值高（暴露 VM 真实缺陷——比任何评分
  都更能驱动迭代）
- 符合 PROP-LOCAL-OPTIMUM-005：0.9851 是局部最优，**新信息（自举探针
  暴露的 VM 缺陷）就是打破局部最优的正确触发**
