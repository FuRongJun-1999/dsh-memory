## 3. 可借鉴点清单（按建议优先级排序）

> 每条五段式：**gbrain 机制** → **灵枢现状**（2026-09-19 实测取证）→ **建议落点** → **验收** → **落地状态**。

### ②★P0 事实有效期进入查询语义（highest：字段与判定已在，只差消费）

- **gbrain 机制**：`facts` 表把「记忆的后半生」做成一等公民——`valid_from / valid_until / expired_at` 三戳表达有效期，「过期」由查询侧判定，不是人工清理任务（报告 §3 生命周期行、§10 第 2 条）。配套 `superseded_by BIGINT REFERENCES facts(id)` 自引用链：**纠错不是删除**。
- **灵枢现状**（实测取证，逐条可复核）：
  - 字段**已在**：`valid_from` / `valid_until` —— `md_cg/nodefile.py:122-123`（`VALID_FROM_FIELD` / `VALID_UNTIL_FIELD`，注释自陈「`valid_until` 既有（已被 scrub 的过期消费面使用）；`valid_from` 本轮补齐」）+ `md_cg/trust.py:61-62`（`FROM_FIELD` / `UNTIL_FIELD`）。
  - **`expired_at` 在灵枢零命中**（全仓唯一命中即本报告自身）——灵枢以 `valid_until` + 验证态 `expired` 表达过期，**不设第三戳**。故本条的灵枢形态是「**双时间戳 + 状态**」，与 gbrain 的「双时间戳 + 过期戳」是**同构不同形**（差异如实列出，不视为缺陷）。
  - 判定函数**已在**：`md_cg/trust.py:225-242` `validity(fm, now)` → `unknown / not_yet / active / expired` 四态。
  - 消费面**只在治理/展示侧**：`trust.patrol`（`trust.py:500-524` 巡检粗判 expired/not_yet 清单出报表）、`md_cg/statushdr.py:77`（状态头展示）、`md_cg/coldverify.py:148`（冷启动复核转 expired 态）。
  - **检索面零处理（关键缺口）**：`mdcg.search` / `mdcos.search_rrf` / `mdcos.recall` / `mdcg._candidates` / `mdcos._candidates` **均无 `validity` 调用**——`_candidates` 的过滤维度现有 layer / session / branch / roles，**没有有效期**。即：**过期节点仍会作为正常候选参与召回**。
- **建议落点**：`md_cg/mdcos.py` 的 `_candidates`（一处过滤全链路生效，与既有 `session=` / `branch=` 过滤同构——该位置已被 Pi④ 验证为「改一处、search/search_rrf/recall 三签名透传」的正确落点）；`mdcg._candidates` 同步（子类覆盖，历史教训：首轮漏改被测试抓住）。**处置语义建议先出裁决再动手**：`expired` 与 `not_yet` 是否同等对待（gbrain 的三戳里 `expired_at` 与 `valid_until` 可分离，灵枢无第三戳 → 需明确「未生效」与「已过期」是否同为不可召回）。参数建议 **opt-in 开关注入**（对齐 `session=`/`branch=` 的「一处过滤全链路生效」与仓内「默认零回归」惯例）。
- **验收**：① 断言 `validity=expired` 节点**不入候选池**（口径同 Pi④ 分支过滤：以「nid 不在命中集」为准，而非「结果为空」）；② `not_yet` 处置按裁决断言；③ `active` / `unknown` 节点召回**逐位不变**（零回归）；④ 全量回归零新增失败。
- **落地状态（2026-09-19）：未开工** · 资格裁决=**ACCEPT**（依据：字段在+判定在+查询面缺位，「已有的判定函数无人消费」是确定性缺口，非相似度推断）。

### ④P2 能力探测降级（fourth：裁决为 DEFER，先取证再动工）

- **gbrain 机制**：`gbrain/src/core/capability.ts` 探测 embeddings 可用性 → `search: 'semantic' | 'keyword-only'`；无 key 时 **BM25 关键词检索完全可用**，加 OpenAI/Voyage key 升级语义检索（混合向量+关键词）。「keyless 先行、按需升级」是其 30k★ 体验的一部分（报告 §0、§6、§10 第 4 条）。
- **灵枢现状**（实测取证）：
  - `bm25` **全仓零命中**（区分大小写检索确认）——灵枢**没有 BM25**，其词法侧是 char-bigram 主链路 + 独立的中英归一原子 + Jaccard 路（`md_cg/semantic/REPRODUCE.md` 双语双路裁定）。
  - 所有相关开关都是**部署期 env**，不是运行期探测：`MDCG_SEMANTIC`（`md_cg/mdcg.py:221-232` `semantic_on()`，注释「默认关闭零回归」）、`MDCG_EN_ATOMS`（`mdcg.py:235-301`，默认 `"0"`）、`MDCG_TOOL_FACE`、`MDCG_MCP_SURFACE`、`MDCG_S7_FRESHNESS`。
  - **灵枢天然零依赖**（无 `requirements.txt` / `pyproject.toml`，主链路纯标准库）→ 「无 API key 完全可用」是**结构性的**，比 gbrain 的「keyless 先行」更彻底：gbrain 无 key 需**退**到 BM25，灵枢**根本不存在该调用**。
  - **降级先例已在（但非探测）**：`mdcg.py:254` 注释「semantic 模块缺失时**静默降级**（不阻断主链路）」；`hive/exec.py` 有**零依赖探测**先例（PNG IHDR / JPEG SOF 读尺寸，不读像素）。
- **建议落点**：**先取证，暂无落点**。真正可迁移的不是「检索降级」（无靶：问题本体是 gbrain 的 embedding 依赖），而是「**能力差异应自动判定而非部署期人工配置**」——即在**多端部署面**把 `MDCG_SEMANTIC` / `MDCG_EN_ATOMS` 一类开关改为「能力自动判定 + 显式覆盖」。但此改动的前提是：存在**真实受损场景**（使用者或某端因不知要开开关而实际损失召回）。
- **验收（DEFER 的解除条件）**：先取证「semantic 路默认关闭导致的可感知召回损失」是否有实例（对齐 Pi⑦「取证结论：默认路径结构性已满足，未做无靶改动」的先例）。**有实例** → 落点=开关改能力自适应，验收=断言「能力可用且未显式覆盖时自动启用 + 显式 override 优先 + 能力探测失败静默降级不阻断」（须保持零依赖）；**无实例** → 本条结案为「**结构性已满足，不学**」，并把它写进 §4 反面清单的姊妹条（避免后续重复立项）。
- **落地状态（2026-09-19）：未开工** · 资格裁决=**DEFER**（依据：capability.ts 解决的是灵枢不存在的问题本体；缺失维度=条件边界「谁是受损者」未取证；**不得为对齐外部做无靶改动**）。

## 4. 反面清单（不学什么）

> 素材来源：报告 §4（治理例外清单）、§5（HTTP/MCP 治理）、§8（多 agent 与信任边界）、§9（哲学对照表）。

| 对方做法 | 为什么不学 | 灵枢对应原则 |
|---|---|---|
| **DB-only by design**：凭证 / `mcp_request_log` / 任务队列 / `raw_data` / `dream_verdicts`（30 天 TTL）/ withdrawal ledger / durable receipts / outbox 均只落 DB，不进 Markdown | 灵枢**真源唯一且是 md 文件**——主链路零 SQLite、派生索引可随时重建是架构决定；一旦开设「DB-only 例外清单」，例外会随需求扩张并最终使 md 真源名存实亡 | 真源唯一 · 派生可重建 · 主链路零外部依赖 |
| **「DB-only for now」偷懒路径**（gbrain 用 CI 门程序化拦截「新增派生表持用户知识却不 FS-first」） | ——**这条不是不学，是学做法**：其价值在「**把偷懒路径做成机器红灯**」而非「人工评审记得拦」 | 与 `scripts/cogmap_sync.py check`（手写行号禁令 / 文件链接守卫）、`scripts/verify_discipline.py`（声明出口 strict）同构——**门禁化是仓内既有方针**，本条作为正面做法单列 |
| **ambient writeback**（对话随口陈述自动写回知识库；默认关闭，公司脑永不开启） | 灵枢写路径已有三道闸（六要素校验 DEFER → 审核队列 / 冲突拦截 / REJECT 负记忆）；自动写回会让「未发现拒绝理由」冒充「确认适用」——灵枢已明确 REJECT 过同类设计 | 未验证不写入 · 写入须过闸门 · 判定归使用者 |
| **队列 TTL 自动放行**（`dream_verdicts` 30 天过期即视为通过） | 灵枢已在审核队列议题上**显式 REJECT 过该候选**（理由：TTL 放行=「未发现拒绝理由冒充确认适用」）；裁决必须显式发生（`cg(op=review, decision, reason)`），不设静默过期 | 裁决显式化 · 未验证不固化 |
| **信任外推**（哲学=「仓库即大脑，真源/备份/验证都推给用户自管」） | 灵枢的定位是**治理内置**（五层 + 条件论 + 白箱化）：结构强制可复算、revision 乐观并发、权限按 op 分档、审计留痕——把验证责任外推给使用者与「白箱化」方向直接冲突 | 治理内置 · 结构强制可复算 · 可审计 |
| **单智能体笔记本定位**（gbrain 作者自述：单写入者假设，无多 agent 并发语义） | 灵枢是**蜂群互联**形态（hive Rust 并发调度 + `session`/`writer` 归属 + `branches` 实验分支隔离 + 互维心跳）；引入单写入者假设会击穿既有的归属与隔离语义 | 多会话归属 · 分支隔离 · 蜂群并发 |
| **PGLite（嵌入式 Postgres/WASM）作为派生索引底座** | 灵枢主链路零依赖（无 `requirements.txt` / `pyproject.toml`）；为对齐其检索形态而引入 DB 运行时，会同时牺牲「零配置可跑」与「派生可重建」两条既有资产 | 零依赖 · 零配置可用 |
| **BM25 词法引擎**（gbrain 无 key 时的检索引擎） | 灵枢词法侧已是 char-bigram 主链路 + 中英归一原子 + Jaccard 路（双语双路已裁定），加 BM25 属**同层第二实现**（对照 §3④：`bm25` 全仓零命中，问题本体不存在） | 单一真源 · 不设同层重复实现 |
