## 0. 一句话立项

给灵枢大脑建一条**记忆评审流水线**：确定性模块选条目、捆条目、配规则 → **蜂巢并发**跑 LLM 复核包 → verify 角色字段级落库 → 治理工单回流。它同时是三件事的答案：验证单元对记忆的**复核校验**、蜂巢并发的**第一个大规模用例**、9-15 审计遗留问题（role 空/evidence 缺/重复/宽进）的**治理产能**。

## 2. 立项依据（为什么是现在）

1. **审计实证的治理欠账**（2026-09-15 审计，node_26b0973a）：knowledge 层索引混层 57.9%、role 存量 99.99% 空、evidence_count 仅 6 条、精确重复 90 条、同模板冗余 233 条、闸门 DROP/DEFER=0（宽进）、召回率 7%。
2. **OCR 规模验证**：阿里两年/数万开发者验证「确定性硬约束×LLM」在评审域有效——同模型 Precision/F1 更高、token 仅 1/9。三痛点（覆盖不全/位置漂移/质量不稳）与记忆写入质量问题一一对应。
3. **蜂巢产能待用**：hive 引擎（worker 池/心跳/强杀/恢复）+wm 三级闸已交付，缺大规模真实用例；记忆评审的「捆绑并发评审」正是其设计目标场景（rust 管并发与生命周期，python 管协议与 LLM）。
4. **验证单元已有地基**：11 模块盘点（灵枢 node_160ca242）——crosscheck 双单元裁决、verify 角色写权限互斥、mdcos 审核队列、forgetting 三问四态。缺的只是三个模块（§4）。

## 3. 架构总设计：五级流水线

```
[1 候选生成] → [2 捆绑] → [3 规则装配] → [4 蜂巢并发评审] → [5 落库与治理]
   确定性        确定性       确定性         LLM(蜂巢 job)      确定性收口
```

| 级 | 职责 | 确定性/LLM | 既有地基 |
|---|---|---|---|
| 1 候选生成 | 产出待评条目清单：census 断言超限项 + 闸门 DEFER 队列 + 冷节点抽样 + 轮巡 | 确定性 | census.py（Pi ⑤ 产品化）、`_forgetting.jsonl` DEFER 记录 |
| 2 捆绑 | 按模板签名组/同源（migrated_from）/同主题聚类成包；**同模板组一包一评，一次裁决全组** | 确定性 | writelimit 的模板签名函数（`tmpl_sig`）可直接复用 |
| 3 规则装配 | 按包特征（层/tags/来源执照/字段覆盖率）从规则库装配检查集 | 确定性 | `crosscheck.SOURCE_POLICY`（雏形泛化，见 D3） |
| 4 并发评审 | 每包一个 hive job：spec=条目包+规则集+定位上下文，worker LLM 产字段级意见 | **LLM（蜂巢）** | hive scheduler+wm；spec/result 契约见 §5 |
| 5 落库治理 | verify 角色校验意见格式 → 意见落 rejected/contextual → 治理工单（回填/合并/降权建议）→ designer 终裁执行 | 确定性收口 | verify 令牌 layers_allow **正好允许**；mcdcos 审核队列复用为工单终裁 |

**分工原则（对齐 OCR）**：机械可算的（重复率/字段完整性/同 hash 组）在蜂巢 job **之前**跑，LLM 只看机械检查无法裁决的语义问题——确定性优先，省 token（OCR 实证 1/9）。

## 4. 三个缺口模块设计（本项目新建件）

### D1 字段级定位模块（对齐 OCR 独立定位）

- **输出契约**：`locate(node_id, issue_hint) -> [{field, span, issue_kind, evidence}]`——field ∈ frontmatter 字段名或 `content`；span = 字符区间或句索引；issue_kind ∈ {dup, missing_field, stale, contradiction, weak_source, template_flow}。
- **实现要点**：①frontmatter 字段级检查直接逐字段扫描（role 空/evidence=0 这类机械定位零成本）；②content 内定位：同 hash 组内 diff 定位差异句（模板流水的"每次只换数字"正是 diff 可见）；③与 `provenance.py` 关系：provenance 管节点间血缘（不动），本模块管**条目内部**定位（新建 `md_cg/mreview/locate.py`）。
- **验收**：对审计已知问题抽样 20 条，字段级定位人工核对准确率 ≥90%。

### D2 反思模块扩展（对齐 OCR 独立反思）

- **现状**：crosscheck 的 verify_prompt 只复核「验证方式」单字段。
- **扩展**：新增**内容复核 prompt 模板**（`md_cg/mreview/prompts.py`）：输入=条目全文+装配规则集+D1 定位候选，输出=结构化意见 JSON：`{verdicts:[{node_id, field, span, issue_kind, verdict(ACCEPT/MERGE/DROP/DEFER), evidence}], summary}`。
- **独立性约束（不可妥协）**：复核执行者持 verify 令牌（只能落 rejected/contextual，禁改 knowledge——`tokens.py:127` 结构保证）；复用 `crosscheck.detect_self_verify` 检出「写入者=复核者」即违例；意见落库后走 mdcos 审核队列终裁（红队门控/判据指纹既有机制全复用）。
- **验收**：意见 100% 过格式校验；自验违例检出测试通过。

### D3 规则装配模板引擎（对齐 OCR 规则匹配）

- **现状**：检查规则以枚举+阈值散落（forgetting 的 DUP_MERGE 阈值、census 的断言、SOURCE_POLICY）。
- **设计**：规则库统一格式 `rule = {id, matcher: {layer?, tags?, source_license?, field_cov?}, checks: [机械检查|llm检查], severity}`；装配器 `assemble(bundle) -> ruleset` 按包特征选规则。**机械检查在 job 前本地跑完**（结果作为 llm 检查的上下文输入），llm 检查才进蜂巢。
- **验收**：新增一条规则不改引擎代码；装配结果可 dump 审查（白箱）。

## 5. 蜂巢对接契约（评审 job 的 spec/result）

```jsonc
// hive jobs/<id>/spec.json
{
  "model": "<评审模型>",
  "system_prompt": "记忆评审员：只依据规则集与定位证据裁决，不臆测；输出严格 JSON。",
  "context_files": ["bundle.json", "rules.json"],   // 包内条目(裁剪后)+装配规则集
  "user_prompt": "对 bundle.json 中每条目按 rules.json 逐检查项裁决…输出 {verdicts:[…], summary}",
  "timeout_s": 600
}
// result.json（执行器写回，ok:true 才过 wm 凭证闸）
{ "ok": true,
  "verdicts": [{"node_id":"…","field":"role","span":null,
                "issue_kind":"missing_field","verdict":"DEFER",
                "evidence":"frontmatter 无 role，来源=agent 令牌即可回填"}],
  "summary": "…" }
```

- 评审 job 由**主代理侧**批量提交（hive_spawn），poll 收卷后走第 5 级落库——**蜂巢 worker 不直写认知图**（wm 三级闸语义：worker 产物只是意见，落库归灵枢写入通路+verify 令牌）。
- 吞吐预估：审计欠账约 1.1 万条目，捆绑后（同模板组并包）预计 300-800 包；HIVE_WORKERS=8 时一至两轮跑完。

## 6. 施工阶段与验收（四里程碑）

| 阶段 | 内容 | 验收口径 |
|---|---|---|
| **M1 机械层** | census 断言集 + 捆绑器（tmpl_sig 复用）+ D3 规则引擎骨架 | 对 9-15 审计基线数字**复现**（11195/57.9%/90 条/233 条）；捆绑结果 dump 可审查 |
| **M2 蜂巢并发** | spec/result 契约 + verify 落库通道（过 Pi⑥ 钩子）+ 自验违例测试 | 10 包×50 条试跑全绿；意见格式校验 100%；worker 零直写认知图 |
| **M3 定位模块** | D1 字段级定位 | 抽样 20 条人工核对 ≥90% |
| **M4 治理闭环** | 工单回流（role 回填/合并建议/降权）+ designer 终裁 + 复跑 census 量化改善 | 首轮治理后：精确重复 90→≤10、role 覆盖 ≥90%（存量可回填范围）、闸门 DEFER>0 |

每阶段：实现 → 全量 `test_pXX` 回归 + 新增 `test_mr*.py` → 灵枢归档（16 条四要素）→ 本文件进度表更新。

## 7. 反面清单（勿违反）

1. **评审不直接改知识层**——意见与工单是产物，执行归 designer 终裁（位置效应：评审者≠执行者）；
2. **永不删除**——治理动作只有合并/降权/回填/移层，删除走既有 rejected 层语义；
3. **LLM 评审不得跳过机械检查**——确定性优先是 token 经济与可复算性的双重要求；
4. **不学 OCR 的全权信任**——评审 worker 经蜂巢执行器跑，无宿主 shell 权限；意见落库必过 verify 令牌校验；
5. **Precision over noise**——裁决不确定一律 DEFER，DEFER 是正常产物不是失败。
