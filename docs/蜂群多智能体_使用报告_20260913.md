## 二、容错实测（真实故障注入）

1. **强杀协调器**（`test_rust_swarm_kill`）：轮询锁定真实中途点（快照轮 K=76）强杀 → 重入同 WAL 续跑 → 终态/事件史/水位与无故障基线**逐项一致**，零重复事件。
2. **强杀两个实例子进程**（`test_swarm_fault`）：运行中 taskkill 两个 `--serve` 实例 → 协调器同线程重建重跑 → 蜂群 rc=0 无感完成，六实例终态与基线逐项一致、对账通过、health 满分——**透明容错**（重试成功在报告中零痕迹）。
3. 被杀实例的重建进程继续参与后续全部轮次，无进程泄漏（协调器死亡时实例因管道关闭自然退场）。

## 五、已声明局限（如实边界）

1. gossip 对账口径为**单机投递覆盖断言**；跨机网络故障域（真丢包/分区）留跨机版。
2. health/watermark 在恢复场景为**在线窗口口径**（重放前轮次不重计）。
3. dead 分支（重试仍败退场）已实现并有代码路径，但单机下确定性触发需在重建后的极窄时序窗内二次击杀，留长稳/跨机验证。
4. 邻接表连接约束/分区复制未实现——单机全连语义下无路由意义，拓扑当前作用于角色推导。
5. md_cg 向量第 5 路检索：评估后暂缓（ruflo HNSW 默认路径实为暴力余弦、收益窗口窄；升级条件 = md_cg 节点 >5 万且语义检索需求明确）。

## 六、对照结论（为什么自研）

A 阶段六份研读笔记（`agi-architectures/研读笔记/`）的横向结论：三个外部标杆的宣传层与代码层差距普遍很大——ruflo 的"共识"是 LLM 角色卡、HNSW 未接入默认路径、零信任三招牌在文档层。而本仓甲案路线交付的每个数字（水位、评分、对账）都能从 HMAC 事件流**复算**——这是与"LLM 评估"路线的本质区别，也是选择甲案的验证依据。
