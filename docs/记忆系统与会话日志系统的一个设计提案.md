# Harness 记忆系统与日志系统完整设计

## 零、设计哲学

整个 harness 的存储架构建立在三条核心原则上：

**第一条：内容是纯文本，索引是 SQLite。**

所有持久化内容——会话日志、记忆条目、FCA 概念格结构——都以纯文本形式存储。Markdown 文件、JSONL 文件、JSON 文件，人类可读，Git 友好，零依赖。SQLite 只做索引，不存内容。索引是纯加速器，随时可以丢弃、重建、替换，不影响任何数据。

**第二条：日志是 DAG，HEAD 是当前视图，任何变化都产生新节点，从不覆盖旧节点。**

日志不是项目，是事件序列。它没有工作区、没有文件树、没有需要协调的并行编辑。修改历史不是重写，而是从某个分叉点长出一条新分支。旧分支完整保留，审计链永不断裂。

**第三条：记忆是跨会话的物化视图，通过三层检索为投影提供召回信号。**

记忆系统不记录"会话里发生了什么"，而是回答"从所有会话里能找到什么"。它与日志系统职责正交，存储独立，生命周期独立。两者通过版本化引用关联。

整个 harness 的存储依赖只有三个：**Git、SQLite、纯文本文件**。

## 一、总体架构

整个系统有五个层次，自下而上：

### 1.1 内容层

纯文本文件。包括：

- **会话日志**：JSONL 文本行，存储在 Git 仓库中。
- **记忆条目**：Markdown 文件，按 FCA 概念格组织成目录结构。
- **FCA 概念格结构**：JSON 文件，描述概念格节点和偏序关系。
- **记忆注册表**：JSONL 文件，记录 `memory_id` 到文件路径的映射。
- **版本映射**：JSONL 文件，记录 `memory_id + version + hash` 的历史。

内容层是真相源。所有其他层都是它的派生。

### 1.2 版本层

Git。负责：

- 不可变内容存储（blob / tree / commit）。
- DAG 可达性与分支。
- 内容寻址（SHA-1 / BLAKE2b）。
- 审计链与回放。

Git 不负责索引和查询。它只管存储与版本。

### 1.3 索引层

SQLite。纯索引，不存内容。包括：

- **日志索引**：B-tree + FTS5，指向 Git 日志。
- **记忆索引**：B-tree + FTS5，指向 Markdown 文件。
- **向量索引**：sqlite-vec，指向 `memory_id + version`。
- **哈希索引**：内容寻址哈希 + token 哈希，指向记忆条目。

索引层可以随时从内容层重建。

### 1.4 检索层

记忆系统的三层检索架构：

- **FCA 目录**：结构化导航。
- **向量模糊索引**：语义召回。
- **哈希精确搜索**：精确命中。

三层通过 RRF（Reciprocal Rank Fusion）融合，并可以为不同通道设置保留槽位。

### 1.5 投影层

从日志派生模型可见历史。回答"模型看到了什么"。投影决策落日志。模型历史可变，日志不变。

### 1.6 数据流总览

```
用户输入 / 工具结果 / 模型输出
        │
        ▼
┌───────────────────────────────────────────────┐
│   内容层：会话日志 (Git + 纯文本 JSONL)         │
│  一个会话一个 Git 仓库                          │
│  分支 = 修改，增量 = 追加                       │
│  DAG 对象模型，plumbing 命令写入                │
│  不负责索引和查询                               │
└────────────────────┬──────────────────────────┘
                     │ 派生
                     ▼
┌───────────────────────────────────────────────┐
│   索引层：SQLite（纯索引，不存内容）             │
│  日志索引 + 记忆索引 + 向量索引 + 哈希索引       │
│  全部指向纯文本内容                              │
│  可重建，可替换，可丢弃                          │
└────────────────────┬──────────────────────────┘
                     │ 召回信号
                     ▼
┌───────────────────────────────────────────────┐
│   检索层：记忆系统三层检索                       │
│  FCA 目录 + 向量模糊 + 哈希精确                  │
│  RRF 融合，保留槽位                              │
└────────────────────┬──────────────────────────┘
                     │ 召回信号
                     ▼
┌───────────────────────────────────────────────┐
│   投影层：模型可见历史                           │
│  纯函数视图，从日志派生                          │
│  决策落 projection_event                        │
│  HEAD 决定投影，模型历史可变，日志不变           │
└────────────────────┬──────────────────────────┘
                     │ 引用
                     ▼
┌───────────────────────────────────────────────┐
│   内容层：记忆库 (纯文本 + FCA 目录)             │
│  Markdown / JSONL 文件                          │
│  FCA 概念格 = 目录结构                          │
│  人类可读，Git 友好                              │
└───────────────────────────────────────────────┘
```

## 二、日志系统

### 2.1 定位

日志不是项目，是事件序列。它没有工作区、没有文件树、没有需要协调的并行编辑。

日志系统的核心职责：

- 记录"这个会话里发生了什么"。
- 提供不可变的审计轨迹。
- 支持分支、回放、追溯。
- 作为记忆系统的来源之一。

日志系统**不负责**：

- 索引和查询（由 SQLite 索引层承担）。
- 跨会话共享（由记忆系统承担）。
- 模型可见历史的生成（由投影层承担）。

### 2.2 存储结构

**一个会话 = 一个 Git 仓库。**

设计理由：

- **本地无远端**：不需要 push/pull，不需要考虑敏感信息脱敏。
- **会话之间完全隔离**：一个会话的历史重构、分支、回滚不影响任何其他会话。
- **会话生命周期独立**：会话结束可以归档、压缩、甚至删除，不影响记忆系统。
- **跨会话共享通过记忆系统完成**：日志本身不承担这个职责。
- **独立仓库比 worktree 更干净**：不需要共享 `.git`，不需要处理分支爆炸影响其他会话。

**一个会话一个仓库，而不是 worktree 共享 `.git`**，因为跨会话不需要日志合并。独立仓库意味着完全隔离的历史，每个会话的 DAG 互不干扰。

### 2.3 日志格式

**纯文本 JSONL。**

每行一个事件，字段包括：

```jsonl
{"seq":1,"type":"user_message","timestamp":"2026-10-07T10:00:00Z","actor":"user","payload":{"content":"帮我看看 K8s Pod 为什么 CrashLoopBackOff"},"parent_seq":null,"branch_ref":"refs/heads/main"}
{"seq":2,"type":"model_output","timestamp":"2026-10-07T10:00:05Z","actor":"model","payload":{"content":"我先检查一下 Pod 日志","tool_calls":[...]},"parent_seq":1,"branch_ref":"refs/heads/main"}
{"seq":3,"type":"tool_result","timestamp":"2026-10-07T10:00:10Z","actor":"system","payload":{"tool":"kubectl_logs","result":"..."},"parent_seq":2,"branch_ref":"refs/heads/main"}
{"seq":4,"type":"memory.read","timestamp":"2026-10-07T10:00:12Z","actor":"model","payload":{"query":"K8s CrashLoopBackOff","memory_ids":["mem_001"],"versions":[3],"hashes":["sha256:abc"]},"parent_seq":3,"branch_ref":"refs/heads/main"}
{"seq":5,"type":"memory.write","timestamp":"2026-10-07T10:00:20Z","actor":"model","payload":{"memory_id":"mem_002","version":1,"hash":"sha256:def","content":"新的排查步骤"},"parent_seq":4,"branch_ref":"refs/heads/main"}
{"seq":6,"type":"projection.apply","timestamp":"2026-10-07T10:00:25Z","actor":"system","payload":{"shadowed_seqs":[3],"inserted_seqs":[5],"fca_node":"deployment/k8s","strategy_version":"v2","embedding_model_version":"text-embedding-3-small","fca_build_version":"2026-10-01"},"parent_seq":5,"branch_ref":"refs/heads/main"}
```

**为什么用 JSONL：**

- 追加写入零成本，不需要事务、不需要锁。
- 人类可读，`cat` / `grep` / `less` 直接可用。
- Git 原生友好，diff 可读，不需要自定义 merge driver。
- 零依赖，任何语言都能读写。
- 可流式处理，逐行读、逐行投影。
- 每行一个事件，`seq`、`type`、`timestamp`、`actor`、`payload` 字段可直接映射到 DAG 节点。

### 2.4 写入路径

直接用 Git plumbing 命令，完全绕过 worktree 和 index：

```
事件 → blob (git hash-object) → tree (git mktree) → commit (git commit-tree) → ref (git update-ref)
```

**具体步骤：**

1. **`git hash-object -w --stdin`**：把事件文本写成 blob，返回 SHA。
2. **`git mktree`**：把 blob 组织成 tree，返回 tree SHA。
3. **`git commit-tree <tree> -p <parent> -m <message>`**：指定 parent 创建 commit，返回 commit SHA。
4. **`git update-ref refs/heads/<branch> <commit>`**：移动分支引用。

**为什么用 plumbing 命令：**

- 不需要 checkout，不需要工作区。
- 不需要暂存区，不需要 index。
- 写入就是"造对象 + 移 ref"，这是 Git 最轻的路径。
- 完全绕过工作区语义，日志不是项目。

**高频 commit 的处理：**

- Git 的 commit 开销在本地场景下可接受。
- 如果某个场景下 commit 太碎，可以把一个事务内的多个事件打包成一个 commit。
- 批量窗口只是优化，不是架构必需。

### 2.5 分支模型

**核心规则：有修改就分支，没修改就增量。**

**增量：**

- 新事件直接 append 到当前分支。
- HEAD 前移，parent 指向当前分支末端。
- 这是默认操作。

**修改：**

- 找到受影响的**最早节点**作为 fork point。
- 从 fork point 创建新分支。
- 旧分支完整保留，不删除、不覆盖。
- 新分支上的后续事件重新生成。

**重构整条会话：**

- 从根节点或某个早期节点 fork 出一条新分支。
- 旧分支仍然可查。
- 新分支从头生成事件序列。

**合并：**

- 从两个分支的交汇处 fork 新分支。
- HEAD 是合并节点，有两个 parent。
- 旧分支不动。
- 合并不是终点，而是一个新分支的起点。

**本质：**

所有操作的结果都是"产生一个新分支"或"推进当前分支"。没有任何操作会原地修改已有分支。

**形式化描述：**

- 当前 HEAD 指向某个分支末端。
- 正常增量：新事件 append 到当前分支，HEAD 前移。
- 需要修改历史：找到 fork point，创建新分支，旧分支保留。
- 重构整条会话：从根节点或早期节点 fork 新分支。
- 合并：从两个分支的交汇处 fork 新分支，HEAD 是两个 parent 的合并节点。

### 2.6 合并语义

在你的模型里，合并不是"把两个分支合到一起"，而是 **"创建一个新分支，它同时继承了两个父分支"**。

**Git 的 merge commit 本来就有两个父节点。**

- 分支 A 和分支 B 原封不动。
- 新分支 C 从 A 和 B 的交汇处创建。
- C 的 HEAD 是一个合并节点，parent 是 A 和 B 的末端。
- C 是全新的历史线。

**为什么不需要考虑冲突：**

- 日志事件之间不存在"内容冲突"。
- 两个分支合并，就是把两条事件序列按时间或因果顺序拼起来。
- 这是 event sourcing + DAG 分支，不是版本控制的协作模型。
- 没有"同一行被两个人改了"这种事，因为事件不会互相覆盖。

**和你"修改即分支"规则完全统一：**

- 增量：在当前分支末尾追加 commit。
- 修改：从分叉点 fork 新分支。
- 合并：从两个分支的交汇处 fork 新分支，HEAD 是合并节点。

本质上，所有操作的结果都是"产生一个新分支"或"推进当前分支"。

**这意味着什么：**

- 没有任何操作会原地修改已有分支。
- 旧分支永远是只读的、不可变的。
- HEAD 始终指向某个分支的末端。
- 模型看到的投影由 HEAD 决定。
- 合并语义被降级为"创建"语义。

### 2.7 日志事件类型

**模型可见输入输出：**

- `user_message`：用户输入。
- `model_output`：模型输出，包括文本和工具调用。
- `tool_result`：工具执行结果。

**记忆读写：**

- `memory.read`：模型读取记忆。带 `memory_id`、`version`、`hash`、`actor`、查询或理由。
- `memory.write`：模型写入记忆。带 `memory_id`、`version`、`hash`、内容引用。
- `memory.update`：模型更新记忆。带旧版本、新版本、变更理由。
- `memory.forget`：模型遗忘记忆。带 `memory_id`、理由。

**投影决策：**

- `projection.apply`：投影应用。记录 shadow 了哪些 `seq`、插入了哪些合成节点、替换了什么、依据了 FCA 格中哪个 concept node、投影策略版本、嵌入模型版本、FCA 构建版本。
- `projection.revert`：投影回滚。
- `projection.branch`：投影分支切换。

**策略与版本：**

- `strategy.version`：投影策略版本变更。
- `embedding_model.version`：嵌入模型版本变更。
- `fca.build_version`：FCA 构建版本变更。

**分支操作：**

- `branch.fork`：创建分支。记录 fork point、parent、理由。
- `branch.merge`：合并分支。记录两个 parent、理由。
- `branch.checkout`：切换 HEAD。记录旧 HEAD、新 HEAD、理由。

**系统事件：**

- `session.start`：会话开始。
- `session.end`：会话结束。
- `session.archive`：会话归档。

### 2.8 日志庞大的处理

日志庞大是 append-only 架构的固有代价，但关系不大。

**索引与日志分离：**

- SQLite 索引是日志的物化视图，不是日志本身。
- 日志可以无限增长，索引只保留当前活跃的检索单元。
- 日志是"线性历史"，索引是"多维加速器"。

**投影缓存：**

- 模型可见历史是纯函数投影，可以缓存。
- 只要底层日志追加了新事件，缓存失效，重新投影即可。
- 不需要每次请求都重扫日志。

**冷热分层：**

- 旧日志段可以压缩归档，只保留索引指针。
- 审计时按需解压检索，日常运行只访问热段和索引。
- 日志分段，每段有独立的索引快照。

**投影决策不复制内容：**

- `projection_event` 只需记录 shadow 了哪些 `seq`、插入了哪些合成节点的引用、依据了哪个 FCA 节点。
- 内容仍在原始日志里，通过 `seq` 可追溯。
- 日志增长的是决策元数据，不是重复内容。

**Git 对象共享：**

- Git 的对象模型天然去重。
- 相同内容的 blob 只存一份。
- 相同 tree 只存一份。

**真正需要担心的不是大小，而是重建成本：**

- 如果索引损坏或需要新增索引通道，重建全量索引的时间和资源。
- 日志分段，每段有独立的索引快照。
- 重建时可以并行、增量进行。

### 2.9 日志的原子性与一致性

**原子写入：**

- Git 的对象写入是原子的。
- blob 写入后，tree 写入，commit 写入，最后 ref 更新。
- 如果中间步骤失败，ref 不更新，日志不变。
- 只有 ref 更新成功，日志才可见。

**一致性保证：**

- 每个 commit 是一个原子快照。
- commit 之间的顺序由 parent 链保证。
- 分支切换由 ref 更新保证。

## 三、记忆系统

### 3.1 定位

记忆系统是跨会话的全局知识库。它不记录"会话里发生了什么"，而是回答"从所有会话里能找到什么"。

**记忆系统与日志系统职责正交：**

- **会话日志**：记录"这个会话里发生了什么"。纵向的、时间性的、单会话封闭的。生命周期和会话绑定，会话结束可以归档。
- **记忆系统**：记录"跨会话沉淀下来的东西"。横向的、语义性的、可全局检索的。FCA 目录、向量索引、精确哈希都服务于"从所有会话里召回知识"。

两者通过 `memory_id + version + hash` 和 `projection_event` 关联，但存储上独立，生命周期独立。

**记忆系统是可变的、可重建的、可替换的。日志不受记忆系统变化的影响。**

### 3.2 存储结构

**记忆库 = 一个目录树 + 纯文本文件。**

```
│   │   └── terraform/           # 子概念：Terraform
```

### 3.3 记忆条目格式

每个记忆条目是一个 Markdown 文件，包含 YAML frontmatter 和正文。

**Frontmatter 字段：**

```markdown
---
memory_id: mem_2026_1007_001
version: 3
content_hash: sha256:abc123...
fca_node: deployment/k8s
created_at: 2026-10-07T10:00:00Z
updated_at: 2026-10-07T12:00:00Z
source_session: session_abc
source_commit: def456...
tags: [k8s, pod, crashloop]
related: [mem_2026_1007_002, mem_2026_1007_005]
---
```

**字段说明：**

- `memory_id`：全局唯一标识符。
- `version`：版本号，从 1 开始递增。
- `content_hash`：内容哈希，SHA-256 或 BLAKE3。
- `fca_node`：FCA 概念格中的节点路径。
- `created_at`：创建时间。
- `updated_at`：最后更新时间。
- `source_session`：来源会话 ID。
- `source_commit`：来源 Git commit SHA。
- `tags`：标签数组。
- `related`：相关记忆 ID 数组。

**正文：**

```markdown
# K8s Pod CrashLoopBackOff 处理

## 症状

Pod 反复重启，状态显示 CrashLoopBackOff。

## 排查步骤

1. `kubectl logs <pod> --previous`
2. `kubectl describe pod <pod>`

根据排查结果，针对性修复。
```

### 3.4 为什么记忆内容用纯文本

**人类可读：**

- 直接打开就能看，不需要工具链。
- 出问题时直接 `cat` / `grep` / `less`。
- 便于人工审查和编辑。

**Git 友好：**

- 记忆库本身可以用 Git 管理，获得版本历史和 diff。
- 纯文本的 diff 可读，merge 冲突可手动解决。
- 不需要自定义 merge driver。

**FCA 目录即语义结构：**

- 概念格节点直接对应目录路径。
- 导航即检索。
- 目录树本身就是一种语义结构。

**零依赖：**

- 不依赖数据库即可访问内容。
- 任何语言都能读写。
- 任何编辑器都能打开。

**可移植：**

- 换个索引引擎，内容不受影响。
- 换个嵌入模型，内容不受影响。
- 换个投影策略，内容不受影响。

### 3.5 记忆版本化

**每条记忆有 `memory_id + version + hash`。**

**版本历史通过 Git 管理记忆库目录获得：**

- 记忆库目录本身是一个 Git 仓库。
- 每次记忆更新产生一个 commit。
- 旧版本保留在 Git 历史中。
- 可以 `git log` 查看版本历史，`git diff` 查看变更。

**旧版本可以保留在 Git 历史中，或者以 `.v1.md`、`.v2.md` 形式并存。**

**日志引用记忆时记 `memory_id + version + hash`，保证可重建：**

- 如果记忆被更新，旧版本仍在 Git 历史中。
- 通过 `memory_id + version + hash` 可以精确定位到当时的记忆内容。
- 日志只记录操作和引用，不复制内容。

### 3.6 FCA 目录的作用

**概念格节点直接对应目录路径。**

- FCA 概念格中的每个节点对应一个目录。
- 子概念对应子目录。
- 记忆条目存放在对应的目录中。

**FCA 的偏序结构记录"这条记忆属于概念格中哪个节点"。**

- 概念格是一个偏序集。
- 每个记忆条目绑定到一个概念节点。
- 概念节点之间的关系由偏序定义。

**目录层为投影决策提供结构化锚点。**

- 投影决策可以绑定到具体的 concept node。
- 形成"为什么模型看到了这个投影"的可追溯链。
- 格中高层的概念节点对应的消息，可以设置为不可 shadow 的"根节点"。

**FCA 格结构存在 `index/fca_lattice.json`，可重建。**

### 3.9 记忆与日志的关联

**日志引用记忆时，不能只记 `memory_id`，要记 `memory_id + version + hash`。**

原因：

- 记忆系统是可变的。
- 如果事后记忆被更新，而日志只记了 ID，就再也无法重建"模型当时看到的那条记忆"。
- 版本化后，日志可以很小，但追溯链完整。

**关联方式：**

- 日志中的 `memory.read` / `memory.write` / `memory.update` 事件记录 `memory_id + version + hash`。
- 记忆注册表和版本映射提供从 `memory_id + version` 到文件路径的映射。
- 内容通过文件路径从纯文本文件读取。

### 3.10 记忆系统的输出角色

在你的架构里，记忆系统的三层输出**不再是"注入片段"**，而是**投影决策的输入源**：

- FCA 目录结构告诉你"这条记忆属于哪个概念节点"。
- 向量通道告诉你"语义上最相关的候选是什么"。
- 精确哈希告诉你"哪个标识符必须原样出现"。

投影层根据这些信号决定：哪些原始消息被 shadow、哪些被替换、哪些合成消息被插入到 API 视图的哪个位置。

## 四、索引层（SQLite）

### 4.1 定位

**SQLite 只做纯索引用途。**

它不存内容，只存指向纯文本内容的索引。所有索引都可以从内容层（Git 日志 + 记忆库目录）重建。

**为什么不用 Git 做索引：**

- **查询是线性的**：`git log --grep` 遍历提交历史，O(n)，没有 B-tree 或倒排索引。
- **Notes 遍历慢**：`refs/notes/` 下的 Notes 没有索引，大规模下遍历成本高。
- **不支持范围查询**：按时间、按类型、按 actor 的范围查询，Git 没有原生支持。
- **不支持聚合**：`COUNT`、`GROUP BY`、`JOIN` 在 Git 里没有对应物。
- **索引需要更新**：索引是频繁更新的物化视图，Git 的内容寻址模型意味着每次更新都产生新对象。
- **全文搜索弱**：`git log -S` 是 pickaxe，不是全文索引，不支持分词、TF-IDF、BM25。

**为什么用 SQLite：**

- `FTS5` 扩展做全文搜索（消息内容、工具结果、记忆内容）。
- B-tree 索引做属性查询（`seq`、`type`、`timestamp`、`actor`、`memory_id`）。
- 标准 SQL 做范围查询、聚合、JOIN。
- `sqlite-vec` 做向量搜索。
- 单文件存储，零外部依赖。
- WAL 模式支持并发读写。

### 4.2 日志索引

#### 4.2.1 表结构

```sql
-- 日志事件索引
CREATE TABLE log_events_index (
    seq INTEGER PRIMARY KEY,
    commit_hash TEXT NOT NULL,
    timestamp TEXT NOT NULL,
    type TEXT NOT NULL,
    actor TEXT NOT NULL,
    payload_hash TEXT,
    memory_id TEXT,
    memory_version INTEGER,
    projection_id TEXT,
    branch_ref TEXT,
    parent_seq INTEGER
);

CREATE INDEX idx_log_timestamp ON log_events_index(timestamp);
CREATE INDEX idx_log_type ON log_events_index(type);
CREATE INDEX idx_log_actor ON log_events_index(actor);
CREATE INDEX idx_log_memory ON log_events_index(memory_id, memory_version);
CREATE INDEX idx_log_branch ON log_events_index(branch_ref);
CREATE INDEX idx_log_projection ON log_events_index(projection_id);
CREATE INDEX idx_log_parent ON log_events_index(parent_seq);

-- 全文搜索索引
CREATE VIRTUAL TABLE log_fts USING fts5(
    content,
    content_rowid='seq',
    tokenize='porter unicode61'
);

-- 投影决策索引
CREATE TABLE projection_events_index (
    projection_id TEXT PRIMARY KEY,
    commit_hash TEXT NOT NULL,
    timestamp TEXT NOT NULL,
    shadowed_seqs TEXT,      -- JSON array of seq
    inserted_seqs TEXT,      -- JSON array of seq
    fca_node TEXT,
    strategy_version TEXT,
    embedding_model_version TEXT,
    fca_build_version TEXT
);

CREATE INDEX idx_projection_timestamp ON projection_events_index(timestamp);
CREATE INDEX idx_projection_fca_node ON projection_events_index(fca_node);
CREATE INDEX idx_projection_strategy ON projection_events_index(strategy_version);
```

#### 4.2.2 索引重建

1. 遍历 Git 日志的 commit DAG。
2. 解析每个 commit 的 JSONL blob。
3. 写入 `log_events_index`、`log_fts`、`projection_events_index`。
4. 建立 B-tree 索引和 FTS 索引。

重建可以并行、增量进行。日志分段，每段有独立的索引快照。

#### 4.2.3 索引与日志的关联

- 索引通过 `commit_hash` 和 `seq` 关联到 Git 日志。
- 日志是真相源，索引是物化视图。
- 索引损坏可以从 Git 重建。
- 索引可以替换（换 SQLite 版本、换 FTS 分词器），不影响 Git 日志。

#### 4.3.5 索引与内容的关联

- 记忆索引通过 `memory_id + version + hash` 和 `file_path` 关联到记忆文件。
- 索引是物化视图，内容层是真相源。
- 索引损坏可以从内容层重建。
- 索引可以替换（换 SQLite 版本、换 FTS 分词器、换嵌入模型），不影响内容。

### 4.4 SQLite 的并发与写入

**WAL 模式：**

- 日志索引和记忆索引可能同时写入。
- SQLite 使用 WAL（Write-Ahead Logging）模式处理并发。
- 读操作不阻塞写操作，写操作不阻塞读操作。
- 只有一个写者，多个读者。

**批量写入：**

- 索引写入是批量的，不是每事件一次。
- 积累一定数量的事件后批量写入。
- 减少事务开销。

**延迟更新：**

- 索引可以延迟更新（最终一致）。
- 内容层是实时的。
- 索引更新可以异步进行。

**事务性保证：**

- 向量索引更新时，内容文件必须已经写入。
- 使用 SQLite 事务保证索引和内容的一致性。
- 如果索引写入失败，内容文件不受影响。


### 4.5 索引的快照与备份

**索引可以从内容层重建，但重建成本高。**

- 定期快照可以加速恢复。
- 快照就是 SQLite 数据库文件的副本。
- 快照可以压缩存储。

**重建策略：**

- 全量重建：从内容层重新生成所有索引。
- 增量重建：只重建变更部分。
- 分段重建：日志分段，每段有独立的索引快照。

## 五、三层检索架构

### 5.1 定位

记忆系统的三层检索**全部基于 SQLite 索引**，不直接访问内容文件。检索结果通过 `memory_id + version + hash` 和 `file_path` 回查内容文件。

### 5.2 第一层：FCA 目录（结构化导航）

**原理：**

- 用形式概念分析（FCA）生成概念格（concept lattice）。
- 把对象和属性之间的关联组织成偏序关系。
- 概念格节点直接对应目录路径，形成层级化聚类结构。

**检索方式：**

- 从 `fca_lattice_index` 表查询概念节点。
- 通过 `node_id` 找到对应的 `memory_ids`。
- 通过 `memory_ids` 找到记忆条目。
- 支持层级导航：从父节点到子节点，从子节点到父节点。

**作用：**

- 目录层回答"这条记忆属于概念格中哪个节点"。
- 为投影决策提供结构化锚点。
- FCA 的偏序结构记录"这条合成历史派生自格中哪个节点"。

**已有先例：**

- ip-CLAIRE 用 interval pattern structures 在概念格结构上支持向量空间模型。
- ACHFCA 把 FCA 和哈希学习结合用于跨模态检索。
- 早期信息检索工作用 FCA 概念格替代传统层级目录模型。

### 5.3 第二层：向量模糊索引（语义召回）

**原理：**

- 用于理解查询的**概念和意图**。
- 处理模糊、概念性的查询，比如"上次讨论的那个部署问题"。
- 只对"可能被语义召回"的单元建索引：用户消息、助手回复、关键工具结果、记忆条目。

**检索方式：**

- 把查询文本嵌入为向量。
- 在 `memory_vec` 表中做 KNN 搜索。
- 返回最相似的 `memory_id + version`。
- 通过 `memory_index` 找到 `file_path`，读取内容。

**存储：**

- SQLite + sqlite-vec。
- HNSW / IVF 索引。
- 向量维度取决于嵌入模型。

**已有先例：**

- nox-mem 的 sqlite-vec 稠密向量 + RRF 融合管线。

### 5.4 第三层：哈希精确搜索（精确命中）

**原理：**

- 用于处理**标识符、错误码、文件路径、函数名**等必须精确匹配的场景。
- O(1) 精确命中。
- 纯向量搜索在这些场景下可能"似懂非懂"。

**两种语义：**

**内容寻址哈希（SHA-256 / BLAKE3）：**

- 对记忆内容本身做哈希。
- 用于去重、完整性校验、增量重嵌入触发。
- `content_hash TEXT PRIMARY KEY`。
- 存储：`memory_hash_index`。

**索引哈希（Cuckoo filter / Bloom filter）：**

- 把向量或 key 映射到桶。
- 用于快速候选召回或精确成员判断。
- 存储：`token_hash_index`。
- 两者在底层表结构上是不同的列/索引，不能混用。

**检索方式：**

- 计算查询的哈希。
- 在 `memory_hash_index` 或 `token_hash_index` 中查找。
- 返回精确匹配的 `memory_id + version`。
- 通过 `memory_index` 找到 `file_path`，读取内容。

**已有先例：**

- ClawQL 用 Cuckoo filter 做快速精确成员判断。

### 5.5 RRF 融合

**三层各自独立，通过 RRF（Reciprocal Rank Fusion）融合。**

RRF 公式：

```
score(d) = Σ (1 / (k + rank_i(d)))
```

其中：

- `k` 是常数，通常取 60。
- `rank_i(d)` 是文档 `d` 在第 `i` 个通道中的排名。
- `Σ` 对所有通道求和。

**保留槽位：**

- 可以为不同通道设置保留槽位。
- 确保精确匹配结果不会被向量结果淹没。
- 例如：前 5 个槽位保留给精确匹配，前 10 个槽位保留给 FCA 目录。

**融合流程：**

1. 三个通道各自返回排序列表。
2. 对每个文档计算 RRF 分数。
3. 按 RRF 分数排序。
4. 应用保留槽位规则。
5. 返回最终排序列表。

### 5.6 检索与内容的关系

- 检索在 SQLite 索引上进行。
- 检索结果返回 `memory_id + version + hash` 和 `file_path`。
- 内容通过 `file_path` 从纯文本文件读取。
- 日志引用记忆时记 `memory_id + version + hash`。

### 5.7 记忆系统的输出角色

记忆系统的三层输出是**投影决策的输入源**：

- FCA 目录结构告诉你"这条记忆属于哪个概念节点"。
- 向量通道告诉你"语义上最相关的候选是什么"。
- 精确哈希告诉你"哪个标识符必须原样出现"。

投影层根据这些信号决定：哪些原始消息被 shadow、哪些被替换、哪些合成消息被插入到 API 视图的哪个位置。

## 六、投影层

### 6.1 定位

**模型可见历史（Model-Visible History）与持久化日志（Persisted Log）的分离。**

- 日志是事实，模型看到的是投影。
- 日志是 append-only 的事件序列，是唯一真相源。
- 模型实际看到的消息历史，是从日志**投影**出来的。
- 投影是纯函数视图，可以随时从日志精确重建。
- 通过投影修改已记录的历史在类型上不可表达。

### 6.2 投影机制

**每次 API 调用时动态生成一份"投影"给模型看。**

- 日志本身永远不变，但模型每次看到的切片可以不同。
- 当前 HEAD 决定模型看到哪个投影。
- 投影是缓存的、冻结的，每次调用返回新数组，引用共享的深冻结消息。
- 模型知道的会话历史被修改，但 harness 的历史消息记录不变。

**投影步骤：**

1. 从当前 HEAD 指向的分支读取事件序列。
2. 应用投影策略：决定哪些事件被 shadow、哪些被替换、哪些合成节点被插入。
3. 生成模型可见消息列表。
4. 发送给 API。
5. 记录 `projection_event`。

### 6.3 投影决策的落日志

**投影决策本身必须落日志。**

一条 `projection_event` 记录：

- `projection_id`：投影唯一标识符。
- `commit_hash`：投影时的 Git commit SHA。
- `timestamp`：投影时间。
- `shadowed_seqs`：被 shadow 的 `seq` 列表。
- `inserted_seqs`：插入的合成节点 `seq` 列表。
- `fca_node`：依据的 FCA 格中 concept node。
- `strategy_version`：投影策略版本。
- `embedding_model_version`：嵌入模型版本。
- `fca_build_version`：FCA 构建版本。

内容仍在原始日志里，通过 `seq` 可追溯。日志增长的是决策元数据，不是重复内容。

### 6.4 投影策略

**投影策略决定模型看到什么。**

策略示例：

- **precision-window**：只保留最近 N 轮对话。
- **associative-divergence**：从全史召回与当前上下文语义相关的事件，前置拼接。
- **critical-focus**：保留关键决策点，压缩中间过程。
- **memory-augmented**：从记忆系统召回相关记忆，插入到投影中。
- **fca-guided**：根据 FCA 概念格节点决定哪些消息被 shadow。

**策略版本管理：**

- 投影策略变化时，旧投影如何回放，新投影如何生成。
- 策略版本、嵌入模型版本、FCA 构建版本都需要记录。
- 否则事后无法重建"当时为什么这么投影"。

### 6.5 已有实现参考

**dsh-memory-projection：**

- append-only 会话事件日志是唯一真相源。
- 投影只是这个日志的纯函数视图。
- 内置 `precision-window`、`associative-divergence`、`critical-focus` 等策略。
- 运行时动态切换模型看到的历史切片。

**dsh-context-offload：**

- 已消费的工具调用及结果在模型可见历史中被替换为 stub。
- 原始内容仍留在 session 日志中用于回放。

**context-surgeon：**

- 位于 Agent harness 和 provider 服务器之间。
- 自己持有"the one true history"。
- 每次模型请求都从自己的状态编译。
- Harness 的 rewrite（工具输出 stubbing、截断、原生 compaction）永远不会破坏 owned history。

**harn 的 `transcript_project`：**

- "read-side dual of compaction"。
- 选择下一次 provider 请求看到哪一片段。
- 不重写不可变审计轨迹。
- 返回 `prefix_hash`，用于记录模型实际看到的那个前缀的哈希。

**dsh-edit-turn：**

- 通过 surface-replace contract 在模型上下文中投放替换事件。
- 原始日志行保留，被 shadow 的行仍然存在。
- `revisions[]` 和 `hidden[]` 记录映射关系。
- 任何 sibling 插件都可以追溯。

### 6.6 安全边界

**如果投影决策不落日志，API 视图层就变成了一个无审计的篡改通道——模型看到了什么将不可重建。**

必须守住这条边界：**投影决策必须落日志**。

**FCA 偏序结构在这里有一个天然优势：**

- 格中每个节点的投影决策可以绑定到具体的 concept node。
- 形成"为什么模型看到了这个投影"的可追溯链。
- 格中高层的概念节点对应的消息，可以设置为不可 shadow 的"根节点"。

**威胁模型：**

- LLM API proxy routers 能够读取、重写、保留或伪造组织应用与上游 AI 提供商之间的每一个 prompt 和 response。
- windtunnel-shear 的 `before_request` hook 可以直接 `req.messages.insert(0, ...)`，在请求到达 API 之前修改消息列表。
- claude-context-editor 的 Intercept Mode 暂停请求，允许编辑或删除单条消息。

**区别在于投影事件是否被记录：**

- harn 和 dsh-edit-turn 把投影决策本身写回了 session 日志。
- 所以"模型看到了什么"是可重建的。
- 如果投影决策不落日志，那么 API 视图层就变成了一个无审计的篡改通道。

### 6.7 投影策略的版本管理

**投影策略变化时：**

- 旧投影如何回放。
- 新投影如何生成。
- 策略版本、嵌入模型版本、FCA 构建版本都需要记录。

**否则事后无法重建"当时为什么这么投影"。**

**版本记录方式：**

- `projection_event` 中记录 `strategy_version`、`embedding_model_version`、`fca_build_version`。
- 这些版本号指向 `meta/` 目录下的版本文件。
- 版本文件记录具体版本号和变更历史。

## 七、整体数据流

### 7.1 写入流程

**用户输入 / 工具结果 / 模型输出：**

1. 生成事件 JSONL 行。
2. 计算事件内容的哈希。
3. 用 `git hash-object` 写入 blob。
4. 用 `git mktree` 组织成 tree。
5. 用 `git commit-tree` 创建 commit，parent 指向当前 HEAD。
6. 用 `git update-ref` 更新分支引用。
7. 异步更新 SQLite 索引。

**记忆写入：**

1. 生成 Markdown 文件。
2. 计算内容哈希。
3. 写入记忆库目录。
4. 更新 `memory_registry.jsonl` 和 `version_map.jsonl`。
5. 异步更新 SQLite 索引。
6. 记录 `memory.write` 事件到日志。

**记忆更新：**

1. 读取旧版本。
2. 生成新版本 Markdown 文件。
3. 计算新内容哈希。
4. 写入记忆库目录。
5. 更新 `memory_registry.jsonl` 和 `version_map.jsonl`。
6. 异步更新 SQLite 索引。
7. 记录 `memory.update` 事件到日志。

### 7.2 读取流程

**日志读取：**

1. 从 SQLite 索引查询 `log_events_index`。
2. 通过 `commit_hash` 和 `seq` 定位到 Git 日志。
3. 解析 JSONL 行。
4. 返回事件内容。

**记忆读取：**

1. 从 SQLite 索引查询 `memory_index`。
2. 通过 `memory_id + version + hash` 定位到 `file_path`。
3. 读取 Markdown 文件。
4. 解析 YAML frontmatter 和正文。
5. 返回记忆内容。

**三层检索：**

1. FCA 目录：查询 `fca_lattice_index`。
2. 向量模糊：查询 `memory_vec`。
3. 哈希精确：查询 `memory_hash_index` 或 `token_hash_index`。
4. RRF 融合。
5. 返回排序后的 `memory_id + version + hash` 列表。
6. 通过 `file_path` 读取内容。

### 7.3 投影流程

1. 从当前 HEAD 读取事件序列。
2. 应用投影策略。
3. 生成模型可见消息列表。
4. 发送给 API。
5. 记录 `projection_event`。
6. 如果投影策略需要记忆召回，调用三层检索。
7. 检索结果作为投影决策的输入源。

### 7.4 分支流程

**创建分支：**

1. 找到 fork point。
2. 用 `git commit-tree` 创建新 commit，parent 指向 fork point。
3. 用 `git update-ref` 创建新分支引用。
4. 记录 `branch.fork` 事件。
5. 更新 SQLite 索引。

**合并分支：**

1. 找到两个分支的末端。
2. 用 `git commit-tree` 创建新 commit，两个 parent 分别指向两个分支末端。
3. 用 `git update-ref` 创建新分支引用。
4. 记录 `branch.merge` 事件。
5. 更新 SQLite 索引。

**切换 HEAD：**

1. 用 `git update-ref` 更新 HEAD 引用。
2. 记录 `branch.checkout` 事件。
3. 更新 SQLite 索引。

## 八、关键设计决策汇总

| 决策      | 选择                               | 理由                                     |
| ------- | -------------------------------- | -------------------------------------- |
| 日志存储引擎  | Git                              | harness 已大量使用 Git，复用 DAG 对象模型          |
| 日志格式    | 纯文本 JSONL                        | 追加写入、人类可读、Git 友好、零依赖                   |
| 日志索引    | SQLite                           | Git 不适合索引，SQLite 提供 B-tree + FTS5 + 聚合 |
| 会话隔离    | 一个会话一个 Git 仓库                    | 跨会话不需要日志合并，记忆系统已承担跨会话职责                |
| 修改语义    | 有修改就分支                           | 旧分支保留，不覆盖，审计链完整                        |
| 合并语义    | 合并即新建分支                          | 不解决冲突，只是创建同时继承两个父节点的新历史线               |
| 日志写入    | Git plumbing 命令                  | 绕过 worktree 和 index，最轻路径               |
| 记忆内容存储  | 纯文本 Markdown / JSONL             | 人类可读，Git 友好，FCA 目录即结构                  |
| 记忆目录结构  | FCA 概念格                          | 概念节点对应目录路径，导航即检索                       |
| 索引引擎    | SQLite（纯索引）                      | 只做索引，不存内容，可重建，可替换                      |
| 索引类型    | B-tree + FTS5 + sqlite-vec + 哈希表 | 属性、全文、向量、精确四种检索                        |
| 记忆检索    | FCA + 向量 + 哈希，RRF 融合             | 三种检索范式互补                               |
| 记忆版本化   | memory_id + version + hash       | 日志引用记忆时保证可重建                           |
| 投影决策    | 必须落日志                            | 否则 API 视图层变成无审计的篡改通道                   |
| 日志庞大    | 索引与内容分离，冷热分层                     | 日志增长的是元数据                              |
| 跨会话     | 通过记忆系统，不通过日志                     | 日志是单会话封闭的                              |
| 内容与索引分离 | 内容纯文本，索引 SQLite                  | 内容不可变，索引可重建                            |
| 并发控制    | SQLite WAL 模式                    | 支持并发读写，读写不互相阻塞                         |
| 索引更新    | 批量 + 延迟                          | 减少事务开销，最终一致                            |
| 原子写入    | Git ref 更新                       | 只有 ref 更新成功，日志才可见                      |
| 记忆原子写入  | 临时文件 + rename                    | 避免半写状态                                 |

## 九、需要进一步设计的点

### 9.1 日志系统

1. **fork point 定位**：修改影响的最早事件是哪个，需要能从日志 DAG 里高效定位。可以用 `git merge-base` 定位分叉点。
2. **分支元数据**：谁创建、为什么、基于哪个投影策略、绑定了哪些记忆版本。可以用 Git Notes 附加到分支 ref 上。
3. **HEAD 选择策略**：模型一次只能看到一个分支的投影。当前 HEAD 是谁？用户/系统/策略怎么切换？
4. **旧分支归档**：修改即分支，分支会累积。旧分支打 tag 后删除 ref，对象仍在对象库里可达。
5. **高频 commit 的批量窗口**：如果某个场景下 commit 太碎，可以把一个事务内的多个事件打包成一个 commit。
6. **日志的压缩与归档**：旧日志段如何压缩，如何保留索引指针。
7. **日志的加密**：本地无远端，泄密不是问题，但日志里仍可能包含 API key 等，是否需要 redaction 取决于使用场景。
8. **日志的备份**：Git 仓库的备份策略。
9. **日志的迁移**：换 Git 版本或换存储后端时的迁移策略。
10. **日志的完整性校验**：如何验证日志未被篡改。

### 9.2 记忆系统

1. **FCA 格的增量更新**：新记忆加入时，概念格如何增量更新，而不是全量重建。
2. **记忆系统的压实与垃圾回收**：旧版本记忆何时可以安全删除，取决于日志中是否还有引用。
3. **记忆文件的原子写入**：纯文本文件的写入需要原子性，避免半写状态。可以用临时文件 + rename。
4. **FCA 目录的 Git 管理**：记忆库目录本身是否用 Git 管理，获得版本历史。
5. **向量与内容的一致性**：向量索引更新时，内容文件必须已经写入。需要事务性保证。
6. **索引的增量更新**：新事件和新记忆加入时，索引如何增量更新，而不是全量重建。
7. **内容文件的命名与组织**：FCA 概念格到目录路径的映射规则，文件命名规范。
8. **记忆文件的格式规范**：YAML frontmatter 的字段定义，正文的 Markdown 规范。
9. **索引与内容的版本对齐**：索引更新延迟时，如何保证检索结果指向的内容版本正确。
10. **记忆的去重**：内容寻址哈希如何用于去重。
11. **记忆的关联**：`related` 字段如何维护，如何自动发现关联。
12. **记忆的标签体系**：标签如何管理，如何用于检索。
13. **记忆的生命周期**：记忆何时创建、更新、归档、删除。
14. **记忆的权限**：不同来源的记忆是否有不同的权限。
15. **记忆的审计**：记忆的变更历史如何审计。

### 9.3 索引层

1. **索引的快照与备份**：索引可以从内容层重建，但重建成本高。定期快照可以加速恢复。
2. **索引的并发控制**：日志索引和记忆索引可能同时写入，需要处理 SQLite 的 WAL 模式和并发控制。
3. **索引的批量写入**：批量写入的窗口大小，如何平衡延迟和吞吐。
4. **索引的延迟更新**：索引更新延迟时，如何保证一致性。
5. **索引的版本管理**：索引 schema 变更时如何迁移。
6. **索引的压缩**：SQLite 数据库的压缩策略。
7. **索引的分片**：大规模索引是否分片。
8. **索引的缓存**：热数据缓存策略。
9. **索引的监控**：索引性能监控，查询延迟、写入延迟。
10. **索引的故障恢复**：索引损坏时的恢复策略。

### 9.4 检索层

1. **日志索引与记忆索引的边界**：哪些查询走日志索引，哪些走记忆索引，边界如何划分。
2. **RRF 融合的参数调优**：`k` 值的选择，保留槽位的数量。
3. **向量嵌入模型的选择**：不同嵌入模型的权衡。
4. **向量维度的选择**：不同维度的权衡。
5. **向量索引的构建**：HNSW / IVF 的选择和参数调优。
6. **FCA 格的构建算法**：不同 FCA 算法的权衡。
7. **哈希函数的选择**：SHA-256 / BLAKE3 的选择。
8. **Cuckoo filter / Bloom filter 的参数调优**：误判率和空间开销的权衡。
9. **检索结果的重排序**：是否需要额外的重排序模型。
10. **检索结果的分页**：大规模结果的分页策略。
11. **检索结果的缓存**：频繁查询的缓存策略。
12. **检索的个性化**：不同用户/会话的检索偏好。
13. **检索的时效性**：时间衰减因子的引入。
14. **检索的多样性**：结果多样性的保证。
15. **检索的可解释性**：为什么返回这个结果。


### 9.5 投影层

1. **投影策略的设计**：不同投影策略的权衡。
2. **投影策略的组合**：多个策略如何组合。
3. **投影策略的动态切换**：运行时如何切换策略。
4. **投影的缓存**：投影结果的缓存策略。
5. **投影的失效**：底层日志追加新事件时，投影缓存如何失效。
6. **投影的回放**：如何回放旧投影。
7. **投影的对比**：不同投影的差异对比。
8. **投影的审计**：投影决策的审计链。
9. **投影的安全性**：防止无审计的篡改。
10. **投影的性能**：大规模日志的投影性能。

### 9.6 系统整体

1. **系统的启动**：如何从冷启动恢复状态。
2. **系统的关闭**：如何优雅关闭，保证数据一致性。
3. **系统的监控**：整体性能监控。
4. **系统的日志**：系统自身的日志。
5. **系统的配置**：配置管理。
6. **系统的迁移**：换存储后端时的迁移策略。
7. **系统的扩展**：如何水平扩展。
8. **系统的容错**：组件故障时的容错。
9. **系统的测试**：单元测试、集成测试、端到端测试。
10. **系统的文档**：架构文档、API 文档、用户文档。

## 十、总结

### 10.1 一句话概括

**内容是纯文本，索引是 SQLite。日志用 Git 管版本，记忆用 FCA 目录管结构，索引全部可重建。投影层从日志派生模型可见历史，三者通过版本化引用关联，职责正交，互不干扰。**

### 10.2 五个层次

**内容层（纯文本）：**

- 会话日志：JSONL 文本行。
- 记忆条目：Markdown 文件。
- FCA 概念格结构：JSON 文件。
- 记忆注册表：JSONL 文件。
- 版本映射：JSONL 文件。

**版本层（Git）：**

- 不可变内容存储。
- DAG 可达性与分支。
- 内容寻址。
- 审计链与回放。

**索引层（SQLite）：**

- 日志索引：B-tree + FTS5。
- 记忆索引：B-tree + FTS5。
- 向量索引：sqlite-vec。
- 哈希索引：内容寻址哈希 + token 哈希。

**检索层（记忆系统）：**

- FCA 目录：结构化导航。
- 向量模糊索引：语义召回。
- 哈希精确搜索：精确命中。
- RRF 融合，保留槽位。

**投影层（模型可见历史）：**

- 从日志派生模型可见历史。
- 纯函数视图，可重建。
- 决策落 `projection_event`。
- HEAD 决定投影，模型历史可变，日志不变。

### 10.3 三个核心原则

**第一条：内容是纯文本，索引是 SQLite。**

所有持久化内容以纯文本形式存储。SQLite 只做索引，不存内容。索引是纯加速器，随时可以丢弃、重建、替换，不影响任何数据。

**第二条：日志是 DAG，HEAD 是当前视图，任何变化都产生新节点，从不覆盖旧节点。**

日志不是项目，是事件序列。修改历史不是重写，而是从某个分叉点长出一条新分支。旧分支完整保留，审计链永不断裂。

**第三条：记忆是跨会话的物化视图，通过三层检索为投影提供召回信号。**

记忆系统与日志系统职责正交，存储独立，生命周期独立。两者通过版本化引用关联。

### 10.4 存储依赖

整个 harness 的存储依赖只有三个：

- **Git**：管不可变日志。
- **SQLite**：管索引。
- **纯文本文件**：管内容。

职责清晰，依赖最少，工程一致性最高。

### 10.5 各层独立演化

- **日志**：可以无限增长，可以分支，可以归档。
- **记忆**：可以换嵌入模型，可以重建 FCA 格，可以调整目录结构。
- **索引**：可以重建，可以替换，可以换 SQLite 版本、换 FTS 分词器、换向量索引。
- **投影**：可以版本化切换策略，可以回放旧投影。
- **关联层**：`commit_hash` + `seq` + `memory_id + version + hash` + `file_path` + `projection_event`。保证追溯链完整。

只要关联层保持完整，整个系统的可追溯性就不会被破坏。

### 10.7 最终定位

整个系统可以概括为：

**一个以 Git 为版本层、以纯文本为内容层、以 SQLite 为索引层、以 FCA + 向量 + 哈希为检索层、以投影为模型可见历史层的 Agent 记忆与日志系统。**

它有三个存储依赖：Git、SQLite、纯文本。

它有五个层次：内容层、版本层、索引层、检索层、投影层。

它有三个核心原则：内容是纯文本，日志是 DAG，记忆是物化视图。

它的所有设计决策都指向同一个目标：**可追溯、可重建、可替换、可审计。**
