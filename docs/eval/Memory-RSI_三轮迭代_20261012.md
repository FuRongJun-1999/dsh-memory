# Memory-RSI 三轮迭代 · 2026-10-12

本报告接续 [基础修复与工具检查](Memory-RSI_续研验证_20261012.md)。按“先多迭代几轮，不急着 PR”继续研发；没有提交、推送、创建 PR 或安装正式插件。

三轮结果：保留默认 CSRE 的正确性修复；增加可选 SQLite 会话降低严格校验成本；修复经验提炼的多检查与条件身份漏洞；元数据紧凑编码没有改善公开指标，**不采纳为默认方案**。没有证明 LLM Agent 的能力提升。

## 第一轮：降低校验成本

默认 `Csre` 仍逐次核验完整来源行指纹。新增 `csre_session.CsreSession`，只有显式 `with` 会话才启用。会话持有只读 SQLite 观察连接；`PRAGMA data_version` 未变时复用上次已核验快照，发生事务提交后重新执行原完整行/schema 哈希。额外检查文件身份，换源重新验证。

适用范围是同一线程内、正常 SQLite 事务写入的短会话。WAL 提交与恢复 mtime 的更新均有反例覆盖。MD 数据源始终新读完整快照，没有套用 SQLite 版本缓存。连续三次检查期间都变化时关闭使用旧结果的路径，返回 source_unavailable。

```python
from csre_session import CsreSession

with CsreSession(fixture_db, fixture_index) as engine:
    if engine.ensure_loaded():
        domains = engine.rank_domains(question)
        cards = engine.top_units_in_domain(domain, question)
# 退出上下文关闭观察连接并清空该会话的矩阵
```

默认导航没有切换到此会话。它额外保留 O(N) 来源行快照；不支持跨线程共享，不认证绕过 SQLite 事务的原始文件篡改，也不声称解决校验之后发生的并发更新。

会话回归 25 项通过：复用 20 项基础反例并新增热命中、mtime 恢复、无关表提交、只读/关闭和不稳定来源的有界重试。基准在没有同时运行完整测试组时，按完整检查 → 会话 → 完整检查串行执行；每侧 20 查询、7 次计时，fixture 哈希相同。

| 卡数 | 完整检查 p50，前/后对照 | 会话 p50 | 完整检查 p95，前/后对照 | 会话 p95 |
|---:|---:|---:|---:|---:|
| 100 | 2.407 / 2.397 ms | 1.582 ms | 2.520 / 2.542 ms | 1.805 ms |
| 1000 | 6.946 / 6.454 ms | 2.605 ms | 7.520 / 7.181 ms | 2.839 ms |

每个样本仍包含域排序和域内 Top-K 两次调用。两侧均为 0/20 负条件违规查询，均拒绝过期与串库索引。1000 卡的温热诊断中，会话 p50 比两次完整检查对照的均值低约 61%；这不是冷启动、生产分布或跨机器速度保证，也没有抹去完整检查相对原不安全基线的成本。

## 第二轮：多检查与条件身份

新增 9 个对抗用例，加上复用的 13 个 Lab 回归共 22 项。修改前出现 6 项失败；修改后 22 项通过，原独立原型模块 16 项也通过。

本轮修复：

- 同一动作的有效绑定工具检查必须全部为布尔 True；“一项成功、一项失败”不再产生修复候选。
- 多项成功检查合并为一个候选，保留全部检查事件引用；不只摘取成功的一项。
- 同一错误已有替代动作时，后来的检查不能反过来归功于旧动作；另一个独立错误的动作不影响它。
- 条件使用原 `condition_space.all` 的集合语义，排序、去重和去首尾空白；原始轨迹的条件字符串保持原样。换序不再绕过同条件冲突门。
- 摘要记录 `reflector_version=2` 及原 error/action。同上下文的旧版候选需要人工复核，不静默按新版重解释或接受。

未放宽单轨迹资源限制、证据哈希、原身份权限、冲突暂缓或 inbox 审核。助手自报的检查仍不作为工具验证。结果只证明局部工具观察，不认证外部工具身份。

真实工具夹具新增“首项值检查通过、第二项必须有 unit=ms 的检查失败”三例。第二项通过实际 Python 进程读取上一项输出检查，不是手填失败。冻结后结果为：

| 指标 | 实测 |
|---|---:|
| 轨迹 / 实际工具调用 | 12 / 30 |
| 成功观察 / 失败观察 | 3 / 9 |
| 修复进程退出码 0，但整体检查失败 | 6 |
| 失败观察产生的候选 | 0 |
| 待审候选 / 自动写入 knowledge | 3 / 0 |
| 新实例固定方案重放 | 3/3 通过 |
| 待审回滚 | 成功，3 → 2 |

修复方案与控制器仍是预定义白名单，没有让 LLM 按记忆完成新任务，Agent 任务成功率保留 null。

## 第三轮：元数据预算消融

新增显式 `query_metadata_compact` 实验臂：将字段表交付一次，逐节点交付等价字段值数组。保留 id、创建时间、来源、条件、验证状态、资格与三个有效/相信时间字段，表头也计入总预算。3 项回归覆盖字段无损往返、总预算、来源偏移与空输出。

使用前轮已经观察过的冻结合成题和公开状态链。协议明确是回顾性复跑，不能当作新盲测；质量仍按唯一问题统计，不把计时重复当新样本。新臂没有改数据、裁判、检索名次、总预算或原交付默认值。

| 指标 | 查询片段+原元数据 | 查询片段+紧凑元数据 |
|---|---:|---:|
| 合成 holdout 名称分组，48 个有标签问题的完整证据率 | 87.5% | 87.5% |
| 合成平均估计 tokens（包括未知题） | 201.75 | 212.32 |
| 公开 63 题、预算 240 的现值字符串出现 | 13/63 | 13/63 |
| 公开 63 题、预算 1200 的现值字符串出现 | 27/63 | 27/63 |
| 公开 1200 平均估计 tokens | 1161.75 | 1159.06 |
| 超预算次数 | 0 | 0 |

共享表头在少量节点时反而增加成本；公开大预算的少量字符节省没有转化成指标收益。原交付该公开指标为 30/63，查询无元数据与前缀控制均为 31/63，元数据两臂都没有超过它们。

因此不采纳此臂为默认方案。代码仅为独立消融保留显式入口，正式接口未接入。出现字符串不是现值答对，也不是时间/多跳推理成功；所有预算采用项目 token 估算器，不是真实模型 tokenizer。

## 最终验证与失败记录

最终完整 Memory 组：本次完整组 308/309 个可运行模块通过，1 项失败；3 项私有语料 SKIP，共 312 个发现模块。唯一失败是新增工具基准的裸索引迭代；改成快照后，原 H4 完整守卫独立复跑通过，工具链也复跑通过。未再重跑整个组，不将两次运行拼称一次全绿。逐模块完整日志齐备，18 个冻结 Python 文件未变，1 个脚本的修复另留版本。

其他已完成：判断覆盖守卫 28 项通过；子进程编码守卫通过；原导入/神经失败守卫的变异自证通过，目标源码按字节恢复；真实 stdio MCP 检查完成，匿名读取与拒绝写入仍有效。没有 DSH UI、正式身份写入或模型 reader 验证。

保留的失败记录：

1. 首轮隔离运行器统一设 MDCG_FRESHNESS=0，干扰自治/模式对拍，提前停止。移除覆盖后自治独立复跑通过。
2. 第二轮完整组 302/306 通过、3 SKIP；模式对拍有一次未解释的差异，独立复跑 15/15 相同；未把偶发失败删去或擅自归因。
3. 该轮安全守卫的 128 字符合法 id 遇到 Windows 路径过长；改用工作区内的短临时根后独立复跑通过。没有宣称修复产品的所有 Windows 长路径问题。
4. 两处新增实验脚本文本子进程调用缺少 encoding，已补 UTF-8 并通过原守卫。
5. 时间核守卫在 300 秒超时。其原文已说明是长耗时测试且建议至少 600 秒；最终组恢复 900 秒单项上限，没有删断言或改性能阈值。
6. 最终组快照守卫 G1 点名新增工具基准裸迭代。仅该脚本改为先取 list 快照，并重跑 30 次工具检查；原始失败和修复后 H4 完整守卫的独立记录分开保留，不将它们拼成一次全组全绿。

3 项私有语料 SKIP：`test_md_access_parity`、`test_p44_md_whitebox`、`test_wisdom_md_store`。没有使用真实记忆补齐它们。

各轮协议、修复前/迭代一/最终源码快照、失败日志、每次工具输出和每次计时随交付包保留。最终组留完整逐模块输出，运行器仍调用原 `scripts.run_tests.main()`，外层只保存日志，不改变判据。

## 当前决定

继续保持实验默认关闭。正确性修复与可选会话有可重复的局部证据；新版 Reflector 的反例拦截比旧版完整；交付候选缺少收益则不升级默认。

尚需独立自然任务、固定模型/reader/预算/重试和相同审核门控对照，才能判断 Memory-RSI 的 Agent 收益。没有以这些局部结果宣称可靠自我进化或 AGI 能力。
