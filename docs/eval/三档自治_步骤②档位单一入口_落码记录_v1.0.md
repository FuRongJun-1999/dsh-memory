## 一、缺陷定义与真实站点

### 1.1 缺陷定义（四件，同一根因：设计 §三 冻结的档位语义在代码里零落点）

1. **装载面**：`md_cg/autonomy_modes.py` **不存在**——任何 `import md_cg.autonomy_modes` 立即 `ModuleNotFoundError`（腿① 实测两条载荷 rc=1）。全仓代码对 `MDCG_AUTONOMY` **零读取点**（HEAD 树 grep：唯一命中在设计稿正文 `:73`；`A_ADD`/`B_MERGE`/`D_DELETE` 零命中——见 1.2 末行）〔本报告实跑〕。
2. **热路径 B/C/D 全部直执行**：C 改写（写链 `cg.add` 直接落盘）、B 合并（`remember_gated` 两个分支直调 `converge_into` / `reinforce`）、D 删除（MCP 工具面两通道直调 `cg.forget` → `publish` 软删）——全部**无档位判定、零变更单产物**（腿②–⑤）。
3. **变更单面缺位**：`propose` 条目 rec 无 `kind` 类型字段；幂等键只有内容签名（`phash = _sig(content)`），**动作类与目标不参与幂等**；合成 mutation 键无处安放（只能落 `extra` 任意槽）（腿⑥）。
4. **裁决面无分派**：`review_decide` 对 mutation 载荷静默按 proposal 处理——「一条声称删除的裁决把节点正文清空而非删除」（腿⑦）；且**非法档位值不 fail-closed**：5 档（含 `bogus-garbage-value`）行为逐字段一致，非法配置静默等同缺省（腿⑧）。

一句话：**对既有记忆的 B/C/D 变更在缺省（甚至计划）档下不经确认静默发生，且非法配置静默降级为放行**——与设计 §三「变更确认（默认档）：B/C/D 需确认」「计划外零变更」两条硬语义直接冲突。

## 三、修法契约与落点

### 3.1 契约（设计 v0.2 §三/§四，逐条）

1. **单一入口**（§三 硬约束①，设计稿 `:73`）：档位是**一个** env 键（`MDCG_AUTONOMY=plan|confirm|full`，缺省 `confirm`），由**一处**判据函数读取与解释；不得各模块各读一份。落法：`autonomy_modes.py` 为全仓唯一 `.py` 字面量落点（键名 `:66`）与唯一读取出口（`autonomy_env() :120` / `mode() :128`）；**改缺省只改 `AUTONOMY_ENV_DEFAULTS` 表（`:61-63`，值在 `:62`）**——`:69` 的 `AUTONOMY_MODES` 只枚举合法值、`:65-67` 只管键名（三者分工见术语速览「档位」行）。
2. **纯加严**（§三 硬约束②）：任一档都不得放宽既有判据——档位判定一律在**既有资格闸通过之后**：写链在 audit/consistency/gated 之后、链尾执行器之前（`:617-652` 注释与 `:726-730` 注册）；删除在 `protect.guard_forget` 等资格闸之后（`forget_gated :2892-2905`）；B 合并在限流闸/遗忘三问**裁决之后**（`_autonomy_gate_merge :3831-3852`）。另：写面资格闸（层闸/写保护/降级闸）住在 `cg.add` 内部，故档位判定前新增 `write_qualify` 资格探针（`mdcos.py:3884-3920`，`override=False` 只判不写快照）。**该探针的覆盖口径（v1.1 补——回应「这两句各覆盖哪些闸类」）**：探针调用的闸 = `guard_overwrite`（→`is_immutable`：层保护 self/anchor、`immutable` 标记 ＋ principal 层白名单；`protect.py:269-281`、`:361-379`）与 `guard_move`（→`is_protected`：**仅跨层**时触发；`:297-304`）；**不覆盖**「`protected` 位/分数」形态的**同层**覆写（`is_immutable` 本就不认位/分——`protect.py:180-198`）——即「本该 AccessDenied/ProtectionError 的覆写不得变成静默入队」在此覆盖面上成立；位/分形态同层覆写会出单且 accept 落盘（实测，见 §6.1 第 8 条），按既有教义不属「本该被拦」。
3. **计划外零变更**（§三 硬约束③）：计划模式下未命中计划步骤的动作 = `forbid`（fail-closed 带 hint），不静默跳过。**适用范围按设计 §三 表逐格**（设计稿 `:63-69`，本报告读码）：「须命中计划步骤」格只有 A/B/E 三个——`plan` 档下无计划输入（`plan=None`）时它们一律 forbid（带「计划输入面待后续批次」hint）；**C/D 两格在 plan 档的定值是「需确认」（与 confirm 档同格），不使用、也不依赖计划输入**——硬约束③的 fail-closed 不作用于 C/D 是矩阵（设计真源）的逐格定值，不是豁免（实现 `MATRIX :92-99` 逐格照抄，守卫 A 组逐格断言；v1.1 改写：原「矩阵如此」表述易被读作拿被质疑对象自证，此处给出契约出处与适用范围的精确划分）。
4. **裁决矩阵**（§三，3 档 × 5 类逐格照抄，`MATRIX :92-99`）：plan 档 A/B/E=`plan_step`（命中计划才 allow，否则 forbid）、C/D=confirm；confirm 档 A/E=allow、B/C/D=confirm；full 档全 allow。
5. **变更单**（§四，`kind="mutation"`）：复用既有审核队列（**不新建第二套**）——类型字段落 rec 顶层（`kind` 只在显式给定时落键；缺键 = proposal，存量零迁移）；业务载荷（动作类/目标/后像/理由/复现 meta）落 `extra.mutation`（沿用 `extra.defer_reason` 先例）；幂等键 = 动作类 ⊕ 目标 ⊕ 后像 的 sha1（`mutation_dedup_key :300`），**显式覆盖** `payload_hash`（内容签名不带目标会撞键）。构造/出单唯一入口 = `propose_mutation :318`（复用既有入队单点 `cg.propose`）。
6. **裁决执行桥**（§四）：变更单 `accept` = 执行对应动作（B 走 `reinforce`/`converge_into` 原语、C 走既有 `add` 覆写、D 走既有 `forget` 软删）；`reject` = 原样留痕不执行；**其余裁决（edit/merge/noop）对变更单未定义 ⇒ fail-closed** 报 `mutation_decision_unsupported` 带 hint（不静默当已处理）。执行失败 ⇒ **不记裁决**、提案保持 pending（不许「落一条 accepted 而动作没做」）。
7. **库层不接线**（§三 硬约束②的机制前提）：`MdCG.add` / `_write_node` / `MdCGOS.forget` 与合并原语（`forgetting.reinforce` / `writelimit.converge_into`）保持无档位判据——「已确认」由调用点保证，不靠可伪造的旗标穿透各层；保护闸不绕（`add`/`reinforce`/`converge_into` 内部 `protect.guard_*` 仍是落盘必经之路）。
