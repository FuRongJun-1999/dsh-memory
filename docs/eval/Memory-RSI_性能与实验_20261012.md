## 2. 冻结协议与实验版本

最终协议 `experiments-v6/protocol.json`：随机种子 `20261012`、`314159`；development/validation/holdout 三个独立命名的集合，每个 seed/split 为 24 道有标签题和 4 道未知题。总共 **168 个唯一问题，其中 144 个有标签**；holdout 是 48 个有标签题加 8 个未知题。

每图含 32 个目标节点与 48 个噪声节点。题型是 head、tail、long_line、temporal、multihop；长文尾部是有意增强的诊断分布，三个别名题故意保留词法检索缺口。不能把该分布当自然用户问题分布。

总交付预算 240，条目摘录预算 120，top-k=5；节点创建时间固定为 Unix 秒 `1767225600`。semantic/freshness/hotcache 关闭，候选索引只在指定臂开启。无 reader、模型、裁判、网络执行器。预算使用项目 `est_tokens`，并非任何真实模型 tokenizer。

fixture 文件 SHA256：`83012594932f3389a151f9bfe85b723ddd7218b045b0edfb3e699549619edee4`。最终运行前后 fixtures 和三个评价/算法源文件哈希均一致；候选只接收 query 与检索结果，答案仅用于评分及明确标记的 oracle。

版本记录不能忽略：v1 首轮有三次计时重复，但原置信区间错误地把重复当样本；v2 修正按 qid 聚类并补同装包前缀消融；v3 将存储模块导入移到路径隔离之后；v4 尝试固定时间时传了字符串，触发 API 类型错误，运行失败；v5 改用 API 要求的 Unix 秒，完整复验；v6 将轨迹角色改为已有 `tool-output` 并复核最终源码，质量每题执行一次。v1/v2/v3/v5 均保留原始结果，v4 失败协议和日志保留。

这些修改不改变 exact-substring 质量评分规则。后续运行读过早先 holdout，属于同一批冻结题的重放，**不能再称新增盲测或独立验证集**。最终置信区间按唯一问题计算，不从重放增加样本数。自然任务的独立验证仍待进行。

## 3. A/B/D 与交付消融

| 代码臂 | 行为 |
|---|---|
| A_original | 实际调用原 `MdCGOS.recall`，按原逻辑摘录与装包，拼接 pack content 作为测量文本。 |
| B_query | 同一原 `search_rrf`，按查询选择原文窗口，预算内交付。 |
| B_query_metadata | B_query 加 ID、创建时间、来源、条件、验证与资格等实际文本；字段占用同一总预算。 |
| C_prefix_control | 使用候选的同一装包函数，摘录改回前缀；这是**交付消融**，不是总任务书的“C 经验巩固”臂。 |
| D_candidate_index | 原 recall，只打开仓库已有 `MDCG_RRF_CANDIDATES`，没有改权重或另建权威库。 |

质量读数为两个 holdout seed 的 48 道有标签题聚合；未知题只进入未知返回率。Recall@K 使用相关节点数分母，多证据题不能把“找到任意一个节点”当全召回；MRR 是首个相关节点倒数名次。

| 指标 | A 原版 | B 查询片段 | B 查询+metadata | 前缀消融 | D 既有索引 |
|---|---:|---:|---:|---:|---:|
| Recall@1 | 72.9% | 72.9% | 72.9% | 72.9% | 72.9% |
| Recall@5 | 87.5% | 87.5% | 87.5% | 87.5% | 87.5% |
| MRR | 0.875 | 0.875 | 0.875 | 0.875 | 0.875 |
| 完整证据字符串交付 | 16.7% | 87.5% | 87.5% | 16.7% | 16.7% |
| temporal 所有支持句交付 | 0% | 100% | 100% | 0% | 0% |
| multihop 所有支持句交付 | 0% | 75% | 75% | 0% | 0% |
| 未知题返回非空上下文 | 100% | 100% | 100% | 100% | 100% |
| 平均估算 token，含未知题 | 197.0 | 87.4 | 201.8 | 195.1 | 197.0 |
| 超总预算 | 0 | 0 | 0 | 0 | 0 |

temporal/multihop 两行是**证据齐全代理**，不是时间推理或多跳推理准确率；没有模型生成答案。查询片段与 metadata 质量相同，不能将额外 metadata 的价值归因到这项质量指标。前缀消融仍为 16.7%，说明该合成分布的收益与摘录位置有关，而不是仅换了装包函数。

逐题 `provenance_exact` 在各臂均为 1，但它只检查原版前缀匹配，或候选的源哈希与偏移范围。这不是完整语义证据正确率、证据足以支持结论的判定或轨迹外部真实性认证。

## 4. Oracle 定位与统计不确定性

holdout 的三个诊断读数：

| Oracle | 完整证据出现率 | 解释 |
|---|---:|---|
| 已知 gold 节点 + 原版预算交付 | 16.7% | 即使检索完美，该合成分布仍会因前缀摘录丢失支持句。 |
| 实际检索 + 不限预算原文 | 87.5% | 检索缺口仍在；不限预算只是诊断上界。 |
| gold 节点 + 不限预算原文 | 100% | 理想构造上界，不能作为同成本候选成绩。 |

B_query 相比 A 的证据完整率差为 **+70.8 个百分点**；固定 seed=827 的 2000 次问题级配对 bootstrap，95% 区间为 **+56.3 至 +83.3 个百分点**，单位为 48 个唯一有标签问题。模板之间高度相关，区间不能代表自然任务总体；也没有衡量 reader 的不确定性。

最终质量表明此类长文样例存在交付损耗，不证明检索全面无瓶颈，更不证明 Agent 任务成功率提高。

## 5. 公开 hive 状态链诊断与负结果

使用 [官方 hive-memory-bench](https://github.com/FuRongJun-1999/hive-memory-bench) 的 `f4509d7282f82982af5de9c8fe71863fc95b38cb`：270 段、642 道答案键，选其 63 道现值题。沿用官方 `probe_judge.norm` 和既有诊断口径，top-k=6，分别测预算 240/1200、条目预算 250。语料与键哈希在 `public-rrf-v2/protocol.json`，运行前后未变。

| 现值字符串代理指标 | A 原版 | B 查询片段 | B 查询+metadata | 前缀消融 | D 既有索引 |
|---|---:|---:|---:|---:|---:|
| 检索原文含现值，k=6 | 50.8% | 50.8% | 50.8% | 50.8% | 50.8% |
| 预算 240：交付含现值 | 20.6% | 20.6% | 20.6% | 20.6% | 20.6% |
| 预算 1200：交付含现值 | 47.6% | 49.2% | **42.9%** | 49.2% | 47.6% |

现值字符串可能也出现在历史链中，**出现不代表选对现值、状态或生效序号**。表格不是官方答案分数、不是标准 Recall@K，也不是时间推理准确率。B_query 在 1200 预算仅多 1/63，前缀消融同样达到该读数，不能把它归因于查询片段算法；metadata 少了 3/63，说明固定字段开销可能挤掉内容。240 预算没有提升。

另外直接运行仓库原 `scripts/bench_chain_retrieval_diag.py`，其单路 `MdCG.search` 诊断命中为 32/63（50.8%），同程序朴素 bigram BM25 为 41/63（65.1%）。这是该程序内同语料的诊断对照，BM25 不是完整官方 adapter 复现，也不等于最终任务胜负。剔除 1 道可推题后分别为 31/62（50.0%）和 40/62（64.5%）。

RRF 诊断中旧值优先于现值的代理率为 79.4%；它只比较字符串首次出现块的名次，不能当作 reader 的错误率。公开结果与合成长文结果共同表明两段都可能损失，不能将主导瓶颈统一归因于交付。

## 6. 经验巩固 C 与策略推荐 E

32 个模拟依赖修复轨迹：16 个工具检查成功、16 个失败。所有命令和检查都是模拟数据，没有真的运行 pip。原 `mine_fix_pairs` 与本轮 Reflector 使用同一个图存储 API。

| 经验臂 | 成功样例产生候选/知识 | 失败样例仍产生候选/知识 | knowledge 直接写入 | 待审提案 |
|---|---:|---:|---:|---:|
| 原 `mine_fix_pairs` 默认直写 | 16/16 | 16/16 | 32 | 0 |
| 原 `mine_fix_pairs(as_proposals=True)` | 16/16 | 16/16 | 0 | 32 |
| 绑定工具检查的 Reflector + Curator | 16/16 | **0/16** | **0** | 16 |

第二臂排除了“只改成提案队列”的影响：新机制确实在这组结构化输入中滤掉了失败观察，没有靠全部禁写得到候选过滤成绩。但失败样例的候选产生率下降，**不等于真实错误知识接受率或跨任务修复收益已测得**。外部回执没有签名认证，scope 泛化也没有自然任务验证；原型未自动接受任何候选。

E 的优化器只在 validation 选择最多 6 个内置策略，1 轮结束后冻结推荐，再评估 holdout。最终推荐为 `B_query_metadata`，`accepted=False`。它与 B_query 在合成验证中质量并列，选择受 P95 次级排序影响，不能把这个噪声敏感推荐当可靠算法胜出。公开语料的 metadata 负结果足以阻止正式接受；没有根据公开题改参数后再宣称独立提升。

## 7. 延迟、计算、token 与存储口径

质量实验使用 tracemalloc，会影响耗时；部分早轮还与原版测试重叠，不能用来比较速度。另行运行 `latency-v2`：无 tracemalloc，两张合成 holdout 图，先排除 1 次暖机，每个唯一 query 再计时 10 次，各臂顺序随机。每臂 560 次调用，只有 56 个唯一问题。延迟包含检索和交付，未测 DSH UI、模型推理、冷启动或正式大库。

| 臂 | P50 ms | P95 ms | 560 次总 CPU ms |
|---|---:|---:|---:|
| A_original | 13.30 | 25.99 | 3234.4 |
| B_query | 12.84 | 22.04 | 3296.9 |
| B_query_metadata | 12.78 | 21.73 | 3062.5 |
| C_prefix_control | 12.78 | 25.49 | 3265.6 |
| D_candidate_index | 13.39 | 22.78 | 3218.8 |

此规模没有证明查询交付或候选索引有稳定速度优势。CPU 为 Windows 进程计时，粒度较粗，很多短调用会计为零；表中总量不能当精确 FLOPs。

Python tracemalloc 的调用增量峰值仅是 Python 分配，不包含全部 native 分配、物理 RSS 或系统缓存。最终运行的逐题与聚合峰值随原始结果保存；此前三次重复运行中 A 约 44 KB、B 约 38–41 KB，而 D 首建候选索引约 1.35 MB。不能据此宣称内存优化；D 的建索引成本在小图里可见，却未换来已证明的延迟收益。

所有交付臂共用同一图；本轮不建立新数据库，因此没有产生第二权威真源。磁盘快照大小是实验结束时节点/派生索引/访问日志的总和，访问次数会影响日志大小，不能当生产库压缩率。P1 保留原始 trace 与提案版本会增加存储，尚未验证长期增长与维护成本。
