## 1. 缺陷定义与真实站点

**缺陷定义**：N225 的攻击面是「**合法 JSON 但顶层非对象**」——`null`、`[]`、`123`、`"abc"`。`json.loads` 对它们全部成功返回，因此 `except ValueError` 类防线看不见它们；而下游判据直接把它当对象用（`d.get(...)` / `r.get(...)`），抛出的 `AttributeError` 不在捕获元组内，于是异常穿透到构造期与工具层。

**真实站点（本报告读码所见）**。下表把**修前文本**与**修后文本**分成两列——「后果」列一律描述**修前文本**的行为；修后的行为见 §3：

| # | 修前文本（`git show HEAD:...` 实读，行号为修前行号） | 修后文本（工作区实读，行号为当前行号） | 修前文本的后果 |
|---|---|---|---|
| ① 装载面 | `md_cg/mdcg.py:1050`：`if d.get("schema") == SCHEMA:` ← **没有 `isinstance` 守卫**（`if` 与 `except` 见 `HEAD:1047-1053`） | `md_cg/mdcg.py:1057`：`if isinstance(d, dict) and d.get("schema") == SCHEMA:` | 顶层非对象时裸 `d.get` 抛 `AttributeError`，而修前 `HEAD:1052` 的 `except (ValueError, OSError)` 不接 ⇒ `MdCG.__init__`（`md_cg/mdcg.py:1028` 调 `_load_index`）**构造即失败** |
| ② 分片日志面 | `md_cg/fsutil.py:386`：`recs.sort(key=lambda r: (r.get("_t", 0), r.get("_s", 0)))` ← **排序键前无任何行类型分流** | `md_cg/fsutil.py:451` 同上（排序键文本未变）；分流新增在 `md_cg/fsutil.py:436-444`（`isinstance(rec, dict)` 判定） | 非对象行直接进 `recs`，排序键对非 dict 裸调 `.get`；单元素列表也调键函数 ⇒ **n=1 即崩** |
| ③ compact 面 | `md_cg/mdcg.py:1235`：`if d.get("schema") == SCHEMA:` ← **没有 `isinstance` 守卫**（`try` 在 `HEAD:1232`、`except` 在 `HEAD:1239`） | `md_cg/mdcg.py:1242-1249` 新增 `if not isinstance(d, dict): scan_fallback = True`；原判据降为 `elif d.get("schema") == SCHEMA:`（`md_cg/mdcg.py:1250`）；`else: scan_fallback = True`（schema 不符）在 `1252-1253` | 崩点（修前 `HEAD:1235` 的 `d.get`）落在修前 `HEAD:1232` 的 `try` 内，而 `except`（修前 `HEAD:1239`）只收 `(ValueError, OSError)` ⇒ **在「顶层非对象」这一类载荷下**标志 `scan_fallback` 保持 `False`，「宁重扫勿清池」走不到（该标志的命名与适用范围见 §2 腿③ 末段） |

**锚点漂移的行数核算（实跑 `git diff -U0 -- md_cg/fsutil.py` 的 hunk 头逐块加总）**：台账旧锚点 `mdcg.py:1050` / `fsutil.py:386` / `mdcg.py:1235` 经 `git show HEAD:md_cg/mdcg.py`、`git show HEAD:md_cg/fsutil.py` 逐行核对，与修前 `HEAD` 版本一致；漂移量按 hunk 分解如下——

## 2. 修前现场取证（改动前，由本工作流「缺陷复现员」取得）

以下三条腿**逐条列 payload / 异常 / 崩溃点**。来源＝本工作流缺陷复现环节采集（§4.2 标注为「未由本报告复跑」）；每条腿都在系统临时目录合成库上跑，跑完 `rmtree`，只用只读手段。

### 腿 ① 快照装载

- **payload**：`null` / `[]` / `123` / `"abc"` 四种非对象形态**逐项独立实跑**——各建一个临时库根，把 `_index.json` 写成该形态后构造 `MdCG`。
- **observed**：四种形态**全部崩**，消息随载荷类型变：
  - `null` → `AttributeError: 'NoneType' object has no attribute 'get'`
  - `[]` → `'list' object has no attribute 'get'`
  - `123` → `'int' object has no attribute 'get'`
  - `"abc"` → `'str' object has no attribute 'get'`
- **崩溃链**：`MdCG.__init__`（`md_cg/mdcg.py:1028`）→ `_load_index`（修前 `HEAD:1050` 的 `d.get`）。构造期的 `except (ValueError, OSError)`（修前 `HEAD:1052`）捕不住 `AttributeError` ⇒ **失败发生在构造期，不是工具层**。
- **站点**：`md_cg/mdcg.py:1050`（`HEAD` 口径）。

### 腿 ② 分片日志重放

- **payload**：一行 `null` 分片记录。用的是仓库自己的写点：`fsutil.append_jsonl(<root>/_index_log/99999-nullprobe.log, None)`，落盘字节为 `b'null\r\n'`。
- **`b'null\r\n'` 的成因与「是否仓库既有行为」**：`append_jsonl` 定义在 `md_cg/fsutil.py:189`，其写点是 `md_cg/fsutil.py:204` 的 `fd = os.open(path, os.O_CREAT | os.O_WRONLY | os.O_APPEND, 0o600)`——**未带 `os.O_BINARY`**；Windows CRT 文本模式把 `\n` 转成 `\r\n`。实跑 `git show HEAD:md_cg/fsutil.py` 核对：`HEAD:189` 与 `HEAD:204` 与工作区**逐字相同**（该文件本次 diff 无这两个函数的 hunk）⇒ 这是**仓库既有行为**，不是这条实验路径的偶发现象。`\r\n` 不影响判定：`read_jsonl`（`md_cg/fsutil.py:212-224`）先 `strip()` 再 `json.loads`，仍得 `None`。
- **observed**：`AttributeError: 'NoneType' object has no attribute 'get'`，**崩在排序键函数**（单元素列表也调键函数，`n=1` 即崩）。
- **崩溃链**：`MdCG.__init__`（`md_cg/mdcg.py:1028`）→ `_load_index`（修前 `HEAD:1067`，`for rec in ShardedLog.read_all(...)`）→ `fsutil.py:386`（修前）`recs.sort(key=lambda r: (r.get("_t", 0), r.get("_s", 0)))` → `<lambda>`。
- **站点**：`md_cg/fsutil.py:386`（`HEAD` 口径）。

### 腿 ③ 压缩重写（compact）

- **payload**：`null`。步骤：先在临时库 `add` 两个节点并 `close` 落快照 → `MdCG` 构造成功 → 把 `_index.json` 覆写为 `null` → 调 `compact_index`。
- **observed**：`AttributeError: 'NoneType' object has no attribute 'get'`。崩点是修前 `HEAD:1235` 的 `d.get`，**就在修前 `HEAD:1232` 起的 `try` 内**，而 `except` 在修前 `HEAD:1239` 只捕 `(ValueError, OSError)` ⇒ 该函数的降级标志（变量名 `scan_fallback`，修前 `HEAD:1230` 初始化、工作区 `md_cg/mdcg.py:1237` 初始化）在这类载荷下**保持 `False`**。
- **标志名与「恒」的适用范围（澄清）**：§1 表③ 与本文提到的是**同一个标志** `scan_fallback`——采集原文里的 `scan_fallback_reached=false` 是复现环节对该标志的原始观测记录，等价写法，本报告统一改用标识符原名。**「走不到」只对「顶层非对象」这一类载荷成立**，不是对所有损坏类型成立：修前同函数对 schema 不符（走 `else` 分支）与 `ValueError`/`OSError`（走 `except`）都能把标志置 `True`——本报告的**对照腿**就实测了 `ValueError` 那一支（写 `'{"broken": '`）能正常降级保池。
- **写盘状态**：崩溃发生在任何写盘之前——`_index.json` 仍为 `"null"`、盘面 2 个 `.md` 未动。即**本次调用没清池**，但该库自此落入腿① 同一形态（同文件同内容已在腿① 实测崩）而**永久不可装载**。
- **对照腿（证明降级机制存在、只是被绕过）**：同函数、同位置写 `'{"broken": '`（触发 `ValueError`）→ `compact_index` 正常返回且节点 `n225_ctrl_node` 保池。**降级机制确凿存在，被 `AttributeError` 绕过。**
- **站点**：`md_cg/mdcg.py:1235`（`HEAD` 口径）。

## 3. 修法契约与落点

修法口径有界：**不新增第三套判据**，把非对象折进既有降级语义。

### 3.1 快照类型闸（装载面）

- `md_cg/mdcg.py:1057`：顶层非 `dict`（`null`/`[]`/`123`/`"abc"`）视同损坏 ⇒ `idx` 保持 `None` ⇒ 落到该函数**既有**的「回退全库扫描」路径（`md_cg/mdcg.py:1072-1073` 的 `idx = {"schema": SCHEMA, "nodes": self._scan_nodes(), "buckets": {}}`）。
- 同步改 `md_cg/mdcg.py:1043` 的生效条件注释，写明顶层非对象面。

### 3.2 compact 走既有 `scan_fallback`

- `md_cg/mdcg.py:1242-1249`：新增顶层非对象分支 → `scan_fallback = True`，与「schema 不符」（`1252-1253`）、「`ValueError`/`OSError`」（`1254-1255`）**同口径**。
- 落点仍走既有分支体 `md_cg/mdcg.py:1256-1262`（`idx = {"schema": SCHEMA, "nodes": self._scan_nodes(), "buckets": {}}`），随后 `_apply_log` / `_count_buckets` / `atomic_write` / `ShardedLog.clear` 原序不变。
- 同步改 `md_cg/mdcg.py:1233` 的生效条件注释。

### 3.3 分片非对象行：跳过且可观测

- 分流点 `md_cg/fsutil.py:436-444`（`ShardedLog.read_all` 循环内）：`isinstance(rec, dict)` 进回放列表，非对象行进 `skips`，整片读成功才 `note_nonobject_rows(skips)`（半途 `PermissionError` 重试不重复计数）；排序键 `md_cg/fsutil.py:451` 因此永不接触非 dict。
- 记账设施 `md_cg/fsutil.py:266-315`（插入块整体 50 行；下列定义在其中的 `276-313`）：
  - `NONOBJECT_ROW_SKIPS`（进程内累计条数）
  - `NONOBJECT_ROW_SAMPLES`（有界样本 ≤ `_NONOBJECT_SAMPLE_CAP = 32`，元素为 `(分片路径, 行号, JSON 类型名)`）
  - `note_nonobject_rows()`（`fsutil.py:282`）每条分片一行 stderr 汇总告警（分片名、本次条数、首条行号与类型名、累计条数、排查方向）
