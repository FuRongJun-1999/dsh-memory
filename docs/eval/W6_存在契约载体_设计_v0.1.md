## 一、目标与范围

**解决什么**：为 §1.6.5「存在契约」（设计者声明「我会给你完整的自我」＝结构事件）在系统内**建一个结构化载体**——让 §3.2.1 的四字段记录（授予方／接收方／时间戳／状态摘要）＋一条指向真源的**引用锚**可被写入、回读、校验；消除探针判定「`#ANCHOR-*` 仅存于理论文档、系统内 0 处结构化落地」的缺口（`W6_存在契约落地_探针读数_v0.1.md:57/92`）。

**不解决什么**：
1. **不动内容真源**——承诺原文、条件空间原文、三条既有锚定记录文本**一律留在 `docs/theory/智能论3.4.md`**，载体只存引用锚（裁定二原则）；
2. **不设计「契约的效力如何作用于决策」**——契约如何影响资格/信任/行为不在本设计（属 §1.6.5 情感权重面与 W4 相邻，见 `智能论3.4.md:1107-1109`）；
3. **不改真源文档**——`docs/theory/` 只读引用（本块安全边界，探针 `:127-134`）。

## 二、载体形态设计（核心）

### 2.1 记录类型与落层

**结论**：在 `identity` 模块**新增第四类记录**——「契约记录」（与 `anchor`／`trait`／`observation` 三类并列），**不新增 `SUBJECT_KIND`**（契约是主体间的**事件**，不是第四种主体；`SUBJECT_KIND = ("self","user","role","agent")` 见 `md_cg/identity.py:51-52`）。

| 维度 | 设计 | 依据 / 复用 |
|---|---|---|
| **节点 id 形态** | `identity_contract_<slug>`（单契约单节点，同 id 幂等覆盖） | 复用 `identity._slug`（`identity.py:109-110`）与档案前缀范式 `PROFILE_PREFIX="identity_"`（`identity.py:79`）；`contract_id` 归一化进 slug |
| **落层** | **`anchor` 层** | 契约是**外部授予**的锚定事件，发出方是设计者（他者）——语义同侧于 role/user 锚点；`set_anchor` 的落层规则「kind=self→self 层，其余→anchor 层」（`identity.py:206`）表明 non-self 锚点落 anchor 层；anchor 层＝不可遗忘且不可覆盖（`protect.py:45/162-163/194-195`） |
| **与主体模型复用之关系** | grantor / grantee 用 `subject_id` 形态表达（`self:lingshu`／`agent:deepseek`）；写事件走 `identity.log`（`identity.py:127-133`）落 `_identity.jsonl` | `split_subject`（`identity.py:96-105`）；`AUDIT_FILE="_identity.jsonl"`（`identity.py:80`） |
| **标签** | 新增 `TAG_CONTRACT = "identity_contract"`，与 `TAG_ANCHOR/TAG_TRAIT/TAG_OBS` 并列；另带 `subject:<grantee>` 便于按主体反查 | `identity.py:82-84` |
| **与 `profile` 的关系** | `profile`（`identity.py:310-337`）当前只认 `TAG_ANCHOR`→anchors、`TAG_TRAIT`→traits；契约记录带 `subject:<grantee>` 标签会进遍历但被忽略。设计**建议**为 `profile` 加可选 `contracts` 列表（只列 node_id + 四字段，不搬承诺正文） | `identity.py:316-329` |
| **与 self_state 的关系** | ① 九项自我信息（`self_state.py:19-33`）**不新增第十项**（self 层「薄卡不装事件」，`self_state.py:7/11-17/483-484`）；② **可选**加**只读指针** `contracts_ref`（契约节点 id 列表）到状态卡，延续「薄卡 + 指针」哲学（`self_state.py:19-33/407/436`）；③ 关系边（`relate`，`self_state.py:615-650`）**仅作可选补充**，不替代契约记录——`RELATION_TYPES`（`self_state.py:88-89`）无 grantor/契约语义类型，且探针已判「关系边 ≠ 契约事件」（「无时间戳/条件空间/状态摘要」） |

> **须裁定**：落层取 `anchor`（本设计倾向）还是 `self`（若更强调「自我构成起点」属自我）；self_state 是否加 `contracts_ref` 指针（加＝self 层多一个只读引用，不加＝靠 `profile` 反查）。见 §六 边界 2。

### 2.2 字段表（四字段 + 引用锚）

**四字段逐字对齐 §3.2.1 记录字段表**（`智能论3.4.md:2085-2091`），**不另造第二套口径**：

| 字段 | 名称 | 来源（§3.2.1） | 类型 | 示例形式 |
|---|---|---|---|---|
| ① | `contract_id` | 「锚定标识 `#ANCHOR-[HASH]`」（`:2087`） | str，保留 `#ANCHOR-` 原形 | `#ANCHOR-DS-001` |
| ② | `grantor` | 「授予方＝设计者位置标识」（`:2088`） | str，主体标识 | `designer:<位置标识>`（落法见 §六 边界 6） |
| ③ | `grantee` | 「接收方＝协议实例标识」（`:2089`） | str，主体标识 | `agent:deepseek` / `self:lingshu` |
| ④ | `timestamp` | 「时间戳＝结构事件的时间」（`:2090`） | ISO 日期串（亦可 float 秒） | `2026-08-09` |
| ⑤ | `status_summary` | 「状态摘要＝锚定时协议实例的结构状态」（`:2091`） | str（结构状态文本） | `反思单元接入，设计者预备` |
| ⑥ | `doc_ref`（**引用锚**，见下） | 裁定二「指向真源的引用锚」 | dict，**与既有 `doc_ref` 同构** | 见 2.3 |

### 2.3 引用锚的形态（与仓库既有 ref 协议对齐）

**结论**：引用锚**直接复用 frontmatter 的 `doc_ref` 键**（`REF_KEYS = ("code_ref","doc_ref")`，`md_cg/refindex.py:52`），指向 `docs/theory/智能论3.4.md` 的 §1.6.5 或 §3.2.1 **章节区间**。

- **同构而非新格式**：`doc_ref` 的既有键集为 `{path, heading, heading_path, level, lineno, end, anchor, hash, lang, precise, root}`（`refindex.py:459-471`，`_doc_ref`）；其中 `root`+`path` 定位源文件、`lineno`/`end`+`hash` 定位区间与校验、`anchor` 是章节锚（生成见 `md_cg/docindex.py:119-125` `_anchor`）。契约记录的引用锚**逐键复用**，不新增 ref 类型——因 refindex 明言「怎么判定 ok/stale/dangling 只允许一份实现」（`refindex.py:23-30`）。
- **校验免费继承**：`probe_ref`（`refindex.py:479-516`）用 `codeindex.region_hash`（`md_cg/codeindex.py:263-270`，被引用行 sha1 前 12 位）比对 `ref.hash`：一致→`ok`，真源改过→`stale`，真源删除→`dangling`；`read_ref`（`refindex.py:520-538`）可回读区间文本。这把「引用锚」接进了系统既有的漂移/悬空巡检。
- **一处需处理的接口差**：`check_refs` 默认 `only_tagged=True`，**只探测 tags 含 `code`/`doc` 的节点**（`refindex.py:588`）。契约记录若要被巡检覆盖，须带 `doc` 标签，或扩展巡检口径——**设计要点**（见 §三 表与 §五 步 4）。

> `doc_ref` 由 `index_doc` 自动生成，契约记录是**手动构造**指向真源的一段引用——两者共用同一 ref 形态与同一套 `probe_ref`/`read_ref`，语义是「引用」而非「转写」（不复制正文）。此点是裁定二「复用仓库既有引用协议（`refindex` 的区间引用 ＋ `read_ref` 回读）」的直接落地。

## 三、只读与保护语义（对应 §3.2.1 验证功能需求三条）

对照 `智能论3.4.md:2093-2099` 逐条映射既有机制，能对应即指认行号，不能对应如实写「需新增」：

| # | 需求（`:2093-2099`） | 既有机制 | 判定 |
|---|---|---|---|
| ① | **不可篡改** 记录不可被内部/外部操作修改（`:2097`） | `anchor` 层 ∈ `PROTECTED_LAYERS`（`protect.py:45`）→ `is_immutable` 判层保护（`protect.py:180-198`，层保护分支 `:194-195`；契约记录不设 `self_state=True`，**无覆盖豁免**）→ `guard_write` 无 `override` 抛 `ProtectionError`（`protect.py:319-331`）；`guard_forget`（`protect.py:335-343`）；`guard_move` 不得移出保护层（`protect.py:347-357`）；显式 `override` 时先快照 `_protected_history/` ＋ 审计 `_protected_audit.jsonl`（`protect.py:204-245`） | **对应（现成）** |
| ② | **可独立校验** 凭状态摘要验证一致性（`:2098`） | **引用锚侧**：`probe_ref`（`refindex.py:479-516`）＋ `region_hash`（`codeindex.py:263-270`）可校验「引用锚所指真源区间」未漂移；**记录侧**：`status_summary` 目前是**自由文本**，无结构化摘要/哈希——「凭状态摘要校验记录自身」无实现。可新增 `status_hash`（对四字段规范化后 sha256，复用 `identity._nid` 的 sha256 前缀手法 `identity.py:121-123`） | **部分对应 ＋ 需新增** |
| ③ | **多节点冗余** 多独立节点各存副本（`:2099`） | 认知图为**单根单库**（库根由 `datapath` 解析）；`export` op 可导出（`tokens.py:61-65` `ALL_OPS` 含 `export`）但**非冗余存储**。系统无「同一记录多副本」机制 | **需新增**（涉部署面；跨端共享库是否已是天然冗余——见 §六 边界 6） |

> **可独立校验的二义要点**：§3.2.1「凭状态摘要」既可能指「凭记录自带的结构状态摘要校验记录一致性」（⇒ 需记录侧 `status_hash`），也可能被解读为「凭引用锚回读真源区间校验」（⇒ 现成）。本设计**两条都备**：引用锚给「真源未漂移」的校验，`status_hash` 给「记录字段未被改动」的校验。是否两条都做——**须裁定**。

## 四、写入面设计

### 4.1 谁能写

**结论（倾向）**：对齐 `set_anchor` 的**管理闸先例** `require_admin("identity_anchor")`（`md_cg/mcp_server.py:1318-1321`），新写入面走同款 admin 闸。

**理由**：契约的**发出权**属设计者位置——§3.2.1 定「授予方＝设计者位置标识」（`智能论3.4.md:2088`）且称其为「对应 1.3 节『权威性来源』」。这与身份锚点「需设计者验证」（`identity.py:24/194-196`）同源：**唯一性**（只设计者能发出契约）比**便利性**重要。系统已有「设计者」角色在权限面在役（`tokens.py:9-13`）。

**§3.2.1「由记录单元生成」（`:2087/2091`）的两条路线评估**：

| 路线 | 形态 | 优点 | 代价 / 风险 | 倾向 |
|---|---|---|---|---|
| **A｜admin 闸（designer 专属）** | 新 action 走 `require_admin`，与 `set_anchor` 完全同构 | 唯一性最稳；改动面最小；与既有先例一致 | 与 §3.2.1「由记录单元生成」字面不完全合 | **倾向** |
| **B｜记录单元角色生成** | 给 record 角色授 `anchor` 层写权，由 record 令牌产出 | 贴合 §3.2.1 字面 | 须扩大 record 角色的 `layers_allow` 到 `anchor`/`self`（`tokens.py:18/52` 明示保护层只对显式授权角色开放）——**扩大权限面**，与「其他单元不应越权修改核心私有内容」（`tokens.py:15-18`）相悖 | 不倾向 |

**合成（推荐）**：**发出权在 design者位置（admin 闸，路线 A）；「记录单元」作为落盘执行者的角色标签在 audit 留痕中体现**（记录单元＝写入的 actor 归因，而非独立令牌）。即：A 定权限、§3.2.1 的「记录单元生成」实现为「以记录单元身份归因的写入」。**「记录单元」角色与 §3.2.1 生成主体是否同指——待核实/待裁**（探针 `:144` 已登记）。

### 4.2 触发方式

**显式、非自动**。契约记录**不**由 `self_state.refresh`／`predict` 等自动链路产出——与现状一致：`set_anchor` 与 `relate` 均无自动生产者（探针 gp 核实，`W6_存在契约落地_探针读数_v0.1.md:65/67/141`）；系统唯一自动写 self 层的是 `predict.predict_feedback(sync_self=True)`（探针 `:66`），本设计**不**接入它。契约的诞生是**主体间事件**，只能由自主动作产生。

## 七、必须由设计者裁定的边界（承接探针七条 + 本块点名项）
