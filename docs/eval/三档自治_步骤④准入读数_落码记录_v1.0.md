`archived_shards` 如实点名未纳入的归档分片数；R4 任一子窗无裁定 ⇒ **`ok=None`**
（「不可判」——既非满足也非不满足，由调用方 fail-closed 计入 missing）。

**「不可判」与「不满足」的分叉依据（回应读者：同为证据不足却三处结论不同）**：
分叉判据＝**判据本身是否仍可判定**，不是「样本多寡」的笼统口径（实现点：
`r1` 的 `ok = bool(total_win > 0 and …)`、`r3` 的 `ok = bool(count >= 1)`、
`r4` 的 `if empty: ok = None`）：
- **R1 空窗与 R3 零证据 ⇒ `ok=False`（可判不满足）**：两者的判据是「出现性」
  阈值（三态各自出现过 ∧ 占比 < 90%；30 天内 ≥1 次回过）——样本不足直接使
  「出现过 / ≥1」不成立，判据**可判**为假；
- **R4 空子窗 ⇒ `ok=None`（不可判）**：判据是「3 个子窗的比率严格递减」——
  某子窗 0 裁定 ⇒ 该窗比率**无定义**（0 分母），判据**无法构成**，只能如实报
  「不可判」（设计 §七 明文「窗口不足 3 子窗时如实判不可判」）；
- **「未实测」措辞的关系**：CLI/detail 对 R3 写的「破坏可逆性未实测」是
  **解释性文案**（现状：没发生过回滚、数据面证不出可逆），其结构化判定仍是
  `ok=False`（可判），**不是** `None`——「未实测」≠「不可判」。

### 3.4 准入闸生效面（settle/mode/结算态）

语义（`autonomy_modes.py:199` `settle`；`:178` `mode`）：
- `settle(environ=None, root=None, force=False, ttl=None)`：
  - `configured != full`（plan/confirm）⇒ **零 IO** 返回
    `{configured, effective=configured, settled=False, admission=None, alerts=[]}`
    ——不受读数影响（设计 §六/§七 只对 full 设门槛）；
  - `configured == full` ⇒ 调 `admission.gate(root or default_root(), ttl, force)`：
    读数全满足 ⇒ `effective=full`、`alerts=[]`（与改动前逐位一致）；
    否则 ⇒ `effective=MODE_CONFIRM`、`alerts=[{reading, ok, detail}…]`
    （逐条报缺哪条读数）+ stderr 一行。**告警全文**（`autonomy_modes.py:232-238`
    模板逐字；`<root>`＝实际结算根）：
    ```text
    [MdCG 三档自治] MDCG_AUTONOMY=full 但准入读数不满足：缺 R1、R2、R3、R4 ——实际生效档位回落 confirm（不静默降级；读数详情：python -X utf8 -m md_cg.admission --root "<root>"）。
    ```
    ——行内「**复查命令**」即尾部的
    `python -X utf8 -m md_cg.admission --root "<root>"`（读数零写入入口，照此可复核）；
  - 结算体写入进程级 `_SETTLEMENT`；`mode()` 对 full 读结算态
    ⇒ 全出口（热路径 `decide`、工具面、CLI）看到**同一实际生效档位**。
- **「不可选中」的作用面**：经 env 选中 full 的路径；`decide(mode_explicit=…)`
  是显式强制指定（守卫/工具用；不经 env 键＝不属「选中」行为——生产热路径
  一律走 env 路径），不参与折算。
- **未 settle = 旧行为**（对拍）：结算态为空时 `mode()` 返回配置档位——
  与改动前**逐位一致**（守卫 E6/L5 钉死）。
- **异常语义（撰写轮实测＋读码；回应读者「settle 抛异常时档位是什么」）**：
  `settle` 对 `admission.gate()` 的异常**不捕获**（唯一的 `try` 只包 stderr
  写入，`autonomy_modes.py:231-240`）——读数抛异常时异常直接传播、
  `_SETTLEMENT.update(out)` 不执行，结算态**保持原值**。实测两情形（合成库、
  溢出触发，读数见 §六.12）：· 从未成功结算 ⇒ 结算态为空 ⇒ `mode()` 返回
  **配置档位（full）**——即「数据面损坏导致 settle 崩溃」时 full **照常生效
  （fail-open）**；· 已有成功结算 ⇒ 取**上一次成功结算**的 effective（不升不降）。
  该 fail-open 属本批留池缺口（§六.12），**不背书为已收口**。
- `admission_state()`：只读返回最近结算体（含 alerts）——「它今天够格吗」的
  程序接口；`reset_settlement()`：清结算态（供测试/宿主重结算）。

### 3.5 触发频度与缓存（本批任务书关键约束的落点；探针定）

- **热路径零 IO**：`mode()`/`decide()` 只读进程级结算态——不扫描任何数据面
  （守卫 E7/L6 以 `admission.cache_stats()["checks"]` 计数机械钉死：TTL 内
  三次结算只扫一次）。

  量级；`_forgetting.jsonl`/`decisions.jsonl` 均 < 0.05s。
- **TTL=60s 的语义（含「自动降档」的前提，撰写轮澄清）**：TTL=60s ⇒ **最坏
  每分钟一次**完整扫描（前提＝有调用方按该频度调 `settle`）。「读数跌破门槛

  是宿主按周期调用 `settle`**；本批**未接任何周期调用方**（见 §六.1）——宿主
  不调用时，档位不随时间自动变化（行为＝改动前），亦不自动降档。
- **调用面留池**：本批**不**在 `mcp_server.main()`/常驻巡检里接 `settle`
  （§六.1 说明）——`settle` 是显式生效面，宿主按需调用。

### 8.4 结算异常语义（失败态判定；契约两句话的解释与可分叉点）

契约两处并置（原文）：「`settle` 异常 ⇒ confirm+告警非 full」与「『已成功结算后
异常 ⇒ 不升不降』保持」。本批按**场景互补**落法（与 §5.3② 的修前实测口径一致）：

| 场景 | 有效档位 | 结算态 | 判定阅读 |
|---|---|---|---|
| **从未**成功结算 + `settle` 异常 | **回落 confirm** | 失败态（error 非空） | 收口 fail-open（契约背景所指缺口） |
| 已有成功结算 + `settle` 异常 | **保持上次 effective**（不升不降） | 失败态（error 非空，alerts 报「读数不可得」） | 既有对拍锚；失败态可观测、可随时重结算 |
| `settle` 之外的读数面异常（未再调 `settle`） | 不变（结算态是冻结快照，`mode()` 零 IO） | 不变 | 「已成功结算后异常 ⇒ 不升不降」的另一半 |
| 未调用过 `settle` | `mode()`＝env（full） | 空态（configured=None、error=None） | 既有对拍锚**不得破** |

**若设计者「回落 confirm」为无条件（含已结算场景）**：改动点为异常分支一行
（`eff = prev or MODE_CONFIRM` → `eff = MODE_CONFIRM`），守卫变异 ⑱ 与该方向
恰相反、G3d/G3e 会同步要求改用例——语义可分叉点已在守卫与变异表中双向钉死
（同 §3.2 偏离③ 的处置体例）。**本批选择按上表落码，若复核判定应为无条件
fail-closed，请以该行改动加守卫同步为收口。**
