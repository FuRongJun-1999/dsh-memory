## 三、修法：接到双端共用的单点

### 为什么不改 TS、不新开 op

两条路都被否掉：

1. **在 `hooks.ts` 里加一次 `state_event` 调用** —— 会把该 op 的 require 从 `recent` 抬到 `write`，属授权面扩张。
2. **新开一个专用 op** —— 要动 op 表、schema、分发三处同步，且同样扩面。

### 选中的落点

`md_cg/mcp_server.py` 的 `op=recent`·`action=add` 分支。理由：

- **双端都必经**：DSH 走 `recentAdd` → `cg(op=recent, action=add)`；zcode 走 `cg.remember_event`。一处接线覆盖两端。
- **op 面零扩张**：本 op 的 require 是 `recent`。
- **随包发货**：`md_cg/` 整目录在 `files` 白名单内。

### 三个前置条件（缺一不抽）

```python
if _role == "user" and _text and _meta.get("session"):
```

- ① `role == "user"` —— 抽取器只认真人发言（助手自述不复盖真值）
- ② `meta` 带 `session` —— 无归属事件无法去重与审计（DSH 的 `sessionTag` 恒带，zcode 的 `meta` 恒带）
- ③ `MDCG_STATE_EXTRACT` 开（缺省开）

**逐轮 fail-soft**：`except Exception: pass` —— 状态台账是派生面，窗口是运行态面，派生面故障不得拖垮运行态面。

## 四、我上一轮说错的那条：越权

上一轮我写：「`op_table` 里 `recent` 的 require 是 `recent`，记账是 `write`。挂进去会把该 op 权限静默抬到 `write`。」

**这句是错的。** 实测 `ROLE_SPECS`：

| 角色 | can_write | 有 recent | 有 write |
|---|---|---|---|
| designer | True | ✅ | ✅ |
| orchestr | True | ✅ | ✅ |
| record | True | ✅ | ✅ |
| reflect | True | ✅ | ✅ |
| verify | True | ❌ | ✅ |
| output | **False** | ✅ | ❌ |
| sustain | True | ❌ | ✅ |
| guest | **False** | ✅ | ❌ |

- 有 `recent` 无 `write` 的只有 `output` / `guest`，二者 `can_write=False`，`remember_event` 在抽取块**之前**就抛 `AccessDenied`，到不了记账。
- 其余可写角色的 `recent` 与 `write` **本就同时在场**。

**结论：挂载前后无任何角色权限变化。** 这需要你知晓——我上一轮把一个「不需要裁决的事」说成了「需要你裁决」。
