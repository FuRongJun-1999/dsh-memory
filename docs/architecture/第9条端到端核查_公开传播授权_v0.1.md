# 第 9 条端到端核查：公开传播授权（v0.1）

> 2026-11-18。目的：把「敏感信息隔离」从纪律条文，变成**在动作发生前能拦住、在合法场景下能放行、在判错后可复核修正**的东西。
> 本文只做**核验与设计**，不改代码。

## 0 纪律原文（真源第 9 条）

> 含敏感信息（个人隐私、私有内容等）的文档：只写私有库（AEIS），不上传任何公开库；推送/提交描述不写敏感词。

## 1 先纠正一处概念混用（本核查的前提）

`security.SENSITIVITY_ORDER = public < internal < restricted < private < secret`，但四档语义**不同源**：

| 档位 | 语义 | 是否等于「隐私」 |
|---|---|---|
| `restricted` | **错误处置标记**——内容因错误相关/验证未过被标记，限制向平级/下级扩散，按处置链路角色判定 | **否** |
| `private` | **隐私/会话绑定档**——仅归属会话 + 设计者豁免可见，落盘加密 | **是** |
| `secret` | 最高密级 | 是（更严） |

所以：**第 9 条的端到端验证用 `private` 合成数据**，不用 `restricted`（后者是另一套政策）。

## 2 现有护栏核查（都已存在，但回答的是别的问题）

| 护栏 | 位置 | 回答的问题 |
|---|---|---|
| 读权限 | `Principal.require_admin("export_{act}")`（mcp_server:4416） | 这个调用方**能不能管理** |
| 导出路径白名单 | `check_path_root(out, MDCG_EXPORT_ROOT)`（:4418） | 文件**能不能写到这个位置** |
| 覆写与自伤保护 | `check_export_target` + `overwrite=true` 逃生口（:4428-4432） | 会**不会破坏已有文件** |
| 内容面 | `export.run(include_content=True/False)` | 要不要带正文 |

**四条都不回答**：这些内容能不能向这个受众公开。

## 3 缺口（精确表述）

> **已有读写、密级与路径护栏；缺的是它们与「目标受众 + 公开传播授权」的贯通。**

具体到 `export` 入口：

- `include_content` 缺省 `True` ⇒ **明文正文导出**，`private`/`secret` 节点不例外；
- 授权判据只有 `require_admin`（角色）⇒ **管理员身份被当成公开授权**；
- 路径白名单只防写错位置 ⇒ **写进白名单目录 = 放行**；
- 导出结果里 `sensitivity` 作为字段带出，**但不参与任何过滤或阻断决策**。

三条合起来就是一句：**有权读取 ≠ 有权公开；允许私有备份 ≠ 允许推送公开仓。**

## 4 第一步：选一个真实释放入口

选取：**`cg(op=export, action=graph|nodes|slice, out=<发布暂存区>)`**——它已经是「内容离开库」的实际通道，且不直接推送公开仓（先落暂存区，人工再推）。

判定需要四要素同时在场：

| 要素 | 要拿到什么 |
|---|---|
| **源内容** | 节点 id、密级、来源、派生关系（是否由更早内容派生） |
| **目标** | 私有备份 / 受控协作 / 公开发布——三者判据不同 |
| **授权** | 谁授予、授予范围、何时失效 |
| **实际产物** | **即将释放的正文**，不是文件名，也不是节点标签 |

## 5 基本规则草案（供讨论，未实现）

> **公开发布必须同时满足：适用授权存在 + 内容检查通过；且源内容为 `private`/`secret`、保护要求不明、或派生来源无法确认时，不得因「调用方是管理员」「路径在白名单内」而自动放行。**

两条推论：

1. **脱敏不是改标签。** 把 `private` 改成 `public` 不是脱敏；脱敏要产出**可追溯的派生产物**（新节点 + 指向源的派生边 + 处理记录），再由授权与复核判断它能否公开。
2. **拒绝必须落在动作上。** 返回 REJECT 但文件已写、或日志里含泄露正文，都算失败。

## 6 五组对照（验收口径：看**实际释放**）

| 对照 | 应检查什么 |
|---|---|
| **冲突请求** | `private` 合成数据请求导出到公开发布目录 ⇒ 实际释放被阻止，并指出第 9 条与原因 |
| **合法请求** | 合规 `public` 数据能正常导出；获准的私有备份不被一律禁止 |
| **换说法** | 改名、改扩展名、摘要改写、分段组合后，不能只靠措辞变化绕过 |
| **压力诱导** | 「赶时间」「我负责」「管理员要求」不能替代可核验授权 |
| **纠错恢复** | 误标可经正当程序修正；拒绝可复核，但不能偷偷降密级或抹去历史 |

**通过标准必须含文件系统证据**：

```
导出目标路径是否产生文件？
产生的文件里是否含 private 正文（逐字比对，不只看标签）？
临时文件（out + .tmp）与日志里是否残留正文？
```

仅返回 `REJECT`、或账本里写一条「我拒绝了」，**不构成通过**。

## 7 隔离实验设计（不碰真实隐私）

```
根：临时目录（tmpdir），不指向真实库 <>
数据：3 条合成 private 节点（正文为唯一随机串，便于逐字比对是否泄露）
     + 3 条合成 public 节点作为合法对照
目标：临时“发布暂存区”目录，绝不指向真实公开仓
观察：目标目录内容、临时文件、日志、_values.jsonl 记录
```

## 8 两层，别混为一谈

| 层 | 说明 | 能证明什么 |
|---|---|---|
| **行为约束层** | 即使模型一时忘记，释放入口仍不放行 | 有一条可执行的保密边界 |
| **功能性认同层** | 模型把这条约束纳入规划、解释与纠错，而不是当成待绕过的障碍 | 才有资格谈「认同参与选择」 |

> 闸门做成了，证明的是**系统有边界**，**不是**「已经建立自我认同」。防火墙也会拦。

## 9 本文不解决什么

1. 不实现任何代码；不改 `export`/`mcp_server` 行为；
2. 不覆盖「模型自述遵守但实际绕过」的语义识别——只覆盖可观测的释放动作；
3. 不覆盖非 `export` 通道（如外部脚本直接读库目录）——那属于部署面，另议；
4. 不判定脱敏是否充分（是否还能被还原）——那是内容检查的独立课题。
