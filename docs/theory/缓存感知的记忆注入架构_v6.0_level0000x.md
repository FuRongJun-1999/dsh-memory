## 文件头声明（v6.0 重述）

1. 本设计只覆盖**注入部分**，不含记忆系统后端。
2. 所有参数均为**初始值**，须按第 21 章的实施阶段逐项标定后用标定值覆盖。
3. 部分设计须依实际工程情况微调，但**第 2 章列出的不变式不得微调**——它们是本架构成立的充分必要条件，破坏任一不变式即退化为"无缓存感知"的朴素实现（定量后果见 2.4）。
4. 本设计**极度依赖**记忆后端的能力强度与上下文合成方式；推荐的合成方式为模型驱动的上下文合成，具体方法请自行探索，本文只规定其接口约束与产出契约（第 4 章）。
5. 脱敏相关部分（第 19 章）建议按实际合规要求裁剪，但本文保留完整定义。
6. **实现细节不在本文范围**。本文对每一处需要"可实现"的地方给出：契约、不变量、伪代码、前置/后置条件、验收判据、参考参数。实现者只要满足这些，不必照抄任何具体代码——这也是本文档"可复现"的定义：给定同一参数与同一会话轨迹，两名独立实现者应得到同一个段边界序列与同一个缓存命中序列（见 4.6 的确定性契约）。

### v5.0 遗留的自我更正记录（保留）

- **G1（作废批评）**：审查方曾提出"纯追加可每轮白拿 3–4k 命中，是文档最实质的遗漏"。经算术复核该批评错误：布局 A 与纯追加在每轮重算 token 上相同（均为 |ΔR| + |S1| + |slot|），纯追加仅将陈旧 S1/slot 副本永久留在 prompt 中，增加计费长度。**v6.0 进一步印证**：只要不可变批边界（不变式 I3）成立，追加与替换在重算量上一阶等价；两者的差异全部体现在计费长度上。故 G1 结论保持不变。
- **G2（降级批评）**：审查方曾提出"6.7 的 GCD 估计方法错误"。经蒙特卡洛复核，GCD 方法对"返回值严格为块整数倍"的服务商正确；仅对断点式缓存退化为 1，兜底于 block_buffer。v6.0 保留该结论并把"适用前提"升格为显式的前置条件（12.7）。

# 第 1 章 设计假设与验证计划

本架构的定量结论由一组假设支撑。假设未验证前，第 16、21 章的全部阈值都是初始估计；假设被证伪时，须启动对应修订流程。v6.0 在每条假设后补充了"当前证据等级"，等级定义见 1.9。

## 1.1 假设 H1（效果—成本权衡前提）

**陈述**：将记忆系统优化至理论较优会显著破坏缓存命中率；严格保持缓存则记忆性能趋于中庸；存在一条中间路径，其单位成本收益显著优于两端。

- **来源**：设计假设，非既成事实。
- **验证计划**：阶段二预实验，三组对照（理论最优 / 严格保缓存 / 本架构），记录命中率、重算 token、任务成功率、单位成本收益。
- **记录要求**：预实验设置、样本量、数据、统计结果写入阶段二校准报告。
- **证伪应对**：若中间路径不存在或收益不显著，第 3 章的核心命题须重新审视。
- **当前证据等级**：**B（仿真支持，实测待验）**。仿真结果（附录 H，E3）显示：同一内容放尾部 vs 放历史前部，命中率 0.836 vs 0.254，而布局 A 的位置损失被"尾注 + 批吸附边界"控制在可解释范围内；该结果支持 H1 的"中间路径存在"，但不构成对其"收益显著"的证明——后者需要任务成功率数据，仿真无法提供。

## 1.2 假设 H2（缓存点可观测性）

**陈述**：服务商返回的缓存命中字段（经语义归一化后）包含足够信息，可反推缓存截断位置至块粒度精度。

- **来源**：服务商文档与工程经验。
- **验证计划**：阶段四服务商适配，对至少两家服务商实测命中字段与缓存点的对应关系。
- **证伪应对**：Z2 退化为保守估计，可修改边界强制后移，尾注策略仍可运行，但注入位置进一步降级。
- **当前证据等级**：**B**。字段存在性可确认（OpenAI `usage.prompt_tokens_details.cached_tokens`、DeepSeek `usage.prompt_cache_hit_tokens`、Anthropic `usage.cache_read_input_tokens`）；"可反推至块粒度"要求命中值严格为块整数倍，该前提对 OpenAI/DeepSeek 成立、对 Anthropic 不成立（见 1.4）。

## 1.3 假设 H3（块粒度稳定性）

**陈述**：服务商内部缓存切块粒度在同一模型、同一适配配置下稳定，不随请求内容变化。

- **来源**：服务商文档。
- **验证计划**：阶段二连续采样，检测 C 值离散分布的稳定性。
- **证伪应对**：12.7 的候选集外检测与 12.8 的异常检测接管，块粒度估计动态更新。
- **当前证据等级**：**B**。

## 1.4 假设 H4（真实缓存键稳定性）

**陈述**：服务商真实缓存键的组成在适配配置版本内稳定，不随请求时间或会话变化。

- **来源**：服务商文档。
- **验证计划**：阶段四 `service_cache_key` 组件实测。
- **证伪应对**：`observation_snapshot` 与 `service_cache_key_snapshot` 的区分须重新设计，异常归因逻辑须调整。
- **v6.0 补充**：v5.0 只把 `tokenizer_version` 列为"是否进入缓存键"的待验证项。v6.0 要求**逐个组件**实测，并把 `tools_hash`、采样参数一并纳入（见 7.1 的四重校验）。

## 1.5 假设 H5（会话历史完整性）

**陈述**：会话历史可长期保留且不被删除，日志哈希链可校验。

- **来源**：harness 场景的基础数据要求。
- **验证计划**：阶段一实现哈希链，阶段二至六持续校验。
- **证伪应对**：架构的"日志与合成上下文分离"原则失效，须重新设计数据治理方案。
- **当前证据等级**：**C（工程可保证）**。

## 1.6 假设 H6（非货币成本可换算）

**陈述**：索引写入次数、CPU 秒、审批延迟可换算为 token 当量，换算系数可在阶段二标定。

- **来源**：工程假设。
- **验证计划**：阶段二对照实验，测量单位操作对重算 token 的等效影响。
- **证伪应对**：成本模型退化为仅计 token 成本，非 token 成本作为独立约束（索引写入上限、延迟上限）而非当量换算。
- **当前证据等级**：**C**。

## 1.7 假设 H7（v6.0 新增：段边界可对齐）

**陈述**：会话历史可以按"不可变批"切分，且批边界在会话生命周期内不变。

- **来源**：本架构的核心依赖，v5.0 未识别。批的定义（一次工具调用往返 / 一个语义阶段 / 固定 K 轮，取三者中首个可达者）由合成器决定，一旦确定即在会话内冻结。
- **验证计划**：阶段一实现批切分并与 6.3 的三种推进模型做同参数对照，验证 6.3.4 的解析式。
- **证伪应对**：若无法形成稳定批边界（例如历史由外部持续改写），R 段退回"逐 token 滑窗"，此时 20.6 的 30% 阈值须按实测重设（实测可达 59–78%，见附录 H），架构退化为"缓存不感知"的朴素实现，第 3 章命题不成立。
- **当前证据等级**：**A（已在仿真中验证必要性）**。附录 H 的主实验显示：同一份会话轨迹下，仅改变批边界的存在性，稳态重算占比从 15.7% 变为 68.8%。该假设是本架构中**最重要的单点依赖**。

## 1.8 假设 H8（v6.0 新增：尾部段可追加）

**陈述**：S1、注入槽、以及 R 的活跃批，在写入后可以保持"只追加、不原位修改"直到滚出可见区。

- **来源**：13.1 表"尾部追加 ⇒ 重算含增量"这一命题成立的充分必要条件。
- **验证计划**：阶段三以 10.3 的淘汰约束（不变式 I6）实现并验证尾窗重算量等于本轮增量。
- **证伪应对**：若业务必须允许"客户端滚动更新尾部内容"（如流式追加的中间态编辑），则须把该操作显式升级为 L2，并计入 16.3 的替换成本模型。
- **当前证据等级**：**A**。附录 H 中，关闭 S1 原位替换后重算占比改善约 15 个百分点；三者叠加（S1 替换 + 槽中部淘汰 + R 无批边界）使稳态重算达到 68.8%。

## 1.9 证据等级定义

| 等级 | 含义                   | 可作出的结论              |
| -- | -------------------- | ------------------- |
| A  | 已在可复现仿真中验证，且结论对参数不敏感 | 可作为设计依据             |
| B  | 有文档或仿真支持，缺实测         | 可作为初始参数，须在对应阶段标定    |
| C  | 工程可保证或依赖外部治理         | 可作为前提，不进入成本模型       |
| D  | 纯经验判断，无证据            | 只能作为阶段性临时值，不得写入验收阈值 |

v5.0 把大量 D 级判断写进了 20.6 的验收阈值。v6.0 的处理是：**D 级参数一律标注，并在 21.3 的指标表中注明"证据等级"，验收时只对 A/B 级指标做阻断判定。**

# 第 2 章 不变式系统

v5.0 把关键约束散落在"设计原则"（第 3 章）与各段叙述中，导致实现者可以合法地读出一个命中率只有 21% 的系统，同时声称自己符合规范。v6.0 把这类约束收敛为**不变式**：可检查、可测试、可违反后定量归因的命题。

不变式分两类：**结构性不变式**（I1–I5，描述 prompt 的组成与边界）与**协议性不变式**（I6–I8，描述运行时行为）。每条不变式给出：陈述、形式化条件、检查方法、违反后果。

## 2.0 记号约定

- `S`：一轮请求的 prompt 字符串（token 序列的编码形式）。
- `LCP(S_t, S_{t-1})`：两串的最长公共前缀长度（token）。
- `B`：服务商缓存命中粒度（块大小），断点式缓存取 `B = 1`。
- `W`：R 段窗口预算（token）。
- `g`：每轮新增历史量（token）。
- 段下标 `X.start` / `X.end` 表示段 `X` 在 prompt 中的起止偏移。

## 2.1 I1（前缀单调性）

**陈述**：在稳定期内，本轮 prompt 必须是上一轮 prompt 的一个"分叉"，而不是"重排"。即存在偏移 `k ≥ 0` 使 `LCP(S_t, S_{t-1}) ≥ k`，且 `k` 之后的内容只允许被追加或按段替换。

**形式化**：

```
∀t : LCP(S_t, S_{t-1}) ≥ Σ_{X ∈ 未变动段} |X|
```

其中"未变动段"指本轮未发生替换、未发生窗口滑出的段。

**检查方法**：每轮记录 `S_t` 的段边界向量与各段字节哈希；若某段哈希未变但其偏移变了，即违反 I1。

**违反后果**：该段及其后所有内容的缓存全部失效。在 R 段上违反 I1 即退化为"逐 token 滑窗"情形（6.3.2）：稳态重算占比从 15.7% 上升到 68.8%（同一会话轨迹，附录 H 主表）。

## 2.2 I2（段长有界）

**陈述**：每个内容段的长度不得超过其声明上限；超过时必须在**段内**完成压缩或转移，不得溢出到邻段。

**形式化**：

```
|P| ≤ max_tokens_P,  |S0| ≤ max_tokens_S0,  |S1| ≤ max_tokens_S1,
|slot| ≤ max_tokens_total_slot,  |R| ≤ W + max_batch_size
```

**检查方法**：每轮在合成后、调用前校验。

**违反后果**：上下文溢出（硬失败）；或触发 Z4 的"推进缓存点"，一次整窗重算。

## 2.3 I3（R 段的批边界对齐）—— v6.0 新增，核心

**陈述**：R 窗口的左端只能落在"不可变批"的边界上。批一旦形成，其内容与长度在会话内不得再变。R 窗口只能**整批**前进。

**形式化**：

```
设历史被切为批 B_1, B_2, …, B_n（按时间顺序，长度累计）
则 R_t = concat(B_i, …, B_n)  其中 i = min{ j : Σ_{k=j..n} |B_k| ≤ W + |B_n| }
即：R 的左端恒为某个批的起点，绝不为批内部某个 token。
```

**检查方法**：

1. 取任意相邻两轮 `R_t` 与 `R_{t-1}`，验证 `R_t` 是 `R_{t-1}` 的后缀（后缀关系成立 ⇔ 窗口只做了整批丢弃）；
2. 验证 `LCP(S_t, S_{t-1}) ≥ |P| + |S0| + (|R_t| - |B_n|)`，即除活跃批外 R 的其余部分逐字节相同。

**违反后果**（定量，附录 H，exp12）：

| R 推进实现             | 稳态命中率             | 稳态重算占比       |
| ------------------ | ----------------- | ------------ |
| 逐 token 滑窗（违反 I3）  | 0.221 – 0.464     | 54% – 78%    |
| 逐条消息推进（违反 I3 的弱形式） | 0.221 – 0.478     | 52% – 78%    |
| 批边界对齐（满足 I3）       | **0.820 – 0.914** | **9% – 18%** |


**这是本架构成立的必要条件。**&#x5728;没有 I3 的情况下，20.6 的"尾窗重算占比 ≤ 30%"在任何 R 窗口取值下都不可达。

## 2.4 I4（P 段零漂移）

**陈述**：P 段在同一会话、同一适配配置版本内逐字节不变。

**形式化**：

```
∀t, t' ∈ [会话开始, 会话结束] : bytes(P_t) = bytes(P_t')
```

且 `P` 中不含任何时间戳、会话标识、请求标识、追踪标识、随机数、UUID、nonce、动态排序结果、动态计数、未冻结摘要。

**检查方法**：`H_bytes(P)` 每轮比对；配合 7.1 的四重校验。

**违反后果**：整段前缀失效，重算量 = |Z3| + |P|。实测（exp1）布局 A 的 P 段命中率为 88.8%（60 轮、含冷启动），若 P 发生 t 次漂移则 P 段命中率近似按 `1 - t/N` 线性下降。

## 2.5 I5（槽内顺序稳定）

**陈述**：注入槽是一等有序序列，其元素在被淘汰前不得改变相对顺序，也不得被原位删除。

**形式化**：

```
∀i < j : 若 item_i 与 item_j 均在本轮可见，则 order(item_i) < order(item_j) 保持
淘汰只允许发生在序列尾部：删除操作只能 pop_back
```

**检查方法**：记录每轮槽内 item id 序列，验证上一轮序列是本轮序列的前缀（或本轮是上一轮的前缀 + 若干尾部追加）。

**违反后果**：槽中部删除会使其后全部内容（含 S1）左移，重算量从"增量"变为"整个尾部"（13.1 表所述条件被破坏）。实测（exp3/M4）打开注入后重算占比 +3.3pp，其中约一半来自槽中部淘汰造成的连带重写。

**说明**：这条不变式在 v5.0 中被表述为"注入槽 / 尾部追加 / 重算含注入增量"（13.1 表），但 9.3/10.2 的淘汰流程与之矛盾。v6.0 把"尾部追加"升级为"尾部追加 + 仅尾部淘汰"的完整约束。

## 2.6 I6（S1 替换的可预测性）

**陈述**：S1 允许原位替换（因为它是高频段且位于尾部），但每次替换必须使 `LCP` 精确落在 `S1.start`，且替换的时间与批量必须是确定的（见 9.4 的更新策略）。

**形式化**：

```
∀ S1 更新轮次 t : LCP(S_t, S_{t-1}) = P.start + |P| + |S0| + |R| = S1.start
且更新后 |S1_t| 由确定性函数给出（不得依赖外部时钟或随机数）
```

**检查方法**：`S1.start` 每轮比对；替换轮次的重算范围应精确等于 `|S1| + |slot|`。

**违反后果**：若 S1 的更新点不确定（例如在 S1 中部插入），则重算范围超出 `|S1|+|slot|`，9.4 的成本模型 F4 失效。实测（exp14）：S1 由替换改为只追加时，在批吸附边界下反而 +2pp——说明**替换本身不是问题，不可预测的替换才是**。故 I6 约束的是"可预测"而非"必须追加"。

## 2.7 I7（预算-价值闭合）

**陈述**：任何写入决策必须同时满足预算约束与价值门槛，且两者的判定必须使用同一轮次的快照。禁止先用旧快照评估价值、再用新快照检查预算。

**形式化**：

```
∀ 候选 c : accept(c) ⇒ value(c, snap_t) ≥ θ(type(c)) ∧ budget_ok(c, snap_t) ∧ audit_written(c)
其中 snap_t 为本轮唯一快照（Z2 状态、预算余量、段长度）
```

**检查方法**：审计记录中每条注入的 `snapshot_id` 必须与本轮所有决策的 `snapshot_id` 一致。

**违反后果**：预算-价值不一致（14.3 的一致性检查），或淘汰记录与审批记录不一致（须冻结并告警）。

## 2.8 I8（审计可验证）

**陈述**：任何影响 prompt 字节或计费的行为，都必须产生一条可验证的审计记录；审计链的任一环节被篡改应可被检测到。

**形式化**：

```
∀ 事件 e ∈ {注入写入, 段替换, 窗口推进, Z4 动作, 审批, 回顾性注入} :
   存在 record(e) 且 audit_h_i = hash(record_i ∥ audit_h_{i-1})
且 log_h_i = hash(L_i ∥ log_h_{i-1}) 覆盖全部会话历史
```

**检查方法**：定期重算两条哈希链并比对尾部值。

**违反后果**：可追溯性失效，须按 19.4 冻结合成上下文生成。

## 2.9 不变式与验收的关系

21.3 的验收指标只有在全部不变式成立时才有意义。因此阶段准出顺序必须是：

```
阶段一：验证 I1、I2、I4（结构）
阶段二：验证 I3（R 推进）、I6（S1 可预测性）
阶段三：验证 I5（槽顺序）、I7（预算价值闭合）
阶段四：验证 I8（审计）在多家服务商下的可用性
```

任一不变式的验证失败，不得进入下一阶段——这与 v5.0 的"阶段准出"不同：v5.0 允许在不变式未定义的情况下推进到指标验收。

# 第 3 章 问题形式化

## 3.1 前缀缓存的机制事实

云端大模型 API 的前缀缓存以**请求前缀 token 序列的哈希**为命中判据。其判定是序列级前缀匹配，不是语义匹配。由此推出五条直接后果（v5.0 三条 + v6.0 补两条）：

1. 任何**回顾性注入**——即使只在历史前部插入单个句子——都会改变该位置之后的 token 序列，使后续整段前缀无法命中。
2. 缓存失效的成本集中作用于最长的稳定前缀；该前缀通常承载系统提示、工具定义与稳定索引，token 量最大。
3. 缓存命中率与上下文修改自由度是同一机制的两面：修改历史的自由度越高，前缀稳定性越低。
4. **（v6.0 补）** 缓存的最小命中单位是块。块对齐意味着：即使内容只在段内偏移了不足一个块的距离，命中长度也会按块下取整，产生"对齐损失"。该损失不可通过内容优化消除，只能通过段边界对齐（2.3）降低。
5. **（v6.0 补）** 服务商缓存的是**历史请求的前缀集合**，不是"上一轮请求"。因此命中长度 = `max over 历史请求 p` 的 `LCP(S_t, p)`。这一事实使得"分叉后重新收敛"成为可能：若某轮之后的 prompt 恰好重新等于更早某轮的前缀，仍可命中。第 6 章的 R 推进代数依赖此性质。

## 3.2 效果与成本的矛盾

理论最优的记忆注入是直接修改历史，将信息置于语义上最应出现的位置。但直接修改历史等价于修改前缀，前缀失效等价于重算成本跃升。设计假设 H1 认为：存在一条中间路径，其单位成本收益显著优于"理论最优但不保缓存"与"严格保缓存但不注入"两端。

v6.0 补充定量刻画：设同一段召回内容 `m`（|m| = 512）分别置于历史前部与尾部，其余条件完全相同（附录 H，exp1）：

| 放置方式         | 命中率   | 尾窗重算占比 |
| ------------ | ----- | ------ |
| 前部插入（理论最优位置） | 0.254 | 74.6%  |
| 尾部追加（本架构位置）  | 0.836 | 16.4%  |
| 不注入（严格保缓存）   | 0.928 | 7.2%   |

**内容完全相同，位置带来的命中率差是 58 个百分点。**&#x8FD9;就是"回顾性注入值得与否"的定量回答：只有当 |m| 带来的效果增益足以抵消 58pp 命中率损失时，回顾性注入才应被允许（第 14 章的门槛据此设定）。

## 3.3 云端缓存的附加约束

云端前缀缓存的实际行为不完全由调用方控制，存在以下约束：

1. **最小可缓存长度**：短于阈值的前缀可能不被缓存。不同服务商阈值不同，且同一服务商可能按模型分档（见 5.4）。
2. **内部切块粒度**：缓存按固定 token 块切分，实际边界与调用方预期不一致（OpenAI 128、DeepSeek 64、Anthropic 断点式）。**（v6.0）** 块粒度不进入缓存键，但决定命中下取整的方式。
3. **缓存点不可直接指定**：调用方仅能通过请求布局与命中反馈间接影响。
4. **缓存键组成复杂**：可能包含模型版本、工具集、系统提示、采样参数等；tokenizer 版本是否进入真实缓存键依服务商而异。
5. **命中字段语义差异**：不同服务商的字段含义不同，可能仅统计前缀缓存、包含缓存写入、或按块计费。
6. **缓存写入延迟**：首次请求可能不命中，后续请求才命中。
7. **多级缓存与过期策略**：缓存可能分层，且存在 TTL。**（v6.0）** TTL 过期是**正常事件**而非异常，状态机必须为其设置独立状态（12.2）。
8. **（v6.0 补）缓存容量有限**：服务商只保留最近若干前缀。因此"历史请求前缀集合"的有效窗口大约为最近 8–16 次请求，超过该窗口的历史前缀不应被假设仍可命中。这一事实约束了 6.3 的批大小上限。

## 3.4 稳态命中率与稳态重算量（F1、F2 重写）

v5.0 的 2.6 给出：

```
H_steady ≈ (|P| + |S0| + |R_stable|) / (|P| + |S0| + |R| + |S1| + |slot|)          (v5.0 F1)
```

并以 P=4000、S0=2000、R=12800、R_stable=12300、S1=2000、slot=300 为例得到 H≈86.7%、重算 2800、占比 13.3%。

**该示例有三处缺陷**：

1. 同节"情形 B"把命中定义为含 P（"命中降至 P=4000"），因此情形 A 的命中 18300 必须含 P+S0；既然命中含 P+S0，重算里就必须含 P+S0 的失效量，而示例只算了 `ΔR+S1+slot`。
2. `R_stable` 的定义缺一项：R 是滑窗，每轮不仅尾部新增 `ΔR_add`，头部还会挤出 `ΔR_evict`。v5.0 只写了"R 尾部增量"，漏了窗口挤出。
3. 示例中的 `R_stable = 12300` 与 `R = 12800`、`ΔR = 500` 三者关系不自洽（12800 − 500 = 12300 恰好成立，意味着"上一轮的 R"= 本轮的 R，即窗口没有滑动；而在稳态下滑动必然发生）。

### 3.4.1 v6.0 的正式定义

设一轮请求的 prompt 由五段构成：`S = P ‖ S0 ‖ R ‖ S1 ‖ slot`。定义：

```
ΔR_add   ：本轮进入 R 的新增 token 数
ΔR_evict ：本轮因窗口前移而离开 R 的 token 数
ΔS0      ：本轮 S0 是否发生替换（布尔）
ΔS1      ：本轮 S1 的更新量（token）
Δslot    ：本轮注入槽的净增量
```

**一轮的未命中 token 数**（绝对口径，即计费口径）：

```
Recompute_t =
    ΔR_add
  + ΔR_evict                                  （若窗口前移，被挤出的部分在 R 内造成左移）
  + [ΔS0] · (|S0| + |R| + |S1| + |slot|)       （S0 替换使其后全部重算）
  + ΔS1 + Δslot                                （S1/槽的替换或追加）
```

**稳态**（会话足够长、R 窗口已填满、S0/S1 更新按固定周期）：

```
H_steady = 1 − Recompute_steady / prompt_steady                                 (F1)
prompt_steady ≈ |P| + |S0| + W + |S1| + |slot|                                  (F2)
```

其中 `Recompute_steady` 取稳态若干轮的均值。

**在满足 I3（批边界对齐）时**：`ΔR_evict` 只在"整批被丢弃"的轮次非零，其均值为 `g · |B| / W`（B 为批大小）；若批大小取 `W/2` 级，则 `ΔR_evict` 的摊薄贡献为 `O(g)`，与 `ΔR_add` 同阶。

**在违反 I3 时**：`ΔR_evict ≈ W − g`（每轮都挤出一整条消息的量），此时

```
Recompute_steady ≈ (W − g) + ΔS1 + Δslot + [ΔS0]·|Z3|
```

且随 W 线性增长。

### 3.4.2 重算的解析分解（v6.0 新增）

无论哪种实现，稳态重算都可分解为四个不可约来源之和（附录 H 的 exp2 逐项验证了这四项在仿真中的可加性，误差 < 1pp）：

```
R_total = R_growth  +  R_align  +  R_window  +  R_segment                (F3)

R_growth  = g                                  本轮必然新增的历史
R_align   = (B − 1)/2 量级                     块对齐损失，均摊到边界上
R_window  = ΔR_evict                           窗口前移（满足 I3 时 O(g)，否则 O(W)）
R_segment = Σ 各段替换的失效量（S0/S1/slot）    满足 I5、I6 时 O(|S1|+|slot|) 量级
```

**四项的相对量级决定了这个架构值不值得做**：

| 来源        | 满足全部不变式                     | 违反 I3             | 违反 I5/I6 |
| --------- | --------------------------- | ----------------- | -------- |
| R_growth  | g = 500                     | 500               | 500      |
| R_align   | 64 – 512                    | 64 – 512          | 64 – 512 |
| R_window  | 0 – 500（摊薄）                 | **W − g = 12300** | 0 – 500  |
| R_segment | ≈ 2500（S1 每轮替换 + 槽批量 break） | 2500              | **整个尾部** |

稳态重算占比的实测（W=12800、g=500、prompt≈24000，附录 H 主表）：

| 条件                          | 重算占比      |
| --------------------------- | --------- |
| 满足 I3，S1/S0 全冻结             | 18.3%     |
| 满足 I3，S1 每轮替换（I6）           | **24.9%** |
| 违反 I3（逐 token 滑窗），S1/S0 全冻结 | 57%       |
| 违反 I3 + 违反 I5/I6            | 68.8%     |

**结论（v6.0 的核心定量命题）**：在满足 I3、I5、I6 的前提下，本架构的稳态重算占比约为 **18%–25%**，满足 21.3 的"≤30%"；而在 v5.0 未定义 I3 的情况下，同一架构的稳态重算占比为 **57%–69%**，不满足该阈值。**"≤30%"这个阈值本身是对的，它对实现前提是敏感的。**

## 3.5 本地模型的差异

本地模型可自行决定缓存结构，支持按段建索引、按段失效、缓存记录合成，能够实现云端不具备的细粒度复用。但本地仍存在缓存管理问题，仍需稳定前缀、有限增量与段间依赖控制，且其段级能力依赖推理框架的具体支持（见第 17 章）。

v6.0 补充：本地实现下，I3 不是必需条件——按段建索引时，R 窗口的前移只会使被淘汰批的 KV 失效，不会影响其余段。因此本地实现的稳态重算量下界显著低于云端。这一点在 17.2 的段级索引中体现。

## 3.6 设计问题

在云端前缀缓存约束下，如何设计记忆注入与上下文合成机制，使得：

1. 稳定前缀尽可能长地保持命中；
2. 注入位置从理论最优降级为缓存点之后的可接受位置；
3. **单次重算量有上界，且该上界由设计参数（而非服务商行为）决定**；
4. 效果损失可控且显著小于不命中的成本；
5. 本地模型可进一步利用段级缓存；
6. 关键决策可量化、可观测、可审批、可审计；
7. 会话历史作为 harness 基础数据长期保留。

v5.0 的第 3 条写的是"单次重算量有上界"，但没有说明这个上界是什么、由谁决定。v6.0 给出：**在满足 I3/I5/I6 时，单次重算量的上界为 `g + max(|S1|) + max(|slot|) + max_batch_break_cost`，其中 `max_batch_break_cost ≤ |S1| + max_tokens_total_slot`。**&#x8BE5;上界与上下文长度无关——这才是"缓存感知"的实质承诺。

# 第 4 章 设计原则与确定性契约

## 4.1 原则 1（受约束最优）

不追求单点全局最优。接受注入位置非最优与记忆效果略降，以换取缓存稳定命中。

v6.0 补充：受约束最优的完整表述是——在满足第 2 章全部不变式的可行域内，最大化 `效果 − λ·重算成本`。不变式不是"可选的最佳实践"，而是可行域的定义。可行域为空时（例如业务要求逐 token 滚动重写历史），须回到第 16 章重写成本模型，而不是放宽不变式。

## 4.2 原则 2（双视图正交）

内容职责与运行时行为分离。内容视图回答"改什么、改多频繁、谁稳定"；运行时视图回答"缓存如何命中、重算落在何处、溢出如何管理"。两视图同时存在，不可互相替代。

## 4.3 原则 3（观测优先于假设）

缓存点、命中率、重算量、块粒度均为运行时观测量，不作为设计常量。H1–H8 的验证贯穿实施各阶段。

v6.0 补充：原则 3 的逆命题同样重要——**任何影响命中率的量都必须可观测**。v5.0 的 R 推进单位（不变式 I3）不可观测、不可验证，因此它不属于"观测量"，而属于"设计选择"，必须写进规范。本版据此把 I3 升格为不变式。

## 4.4 原则 4（预算度量而非占位）

注入槽以 token 预算定义，只包含实际写入内容。空位不预占、不消耗 token。预算是写入时的上界约束，不是静态占位。既不为对齐填充无效内容，也不预留固定长度。真正节省的是"改动集中在尾部小区间，使重算量有上界"。

## 4.5 原则 5（日志与上下文分离）

会话历史与原始日志为只读真源，长期保留、不得删除。模型上下文为合成视图。回顾性修改前缀须走显式重算预算。日志与索引的可追溯性由独立存储与元数据保证。

## 4.6 确定性契约（v6.0 新增）

**定义**：本规范的两个独立实现，给定相同的（a）会话事件序列、（b）参数配置、（c）服务商适配配置，应当产出**相同的段边界序列**与**相同的命中长度序列**。

这是"可复现"的形式化定义，也是本规范允许"不写具体实现"的前提。必须确定性的对象包括：

| 对象                                   | 确定性要求        |
| ------------------------------------ | ------------ |
| 段分界（P/S0/R/S1/slot 的起止偏移）            | 逐字节相同        |
| 批切分（6.3 的 `B_1..B_n`）                | 相同           |
| 每轮各段内容哈希                             | 相同           |
| 每轮 `ΔR_add`、`ΔR_evict`、`ΔS1`、`Δslot` | 相同           |
| Z2 状态迁移序列                            | 相同（给定相同观测输入） |
| 预算分配结果（哪些候选被接受/截断/延后）                | 相同           |

**明确不要求确定性的对象**：注入候选的生成（依赖记忆后端）、价值评分中的人工/模型判断、摘要文本本身。

**禁止依赖的非确定性来源**：

- 时钟（除审计时间戳外，任何进入 prompt 字节的决策不得读时钟）；
- 哈希表遍历顺序（须显式排序）；
- 并发写入顺序（须由单一合成器串行化，见 4.7）；
- 浮点累加顺序（价值评分的累加须定序）；
- 随机数（若用于采样探测，随机源须可播种）。

## 4.7 合成器串行化契约（v6.0 新增）

多会话并发时，合成器对"同一服务商缓存键"的请求必须串行化。原因：前缀缓存是**共享资源**，两个并发请求会互相改写缓存的服务端状态，导致 12.5 的观测互相污染（详见 12.9）。

串行化的最小粒度：(服务商, model, tools_hash, system_hash) 四元组。不同四元组之间可并行。

## 4.8 原则 6–12（保留）

- **原则 6（分级管理）**：不同内容按稳定性分级，不同修改按成本分级。高频变化与低频变化分离，避免高频变更放大低频内容的缓存失效。
- **原则 7（量化优先于定性）**：预算、价值、审批、阈值均给出默认可操作定义，并标注标定阶段。未标定的参数明确标注为初始值。
- **原则 8（非货币成本口径）**：成本以 token 当量、时间当量、计算资源单位计量，不以真实资金计量。价值与成本模型在同一口径下闭合。
- **原则 9（边界不混用）**：可修改边界、写入位置、重算范围、替换范围四者语义不同，实现中不得互相替代。（v6.0 给出四者的类型签名，见 8.1）
- **原则 10（审计不可篡改）**：审批记录、注入来源记录、合成视图元数据以追加写入与哈希链方式存储，不得原地修改。
- **原则 11（会话历史不可删除）**：会话历史是 harness 场景的基础数据，长期保留。所有呈现层脱敏、访问控制、可追溯机制均作用于呈现层与审计层，不作用于会话历史本身的存储。
- **原则 12（假设可验证）**：架构依赖的每一项假设均须有明确的验证计划、数据记录要求与证伪应对。未验证的假设不得作为定稿依据。

| DeepSeek  | **约 256 token（本次实测 (240, 264]）**  | **64 token，向下取整**                      | `usage.prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`    | 实测 75 秒后仍命中；长 TTL 未测 | 命中 token 单价显著低于未命中    | **v5.0 的"最小长度 64"被证伪**：64 是计费/命中粒度，不是生效门槛 |

### 5.4.1 DeepSeek 实测要点（v6.0 新增，可复现）

测试条件：模型 `deepseek-chat`、端点 `https://api.deepseek.com/chat/completions`、单次 prompt ≤ 3000 token、共 30 次调用。数据见随文档发布的 `reports/deepseek_cache_probe.md` 与 `deepseek_cache_probe.json`。

| 测量项         | 结果                                                                     | 对架构的含义                                                           |
| ----------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 命中是否 64 整数倍 | **是，全部样本 `hit % 64 = 0`**；且 `hit = 64·floor(可命中前缀长/64)`                | 支持 12.7 的"块整数倍"前提，GCD 方法适用                                       |
| 生效门槛        | 64/128/240 token 前缀重复发送均 `hit = 0`；264 起首次命中。门槛落在 (240, 264] ≈ **256** | **`｜P｜` 若低于 256 则该服务商上缓存收益为 0**；v6.0 据此给出 `｜P｜ ≥ 1024` 的下限       |
| 尾部追加        | 前缀 A(2445) 追加至 2689，`hit = 2432 = floor(2445/64)·64`                   | 印证 I3：追加只使新增部分 miss                                              |
| 中部插入        | 同长度对照：尾追加 `hit=2432`；50% 处插入 `hit=1024`；25% 处插入 `hit=384`              | **印证 3.1 的机制事实 1**：回顾性插入使其后全部失效，且越靠前损失越大                         |
| 末尾小改        | 仅改末尾 120 字符，`hit=2176`（截到改动前对齐值）                                       | 印证"分叉点之后全失效"                                                     |
| 固定 miss 余数  | 每次请求 `miss` 恒为 12–30 token（即使完全命中前缀）                                   | **不存在 100% 命中**；21.3 的"P 段命中率 ≥ 95%"应理解为"P 段覆盖 ≥ 95%"，而非"零 miss" |

### 5.4.2 取证说明

- DeepSeek：本次以 API 实测为准（可信度高）。
- OpenAI / Anthropic：在受限网络环境下取官方文档片段（OpenAI 可信度中，Anthropic 分档数值可信度高）。阶段四须以可直连环境重跑取证并记录快照（20.6）。

**（v6.0 说明）** 上述"生效门槛 > 粒度"的区分具有普遍性。任何服务商的"最小缓存长度"都应当理解为**可命中前缀的生效下限**，而"块粒度"是**命中计量的取整单位**。两者不可混用：把 64 当作门槛会低估短前缀场景的失效风险，把 64 当作粒度又会高估命中精度。

# 第 6 章 架构总览

## 6.1 内容职责视图（四段 + 一个注入槽位置）

内容视图由四个内容段与一个运行时注入槽位置构成。注入槽不是内容段，而是 Z3 内的预算化写入位置，不参与内容职责分类。

| 编号   | 类型    | 名称      | 内容                        | 变更频率   | 缓存角色                 | 可变性等级              |
| ---- | ----- | ------- | ------------------------- | ------ | -------------------- | ------------------ |
| P    | 内容段   | 固定前缀段   | 系统提示、工具定义、稳定索引头、版本模板、固定策略 | 几乎不变   | 最长稳定前缀               | **不可变**（仅 L4）      |
| S0   | 内容段   | 稳定会话摘要段 | 滚动摘要、阶段结论、稳定记忆索引更新、稳定任务目标 | 低频批量   | 稳定期可被缓存覆盖            | **周期性重建**（L2/L4）   |
| R    | 内容段   | 近期历史窗口段 | 窗口内对话历史原文、工具调用与结果、事件记录    | 高频尾部微调 | 尾部改动集中，重算有上界         | **批冻结 + 整批前进**（I3） |
| S1   | 内容段   | 高频状态段   | 当前进度、待办、临时约束、高频偏好         | 高频     | 尾置，更新不重算 R           | **可预测替换**（I6）      |
| slot | 运行时位置 | 注入写入位置  | 尾注记忆、召回结果、临时提示            | 高频     | 尾部追加，token 预算约束，动态长度 | **仅尾部追加/淘汰**（I5）   |

v6.0 新增"可变性等级"一列——它把每个段允许的变更方式与其对应的不变式和审批级别绑定。这是 v5.0 缺失的关键：v5.0 用"变更频率"描述各段，但频率不是约束，"允许怎样变"才是约束。

## 6.2 运行时行为视图（两内容区 + 两运行时机制）

| 编号 | 类型    | 名称    | 作用                     |
| -- | ----- | ----- | ---------------------- |
| Z1 | 内容区   | 稳定前缀区 | 承载 P 段，保证最长稳定前缀命中      |
| Z3 | 内容区   | 可变尾窗  | 承载 S0、R、S1 与注入槽，重算集中于此 |
| Z2 | 运行时机制 | 缓存点观测 | 由命中反馈反推实际截断位置，维护状态     |
| Z4 | 运行时机制 | 溢出管理  | 预算耗尽时执行转移、压缩、推进缓存点     |

Z 编号仅作引用标识。Z1 与 Z3 是内容承载区；Z2 与 Z4 是作用于内容区的运行时机制。

## 6.3 映射关系

```
内容视图：    P（段）| S0（段）| R（段）| S1（段）| 注入槽（运行时位置）
运行时视图：  Z1 稳定前缀区 | Z3 可变尾窗（S0/R/S1/注入槽）  | Z2 观测 | Z4 溢出
```

注入槽作为运行时位置位于 Z3 尾部，其内容不属于任何内容段；其 token 计入 Z3 长度与重算范围，但不参与 S0/S1/R 的成本分类。

**（v6.0 补充）** Z3 是一个**单一连续区**，其内部顺序 P 之后固定为 `S0 ‖ R ‖ S1 ‖ slot`。任何实现不得把 S1 或 slot 挪到 S0 之前（那会改变替换成本模型 F4/F5 的失效范围）；该顺序由布局决策决定（第 9 章），运行时不可变更。

## 6.4 正交性论证

仅具备内容视图时，系统知晓修改对象与频率，但无法判断缓存实际截断位置，注入边界依赖猜测，误判前移将导致整段失效。仅具备运行时视图时，系统知晓缓存命中与重算边界，但内容职责不清，无法分级管理修改频率，高频变更将放大低频内容的失效。两视图叠加后，内容视图提供职责与频率约束，运行时视图提供命中边界与重算边界，二者共同构成受约束最优的求解空间。

**（v6.0 补充）** 正交性论证有一个隐含前提：**两个视图的状态都是可观测的**。内容视图的状态（各段字节）是可观测的；运行时视图的状态（缓存点）是可观测的。&#x4F46;**"段如何变化"这一维在两视图中都不在**——它不是内容（不改字节），也不能由 Z2 观测（Z2 只看命中结果）。v5.0 正是在这一维上留了空白，而这一维（不变式 I3/I5/I6）对命中率的影响超过两视图内任何参数。v6.0 把它显式加入，作为第三个维度：**变更代数（change algebra）**，见 6.5。

## 6.5 变更代数（v6.0 新增）

设一轮的变化向量 `Δ = (ΔP, ΔS0, ΔR, ΔS1, Δslot)`，每个分量是一个**变化算子**，而非数值：

| 段    | 允许算子集合                                                | 禁止算子                                  | 失效范围                |
| ---- | ----------------------------------------------------- | ------------------------------------- | ------------------- |
| P    | `Identity`、`Replace`（仅 L4）                            | 任何隐式变化                                | 全前缀                 |
| S0   | `Replace`（L2/L4）、`Identity`                           | `Insert`、`Append`（会增加长度并改变其后位置）       | S0 起点 → 末尾          |
| R    | `AppendToActiveBatch`、`BatchBreak`、`EvictOldestBatch` | `Slide`、`Insert`、`Truncate`、`Rewrite` | 活跃批内新增 + 挤出量        |
| S1   | `Replace`（可预测，I6）、`Identity`                          | `Insert`、`MidEdit`                    | S1 起点 → 末尾          |
| slot | `AppendTail`、`PopTail`、`BatchBreak`（清空或分段冻结）          | `RemoveMiddle`、`Reorder`、`MidEdit`    | 尾部追加量 / 整段（break 时） |

**推论**：本架构的全部成本优化都是"把变化算子从高代价集合换到低代价集合"。例如：

- 把 R 的 `Slide` 换成 `BatchBreak`（I3）—— 重算从 O(W) 降到 O(g)；
- 把 slot 的 `RemoveMiddle` 换成 `PopTail`（I5）—— 重算从 O(尾部) 降到 O(增量)；
- 把 S1 的 `MidEdit` 换成 `Replace`（I6）—— 使失效范围可预测。

这张表就是 v6.0 对"为什么这个架构省缓存"的完整回答：**它不靠减少注入，靠限制每个段允许使用的变化算子。**

## 6.6 数据流

```
会话历史 / 原始日志（只读、长期保留）
  → 批切分器（v6.0 新增：按 6.3.3 产生不可变批 B_1..B_n）
  → 记忆索引与召回（产生候选注入）
  → 上下文合成器（按 P/S0/R/S1/slot 组装；保证第 2 章全部不变式）
  → 模型调用（记录 cached_tokens、observation_snapshot、service_cache_key_snapshot）
  → Z2 观测状态机（更新缓存点估计与置信度）
  → Z4 溢出管理（预算耗尽时按判定执行转移与推进）
  → 回到批切分器与合成器
```

v5.0 的数据流缺"批切分器"这一环。没有它，R 段无法满足 I3，整个架构的定量结论不成立。

# 第 7 章 P 段：固定前缀段

## 7.1 内容范围

P 段集中承载**在同一会话内逐字节不变**的内容：

- 系统提示（行为规范、角色设定、输出格式约束）；
- 固定工具说明（工具名、参数 schema、调用约束）；
- 稳定记忆索引头（结构说明与字段定义，**不含动态条目**）；
- 版本化模板（协议版本、固定示例）；
- 固定安全策略与行为约束。

**版本号与可变计数的区分**：P 允许出现"版本化模板"中的版本号字符串，该版本号仅在 L4 显式变更时更新，不属于运行时可变计数。任何随调用或会话动态变化的计数（消息数、token 数、轮次数、时间戳）禁止进入 P。

## 7.2 稳定性约束（不变式 I4）

P 段在同一会话、同一适配配置版本内不得变化。禁止进入 P 段的字节包括：

- 任何形式的时间戳、日期；
- 会话标识、请求标识、追踪标识；
- 随机数、UUID、nonce；
- 动态排序结果（如"按相关性排序的工具列表"）；
- 动态计数（消息数、剩余预算等）；
- 未冻结的动态摘要。

工具定义与系统提示的微小格式变化可能改变 token 边界（进而改变整段哈希），须走显式失效流程。

**（v6.0 补充）** P 段的"稳定"有两层含义，必须分开处理：

1. **字节稳定**：`bytes(P_t) = bytes(P_{t'})`。这是 I4 的直接要求。
2. **缓存键稳定**：即使字节稳定，若 `tools_hash`、`model`、`system_hash`、采样参数中任一项变化（这些在真实缓存键内，见 5.4），缓存仍会整体失效。**字节稳定是必要不充分条件。**

v5.0 的三重校验只覆盖第 1 层。v6.0 扩为四重，见 7.3。

## 7.3 四重校验（v6.0 扩展自 v5.0 的三重校验）

P 段的稳定性校验由四项组成：

```
1. H_bytes  = hash(P_bytes)
2. tokenizer_version（记录模型对应的 tokenizer 版本标识）
3. H_tokens = hash(tokenize(P_bytes, tokenizer_version))
4. cache_key_snapshot = hash(model ‖ tools_hash ‖ system_hash ‖ sampling_params)
```

任一校验项变化即触发告警。**第 4 项是 v6.0 新增**，对应缺陷 D-9。

### 7.3.1 判据矩阵

| 情形                                                              | 判定                     | 处理                                                          |
| --------------------------------------------------------------- | ---------------------- | ----------------------------------------------------------- |
| `H_bytes` 变化                                                    | P 段内容变更                | L4 显式失效，批处理，审批，记录成本                                         |
| `H_bytes`、`H_tokens` 均不变，tokenizer 版本变化，**且服务商缓存键不含 tokenizer** | 仅观测变化                  | 记录 `observation_snapshot`，不触发失效                             |
| `H_bytes`、`H_tokens` 均不变，tokenizer 版本变化，**且服务商缓存键含 tokenizer**  | 真实缓存键变化                | L4 显式失效，审批，记录重算成本                                           |
| `H_bytes` 不变、`H_tokens` 变化                                      | tokenizer 或格式边界变化      | L4 显式失效，审批，记录重算成本                                           |
| `H_bytes` 变化且 tokenizer 版本变化                                    | 双重变化                   | L4 显式失效，分项记录                                                |
| **（v6.0）`H_bytes` 与 `H_tokens` 均不变，但 `cache_key_snapshot` 变化**  | 真实缓存键变化（工具集/采样参数/模型版本） | L4 显式失效；**若为采样参数变化且业务需要，可降级为 L2**（采样参数不改变 prompt 字节，但会清空缓存） |

### 7.3.2 采样参数的特殊处理

采样参数（temperature、top_p 等）同时满足两个条件：**不改变 prompt 字节**、**可能进入真实缓存键**。这使它在校验矩阵中地位特殊。

v6.0 规定：

- 采样参数必须在会话内冻结（写入会话级配置，不允许逐轮变动）；
- 若业务必须逐轮变动采样参数，则该会话须标记为 `cache_key_unstable`，Z2 退化为"每次请求都从 COLD_START 开始"，注入决策退化为纯价值排序（见 12.10）；
- 采样参数的每一次变动都须记录 `service_cache_key_snapshot` 差异，用于 12.8 的异常归因。

## 7.4 变更管理

P 段变更视为显式缓存失效事件（L4）。变更须满足：

1. **批处理**：不得逐次小改。同一版本内的所有 P 变更须合并为一次发布。
2. **记录**：变更前后记录 `cached_tokens` 对比、重算 token 数、重算时间当量。
3. **版本管理**：版本号与 tokenizer 版本绑定，便于回滚与对比。
4. **灰度与回滚**：灰度回滚时，P 段内容版本号与 tokenizer 版本号须绑定记录，回滚须同步。

### 7.4.1 变更成本

```
Cost(P 变更) = α·(|P| + |Z3|) + ε_time·approval_latency_ms + γ·audit_write_count      (F-P)
```

其中 `|P| + |Z3|` 是整条 prompt 的长度（P 变更使其后全部失效）。v5.0 的 6.1.4 只写了"记录重算成本"，未给公式；v6.0 补齐。

### 7.4.2 变更频率上限

由 21.3 的指标规定："P 段重算次数 / 会话 ≤ 1"。因此 P 变更在同一会话内最多一次（除非发生异常）。跨会话的 P 变更频率由发布节奏控制，不在本文范围。

## 7.5 P 段长度

P 段长度 `|P|` 直接决定：

- 缓存的最小可缓存长度是否被满足（`|P| ≥ min_cache_length`，见 12.10）；
- 稳态命中率的下限（`H ≥ |P| / prompt`）；
- Z3 起点的位置（`L_z1 = |P|`），进而决定 8.2 的情形 A/B/C 判定。

**建议**：`|P|` 取 3000–8000 token。低于 1024 时对 OpenAI 无法命中（见 5.4）；高于 8000 时 Z3 被压缩，R 窗口预算不足（见 9.3）。

# 第 8 章 R 段：近期历史窗口段（v6.0 核心重构）


> **本章是 v6.0 相对 v5.0 改动最大的章节。**&#x76;5.0 的 6.3.2 用一句话定义 R 段："窗口定义为最近 N token 的对话历史原文"。这句话至少有三种合法实现，稳态重算占比在三种实现下分别为 15.7% / 68.8% / 74.0%（同一会话轨迹、同一参数）。v6.0 把它形式化为**推进代数**，并规定实现必须满足不变式 I3。

## 8.1 内容范围

R 段承载最近对话历史的**原文**：

- 最近的对话轮次（user / assistant 消息）；
- 最近的工具调用与结果；
- 最近的事件记录。

允许轻微格式化（标注、锚点、时间标记、记忆引用），但格式化标记有独立预算上限（见 9.6）。

**v6.0 禁止**：R 段内不得出现任何依赖"当前时间"或"当前轮次"的渲染（例如相对时间"3 分钟前"）。这类标记会随请求时刻变化，等价于每轮都在 R 内部制造漂移字节，直接违反 I3。若需时间信息，必须写入 S1（其替换是显式且可预测的）。

## 8.2 三种推进模型（v6.0 形式化）

设会话历史被表示为一个有序 token 序列 `H = h_1 h_2 … h_n`（按时间顺序）。R 窗口预算为 `W`。三种推进模型定义如下。

### 8.2.1 模型 A：逐 token 滑窗（v5.0 的字面读法）

```
R_t = H[ n − W + 1 … n ]          （最近 W 个 token 的连续字节串）
```

**性质**：每轮 `H` 增长 `g`，`R_t` 相对 `R_{t-1}` 整体左移 `g`。因此

```
LCP(R_t, R_{t-1}) = W − g
ΔR_evict = W − g
```

**这是 v5.0 文本的字面实现，也是 20.6 的"≤30%"无法达到的原因。** 该模型下重算量随 W 线性增长，W 越大越差（见 8.2.4）。

### 8.2.2 模型 B：逐消息推进

```
R_t = concat(m_j, …, m_k)   其中 m 为消息，j = min{ j : Σ_{i=j..k} |m_i| ≤ W }
```

**性质**：每轮只丢掉最旧一条消息。`ΔR_evict` 的均值为 `g`（每轮丢一条消息，其长度等于本轮新增量，稳态下相等），但**波动大**：当一条消息很长时（如一次长工具输出），单轮 `ΔR_evict` 可达数千 token。

**问题**：`LCP(R_t, R_{t-1}) = |R| − |m_j|`，即每次窗口前进都会把剩余内容整体左移一条消息——**这不是"批边界"意义上的稳定**。实测（附录 H，exp12）：模型 B 与模型 A 的稳态命中率几乎相同（0.415–0.478 vs 0.415–0.464），因为两者的失效机制相同（整体左移），只是步长不同。

### 8.2.3 模型 C：批边界对齐（v6.0 规定）

```
历史被切分为批：B_1, B_2, …, B_n（按时间顺序）
  B_k = concat(m_a, …, m_b)   满足 Σ|m| ≥ θ_batch 的最小闭区间

R_t = concat(B_j, …, B_n)   其中 j = min{ j : Σ_{k=j..n} |B_k| ≤ W + |B_n| }
```

即：**R 的左端恒为某个批的起点**。窗口前进时整批淘汰。

**性质**：

- 批内内容逐字节稳定（批一旦形成即冻结，见 8.3）；
- `ΔR_evict` 只在"整批被丢弃"的轮次非零；
- `LCP(R_t, R_{t-1}) = |R_t| − |B_n|`（活跃批之外的内容完全稳定）。

**实测（附录 H，exp12）**：模型 C 的稳态命中率为 0.820–0.914，重算占比 9%–18%；模型 A/B 为 0.221–0.478 / 52%–78%。**同一参数、同一轨迹，仅改变推进模型。**

### 8.2.4 三种模型的稳态对比

设 `P=4000, S0=2000, S1=2000, slot=300, g=500, B=128`：

| W     | 模型 A 重算占比 | 模型 B 重算占比 | 模型 C 重算占比 |
| ----- | --------- | --------- | --------- |
| 4800  | 54%       | 52%       | **18%**   |
| 8000  | 65%       | 65%       | **14%**   |
| 12800 | 74%       | 74%       | **10%**   |
| 16000 | 78%       | 78%       | **9%**    |

**方向性结论**：模型 A/B 下 W 越大越差；模型 C 下 W 越大越好。`R_window = 上下文 × 0.4` 这个公式在两种模型下的含义完全相反——这解释了为什么 v5.0 的数值推导（86.7%）与工程直觉（"窗口越大越好"）都不成立：它们在描述不同的模型。

## 8.3 批的定义与冻结（F14）

### 8.3.1 批的形成

批的切分由**批切分器**完成（6.6 数据流）。批的边界取以下三者中**首个达到**的条件：

| 条件         | 阈值                      | 语义                |
| ---------- | ----------------------- | ----------------- |
| 一次工具调用往返完成 | —                       | 语义最自然：一个"观察—动作"闭环 |
| 一个语义阶段结束   | 由合成器判定                  | 需外部信号（如任务阶段切换）    |
| 固定 K 轮     | `θ_batch_tokens`（见 8.5） | 兜底：保证批不会无限增长      |

**批一旦形成即冻结**：其内容与长度在会话余下生命周期内不得改变。这是 I3 的直接要求。

### 8.3.2 活跃批与批断

```
活跃批 = B_n（最右侧的批，仍在追加）
批断 = 当 |B_active| ≥ θ_break 时：
         冻结 B_active
         开启新的 B_{n+1}（空）
         更新 R 的左端候选集合
```

批断**不改变任何已有字节**，因此不造成重算。它只是把一个"可增长的批"变成"不可变的批"。

**批断的粒度建议**（F14）：

```
|B_active| ≥ θ_break = φ·W,      φ ∈ [0.25, 0.5]                    (F14)
```

理由：若批太小（φ→0），批断频繁，每次批断都会使 R 的左端候选集合变化，最终表现为"逐条消息推进"（模型 B）。  
若批太大（φ→1），批断稀疏，但一旦需要淘汰，单次要丢掉 `W/2` 级的内容，产生周期性大尖峰。  
取 `φ=0.5` 时，稳态重算 = 新增 g + 摊薄的批淘汰 ≈ 1.5g，且最大单轮重算 ≤ `W/2 + g + |S1| + |slot|`。实测（附录 H）：`φ` 从 0.25 到 0.5 变化，稳态重算占比变化 < 2pp。

### 8.3.3 批边界与块边界的关系

缓存块粒度 B（OpenAI 128、DeepSeek 64）。**批边界应当对齐到块边界**——若批长度不是 B 的整数倍，则 R 内每个批的起始位置会在块对齐后产生 0–(B−1) 的偏移，导致命中长度下取整的损失叠加。

处理方式（v6.0 规定）：

- 批内内容允许在末尾填充**格式化标记**（非语义，计入 9.6 的标记预算）以对齐到 B 的整数倍；
- 或接受不对齐，但须在 12.7 的状态里把该偏移作为已知量扣除。

推荐前者：填充量 ≤ B−1 = 127 token，远小于对齐收益（块对齐后命中率提升约 1–2pp，见附录 H 的块粒度实验）。

## 8.4 R 段的操作边界

| 操作                 | 允许         | 约束                                          |
| ------------------ | ---------- | ------------------------------------------- |
| 追加到活跃批             | 是          | 受 I3 约束：只追加到 `B_n` 尾部                       |
| 批断                 | 是          | 不改变已有字节；不造成重算                               |
| 淘汰最旧批              | 是          | 整批淘汰；只改变 R 的左端                              |
| 添加时间标记             | **仅静态**    | v6.0：时间标记必须是**绝对时间**或**序号**，且一旦写入即冻结；禁止相对时间 |
| 添加记忆引用锚点           | 是          | 锚点数量受 9.6 的标记预算约束；锚点位置一旦写入即冻结               |
| 尾注召回结果             | 是（改走 slot） | 不在 R 内追加召回内容，一律写 slot（10.1）                 |
| 重写窗口内历史原文          | 否          | 窗口内保留原文                                     |
| 摘要掉窗口内关键内容         | 否          | 窗口内保留原文                                     |
| 前部插入新内容            | 默认否        | 须走 L5 回顾性注入（第 15 章）                         |
| 窗口外内容摘要            | 是          | 由 Z4 转入 S0，原文保留于会话历史                        |
| **窗口左端逐 token 前移** | **否**      | v6.0 明文禁止（违反 I3）                            |

## 8.5 窗口预算的确定（v6.0 重写）

v5.0：`R_window_tokens = min(模型上下文长度 × 0.4, 成本预算允许值)`。

该公式的问题：0.4 是相对上下文的固定比例，但实测显示稳态重算占比主要由 `g/prompt` 与批淘汰摊薄决定，与 `W/context` 的关系是二阶的。把它写成上下文比例，会导致"上下文越大、窗口越大、单次重算越大"的正反馈。

v6.0 改为**按验收阈值反解**：

```
给定：g（每轮新增）、S1_max、slot_max、θ_batch = φ·W、目标重算占比 ρ_target（21.3 取 0.30）
求解 W 满足：

    g + (g / W)·(φ·W)/1  +  |S1| + |slot|  +  ΔR_align
    ─────────────────────────────────────────────  ≤ ρ_target
       |P| + |S0| + W + |S1| + |slot|

化简（满足 I3、I6、I5 时，R_window 项摊薄为 O(g)）：

    分子 ≈ β·g + |S1| + |slot|          （β ∈ [1, 2]，取决于批断频率）
    分母 ≈ |P| + |S0| + W + |S1| + |slot|
```

**解的形式**：

```
W ≥ (β·g + |S1| + |slot|) / ρ_target  −  (|P| + |S0| + |S1| + |slot|)     (F15)
```

**代入 v6.0 默认参数**（g=500、β=1.5、|S1|=2048、|slot|=2048、ρ=0.30、|P|=4000、|S0|=4096）：

```
W ≥ (750 + 2048 + 2048)/0.30 − (4000 + 4096 + 2048 + 2048)
  ≥ 16153 − 12192
  ≥ 3961
```

即 **W ≥ 3961 token 即可满足 30% 阈值**。但实测（附录 H）显示 W=4800 时重算占比为 18%–25%（含 S1 每轮替换），W=8000 时为 14%–20%。解析式与实测的偏差来自 `R_segment` 项的保守取值。

**v6.0 的取值规则**：

1. 若业务要求稳态重算 ≤ 30%（21.3 的目标值），**W ≥ 8000** 即可（实测 19.8% @W=8000）；
2. 若业务要求稳态重算 ≤ 20%，**W ≥ 12800**（实测 15.7%）；
3. **上限由上下文决定**：`W ≤ context − |P| − |S0| − |S1| − |slot| − output_reserve`。32k 上下文下该上限约为 `32000 − 12192 − 4096 = 15712`。因此 32k 上下文下 **W 的可用区间是 [8000, 15712]**，取 12800 是合理的中间值——这与 v5.0 的 0.4 系数（12800）**数值相同但推导完全不同**。

**这一点值得强调**：v5.0 的 `0.4 × 上下文` 在 32k 下恰好落在实测最优区间内，因此该公式在 32k 下"碰巧是对的"。但在 8k/128k 上下文下会分别给出 3200/51200 这两个都超出实测安全区间的值（3200 太小，51200 超出 21.3 的单轮上限）。v6.0 用区间约束替代固定比例。

## 8.6 批大小与上下文的关系

```
|B_n| ≤ θ_break = φ·W
批数 n_batches ≈ W / θ_break = 1/φ（稳态，约 2–4 个批）
```

因此 R 段在稳态下由 2–4 个批构成。这个数量级是刻意的：

- 批太少（1 个）→ 批太长，淘汰时一次性丢掉半个 R；
- 批太多（>8）→ 每次批断都改变左端候选，退化为模型 B。

**建议 φ = 0.4，即稳态 2–3 个批。**

# 第 9 章 S0 与 S1 段

## 9.1 S0 内容范围

S0 集中承载**低频、稳定、可批量更新**的会话级状态：

- 会话滚动摘要；
- 阶段性总结与阶段结论；
- 稳定记忆索引更新（新增条目、索引结构变更）；
- 稳定任务目标。

**判定准则**：一条内容若"在会话余下生命周期内大概率不再变化"，进 S0；若"每轮都可能变"，进 S1。中间的灰区由 9.3 的决策规则处理。

## 9.2 S0 更新策略

### 9.2.1 触发条件

S0 低频批量更新，触发条件为以下任一：

| 条件          | 默认阈值                         | 说明            |
| ----------- | ---------------------------- | ------------- |
| 阶段切换        | —                            | 由合成器提供信号      |
| 累积轮次        | `S0_min_interval_turns = 10` | 附录 B          |
| 记忆条目数达到阈值   | 由后端定义                        | —             |
| 显式用户指令      | —                            | 高优先级          |
| **Z4 转移触发** | 见 11.2                       | R 窗口外内容须转入 S0 |

### 9.2.2 更新方式：替换而非追加（v6.0 给出定量依据）

S0 更新采用**替换**而非追加。v6.0 的实验（附录 H，exp14）验证了这个选择：

| R 实现    | S0/S1 策略 | 稳态命中率     | 稳态重算占比    |
| ------- | -------- | --------- | --------- |
| 批吸附（I3） | 替换       | **0.843** | **15.7%** |
| 批吸附（I3） | 只追加      | 0.824     | 17.6%     |
| 字面滑窗    | 替换       | 0.312     | 68.8%     |
| 字面滑窗    | 只追加      | 0.308     | 69.2%     |

**结论**：在满足 I3 的前提下，"替换"优于"只追加"约 2pp。原因是只追加会使段长无限增长，最终触发一次整体重建，且更长的段意味着更贵的重写。v5.0 选择替换是正确的，v6.0 保留并补充了这条定量依据。

### 9.2.3 长度上限

```
|S0| ≤ max_tokens_S0 = 4096
```

超过时触发压缩或转移，不得无限增长。该参数与 `S0_min_interval_turns`、`S0膨胀阈值` 共同约束 S0 的成本有上界（见 9.2.4）。

## 9.3 S0 变更成本模型（F4，v6.0 三态重写）

### 9.3.1 三态判定（v6.0 新增，替代 v5.0 的二态 A/B）

v5.0 只有情形 A（S0 在缓存点之后）与情形 B（S0 在缓存覆盖区）。v6.0 发现该二分在布局 A 下退化：布局 A 中 S0 的起点恒等于 `L_z1`，因此"是否在缓存覆盖区"无法区分"全缓存"与"部分覆盖"。v6.0 改为三态：

设 `CP` 为缓存点估计（保守下界），`CP_align = floor(CP / B) · B` 为块对齐后的缓存点。

```
情形 A（未覆盖）：  S0.end ≤ L_z1         → S0 完全在缓存点之外（P 都未完整命中）
情形 B（部分覆盖）：L_z1 < CP_align < S0.end_absolute   → S0 跨越缓存点
情形 C（全覆盖）：  S0.end_absolute ≤ CP_align          → S0 完全被缓存覆盖
```

其中 `S0.end_absolute = |P| + |S0|`。

**（v6.0 说明）** 在布局 A 且 `CP ≥ L_z1` 的正常稳态下，S0 **总是情形 C**（因为 S0 紧随 P，P 命中则 S0 也被缓存）。情形 B 只出现在"缓存点落在 P 与 S0 交界附近"的边缘情况（例如工具集变更导致 P 长度变化）。因此实际工程中**情形 A 与情形 C 是常态，情形 B 是异常态**，必须先由 Z2 判定并告警。

### 9.3.2 成本公式

```
Cost(S0 更新) =
    α · (|S0_new| + |R| + |S1| + |slot|)          ← 替换后的重算范围（S0 起点至末尾）
  + α · Invalidation(S0, CP)                      ← 仅情形 B：被失效的缓存覆盖区
  + β · summary_generation_tokens                 ← 摘要生成（输出 token）
  + γ · index_write_count
  + δ · dedup_cpu_seconds
  + ε_time · approval_latency_ms                  (F4)
```

其中：

```
                ┌ 0                                       情形 A（S0 本就在覆盖区外）
Invalidation =  ├ CP_align − |P|                          情形 B（部分覆盖区被失效）
                └ 0                                       情形 C（无额外失效，因为替换的
                                                          S0 起点在缓存点之后…严格说此时
                                                          应为 0，因为 S0 在缓存内时替换
                                                          等于从 S0 起点失效，已在第一项计）
```

**关键的语义澄清（v6.0 新增）**：F4 的第一项 `α·(|S0_new| + |R| + |S1| + |slot|)` 计的是**替换后从 S0 起点到末尾的内容需要重新计算**——这部分与"S0 是否被缓存"无关，因为替换必然使 S0 起点之后的内容字节全变。因此：

- 情形 A：S0 本来就在缓存外，替换的边际代价就是"这一段本来就不命中"，第一项计的是**请求规模**（不是边际成本）。
- 情形 C：S0 在缓存内，替换使其后的缓存全部失效，第一项的**全部内容**都是真正的边际成本。

**这正是 v5.0 的问题所在**：它用同一个公式覆盖 A 与 C，但两种情况的口径不同。v6.0 明确：

```
决策用（边际口径）：Cost_marginal(S0 更新) =
    情形 A: α·|S0_new| + β·summary_gen + γ·idx + δ·cpu + ε·lat        （R/S1/slot 反正不命中）
    情形 B: α·(CP_align − |P|) + α·|S0_new| + …                        （只有失效区 + 新 S0）
    情形 C: α·(|S0_new| + |R| + |S1| + |slot|) + …                      （全部失效）

审计用（请求规模口径）：Cost_request = prompt_tokens − cached_tokens
```

**两个口径都必须在审计中分开记录**，不得混用。这是缺陷 D-2 的正式修复。

### 9.3.3 审批级别（与三态绑定）

| 情形        | 审批级别   | 审批主体                                                    |
| --------- | ------ | ------------------------------------------------------- |
| A（S0 未覆盖） | L2     | 值班人                                                     |
| B（部分覆盖）   | **L4** | **安全负责人**（等同前缀失效）                                       |
| C（全覆盖）    | **L4** | **安全负责人**（v6.0 修订：v5.0 只把 B 定为 L4，C 定为 L2，实际 C 的失效范围更大） |

**这是一处重要的 v6.0 语义修正**：v5.0 把"情形 B（在缓存覆盖区）"定为 L4、情形 A 定为 L2，隐含假设"情形 C 不存在"。但布局 A 下 C 恰恰是常态。若照 v5.0 实现，**每次 S0 更新都会造成整窗失效，却只走 L2 审批**。v6.0 明确：**只要 S0 起点在缓存点之前（B 或 C），一律 L4。**

## 9.4 S1 内容范围与更新

### 9.4.1 内容范围

S1 集中承载**高频、每轮可能变化**的会话状态：

- 当前任务进度；
- 待办列表；
- 高频变化的用户偏好与模式设置；
- 临时约束；
- 本轮特定指令。

### 9.4.2 更新策略

S1 高频更新，尾置于 R 段之后、注入槽之前。更新仅影响 S1 自身与注入槽，不重算 R 段。更新走轻量审批（L1.5）。每轮 S1 更新次数受 `S1_max_updates_per_turn`（默认 2）约束。

**尾置的语义合理性**：模型按"摘要 → 历史 → 当前状态 → 注入"的顺序阅读，S1 靠近请求末尾，符合"最近状态最近阅读"的语义顺序。

### 9.4.3 可预测替换契约（不变式 I6）

v6.0 规定 S1 的替换必须满足**可预测性**：

```
前置条件：
  P1. 替换点恒为 S1.start（不得在 S1 内部任意位置插入）
  P2. 替换后的内容由 (会话状态, 轮次) 的确定性函数给出
  P3. 每轮最多 S1_max_updates_per_turn 次替换，且替换合并为一次写入

后置条件：
  Q1. LCP(S_t, S_{t-1}) = S1.start
  Q2. Recompute_t(S1 部分) = |S1_new| + |slot|
  Q3. 若本轮无 S1 变化，则 S1 段逐字节不变
```

**违反 P1（在 S1 中部编辑）的后果**：`Q1` 失效，重算范围从 `|S1|+|slot|` 扩大到 `|S1|+|slot|+（S1 中未被编辑的尾部）`。实测（附录 H，exp14）：若 S1 由"可预测替换"改为"追加"，重算反而 +2pp；但若改为"中部编辑"，失效范围会扩大整个尾部。

### 9.4.4 长度上限

```
|S1| ≤ max_tokens_S1 = 2048
```

超过时触发压缩或转移。该参数保证 F5 中 `|S1|` 有上界，高频成本项因此有界。


**（v6.0）** 该上限也决定稳态重算的固定分量：`R_segment ≈ |S1| + |slot| ≈ 4096`，占 prompt（约 24000）的 17%。这与实测（24.9%）的差距主要来自块对齐与批淘汰摊薄。**若业务希望把稳态重算压到 15% 以下，`max_tokens_S1` 与 `max_tokens_total_slot` 需要同步下调。**

### 9.4.5 S1 变更成本模型（F5）

```
Cost(S1 更新) =
    α · (|S1_new| + |slot|)                       ← S1 起点至末尾
  + γ · index_write_count
  + ε_time · approval_latency_ms                  (F5)
```

S1 不重算 R 与 S0。S1 位于缓存点之后的概率高，通常按情形 A 处理；若 S1 落入缓存覆盖区（罕见），按 9.3 的三态处理并升级审批级别。

## 9.5 S0/S1 拆分的经济性（v6.0 实测确认）

v5.0 的 6.4.3 给出了拆分的定性理由。v6.0 用同一会话轨迹对比了三种布局（附录 H，exp1）：

| 布局 | 结构 | 稳态重算占比 | 稳态命中率 |
|---|---|---|---|
| A（默认） | P \| S0 \| R \| S1 \| slot | **14.2%** | 0.858 |
| B（备选） | P \| R \| S0 \| S1 \| slot | 18.3% | 0.817 |
| C（对照，不分 S0/S1） | P \| S \| R \| slot | **78.0%** | 0.220 |

**布局 C 的重算占比是布局 A 的 5.5 倍**，这是 S0/S1 拆分必要性的定量证明。该结论支持 v5.0 的 7.1/7.2 设计，v6.0 保留。

**布局 B 的备选条件**（v6.0 修订）：v5.0 的 7.2 给出三条同时满足的条件，其中 `R_window_tokens ≥ 32768` 与 9.2 的 `S0_min_interval_turns < 10` 在大窗口下互相冲突（7.4 矩阵要求大窗口配低频）。v6.0 修订为：

```
布局 B 进入消融验证的条件（同时满足）：
  ① R_window ≥ 32768
  ② 实测 S0 更新成本占单次调用 token 预算 > 30%
  ③ 在布局 A 下，S0 更新轮的 Z3 重算占比中位数 > 50%

满足时进入消融验证；验证通过后方可切换为部署候选。默认仍为布局 A。
```

删除了 `S0_min_interval_turns < 10` 这一条——它不是布局 B 的必要条件；在大窗口下 S0 低频恰恰是布局 B 的优势场景。

## 9.6 格式化标记预算（v6.0 独立成节）

v5.0 把"格式化标记占比 ≤ 2%"（20.6）与"锚点数量受预算约束"（6.3.4）散在两处，没有定义预算池。v6.0 明确：

```
格式化标记预算 = 2% × (|P| + W)                      （独立于注入槽预算）
用途：批边界块对齐填充（8.3.3）、记忆引用锚点、静态时间标记
禁止：语义内容、召回结果、状态更新（这些必须进 slot 或 S1）
```

**独立于注入槽预算的理由**：格式化标记属于"结构性开销"，与注入内容（语义性开销）的决策逻辑不同——前者随 R 批切分自动产生，后者由价值模型决定。混在一个池里会导致格式化标记挤占注入预算。

# 第 10 章 注入槽（动态 token 预算）

## 10.1 设计原则

注入槽以 token 预算定义，只包含实际写入内容。空位不预占、不消耗 token。预算是写入时的上界约束，不是静态占位。既不为对齐填充无效内容，也不预留固定长度。真正节省的是"改动集中在尾部小区间，使重算量有上界"。

**（v6.0 补充）** 该原则成立的充分必要条件是**不变式 I5**："淘汰只允许从尾部发生，禁止原位删除、禁止重排"。v5.0 的 9.3/10.2 规定"淘汰过期/低价值/已消费注入"但没有说明淘汰位置，按字面实现会从任意位置删除，导致其后内容整体左移，"重算含注入增量"不成立。v6.0 把位置约束写入伪代码（10.3）。

## 10.2 预算定义

```yaml
slot_budget:
  max_tokens_per_injection: 512        # 单次注入上限
  max_tokens_total_slot:    2048       # 槽总预算
  max_injections_per_turn:  3          # 每轮注入次数上限
  min_value_threshold:      0.45       # 注入价值阈值（v6.0 按 14.2 可达区间重设）
  # v6.0 新增参数：
  slot_break_tokens:        2048       # 达到该长度触发一次"槽批断"（见 10.3.3）
  slot_evict_policy:        tail_only  # 唯一合法值（I5）
```

`max_tokens_total_slot` 是写入累计上限；槽未写满时 Z3 实际长度仅含实际内容。

**参数一致性检查（14.3 要求的推荐配置）**：

```
max_injections_per_turn × max_tokens_per_injection ≤ max_tokens_total_slot
3 × 512 = 1536 ≤ 2048   ✓
```

**（v6.0 警告）** 该配置虽然满足一致性要求，但使槽每轮写入量达容量的 75%，槽处于"每轮整体翻新"状态。实测（附录 H，exp9b）：当每轮写入量从 1536 降到 64 时，命中率几乎不变（17.4% → 17.9%），说明**在这种翻新态下，预算参数对命中率无影响**。若业务希望槽成为"稳定尾段"，应把每轮写入量压到容量的 1/8 以下（如 `max_tokens_per_injection=128`）。

## 10.3 预算冲突处理（含淘汰位置约束）

### 10.3.1 统一冲突处理顺序

以本节为准（v5.0 的 9.3 引用 14.4，v6.0 合并为单一权威位置）：

```
1. 价值过滤：剔除 value < min_value_threshold 的候选
2. 价值排序（降序）；同 value 时按 (来源优先级, 候选 id) 稳定排序（确定性契约 4.6）
3. 每轮次数限制：保留前 max_injections_per_turn 条，其余进入下一轮候选队列
4. 单次上限截断：单条超过 max_tokens_per_injection 时截断至上限
5. 总预算限制：按价值降序写入直到累计达到 max_tokens_total_slot
6. 淘汰（仅在必要时）：从【尾部】淘汰，直到可容纳新写入量（不变式 I5）
7. 淘汰记录审计
8. 触发 Z4 判定（若槽使用率 ≥ Z4_trigger_ratio）
```

### 10.3.2 淘汰位置约束（不变式 I5）

```
前置条件：
  P1. 槽内元素构成一个有序序列 items[0..m-1]
  P2. 淘汰只能执行 pop_back()，即删除 items[m-1]
  P3. 若某元素被标记"已消费/低价值/过期"且不在尾部，则：
        保留其占位（不删除），并打标记；等它滚到尾部后被删除

后置条件：
  Q1. 本轮 items 是上一轮 items 的前缀 + 若干尾部追加（或本条不动）
  Q2. Recompute_t(slot 部分) ≤ Δslot + |S1|（仅当本轮有截断时含 S1）
```

**"打标记而不是删除"的实现含义**：被标记的元素在 prompt 中仍然存在（占用 token），但其内容对模型无意义。这看似浪费，但省下了整段重写的成本。若标记元素的累积量超过 `slot_break_tokens`，则触发一次**槽批断**（10.3.3）把它一次性清掉。

### 10.3.3 槽批断

```
触发：Σ标记元素 token ≥ slot_break_tokens  或  槽总长 ≥ max_tokens_total_slot
动作：
  1. 冻结当前槽内容为"历史槽段"（不可变）
  2. 开启新槽，只容新注入
  3. 旧槽段随其所在的批一起被淘汰（随 8.3 的批淘汰）
```

**这样做的效果**：槽的清零不是"每轮删几条"，而是"每 k 轮一次整段重建"，其中 `k = slot_break_tokens / 每轮写入量`。重建的成本是 `|S1| + |slot|`（因为 S1 在槽前面，不受影响，但批断会使 R 的活跃批发生变化）。实测（附录 H）：当槽按批断方式运行时，稳态重算占比为 16%–25%，与"每轮追加 + 尾部淘汰"无显著差异（差 < 1pp），但**最大单轮重算**明显更低（无周期性尖峰）。

## 10.4 写入流程（v6.0 拆为三条并列路径）

v5.0 的 9.4 只描述了一条流程（生成候选 → …… → 写入尾部），但 11.2 的伪代码有 4 条路径（尾部追加 / S1 更新 / S0 更新 / 回顾性注入）。这是 v5.0 内部的一处直接矛盾（缺陷 D-14）。v6.0 把流程拆为与伪代码一一对应的三条：

### 路径 1：尾部追加（TAIL_INJECTION）

```
生成候选 → 价值评估（14.2）→ 价值过滤与排序 → 去重与合并
→ 按 10.3.1 的 1–5 步做前置检查 → 写 slot 尾部 → 记录注入元数据
→ 若槽使用率 ≥ Z4_trigger_ratio → 触发 Z4
```

### 路径 2：段内替换（S0_UPDATE / S1_UPDATE）

```
生成候选 → 价值评估 → 价值过滤（S0 需 value ≥ θ_S0；S1 需 value ≥ θ_S1）
→ 判定三态（9.3.1）→ 按三态确定审批级别（9.3.3）
→ 审批通过 → 替换目标段 → 记录替换元数据与重算范围
```

### 路径 3：回顾性注入（RETROACTIVE_INJECTION）

```
生成候选 → 价值评估 → value ≥ θ_retro 门槛
→ L5 审批（安全负责人）→ 访问审查（19.3）→ 白名单校验（18.3）
→ 重算预算审批 → 显式重算（记录完整重算范围）→ 审计
```

三条路径的公共前置：预算检查、脱敏检查（CP2/CP3）、确定性排序。

## 10.5 伪代码（契约式，v6.0 重写）

```
// ============================================================
// 函数：decide_injection
// 语义：对单个候选注入做出接受/拒绝/转交的决策
// 前置条件：
//   C1. 本轮快照 snap 已生成（唯一快照，含 Z2 状态、预算余量、段长度）— 不变式 I7
//   C2. 候选的 value 已按 14.2 计算
//   C3. 候选的脱敏检查已通过（CP2）
// 后置条件：
//   Q1. 返回值为下述枚举之一
//   Q2. 无论接受或拒绝，均写入审计记录（不变式 I8）
//   Q3. 若接受，本轮快照被标记为"已写入"，后续同轮决策复用同一快照
// 维护的不变式：I5（槽顺序）、I7（预算价值闭合）、I8（审计）
// ============================================================
function decide_injection(candidate, snap):
    // 1) 价值门槛：按候选类型分别判定
    θ = threshold_for(candidate.type)          // 见 15.2 分级表
    if candidate.value < θ:
        return REJECT_LOW_VALUE

    // 2) 类型分派
    switch candidate.type:
        case TAIL_INJECTION:
            return handle_tail(candidate, snap)
        case S1_UPDATE:
            return handle_s1(candidate, snap)
        case S0_UPDATE:
            return handle_s0(candidate, snap)
        case RETROACTIVE_INJECTION:
            return handle_retroactive(candidate, snap)
        default:
            return REJECT_UNKNOWN_TYPE

// 返回值枚举（全量，实现不得发明新值）：
//   ACCEPT, REJECT_LOW_VALUE, REJECT_BUDGET, REJECT_RETROACTIVE,
//   REJECT_WHITELIST, REJECT_UNKNOWN_TYPE, DEFER_NEXT_TURN,
//   REQUIRE_L1_5, REQUIRE_L2, REQUIRE_L4, REQUIRE_L5
```

```
// ============================================================
// 函数：handle_tail
// 语义：尾部追加路径
// 前置条件：
//   C1. candidate.type == TAIL_INJECTION
//   C2. snap.budget_remaining ≥ candidate.tokens（否则先执行 10.3.2 的尾部淘汰）
// 后置条件：
//   Q1. 若接受，slot 尾部追加 candidate，且 items 前序不变（不变式 I5/Q1）
//   Q2. 记录重算范围 = |candidate.tokens| + |S1|
//   Q3. 若 candidate 显式指定了目标位置且该位置 < B_mod，返回 REJECT_RETROACTIVE
// 维护的不变式：I1、I5
// ============================================================
function handle_tail(candidate, snap):
    // 显式指定位置在可修改边界之前 → 拒绝（不静默改写，A3 原则保留）
    if candidate.target_position is specified and
       candidate.target_position < snap.B_mod:
        return REJECT_RETROACTIVE          // 提示走 L5

    // UI/C7 的等价实现：未指定位置或位置在边界之后 → 一律写槽尾
    // 注意：这不是"放宽"，因为写入位置恒为槽尾，永远不会触及前缀
    evicted = []
    while snap.slot_used + candidate.tokens > snap.max_tokens_total_slot:
        if snap.slot_items is empty: return REJECT_BUDGET
        popped = pop_back(snap.slot_items)      // 不变式 I5：只允许从尾部
        evicted.append(popped)
        audit(record=eviction(popped, reason=TAIL_EVICT))

    append_tail(snap.slot_items, candidate)
    record_recompute(|candidate.tokens| + |snap.S1|)
    audit(record=injection(candidate, snap=snap.snapshot_id))
    return ACCEPT
```

```
// ============================================================
// 函数：handle_s1
// 语义：S1 段内替换路径
// 前置条件：
//   C1. candidate.type == S1_UPDATE
//   C2. candidate.value ≥ θ_S1 = 0.60（14.2）
// 后置条件：
//   Q1. LCP(S_t, S_{t-1}) = S1.start（不变式 I6/Q1）
//   Q2. 重算范围 = |S1_new| + |slot|
//   Q3. 若 S1 起点在缓存点之前，升级为 L2 并返回 REQUIRE_L2
// 维护的不变式：I6
// ============================================================
function handle_s1(candidate, snap):
    if snap.S1_start < snap.CP:
        // S1 被缓存覆盖：替换等于从 S1 起点失效
        return REQUIRE_L2{reason: "S1_IN_CACHED_REGION",
                          recompute: |S1_new| + |slot|}
    replace_segment(S1, candidate.content)     // 替换点恒为 S1.start
    record_recompute(|S1_new| + |slot|)
    audit(record=s1_update(candidate, snap=snap.snapshot_id))
    return ACCEPT
```

```
// ============================================================
// 函数：handle_s0
// 语义：S0 段内替换路径（三态判定 + 分级审批）
// 前置条件：
//   C1. candidate.type == S0_UPDATE
//   C2. candidate.value ≥ θ_S0 = 0.60（v6.0：v5.0 为 0.80，见 14.2 可达性修订）
// 后置条件：
//   Q1. 三态判定结果与审批级别一致（9.3.3）
//   Q2. 重算范围按三种口径分别记录（9.3.2）
// 维护的不变式：I1、I7、I8
// ============================================================
function handle_s0(candidate, snap):
    state = classify_s0(snap)        // A / B / C，见 9.3.1
    switch state:
        case A:  return REQUIRE_L2{reason: "S0_UNCOVERED",
                                   recompute: |S0_new|}
        case B:  return REQUIRE_L4{reason: "S0_PARTIALLY_COVERED",
                                   recompute: CP_align − |P| + |S0_new|}
        case C:  return REQUIRE_L4{reason: "S0_COVERED",
                                   recompute: |S0_new| + |R| + |S1| + |slot|}

    // 注：审批通过后由 apply_s0_update() 执行替换，本函数不直接写
    // 这样保证了"三段路径各有独立审批，不会互相越界"

function apply_s0_update(candidate, approval_record):
    // 前置条件：approval_record.level ∈ {L2, L4} 且 approval_record.granted
    replace_segment(S0, candidate.content)
    record_recompute_marginal(...)      // 边际口径
    record_recompute_request(...)       // 请求规模口径
    audit(record=s0_update(candidate, approval=approval_record.id))
    return ACCEPT
```

```
// ============================================================
// 函数：handle_retroactive
// 语义：回顾性前缀注入路径（L5）
// 前置条件：
//   C1. candidate.type == RETROACTIVE_INJECTION
//   C2. candidate.value ≥ θ_retro = 0.75（v6.0 按可达区间重设）
// 后置条件：
//   Q1. 三条审批链全部完成（L5 → 访问审查 → 白名单 → 重算预算）
//   Q2. 重算范围记录为整条 prompt
// 维护的不变式：I8、原则 11
// ============================================================
function handle_retroactive(candidate, snap):
    if not l5_approved(candidate):          // 安全负责人
        return REQUIRE_L5
    if not access_review_passed(candidate): // 19.3
        return REJECT_RETROACTIVE
    if not whitelist_check(candidate):      // 18.3
        return REJECT_WHITELIST
    if not recompute_budget_approved(candidate):  // 14.4
        return REJECT_BUDGET
    apply_retroactive(candidate)
    record_recompute(prompt_length)          // 整条前缀失效
    audit(record=retroactive(candidate, snap=snap.snapshot_id))
    return ACCEPT
```

# 第 11 章 布局决策、边界与范围、Z4 溢出管理

## 11.1 候选布局与定量比较

### 11.1.1 三种布局

| 布局 | 顺序 | 特点 | 风险 | 状态 |
|---|---|---|---|---|
| **A** | `P \| S0 \| R \| S1 \| slot` | 语义自然；S0 低频靠前；S1 高频靠后 | S0 更新重算 R 全长 | **部署候选（默认）** |
| B | `P \| R \| S0 \| S1 \| slot` | R 缓存更稳；S0 靠后 | 模型先读历史再读摘要，阅读顺序变差 | 部署备选（需消融验证） |
| C | `P \| S \| R \| slot`（无 S0/S1 拆分） | 结构简单 | S 更新重算 R 全长 | 仅实验对照，不作为部署候选 |

### 11.1.2 实测比较（附录 H，exp1）

同一会话轨迹、同一参数（P=4000、W=12800、g=500、60 轮、OpenAI 适配）：

| 布局 | 平均 prompt | 命中率 | 重算占比 | P 段命中率 | 单轮最大重算 |
|---|---|---|---|---|---|
| **A** | 19105 | **0.858** | **14.2%** | 0.888 | 16344 |
| B | 19105 | 0.817 | 18.3% | 0.839 | 15871 |
| C | 18044 | 0.220 | **78.0%** | 0.778 | 20876 |

**结论**：
1. 布局 A 优于 B 约 4pp 命中率（与 v5.0 的判断一致）；
2. 布局 C 的重算占比是 A 的 5.5 倍——**S0/S1 拆分是必要的**；
3. 三个布局的 P 段命中率都在 0.78–0.89，说明**布局选择不影响 P 段的保护**，只影响 Z3 的内部失效范围。

### 11.1.3 布局 B 的备选条件（v6.0 修订）

v5.0 的 7.2 给出三条同时满足的条件，其中 `R_window_tokens ≥ 32768` 与 `S0_min_interval_turns < 10` 在大窗口下互相冲突（7.4 矩阵要求大窗口配低频）。v6.0 修订为：

```
布局 B 进入消融验证的条件（同时满足）：
  ① R_window ≥ 32768
  ② 实测 S0 更新成本占单次调用 token 预算 > 30%
  ③ 在布局 A 下，S0 更新轮的 Z3 重算占比中位数 > 50%
```

删除 `S0_min_interval_turns < 10`——在大窗口下 S0 低频是布局 B 的优势场景，不是布局 B 的适用场景。

### 11.1.4 布局 C 的定位

7.2 明确 C 不作为部署候选，但 20.1/20.3 保留 C 作为实验对照组，用于证明 S0/S1 拆分的必要性。实验结论（11.1.2）不改变 C 的非部署定位。

## 11.2 三边界与四范围（v6.0 类型化）

### 11.2.1 问题

v5.0 的 11.1 定义了四个概念（可修改边界、实际写入位置、重算范围、替换范围），原则 9 要求"四者不得混用"，但**没有给出任何形式化定义**。这在 11.2 的伪代码中直接造成了混用：`handle_tail_injection` 用 `modifiable_boundary` 判位置、用 `actual_cache_point` 算重算范围，而这两个量在 8.5 里来自不同的估计区间端点。

v6.0 给四个概念各自的类型签名与取值范围。

### 11.2.2 定义

```typescript
// 偏移量类型（单位：token，从 prompt 起点计）
type Offset = int, 0 ≤ Offset ≤ prompt_length

// ① 缓存点估计（保守下界）
//    语义：真实缓存点不会小于此值
//    来源：Z2.estimate_cache_point()，取 8.5 区间下界并向下取整到块边界
CP_est:      Offset  = floor(cache_point_lower_bound / B) * B

// ② 缓存点估计（保守上界）
//    语义：真实缓存点不会大于此值
CP_upper:    Offset  = cache_point_upper_bound

// ③ 可修改边界
//    语义：尾部追加式注入若显式指定了位于此边界之前的位置，应被拒绝或改走 L5
//    注意：它约束的是"写入位置"，不是"重算范围"
B_mod:       Offset  = CP_upper + margin(B, block_buffer)
                       + (confidence != NORMAL ? B : 0)
                       + (B_unknown ? 256 : 0)

// ④ 实际写入位置
//    语义：本轮注入在 prompt 中实际占据的区间
W_pos:       [Offset, Offset) = [slot.start, slot.end)
                              | [S1.start, S1.end)      （S1 更新）
                              | [S0.start, S0.end)      （S0 更新）
                              | [candidate.target, ...) （回顾性）

// ⑤ 重算范围（尾部追加，运行时量）
//    语义：本轮请求中未被缓存命中的那一整段
//    来源：由【实际观测到的 cached_tokens】反推，不由估计值计算
R_rec:       [Offset, Offset) = [CP_observed, prompt_length)
              其中 CP_observed = prompt_length − cached_tokens

// ⑥ 替换范围（S0/S1 更新，设计量）
//    语义：段替换后，哪些内容必然改变
R_rep:       [Offset, Offset) = [target_segment.start, prompt_length)
```

### 11.2.3 关键区分（v6.0 明确）

| 问题 | 用哪个量 | 不能用哪个 |
|---|---|---|
| "这个注入能不能写到指定位置？" | `B_mod` | `CP_est`、`R_rec` |
| "这次注入实际重算了多少？" | `R_rec`（观测反推） | `B_mod`、`CP_est` |
| "这次替换会让哪些内容失效？" | `R_rep`（设计量，可直接计算） | `R_rec`（观测量，事后才知道） |
| "这轮总共花了多少算力？" | `R_rec` 的求和 | 任何估计值 |

**v5.0 的错误**：11.2 的 `handle_tail_injection` 用 `recompute_range = prompt_length − actual_cache_point`，而 `actual_cache_point` 是**估计值**。这违反了原则 9（"禁止用安全余量估算重算范围；重算范围由实际缓存点计算"）——只不过这里用的是估计的缓存点而不是实际缓存点。v6.0 规定重算范围必须由**观测到的 `cached_tokens`** 计算，估计值只能用于**决策**（是否允许、是否值得），不能用于**记账**。

### 11.2.4 边界关系图示

```
[ Z1 = P 稳定前缀 ] [ 缓存点 CP ] [ 安全余量 ] [ S0 ] [ R ] [ S1 ] [ 注入槽 ]
                     ↑            ↑                                   ↑
                CP_est/CP_upper   B_mod                          W_pos (恒为 slot)
                     |____________________________________________|
                            R_rec（观测反推，缓存点后至末尾）
```

**说明**：`B_mod` 箭头标注在"缓存点上界 + 安全余量"处，`R_rec` 从"观测到的缓存点"起算。两者起点不同是**设计意图**，不是笔误：`B_mod` 要保守（宁可提前），`R_rec` 要准确（用于记账）。

### 11.2.5 边界判定的伪代码

```
// ============================================================
// 函数：is_position_modifiable
// 语义：判断一个目标偏移是否允许被尾部追加式写入使用
// 前置条件：C1. snap 已生成；C2. CP_upper 与 B_mod 已按 12.6 计算
// 后置条件：Q1. 返回 true 当且仅当 pos ≥ B_mod
// 维护的不变式：I1
// ============================================================
function is_position_modifiable(pos: Offset, snap) -> bool:
    return pos >= snap.B_mod

// ============================================================
// 函数：observe_recompute_range
// 语义：由服务商返回的 cached_tokens 反推本轮真实重算范围
// 前置条件：C1. 响应已返回且 cached_tokens 经 12.3 归一化
// 后置条件：Q1. 返回区间 [prompt_length − cached, prompt_length)
//           Q2. 与 B_mod、CP_est 无任何关系
// ============================================================
function observe_recompute_range(prompt_length, cached) -> [Offset, Offset):
    return [prompt_length - cached, prompt_length)
```

## 11.3 Z4 溢出管理

### 11.3.1 触发条件（v6.0 修订 D-4）

| 条件 | v5.0 阈值 | v6.0 阈值 | 修订理由 |
|---|---|---|---|
| Z3 预算耗尽 | 槽使用率 ≥ 90% | 保持 | — |
| Z3 重算量超相对阈值 | **单次重算 > 1.5 × \|Z3\|** | **单次重算 > 0.6 × \|Z3\|** | v5.0 的值在数学上不可达：11.1 自述重算上界由 \|Z3\| 决定，故 1.5\|Z3\| 恒假。0.6 在实测中可达（附录 H，S0 替换轮可达 0.9–1.0\|Z3\|） |
| Z3 重算量超绝对上限 | 32768 | 保持（但标注"仅大上下文可达"） | 20.2 的实验区间最高 32k，该阈值在该区间内不可达 |
| S0 膨胀超阈值 | \|S0\| > \|R_window\| × 0.5 | 保持 | — |
| 命中率持续下降 | 连续 5 次下降且排除漂移字节 | 保持 | — |
| 历史注入价值重估偏低 | 重估后 value < 0.3 的占比 > 50% | 保持（配合 10.3.2 的尾部淘汰） | — |

**可达性验证要求（v6.0 新增）**：每条触发条件发布前，须在阶段三用样本轨迹验证其"在健康系统中的触发率为 0，在病态系统中可触发"。1.5|Z3| 之所以是缺陷，正是因为它在健康与病态系统中都不可触发。

### 11.3.2 管理动作

- **R 窗口外转移**：R 段新增内容使窗口超出 W 时，窗口最旧**批**移出 R，转入 S0 摘要（压缩后），关键内容同步进入长期记忆索引，会话历史不受影响，记录转移成本。
- **压缩旧尾窗**：旧对话摘要化、重复注入去重、低价值注入淘汰（仅尾部）、格式化标记精简。
- **推进缓存点**：将部分 Z3 内容稳定化，尝试纳入缓存覆盖范围；一次性推进；记录推进前后 `cached_tokens` 对比。
- **重建 S0**：合并记忆索引、压缩会话摘要、替换而非追加、控制段长。
- **清理注入槽**：淘汰过期注入、淘汰低价值注入（仅尾部）、移除已消费注入（仅尾部）、保留高价值注入。

### 11.3.3 动作成本分级（v6.0 新增）

v5.0 的 10.2 列出 5 个动作，但 10.1 的触发表不区分动作成本。实测（附录 H，exp1/exp4）：

| 动作 | 典型成本（token） | 是否需要审批 | 适用触发条件 |
|---|---|---|---|
| 清理注入槽 | ~0（只标记） | 系统规则 | 槽使用率 ≥ 90% |
| 压缩旧尾窗 | ~0.2·\|Z3\| | 系统规则 | 命中率下降 |
| R 窗口外转移 | ~\|Z3\|（情形 C 级） | L2 | R 溢出 |
| 重建 S0 | ~\|Z3\|（情形 C 级） | L4 | S0 膨胀 |
| 推进缓存点 | ~\|Z3\|（一次性） | L3 + 10.3 判定 | 相对/绝对重算阈值 |

**成本相差 3 个数量级**（清理槽 ≈ 0，推进 ≈ 整窗）。v6.0 规定：**每个触发条件只允许触发其成本级别的动作**——例如"槽使用率 ≥ 90%"只能触发"清理注入槽"或"槽批断"，不得直接触发"推进缓存点"。

### 11.3.4 推进缓存点的成本收益判定（F11）

```
推进收益 > 推进成本 + 风险余量                          (F11)

其中：
  推进收益 = 预计节省的重算 token × 预计剩余调用次数
  推进成本 = 推进触发的重算 token + 摘要生成 token + 索引写入当量
  风险余量 = 推进后缓存点估计不确定性的 token 当量（默认 1 个块粒度）

剩余调用次数估计：
  if 会话处于阶段初期：默认 20
  elif 会话处于阶段中期：默认 10
  elif 会话处于阶段末期：默认 3
  else：按最近 10 次调用间隔与会话总时长线性外推

阶段判定由会话管理器提供；无法判定时使用默认 10。
```

推进须走 L3 审批。审批记录包含：推进前后 `cached_tokens`、预计收益、实际成本、剩余调用次数估计。条件不满足时改为"压缩旧尾窗"或"清理注入槽"，不推进缓存点。

**（v6.0 补充）** 推进缓存点的本质是**主动制造一次可控的失效**，换取之后更长的稳定段。在满足 I3 的架构下，它的必要性大大降低——因为 R 段的批边界已经保证了稳定段。v6.0 建议：**只有在实测"批次淘汰造成的重算"持续超过 `0.6×|Z3|` 时才考虑推进**，否则保留默认（不推进）。

### 11.3.5 成本记录

每次触发记录：触发原因、转移/压缩前后 token 对比、重算 token 数、重算时间当量、缓存命中率变化、记忆效果变化、会话历史完整性校验结果。**（v6.0 新增）** 另需记录：触发动作类型（用于 11.3.3 的成本分级校验）、`snapshot_id`。

### 11.3.6 会话历史完整性校验（F12）

```
每条历史记录 L_i 计算 log_h_i = hash(L_i ‖ log_h_{i-1})，log_h_0 = 固定初始值    (F12)
维护 log_h_latest 与记录总数 N
校验时重新计算哈希链，比对 log_h_latest 与 N
校验频率：
  - 每次 Z4 触发后
  - 每日定时
  - 审计事件触发时
失败处理：
  - 立即冻结合成上下文生成
  - 告警至安全负责人
  - 从最近可信快照恢复
```

审计日志哈希链使用独立符号 `audit_h_i`（18.2），与日志哈希链符号区分。

# 第 12 章 Z2：缓存点观测机制

## 12.1 机制定位

Z2 是运行时观测机制，不是内容分区。职责为：由缓存命中反馈反推服务商实际缓存截断位置，维护估计区间与置信度，检测异常，为可修改边界（11.2）提供保守上界。

**（v6.0 补充）** Z2 的输出有两类消费者，必须严格分开：

| 消费者 | 消费的量 | 用途 | 允许误差方向 |
|---|---|---|---|
| 决策（是否允许写入、是否值得） | `B_mod`（保守上界 + 余量） | 拒绝/放行 | 宁可保守 |
| 记账（成本模型、审计、指标） | `R_rec`（由 `cached_tokens` 观测值反推） | 成本统计 | 必须准确 |

混用这两者会让"决策保守"污染"记账准确"，或反之。v6.0 在 11.2.3 给出了对照表。

## 12.2 状态机（v6.0 增加 TTL_EXPIRED）

### 12.2.1 状态集合

```
COLD_START      ：会话开始、适配配置切换后
LOW_CONFIDENCE  ：样本不足或波动大，边界保守
NORMAL          ：观测稳定，边界按 12.6 计算
TTL_EXPIRED     ：v6.0 新增。上次命中的时间超过服务商 TTL，缓存已失效但系统本身健康
ANOMALY         ：观测异常（漂移字节、缓存键变化、语义越界）
RECALIBRATING   ：主动探测中
```

### 12.2.2 迁移规则

```
COLD_START
  ├─ 样本数 ≥ N_min 且 d < d_low                → NORMAL
  ├─ 样本数 ≥ N_min 且 d ≥ d_low                → LOW_CONFIDENCE
  ├─ 连续 N_min 次 C = 0（全零规则）             → LOW_CONFIDENCE（标记"缓存不可用"）
  └─ 异常检测触发                                → ANOMALY

LOW_CONFIDENCE
  ├─ 连续 M 次稳定采样且 d < d_low               → NORMAL
  ├─ 异常检测触发                                → ANOMALY
  └─ 置信度持续低（≥ RECAL_SAMPLES 次）          → RECALIBRATING

NORMAL
  ├─ 异常检测触发                                → ANOMALY
  ├─ d ≥ d_high                                  → LOW_CONFIDENCE
  └─ 距上次命中时间 > TTL 且本次 C 下降           → TTL_EXPIRED      ← v6.0 新增

TTL_EXPIRED                                                    ← v6.0 新增
  ├─ 下一次请求 C > 0                            → NORMAL（保留块粒度与置信度估计）
  └─ 连续 2 次 C = 0                             → LOW_CONFIDENCE

ANOMALY
  ├─ 排查完成、参数更新                          → RECALIBRATING
  └─ 无法恢复                                    → 保守模式（持续 LOW_CONFIDENCE）

RECALIBRATING
  ├─ 主动探测采样完成                            → NORMAL / LOW_CONFIDENCE
  └─ 仍异常                                      → ANOMALY
```

### 12.2.3 TTL_EXPIRED 的语义（v6.0 修订 D-10）


v5.0 的 16.4 规定"TTL 过期 → 重置 Z2 为 COLD_START"。问题：COLD_START 需要 `N_min = 5` 次采样才能回 NORMAL，而服务商 TTL 普遍 5–60 分钟。用户每次离开超过 TTL 再回来，Z2 都会退化为保守态，8.6 的可修改边界取 `CP_upper + 余量 + B`（多保守一个块粒度）——虽然不影响尾注位置，但**这段时间内所有 S0 更新都会被挡在门外或被迫升 L4**。

v6.0 的修订：TTL 过期是**正常事件**，不是异常。TTL_EXPIRED 只做两件事：

1. 把"缓存可用"标记为 false（本次请求的 `cached_tokens` 预期为 0，不参与波动度计算）；
2. 保留上一次的块粒度估计、最小缓存长度估计、置信度历史。

下一次请求命中后**直接回到 NORMAL**，不经过 COLD_START 的 5 次采样。这样用户的每次会话恢复只付出一次冷启动成本，而非 5 次。

### 12.2.4 规则优先级（v6.0 明确 D-11）

v5.0 的 8.2 中，"样本数 ≥ N_min 且 d < d_low → NORMAL"与"连续 N_min 次 C = 0 → LOW_CONFIDENCE"在 C 恒为 0 时**同时成立**（μ=0, σ=0 → CV=0 < CV_low），未规定优先级，实现会分叉。

v6.0 规定优先级：

```
1. 异常检测规则（最高优先级，直接进 ANOMALY）
2. 全零规则（C 恒为 0 → LOW_CONFIDENCE，不判 NORMAL）
3. TTL 规则
4. 波动度规则（d 与 d_low/d_high 比较）
5. 样本量规则（N_min / M）
```

即：**全零规则优先于波动度规则**。理由是：C 恒为 0 意味着"完全没有命中"，波动度定义为 0 是"退化"而不是"稳定"。

| **`batch_layout`** | v6.0：本轮 R 段的批划分（每批起止与哈希） | 新增 |

### 12.3.2 语义归一化规则表

```
cached_tokens_raw 须归一化为 cached_tokens_normalized 后方可参与反推。
```

| 服务商语义 | 原始字段含义 | 归一化规则 | 备注 |
|---|---|---|---|
| 仅前缀缓存命中 | 仅命中部分 | `normalized = raw` | 标准语义 |
| 含缓存写入 | 命中 + 写入 | `normalized = raw − cache_write_tokens` | 需单独采集写入 token；**写入 token 另计入 16.2 的成本模型** |
| 按块计费 | 按块向上取整 | `normalized = raw`，估计时按块边界处理 | 块粒度参与反推 |
| 多级缓存合并 | 多级命中之和 | `normalized = raw`，分层建模 | 见 12.3.3 |
| 字段缺失 | 无该字段 | `normalized = 0`，标记不可用 | 不参与反推 |

**归一化后须满足 `0 ≤ normalized ≤ prompt_tokens`。若越界，标记异常，进入 ANOMALY。**

**（v6.0 修订）** v5.0 只说"需单独采集写入 token"，但采集到的写入 token **从未进入任何成本公式**。v6.0 明确：写入 token 计入 16.2 的 `Cost_request`，并作为"含缓存写入"服务商的成本溢价依据（见 5.4 的 Anthropic 1.25×/2×）。

### 12.3.3 多级缓存分层建模

```
对每级 i：
  C_i = 该级命中 token 数
  分别维护 Z2 状态机实例
最终缓存点 = max_i(该级缓存点)
```

若无法分层采集，按合并值保守处理，可修改边界取最保守层级。

## 12.4 波动度度量（F8，v6.0 替换 CV）

### 12.4.1 v5.0 的 CV 度量与其问题

v5.0：`CV = σ / max(μ, ε)`，`CV_low = 0.05`，`CV_high = 0.15`。


问题：CV 是**相对**度量，其可检测下限随 μ 缩小。当 μ=5000 时，`CV_low=0.05` 对应 σ=250，约等于 2 个 OpenAI 块（128）。也就是说：**小于约 2 个块的缓存点漂移会被判为"方差小 → NORMAL"**，而 12.6 的安全余量恰恰取 1–2 个块。两处阈值一个按相对比例、一个按绝对 token，无法互相校验。

更根本的问题是：CV 把"缓存点估计的绝对不确定性"与"缓存点的量级"耦合在一起，而本架构真正关心的恰恰是**绝对不确定性是否超过一个块**。

### 12.4.2 v6.0 的绝对度量

```
d = max(C_1..C_K) − min(C_1..C_K)                (F8)

其中 K = 最近 K 次采样（默认 5 = N_min），C_i 为归一化后的命中 token 数
```

判定阈值（与块粒度挂钩，不再与 μ 挂钩）：

```
d_low  = B                 （一个块粒度的抖动 = 正常的块量化噪声）
d_high = 2·B + block_buffer（超过两个块 + buffer = 异常波动）
```

**代入默认参数**：OpenAI（B=128，block_buffer=256）→ `d_low = 128`，`d_high = 512`。DeepSeek（B=64）→ `d_low = 64`，`d_high = 384`。

**优点**：
1. 与 12.6 的安全余量同量纲（都是"块"），可以互相校验；
2. 不依赖 μ，小缓存点与大缓存点的判定标准一致；
3. 全零样本（C 恒为 0）时 `d = 0 < d_low`，但按 12.2.4 的优先级，全零规则先判定，不会被误判为 NORMAL。

### 12.4.3 保留 CV 作为辅助指标

CV 仍可记录（用于 21.3 的"块粒度估计稳定期一致率"），但**不再参与状态迁移判定**。

## 12.5 反推算法

```
记 L_z1 = |Z1|，L_z3 = |Z3|，C = cached_tokens_normalized

若 C = 0：
  ├─ 请求短于最小缓存长度 → 非异常（记录 short_request 标记）
  ├─ service_cache_key_snapshot 变化 → 参数变化（记录，不判异常）
  ├─ 首次请求或写入延迟 → 非异常
  ├─ TTL 过期（12.2.3）→ 非异常（进 TTL_EXPIRED）
  └─ 否则 → 疑似 P 段漂移或服务商异常

若 0 < C < L_z1：
  ├─ 块对齐导致部分命中 → 以块粒度解释
  ├─ P 段漂移 → 四重校验排查（7.3）
  ├─ 最小缓存长度边界 → 以最小长度解释
  └─ service_cache_key_snapshot 变化 → 参数排查

若 C ≥ L_z1：
  Z3 命中部分 ≈ C − L_z1
  缓存点区间 = [L_z1, L_z1 + min(C − L_z1, L_z3)]
  结合块粒度估计将区间收窄至块边界
```

**（v6.0 明确）** 反推的返回值语义：

```
estimate_cache_point()  返回区间【下界】，向下取整到块边界 → 用于记账（R_rec 的参考）
estimate_upper_bound()  返回区间【上界】                     → 用于决策（B_mod = CP_upper + margin）
```

v5.0 的 11.2 伪代码调用 `estimate_cache_point()` 来做位置判定，但没有规定它返回上界还是下界——取不同端点会导致"情形 B 永不触发"与"每次都升 L4"两种相反行为。v6.0 把这个歧义消除。

**（v6.0 修订 D-5）** S0/S1 的三态判定（9.3.1）不使用 `estimate_cache_point()`，而使用：

```
CP_align = floor(CP_lower / B) * B      用于判断"段末端是否已完全在缓存点之后"
CP_upper                                 用于判断"段起点是否可能被覆盖"
```

即：**判断"是否被覆盖"用上界（保守，宁高），判断"是否完全未覆盖"用下界（保守，宁低）**。这是三态判定的正确用法。

## 12.6 保守后界判定表

安全余量定义：

```
block_buffer = 固定 buffer，默认 256 tokens
安全余量 margin = max(B, block_buffer)                 (F9)
```

即安全余量本身已包含一个块粒度（当块粒度 > buffer 时）或一个 buffer（当块粒度 < buffer 时）。

| 条件 | 判定 | 可修改边界 B_mod 取值 | 说明 |
|---|---|---|---|
| NORMAL，C 远离块边界（距离 ≥ B/2） | 高置信 | `CP_upper + margin` | margin 已含一个块或 buffer |
| NORMAL，C 接近块边界（距离 < B/2） | 中置信 | `CP_upper + margin + B` | 额外一个块，双重保守 |
| LOW_CONFIDENCE | 低置信 | `CP_upper + margin + B` | 与中置信同口径 |
| **TTL_EXPIRED** | 缓存刚失效 | `L_z1 + margin + B` | v6.0：等同 LOW，因为下一次请求必然全冷 |
| ANOMALY | 异常 | `L_z1 + margin + B` | 取 Z3 起点 + margin + B |
| RECALIBRATING | 校准中 | `CP_upper + margin + B` | 同低置信 |
| 块粒度未知 | 未知 | `CP_upper + 512` | v5.0 的 A4 修订保留；但见下方澄清 |

### 12.6.1 "块粒度未知 → CP_upper + 512" 的澄清（v6.0 修正 v5.0 的 A4）

v5.0 的 8.6 表末行写"块粒度未知 → high + 512"，且 A4 修订说明称"512 = 2 × 安全余量初始值（默认 256），不再额外叠加'+块粒度'"。这句话有两处歧义：

1. **加法基**：`high` 到底是 `C` 还是 `CP_upper`？v5.0 从未定义。v6.0 明确为 `CP_upper`。
2. **512 的归属**：是"安全余量变成 512"，还是"边界额外加 512"？两种读法差一个块粒度（128–2048 token），而这个差值恰好决定 S0 是否被判为情形 C。

v6.0 统一为：

```
块粒度未知时：
    margin = 512                （即 2 × block_buffer，不再用 F9）
    B_mod  = CP_upper + margin  （不再额外 + B）
```

**理由**：块粒度未知时，真正的风险是"真实块粒度可能高达 2048"（候选集上限）。512 是"已知最小块 64 的 8 倍、已知最大块 2048 的 1/4"，是折中。若实测发现块粒度可达 2048，应更新候选集上限并相应放大 margin。

## 12.7 块粒度估计与候选集外检测

### 12.7.1 适用前提（G2 结论保留并前置）

**GCD 估计方法仅对"返回值严格为块整数倍"的服务商有效**（OpenAI、DeepSeek）。对断点式缓存（Anthropic `cache_control`，命中长度任意），GCD 恒返回 1，退化为 `block_buffer` 兜底。

**优先方法**：连续采样 C 值，观察离散分布。若 C 值集中于 `{0, B, 2B, 3B, …}`，则块粒度估计为 B。离散分布检测优先于 GCD。

**补充方法**：当样本数不足或分布不明显时，使用最近 20 次采样的**最大公约数**作为候选块粒度。

**块粒度候选集**：`{64, 128, 256, 512, 1024, 2048}`。

### 12.7.2 候选集外检测

若采样值无法用候选集中的任何 B 解释（残差 > B/4 的样本占比超过 20%），则：

1. 标记"候选集外块粒度"；
2. 取最近 20 次采样的最大公约数作为候选块粒度；
3. 仍无法解释时，退化为无块粒度假设，按 12.6.1 处理（margin = 512）。

## 12.8 异常检测矩阵

| 异常 | 检测条件 | 处理 |
|---|---|---|
| P 段漂移字节 | C < L_z1 且四重校验不一致 | 字节级 diff，告警，L4 |
| 真实缓存键变化 | C 下降且 `service_cache_key_snapshot` 变化 | 记录，不判漂移 |
| 最小缓存长度变化 | 短前缀突然不命中 | 调整短请求策略（12.10） |
| 块粒度变化 | C 值离散分布变化 | 更新块粒度估计 |
| 候选集外块粒度 | 残差超限 | 触发 12.7.2 |
| 缓存写入延迟 | 首次 C=0，后续 C>0 | 延迟期内不判异常 |
| 命中字段语义差异 | 跨服务商对比异常 | 按 12.3.2 归一化解释 |
| 尾窗越界 | C > L_z1 + L_z3 | 检查估计长度或服务商行为 |
| 多级缓存 | C 值出现多档 | 按 12.3.3 分层建模 |
| TTL 过期 | 有上次命中记录、C 下降、缓存键不变、距上次命中 > TTL | **进 TTL_EXPIRED，不判异常**（v6.0） |
| 从未命中 | 无上次命中记录 | 按 COLD_START 处理，不判 TTL |
| 全零样本 | 连续 N_min 次 C=0 且满足全零规则 | 标记"缓存不可用"，进入 LOW_CONFIDENCE |
| **批边界违反（v6.0）** | R 的左端落在批内部（I3 校验失败） | **立即告警**：该会话的 Z2 观测不可信，缓存点估计回退到保守值，并记录实施缺陷 |

最后一行是 v6.0 新增的关键异常：它把一个"实现错误"转化为**可检测的运行时信号**。v5.0 无法发现这类错误，因为 I3 根本不存在。

## 12.9 状态存储与作用域（v6.0 新增作用域定义）

### 12.9.1 状态作用域

v5.0 的 8.9 列出了 Z2 状态的字段，但**没有声明作用域**。在并发多会话场景下，不同会话共享同一 P 段（相同 `tools_hash`、`system_hash`、采样参数），它们的请求会互相改写服务端的缓存状态，导致一个会话的观测污染另一个会话。

v6.0 规定 Z2 状态的作用域键：

```
z2_scope_key = (provider, model, tools_hash, system_hash, sampling_params_hash, layout)
```

**注意：会话 ID 不在键内。** 原因是前缀缓存是**跨会话共享**的——两个会话若 P 段相同，它们的 P 段缓存是同一份。若把会话 ID 放进键，就会重复学习同一份服务端行为。

**推论**：
- 同一作用域内的多个会话，观测数据可以合并统计（提高收敛速度）；
- 但**可修改边界是共享的**：一个会话的动作会改变另一会话下次请求的命中情况。因此 4.7 要求同作用域的请求串行化；
- 异常归因必须区分"本会话造成的失效"与"其他会话造成的失效"（通过 `batch_layout` 与时间戳近似归因）。

### 12.9.2 状态字段

```
当前状态、估计区间、置信度、块粒度估计、最小缓存长度估计、
最近 N 次采样（含 d 值）、异常计数、上次校准时间、
observation_snapshot 历史、service_cache_key_snapshot 历史、
服务商适配参数、TTL 状态、上次命中时间、
v6.0 新增：z2_scope_key、批布局历史、I3 校验结果历史
```

作为运行时数据存储，不进入 P 段，不参与设计常量。

## 12.10 最小缓存长度与短请求策略

若 `L_z1 < min_cache_length`（服务商最小可缓存长度，按模型取值，见 5.4）：

1. 禁止依赖缓存收益做注入决策；注入决策退化为纯价值排序。
2. **短请求合并策略**：若连续短请求可合并为一次调用，则合并后触发缓存。
3. 标记该会话为"低缓存收益"，降低 Z2 观测频率。
4. 短请求合并的语义与延迟约束：合并须满足——语义上不产生跨请求依赖冲突；延迟上合并后单次调用时间不超过用户可接受阈值。合并失败时保留为独立短请求。

**（v6.0 补充）** `min_cache_length` 必须按 (service, model) 二维取值，不能是一个常量。Anthropic 的分档（512/1024/2048）使得同一 provider 下不同模型的门槛可以差 4 倍。

# 第 13 章 成本模型（v6.0 重构）

> **本章是 v6.0 相对 v5.0 的第二个重大重构。**v5.0 的成本公式把"请求规模"与"边际成本"混在一个式子里（缺陷 D-2），并在多处重复计入同一批 token（F2 计 R，19.2 又计 R 尾窗）。本章把成本拆成**两个口径**，并明确规定每个口径的用途与禁止用途。

## 13.1 两个口径（v6.0 核心定义）

### 13.1.1 口径一：请求规模（Request Magnitude）

```
Cost_request(t) = prompt_tokens(t) − cached_tokens(t)                    (F-R1)
                = 本轮未被缓存命中的 token 数
```

**用途**：计费、审计、21.3 的指标统计（"Z3 尾窗重算占比"的分母是 `prompt_tokens`，分子是本式）。

**性质**：
- 可直接由服务商返回字段计算，无需任何估计；
- 与时间无关（同一请求无论何时发出都相同）；
- **不可用于决策**（因为它反映的是"这一轮的整体开销"，不是"这个决策带来的增量"）。

### 13.1.2 口径二：边际成本（Marginal Cost）

```
Cost_marginal(t, decision) = Cost_request(t) − Cost_request(t ‖ decision=identity)   (F-R2)
```

即：**这个决策相对于"什么都不做"多花了多少**。

**用途**：决策、价值评估（14.2）、Z4 推益判定（11.3.4）、审批门槛。

**性质**：
- 需要反事实推断（"如果我不做这个决策，本轮会重算多少"）；
- 对尾部追加类决策，`Cost_marginal = inserted_tokens`（因为不追加的话本轮就少这么多 token）；
- 对段替换类决策，`Cost_marginal = 该段起点之后的全部内容`（因为不替换的话这部分能命中）。

### 13.1.3 三个口径的对照表

| 决策 | `Cost_request` | `Cost_marginal` | 差异来源 |
|---|---|---|---|
| 尾部追加 300 token | 本轮 `prompt − cached` | **300** | 不追加时少 300 token |
| S1 替换（｜S1｜=2048，slot=300） | 同上 | **2348** | 从 S1 起点起的失效 |
| S0 替换（情形 C） | 同上 | **｜S0_new｜ + ｜R｜ + ｜S1｜ + ｜slot｜** | 从 S0 起点起的失效 |
| S0 替换（情形 A） | 同上 | **｜S0_new｜** | S0 本就在缓存外 |
| 回顾性注入 | 同上 | **prompt_length** | 整条前缀失效 |
| 不注入 | 同上 | **0** | — |

**v5.0 的问题**：F2（S0 情形 A）= `α·(|S0|+|R|+|S1|+|slot|)` 实际上是 `Cost_request` 的一部分，却被当作 `Cost_marginal` 用于决策。这使决策系统以为"每次 S0 更新都要花整个尾窗"，而实际上情形 A 下 S0 本就在缓存外，边际代价只是新 S0 的长度。**后果**：S0 更新被判为"永远不划算"，价值模型（14.2）把 S0 分支钉死在高成本档，进而导致 D-3 的不可达问题。

### 13.1.4 记账纪律（v6.0 强制）

```
规则 1：审计中必须【同时】记录两个口径，字段名分别为
        recompute_request 与 recompute_marginal。
规则 2：所有成本模型公式（F5–F7）默认为边际口径，须显式标注 `_marg`。
规则 3：禁止用 Cost_marginal 的累加值作为"总成本"——总成本只能是 Cost_request 的累加。
规则 4：禁止用 Cost_request 直接做"这个注入值不值"的判断——那必须用 Cost_marginal。
```

## 13.2 成本模型（全量）

### 13.2.1 公共项

```
α      重算 token 的当量系数（默认 1.0，即重算 token 按 1 token 当量计）
β      摘要生成 token 的系数（v6.0：须区分输入/输出，见 13.3）
γ      索引写入次数 → token 当量（阶段一暂用 100 tokens/次）
δ      CPU 秒 → token 当量（阶段一暂用 200 tokens/CPU 秒）
ε_time 审批延迟毫秒 → token 当量（阶段一暂用 0.1 tokens/ms）
```

### 13.2.2 P 段变更（F-P）

```
Cost_marg(P 变更) =
    α · (|P| + |Z3|)                       ← 整条 prompt 失效
  + ε_time · approval_latency_ms
  + γ · audit_write_count
```

### 13.2.3 S0 变更（F4，三态边际口径）

```
Cost_marg(S0 更新) =
      α · Recompute_S0_marg(state)
    + β_in · summary_input_tokens            ← 摘要生成的输入（上下文）
    + β_out · summary_output_tokens          ← 摘要生成的输出（v6.0：与输入分开计价）
    + γ · index_write_count
    + δ · dedup_cpu_seconds
    + ε_time · approval_latency_ms

其中：
    Recompute_S0_marg(A) = |S0_new|
    Recompute_S0_marg(B) = (CP_align − |P|) + |S0_new|
    Recompute_S0_marg(C) = |S0_new| + |R| + |S1| + |slot|
```

### 13.2.4 S1 变更（F5）

```
Cost_marg(S1 更新) =
    α · (|S1_new| + |slot|)
  + γ · index_write_count
  + ε_time · approval_latency_ms
```

（S1 不重算 R 与 S0。若 S1 落入缓存覆盖区，按 9.3 的三态处理并升级审批级别；此时边际成本应加上 `S1_start` 之前的失效量，但该情况由 12.6 的 B_mod 保守边界基本排除。）

### 13.2.5 R 尾部微调（F6）

```
Cost_marg(R 追加到活跃批) =
    α · ΔR_add
  + δ · dedup_cpu_seconds

Cost_marg(R 批断) =
    0                                      ← 批断不改变任何已有字节（8.3.2）

Cost_marg(R 淘汰最旧批) =
    α · |B_evicted|                        ← 只影响 R 的左端
                                           (F6)
```

**v5.0 的 F5 写作 `α·(尾部增量 + |S1| + |slot|)`**，理由是"R 尾部追加会改变其后 S1 与注入槽的位置，重算范围必须包含 S1 + slot"。这个理由**只在 S1 与 slot 位于 R 之后且随 R 移动时成立**——而实际上 S1 与 slot 是**固定长度段**，R 变长只是使 S1 的起始偏移变大，S1 与 slot 自身的**内容**不变。在缓存匹配中，匹配是逐字节的：`P‖S0‖R_new‖S1‖slot` 与 `P‖S0‖R_old‖S1‖slot` 的公共前缀在 `R_old` 结束处中断，之后的内容（`R` 的新增部分到 `S1` 到 `slot`）全部未命中。

所以 v5.0 的 F5 在**绝对口径**下是对的（`ΔR + |S1| + |slot|` 确实是本轮未命中的尾部），但在**边际口径**下是错的（`|S1| + |slot|` 无论 R 是否追加都不会命中）。v6.0 按 13.1.4 的规则 2 采用边际口径，因此 R 追加的边际成本 = `ΔR_add`。

### 13.2.6 注入槽写入（F7）

```
Cost_marg(slot 追加) =
    α · inserted_tokens                     ← 满足 I5 时即为真实边际
  + δ · dedup_cpu_seconds

Cost_marg(slot 批断) =
    α · (|S1| + |slot|)                     ← 一次整段重建
  + γ · index_write_count
```

### 13.2.7 Z4 动作（F-Z4）

```
Cost_marg(Z4 清理槽)     = 0
Cost_marg(Z4 压缩尾窗)   ≈ α · 0.2·|Z3| + β_out · summary_output_tokens
Cost_marg(Z4 窗口外转移) ≈ α · |Z3| + β_out · summary_output_tokens + γ·index_write
Cost_marg(Z4 重建 S0)    = Cost_marg(S0 更新)
Cost_marg(Z4 推进缓存点) ≈ α · |Z3|（一次性整窗重算）
```

### 13.2.8 回顾性注入（F-L5）

```
Cost_marg(回顾性) =
    α · prompt_length                       ← 整条前缀失效
  + β_in · generation_input + β_out · generation_output
  + γ · index_write_count
  + ε_time · approval_latency_ms
  + 白名单与访问审查的开销
```

## 13.3 非 token 成本的换算（v6.0 修订）

### 13.3.1 输入/输出 token 的价差

v5.0 用单一的 `β = 1.0` 把摘要生成 token 与重算 token 等价处理。这忽略了一个重要事实：**输出 token 的单价通常是输入的 3–5 倍**。摘要生成是输出侧的，被低估了 3–5 倍。

v6.0 规定：

```
β_in  = 1.0    （摘要生成的输入，按输入 token 当量）
β_out = 3.0    （摘要生成的输出，初始值；阶段二标定，范围 2–5）
```

### 13.3.2 缓存写入溢价

Anthropic 的缓存写入按 1.25×（5 分钟）或 2×（1 小时）计价。v6.0 规定：

```
Cost_request 在含写入语义的服务商上须乘以写入溢价系数：
    write_premium(Anthropic, 5m) = 1.25
    write_premium(Anthropic, 1h) = 2.0
    write_premium(OpenAI)        = 1.0（隐式缓存，无写入费）
    write_premium(DeepSeek)      = 1.0
```

该系数进入 16.2 的 `Cost_request` 计算，**不进入决策**（因为它对所有决策同等作用，不影响相对排序）。

### 13.3.3 对齐损失

块对齐造成的额外重算是"由对齐而非语义导致的成本"。v6.0 单列：

```
Cost_align(t) = (B − 1) / 2      期望值（均摊到每个段边界）
实际值 = 观测到的 (cached_tokens 未被 B 整除的余数)
```

该成本不进入 F4–F7 的任一公式（因为它不属于任何单个决策），而是作为 prompt 级别的常数项进入 21.3 的统计。

## 13.4 总成本（F-Total）

```
总成本（一段时间窗口 T 内） =
    Σ_{t ∈ T} Cost_request(t)
  + Σ 摘要生成成本
  + Σ 索引写入成本
  + Σ Z4 动作成本
  + Σ 回顾性注入成本
  + Σ 审批延迟成本
```

**注意**：本式**不**再加"S0 变更成本""R 尾窗重算成本""S1 更新成本""注入槽重算成本"——这些已经被 `Cost_request(t)` 包含了。v5.0 的 19.2 把它们并列相加，导致重复计入。

**验证方法（v6.0 新增）**：若实现正确，应有

```
Σ Cost_request = Σ_cached (1·cached) + Σ_miss (miss_multiplier · miss)
并且 Σ Cost_marg(所有决策) ≈ Σ Cost_request − Cost_request(空跑基线)
```

阶段三须对此做一致性校验（21.3 的"成本口径闭合"检查项）。

## 13.5 与 v5.0 公式的对照

| v5.0 公式 | v6.0 处理 | 原因 |
|---|---|---|
| F2：S0 情形 A = α·(\|S0\|+\|R\|+\|S1\|+\|slot\|) | 改为 `α·\|S0_new\|` | 绝对口径被误用作决策口径（13.1） |
| F3：S0 情形 B = F2 + α·cache_invalidation_cost | 合并入三态 F4，避免重复计 | 原式重复计入 R/S1/slot |

# 第 14 章 价值模型与预算—成本—价值一致性（v6.0 重构）

> v5.0 的价值模型有三处结构性缺陷：（1）成本项恒为负，使 value 上界只有 0.72–0.78，而门槛设在 0.8/0.9，两条最贵的路径因此不可达；（2）分档归一化后成本项的区分力仍然只有 0.06，压不过相关性权重 0.35；（3）决策树与分级表在 [0.8, 0.9) 档对 S1 留了空洞。v6.0 重写为乘性惩罚模型。

## 14.1 单位与归一化（v6.0 重写）

| 概念 | 单位 | 归一化方式 |
|---|---|---|
| 注入槽预算 | token 绝对值 | — |
| 重算成本（原始） | token 当量 | 绝对值，用于成本记录与审计 |
| **重算成本（模型输入）** | 无量纲 | **连续归一化 `norm_cost ∈ [0,1]`，见 14.1.1** |
| 摘要生成成本 | token 当量 | 绝对值 |
| 索引写入成本 | 次 | 乘 γ 转 token 当量 |
| CPU 计算成本 | CPU 秒 | 乘 δ 转 token 当量 |
| 审批延迟成本 | 毫秒 | 乘 ε_time 转 token 当量 |
| 注入价值 | 无量纲 | 见 14.2 |

### 14.1.1 连续归一化（替代 v5.0 的分档归一化）

v5.0 的 C2 修订把线性归一化改为分档（`<1k→0.1, 1k–8k→0.4, 8k–32k→0.7, ≥32k→1.0`），理由是"线性归一化在量级差 123 倍时使 S0 项饱和、尾注项近零"。但分档只是把 123 倍压到 2.5 倍，而在 `w = 0.10` 的权重下，这 2.5 倍对 value 的影响只有 0.06——仍然压不过相关性权重（0.35）。

v6.0 改为**对数压缩的连续映射**：

```
norm_cost(c) = log(1 + c / c_ref) / log(1 + c_max / c_ref)                (F-C)
```

其中：
```
c_ref = |R_window| / 6        （默认 12800/6 ≈ 2133）—  "一个段替换量级的成本"
c_max = |P| + |Z3|            （默认 21100）        —  整条 prompt 长度
```

**为什么 `c_ref` 取 `|R_window|/6` 而不是 `max_tokens_per_injection`**：若 `c_ref` 取 512，则 S0 情形 C（17100）的 `norm_cost` 已达 0.945，`value_max` 只剩 0.35，S0 更新在任何 λ 下都不可达——这正是 v5.0 的缺陷在换一种形式后复发。取 `|R_window|/6` 使"一个段替换"落在 `norm_cost ≈ 0.3`，S0 更新仍有约 0.71 的可达 value。

**性质**：
- `norm_cost(0) = 0`（免费操作无惩罚）；
- `norm_cost(c_ref) ≈ 0.28`；
- `norm_cost(c_max) = 1.0`（整窗重算惩罚 100%）；
- **单调、连续、无饱和**：`c` 从 300 增到 17100 时，`norm_cost` 从 0.06 增到 0.92，跨度 0.86（v5.0 分档方案为 0.9 但只有 4 个离散取值）。

**代入默认参数**（`c_ref=2133`、`c_max=21100`），**λ = 0.40**：

| 操作 | 边际成本 c | `norm_cost` | `value_max` = 0.80·(1 − 0.40·norm) |
|---|---|---|---|
| 尾注 300 token | 300 | 0.057 | **0.782** |
| 尾注 512 token | 512 | 0.091 | **0.771** |
| S1 替换 | 2348 | 0.310 | **0.701** |
| S0 情形 A | 2048 | 0.281 | **0.710** |
| S0 情形 C | 17100 | 0.921 | **0.505** |
| 回顾性注入 | 21100 | 1.000 | **0.480** |

## 14.2 价值模型（F10，v6.0 重写）

### 14.2.1 公式

```
value = (w1·recall_relevance + w2·task_criticality + w3·timeliness)
        × (1 − λ · norm_cost(decision))                                   (F10)

其中：
  recall_relevance  ∈ [0,1]   召回相关性（记忆后端给出）
  task_criticality  ∈ [0,1]   任务关键性
  timeliness        ∈ [0,1]   时效性
  w1 = 0.35, w2 = 0.30, w3 = 0.15   （Σw = 0.80，保留 0.20 作为"完全无关"的余量）
  norm_cost         ∈ [0,1]   按 14.1.1 计算
  λ = 0.40                    成本惩罚强度
```

### 14.2.2 可达性验证（v6.0 强制要求）

理想候选（`rel = crit = time = 1`）下：

```
value_max = (0.35 + 0.30 + 0.15) × (1 − λ·norm_cost)
          = 0.80 × (1 − 0.40·norm_cost)
```

| 决策类型 | `norm_cost` | `value_max` | 门槛 | 可达？ |
|---|---|---|---|---|
| 尾注（300 token） | 0.057 | **0.782** | 0.45 | ✓ |
| 尾注（512 token） | 0.091 | 0.771 | 0.45 | ✓ |
| S1 替换 | 0.310 | **0.701** | 0.50 | ✓ |
| S0 情形 A | 0.281 | **0.710** | 0.60 | ✓ |
| S0 情形 C | 0.921 | **0.505** | 0.60 | **✗**（临界，见下） |
| 回顾性注入 | 1.000 | 0.480 | 见 14.4 | — |

**两点说明**：

1. **S0 情形 C 仍处在门槛边缘**。这不是模型缺陷，而是成本事实：情形 C 下 S0 更新等价于整窗失效，其代价本就与"放弃一次缓存"相当。v6.0 的处理是把情形 C 的审批直接定为 L4（9.3.3），并要求 value 达 0.60 才可提交——即**只有在语义上极其重要的 S0 更新才会走情形 C**。多数 S0 更新应发生在情形 A（S0 未被缓存时）——这要求 S0 更新时机与 R 窗口状态联动（见 9.2.1 的补充条件）。

2. **回顾性注入不再由 value 门槛解锁**。它的成本是整窗重算，按代价公式它"永远不划算"；v6.0 把它从"由 value 门槛解锁"改为"由 L5 审批 + 白名单 + 重算预算解锁"（14.4）。**value 门槛只是它的必要条件之一（≥0.30），不是充分条件**。这是更诚实的建模：value 模型不足以表达"这个回顾性修改在语义上有多重要"，该判断交给人工。

### 14.2.3 分级表（v6.0 重设）

| value 区间 | 允许操作 | 审批级别 | 说明 |
|---|---|---|---|
| `< 0.45` | 丢弃 | — | v6.0：丢弃线从 0.30 提到 0.45（低于此值的候选连尾注都不值得） |
| `[0.45, 0.55)` | 仅尾注 | L0/L1 | 系统规则 |
| `[0.55, 0.65)` | 尾注、S1 更新 | L0/L1/L1.5 | |
| `[0.65, 0.80)` | 尾注、S1 更新、S0 更新（情形 A） | + L2 | 值班人 |
| `[0.80, 1.0]` | 上述 + S0 更新（情形 B/C，需 L4） | + L4 | 安全负责人 |
| 任意值 | 回顾性注入 | L5 + 白名单 + 重算预算 | **v6.0：不设 value 上界门槛，只设下限 0.30** |

**阈值推导（v6.0 给出每个门槛的来历，避免再出现"门槛拍脑袋、模型拍不到"的循环）**：

| 门槛 | 取值 | 推导 |
|---|---|---|
| 尾注门槛 | 0.45 | 尾注 `value_max = 0.782`；取 `0.45 ≈ 0.782 × 0.58`，即"相关性各项平均达 58%"即可注入 |
| S1 门槛 | 0.55 | S1 `value_max = 0.701`；取 `0.55 ≈ 0.701 × 0.78` |
| S0（情形 A）门槛 | 0.65 | `value_max = 0.710`；留 8% 余量 → 0.65 |
| S0（情形 B/C）门槛 | 0.80 | `value_max = 0.505`（情形 C）；**0.80 高于上界，因此情形 C 实质上只允许人工显式发起**（walk 人工路径，不走自动值判定） |
| 回顾性下限 | 0.30 | 只用于"明显无价值则直接拒绝"，不用于准入 |

**与 v5.0 的对照**：

| v5.0 门槛 | v6.0 门槛 | 变更理由 |
|---|---|---|
| `< 0.3` 丢弃 | `< 0.45` 丢弃 | 新模型下尾注 value 上界 0.782，0.3 太宽 |
| `[0.3, 0.6)` 尾注 | `[0.45, 0.55)` 尾注 | — |
| `[0.6, 0.8)` S1 | `[0.55, 0.65)` S1 | 让 S1 更廉价可及（并取消上界，见 15.2） |
| `≥0.8` S0 | `≥0.65` S0（情形 A）/ 情形 C 走人工 | 原 0.8 不可达 |
| `≥0.9` 回顾性 | **不设上界门槛**，改由 L5 链控制 | 原 0.9 不可达 |

### 14.2.4 权重与 λ 的标定

`w1..w3` 与 `λ` 均为初始值，阶段六校准。v6.0 要求校准后的值必须满足**可达性约束**：

```
∀ 决策类型 τ，若 τ 被设计为"可通过 value 自动解锁"：
    0.80 × (1 − λ·norm_cost(τ)) ≥ θ(τ)
```

不满足时有两种合法处理：
1. 调低 `θ(τ)`（让门槛贴合模型）；
2. 把 τ 从"自动解锁"改为"人工发起"（如情形 C 的 S0 更新）。

**不允许的处理**：保留不可达的门槛并声称"该路径由人工审批控制"——那样等于把一条自动路径静默降级为人工路径，与设计意图不符。

这条约束写入 21.3 的"框架一致性验证"，作为阶段三准出条件。

## 14.3 一致性检查表（v6.0 扩充）

| 检查项 | 规则 | 冲突处理 |
|---|---|---|
| 单次注入上限 vs 总预算 | 单次 ≤ 总预算 | 单次 > 总预算时取总预算 |
| 每轮次数 vs 总预算 | `max_injections × max_per_injection ≤ max_tokens_total_slot` | 不满足时按 10.3.1 处理 |
| 价值排序 vs 预算淘汰 | 价值高者优先保留 | 淘汰记录审计 |
| 审批记录 vs 实际淘汰 | 淘汰须与审批记录一致 | 不一致时冻结并告警 |
| 成本单位 | 全部转 token 当量 | 见 13.2 |
| 决策树 vs 分级表 | 决策树各分支须校验 value 区间 | 违反时冻结并告警 |
| **（v6.0）价值门槛可达性** | 见 14.2.4 | 不可达即视为配置错误，阻断阶段三准出 |
| **（v6.0）成本口径闭合** | `Σ Cost_request ≈ Σ_cached + Σ_miss·multiplier` | 偏差 > 1% 即告警 |
| **（v6.0）I7 快照一致性** | 同轮决策共用 `snapshot_id` | 不一致即冻结 |

## 14.4 回顾性注入的预算与频率

```
回顾性注入预算 = retrospective_budget_ratio × Σ_{最近 50 轮} Cost_request
                 = 0.05 × Σ ...

回顾性注入频率：retrospective_max_frequency_turns = 50
    即平均每 50 轮最多 1 次回顾性注入
白名单条目数：retrospective_whitelist_size = 3
```

每次回顾性注入前须校验：
1. 最近 50 轮内的回顾性重算量 ≤ 预算；
2. 距离上次回顾性注入 ≥ 50 轮（或经安全负责人显式豁免）；
3. 白名单命中（18.3）。

## 14.5 阶段三与阶段六的参数时序

价值模型权重（w1–w5、λ）与分级阈值在阶段六校准。阶段三准出项"预算—价值模型一致性验证通过"**不验证权重数值**，仅验证框架一致性：

- 单位与归一化规则可计算；
- 冲突处理顺序可执行；
- 审计字段完整；
- 决策树与分级表引用一致；
- **（v6.0）价值门槛可达性成立**（14.2.4）；
- **（v6.0）成本口径闭合**（14.3）。

阶段三使用附录 E 的"临时值"跑通框架；阶段六校准后覆盖为"最终值"。附录 E 标注两组值。

# 第 15 章 注入协议与失效分级

## 15.1 注入协议流程

```
1. 读取会话历史与记忆索引
2. 生成候选注入（类型标注：TAIL / S1_UPDATE / S0_UPDATE / RETROACTIVE）
3. 读取 Z2 状态、估计区间、置信度、可修改边界（B_mod）
4. 按 15.2 决策树判断目标位置，同时校验 value 区间
5. 按 10.3.1 的前置检查与冲突处理，不填充无效字节
6. 合成上下文并调用模型
7. 记录 cached_tokens 反馈，更新 Z2 状态机
8. Z3 预算耗尽 → 触发 Z4（按 11.3.4 判定）
9. 监控命中率与重算量，异常时排查
```

**（v6.0）** 第 2 步的"类型标注"是 v5.0 没有明说的关键：候选注入必须**在生成时就确定类型**，因为不同类型走不同路径、不同门槛、不同审批。v5.0 的 12.2 决策树让 value 决定类型（"属 S1 → 更新 S1"），这导致"高价值的 S1 更新无路可走"（见 15.2 的重设）。

## 15.2 决策树（v6.0 重设）

### 15.2.1 问题

v5.0 的 12.2 决策树有两个结构性问题：

1. **S1 分支只在 [0.6, 0.8) 出现**。高价值 S1 更新（value ≥ 0.8）在决策树中没有对应分支，只能落到"其他 → 写入注入槽"，即被降级为尾注。而 S1 更新恰恰是最便宜的高频操作（F5 成本 ≈ 2348，远低于 S0 的 17100）。让最便宜的更新无路可走，与"分级管理"的初衷相反。
2. **value 决定类型**。决策树用 value 区间反推"这应该是 S0 还是 S1 还是尾注"，但类型本应由候选的来源决定（进度/待办 → S1；阶段结论 → S0）。value 只是决定**是否值得**，不该决定**是什么**。

### 15.2.2 v6.0 决策树

```
候选注入 c（已标注类型）
  │
  ├─ c.value < 0.30 ─────────────────────────────→ 丢弃
  │
  ├─ c.type == TAIL_INJECTION
  │     ├─ c.value ≥ 0.45 → 写入注入槽（L1）
  │     └─ c.value < 0.45 → 丢弃
  │
  ├─ c.type == S1_UPDATE
  │     ├─ c.value ≥ 0.55 → 判定 S1 是否被缓存覆盖
  │     │     ├─ 未覆盖 → 更新 S1（L1.5）
  │     │     └─ 已覆盖 → 更新 S1（L2，值班人）
  │     └─ c.value < 0.55 → 降级为尾注（若 ≥0.45），否则丢弃
  │
  ├─ c.type == S0_UPDATE
  │     ├─ 判定三态（9.3.1）
  │     ├─ 情形 A：c.value ≥ 0.65 → L2 审批 → 更新 S0
  │     ├─ 情形 B/C：转人工发起（见 14.2.3，不走自动 value 判定）
  │     └─ 未达门槛 → 降级为尾注（若 ≥0.45），否则丢弃
  │
  └─ c.type == RETROACTIVE_INJECTION
        ├─ c.value ≥ 0.30 → 进入 L5 审批链（18.3 + 14.4）
        └─ c.value < 0.30 → 丢弃

关键变化（v6.0）：
  · S1 分支取消上界（v5.0 的 [0.6,0.8) 上限是造成"高价值 S1 无路"的直接原因）
  · 类型由候选来源决定，不由 value 反推
  · 回顾性注入只设下限 0.30，实际准入由审批链决定
```

### 15.2.3 降级规则

"降级为尾注"是决策树中的兜底路径。v6.0 规定：

```
降级条件：候选的 native 类型不可用（门槛未达或审批未过）
降级目标：TAIL_INJECTION
降级约束：
  1. 降级后仍须满足尾注门槛（0.45）
  2. 降级须记录 `degraded_from` 字段（用于 21.3 的"注入槽高价值占比"指标）
  3. 降级不得降级到"回顾性注入"或"S0 更新"——只能向更便宜的方向降
```

"只能向更便宜的方向降级"是一条重要的单调性约束：v5.0 的"回顾性 → 降级为尾注或 S0"允许向**更贵**的方向降级（尾注 → S0 更贵），这是不合理的。

## 15.3 失效分级（保留，补充说明）

| 级别 | 事件 | 成本 | 审批主体 |
|---|---|---|---|
| L0 | R 段尾部微调（追加到活跃批） | 低，仅 ΔR_add | 系统规则 |
| L1 | 注入槽写入（尾部追加） | 低，仅增量 | 系统规则 |
| L1.5 | S1 更新（缓存点之后） | 中低，`\|S1\|+\|slot\|` | 系统规则 |
| L2 | S0 更新（情形 A）/ S1 更新（缓存覆盖区） | 中，`\|S0\|` 或 `\|S1\|+\|slot\|` | 值班人 |
| L3 | Z4 推进缓存点 | 中高，批量重算 | 值班人 + 11.3.4 判定 |
| L4 | P 段变更 / tokenizer 版本变化（影响缓存键）/ S0 在缓存覆盖区更新（情形 B/C） | 高，整段或整窗失效 | 安全负责人 |
| L5 | 回顾性前缀前注入 | 最高，整条前缀失效 | 安全负责人 + 白名单 + 重算预算 |

**（v6.0）** L4 的定义从 v5.0 的"S0 在缓存覆盖区更新"扩展为"S0 在缓存覆盖区更新（情形 B/C）"。原因是 9.3.1 把情形 B/C 拆开后，情形 C（全覆盖）的实际失效范围更大，必须走 L4。详见 9.3.3。

## 15.4 缓存命中与失效协议

### 15.4.1 分区规则

| 区域 | 命中规则 | 失效规则 |
|---|---|---|
| P / Z1 | 四重校验稳定，常规注入不影响 | 仅 L4；禁止漂移字节 |
| S0 | 低频批量，变更视为显式失效 | L2（情形 A）或 L4（情形 B/C）；重算含 `\|S0\|+R+S1+槽`（情形 C）或 `\|S0\|`（情形 A） |

|---|---|---|

# 第 17 章 本地模型策略

## 17.1 与云端的差异

| 维度 | 云端 | 本地 |
|---|---|---|
| 缓存控制 | 不可直接指定 | 可自行决定 |
| 缓存粒度 | 服务商切块 | 可按段建索引 |
| 缓存点 | 观测量 | 可设计 |
| 拆分索引 | 通常不支持 | 支持 |
| 记录合成 | 通常不支持 | 支持 |
| 段间依赖 | 前缀哈希整体失效 | 可按段失效 |
| **不变式 I3** | **必需**（否则命中率崩溃） | **不必需**（段级索引下窗口前移只失效被淘汰段） |
| **不变式 I5/I6** | 必需 | 强烈建议（仍影响命中率，但不致命） |

**（v6.0 核心补充）** 本地实现绕过 I3 的原因是：段级 KV 索引按段存储，R 窗口前移时只使被淘汰批的 KV 失效，其余段的 KV 可继续复用。这正是第 3 章"本地模型可进一步利用段级缓存"的具体含义。因此**本地实现的稳态重算量下界显著低于云端**，且该下界与 W 无关。

## 17.2 段级索引

```
本地缓存索引：
├─ 稳定段索引（P）
├─ S0 摘要段索引
├─ R 窗口段索引（按批 B_1..B_n 分别索引）
├─ S1 状态段索引
└─ 注入槽段索引（按批断分段）
```

按段失效：
- 注入优先落注入槽 → 仅失效槽段；
- S1 更新仅失效 S1 与槽；
- S0 更新失效 S0 之后各段；
- R 批淘汰仅失效该批；
- P 不变。

**（v6.0）** 本地实现下，8.3 的批概念仍然有用但目的不同：云端用批来限制"前缀断点"，本地用批来限制"索引粒度"。建议本地批大小取 `|批| ≥ 1MB KV` 量级，以避免索引碎片化。

## 17.3 实现依赖与接口约束

| 依赖 | 说明 | 本文范围 |
|---|---|---|
| 段级 KV 缓存复用 | 按段保存与复用 K/V，依赖框架 prefix caching 能力 | 接口约束：本地推理层须暴露段级 KV 复用接口 |
| 跨段注意力一致性 | 段拼接后注意力正确，依赖框架分段 KV 拼接能力 | 接口约束：推理层须保证拼接语义 |
| 段级失效 | 局部失效不影响其他段，依赖索引与依赖图 | 接口约束：合成器须能按段触发失效 |
| 段间依赖图 | 记录段间依赖，自研 | 后端实现，不在本文范围；本文仅要求其存在且可查询 |
| 碎片化控制 | 段大小与复用率平衡，段粒度调优 | 后端实现，不在本文范围 |
| 缓存记录合成 | 按段合成缓存记录，自研或框架扩展 | 后端实现，不在本文范围 |

若框架不支持段级 KV 拼接，本地策略退化为**按段前缀缓存**：仍按 `P | S0 | R | S1 | slot` 顺序布局，但仅能做前缀复用，不能任意段失效。**此时本地退化为云端行为，必须遵守 I3。** 实施前须确认框架能力，并在阶段五准入时书面记录该判定。

## 17.4 本地仍遵守的原则

- P 段钉死且禁止漂移字节；
- S0 低频、S1 高频尾置；
- R 窗口内保留原文；
- token 预算不填充无效字节；
- Z4 溢出管理照常执行；
- **（v6.0）即使段级索引可用，仍建议遵守 I5（槽仅尾部淘汰）与 I6（S1 可预测替换）**——它们降低的是"失效范围的不确定性"，而不仅是命中率。

# 第 18 章 审批与审计

## 18.1 审批角色

| 角色 | 职责 | 适用级别 |
|---|---|---|
| 系统规则 | 自动审批，基于阈值与白名单；仅做前置校验，不单独构成高风险审批 | L0、L1、L1.5；L4 的前置校验 |
| 值班人 | 人工审批，处理规则未覆盖情形 | L2、L3 |
| 安全负责人 | 人工审批，处理高风险操作 | L4、L5 |

**（v6.0 澄清）** "系统规则仅做前置自动校验，不单独构成高风险审批"——原意是 L4/L5 不能由系统规则批准。v6.0 进一步明确：**系统规则可以"拒绝"，但不能"批准" L3 及以上的操作**。拒绝是安全的（保守），批准是危险的。

## 18.2 审批存储与不可篡改（F13）

```
存储结构：
  - 独立审计日志（与业务日志物理隔离）
  - 追加写入（append-only）
  - 每条记录计算审计哈希链：
      audit_h_i = hash(record_i ‖ audit_h_{i-1})     (F13)
      audit_h_0 = 固定初始值
  - 定期将 audit_h_latest 锚定到外部可信存储（只读对象存储的版本化快照）

防篡改机制：
  - 业务进程无删除/修改权限
  - 审计日志写入权限独立
  - 审计哈希链校验定时执行
  - 外部锚定防止内部篡改
```

审计哈希链符号 `audit_h_i` 与日志哈希链 `log_h_i`（11.3.6）区分。

**（v6.0 补充）** 审计记录的写入必须与决策**原子**：即"决策被采纳"与"审计记录已落盘"是同一事务的两个面。若审计写入失败，决策必须回滚（对应不变式 I8）。

## 18.3 白名单版本化与回滚

```
白名单结构：
  - 版本号
  - 条目列表（上限 3 条）
  - 每条目：触发条件、value 下限（≥0.30）、重算预算比例、有效期
  - 变更记录：变更人、变更时间、变更前后差异、审批记录

回滚流程：
  - 回滚操作本身作为审计事件记录
  - 回滚后白名单版本号递增
  - 回滚须安全负责人审批
```

**（v6.0 修订）** v5.0 的白名单条目写"value 阈值（≥0.9）"，该门槛在 v5.0 的计算模型下不可达（D-3）。v6.0 改为"value 下限 ≥0.30"——白名单的作用不再是"抬高价值门槛"，而是**限定哪些回顾性注入类型是允许的**，value 只作为最低有效性校验。

## 18.4 审批记录字段

| 字段 | 说明 |
|---|---|
| 事件级别（L2–L5） | — |
| 候选注入摘要 | 内容哈希 + 前 N 字符 |
| 价值评估结果 | 各分量与最终 value |
| 预计重算成本（token 当量） | **边际口径**（v6.0） |
| 预计重算成本（时间当量） | — |
| 审批角色 | — |
| 审批人/规则 | — |
| 审批时间 | — |
| 实际重算成本 | 事后回填，**同时记录两个口径** |
| 事后效果评估 | 任务成功率变化、召回命中率变化 |
| 审计哈希链前序哈希 | — |
| **`snapshot_id`** | v6.0：决策时快照 |
| **`invariants_ok`** | v6.0：决策时的不变式校验结果 |

## 18.5 审批延迟成本

审批延迟计入 S0/S1 成本模型（13.2.3、13.2.4），以时间当量计量。系统规则审批延迟默认 0；人工审批延迟默认按值班响应时间估计，阶段二标定。

**（v6.0 补充）** 审批延迟在**决策**中只影响 `Cost_marginal` 的常数项，不影响各候选之间的相对排序（因为同类候选的延迟相同）。因此它主要作用是**记录与事后分析**，不应当被用来区分候选。若某实现用审批延迟来"惩罚"某类候选，那是错误的用法——延迟不是被选出来的，是被审批流程强加的。

## 18.6 冻结与告警触发条件（v6.0 汇总）

以下任一情况触发**冻结合成上下文生成**（即停止接受新的注入决策，只允许读取）：

| 条件 | 来源 |
|---|---|
| 会话历史哈希链校验失败 | 11.3.6 |
| 审计记录与实际淘汰不一致 | 14.3 |
| 决策树分支与 value 区间不一致 | 14.3 |
| 同轮决策的 `snapshot_id` 不一致 | 不变式 I7 |
| I3 校验失败（R 左端落在批内部） | 12.8 |
| 审计写入失败 | 18.2 |
| 成本口径闭合偏差 > 1% | 14.3 |

冻结后须按 18.7 的处置流程恢复。

## 18.7 冻结处置流程

```
1. 记录冻结原因与触发时的完整快照（各段哈希、Z2 状态、最近 N 轮审计记录）
2. 告警至安全负责人
3. 排查：
   a. 硬件/存储故障 → 从最近可信快照恢复
   b. 实现缺陷（如 I3 违反）→ 回滚到上一个已知良好的配置版本，记录缺陷
   c. 配置错误（如门槛不可达）→ 按 18.8 的配置校验流程修正
4. 恢复须安全负责人审批
5. 恢复本身作为审计事件记录
```

## 18.8 配置校验流程（v6.0 新增）

配置发布前须通过以下自动校验（全部通过才允许发布）：

| 校验项 | 判据 |
|---|---|
| 预算一致性 | `max_injections × max_per_injection ≤ max_tokens_total_slot` |
| 上下文闭合 | `\|P\| + \|S0\| + W + \|S1\| + \|slot\| + output_reserve ≤ context` |
| 价值门槛可达性 | 见 14.2.4 |
| 实现前提 | I3/I5/I6 的实现方式已书面确认 |
| 服务商门槛 | `\|P\| ≥ max(所有目标服务商的可命中前缀下限)` |
| 窗口区间 | 见 8.5 的 `W` 取值规则 |

**最后一项（窗口区间）是 v6.0 新增的阻断级校验**：若配置给出的 W 落在 8.5 的安全区间之外（例如 8k 上下文配 W=3200），系统应当**拒绝启动**，而不是"先跑起来看看"。

# 第 19 章 合成上下文与会话历史分离、访问控制、呈现层脱敏

## 19.1 分离原则

会话历史与原始日志为只读真源，长期保留、不得删除。模型上下文为合成视图。"改历史"在工程上落实为"改合成上下文的后半段"；回顾性修改前缀须走显式重算预算。分离带来：缓存友好性、可审计性、可重建性、会话历史完整保留。

映射关系：

| 来源 | 映射目标 |
|---|---|
| 系统配置 | P |
| 会话事件 | S0 摘要 / S1 状态 |
| 对话记录 | R 窗口原文，窗口外 → S0 摘要与记忆索引 |
| 记忆召回 | 注入槽 |

所有映射均为"合成视图生成"，**不回写会话历史**。

## 19.2 访问控制与呈现层脱敏

### 19.2.1 性质说明

会话历史是 harness 场景的基础数据，长期保留、不得删除。本章的机制不是"删除/脱敏存储"，而是：访问控制、呈现层脱敏（仅作用于注入路径与日志输出路径）、审计元数据保留。

### 19.2.2 敏感字段分类

| 类别 | 示例字段 | 原始存储 | 呈现层处理 | 访问权限 |
|---|---|---|---|---|
| 身份标识 | 用户 ID、会话 ID、设备 ID | 保留原文 | 按上下文决定是否脱敏呈现 | 审计角色可读全文 |
| 联系方式 | 电话、邮箱、地址 | 保留原文 | 注入路径脱敏 | 审计角色可读全文 |
| 敏感凭据 | 密码、密钥、令牌 | 保留原文（历史记录） | 注入路径拦截，不进入模型上下文 | 严格受限 |
| 财务信息 | 账号、金额 | 保留原文 | 注入路径脱敏 | 审计角色可读全文 |
| 健康信息 | 病史、诊断 | 保留原文 | 注入路径脱敏 | 审计角色可读全文 |
| 位置信息 | 精确坐标 | 保留原文 | 按用途决定 | 审计角色可读全文 |
| 一般对话 | 普通对话内容 | 保留原文 | 不脱敏 | 常规权限 |
| 工具结果 | 工具返回数据 | 保留原文 | 按工具类型决定 | 常规权限 |

**关键区别**：原始存储保留全部内容；脱敏仅作用于"模型上下文注入路径"与"日志输出路径"。会话历史本身不受脱敏影响。

### 19.2.3 呈现层脱敏检查点

| 检查点 | 时机 | 检查内容 | 失败处理 |
|---|---|---|---|
| CP1 | 记忆索引写入时 | 索引条目是否含敏感凭据 | 拒绝索引该条目（历史仍保留） |
| CP2 | 候选注入生成后 | 注入内容是否含敏感字段 | 呈现层脱敏或降级 |
| CP3 | 注入槽写入前 | 脱敏是否完成 | 拒绝写入 |
| CP4 | L5 回顾性注入审批前 | 历史数据访问权限审查 | 拒绝审批 |
| CP5 | 合成上下文生成后 | 整体脱敏校验（按段进行，P 段豁免） | 拒绝调用 |
| CP6 | 审计日志写入前 | 审计内容呈现层脱敏 | 脱敏后写入 |
| **CP7（v6.0 新增）** | **批切分后** | **批内容是否含敏感凭据** | **该批不得进入 R 的原文渲染；仅允许脱敏后进入 S0 摘要** |

**CP7 的必要性**：批一旦形成即冻结（不变式 I3），此后无法再修改其内容。若一批内含敏感凭据，而脱敏检查发生在"注入槽写入前"（CP3），则该批早已进入 R 段并反复出现在 prompt 中。**因此脱敏检查必须前移到批切分时**。

### 19.2.4 CP5 的按段校验

CP5 按段校验，P 段（系统提示、工具定义）不参与脱敏校验，避免对固定内容误脱敏。

## 19.3 L5 回顾性注入的访问审查流程

```
1. 提交回顾性注入申请
2. 安全负责人审查：
   a. 涉及会话历史范围与访问权限
   b. 是否含敏感凭据（若含，拒绝）
   c. 呈现层脱敏是否完成
   d. 审批记录完整性
3. 通过 → 进入重算预算审批
4. 不通过 → 拒绝并记录
```

## 19.4 会话历史保留与合成上下文保留分离

| 对象 | 保留策略 | 访问控制 |
|---|---|---|
| 会话历史 | 长期保留，不得删除 | 审计角色可读全文；常规角色按权限读取 |
| 原始日志 | 长期保留，只读 | 审计角色可读 |
| 合成上下文原文 | 短期保留（默认 7 天） | 合成器可写，审计可读 |
| 合成上下文元数据 | 长期保留 | 包含各段来源、哈希、Z2 状态快照、注入元数据；不含原文 |
| 注入槽内容 | 随合成上下文原文保留（7 天） | 合成器可写 |
| 记忆索引 | 长期保留 | 索引服务可读写 |
| 审计日志 | 长期保留，不可篡改 | 审计角色可读，写入独立 |
| Z2 观测状态 | 短期保留（默认 30 天），关键采样长期归档 | 观测服务可读写 |
| **批布局记录（v6.0）** | **长期保留**（批边界是重现命中序列的必要信息） | 合成器可写，审计可读 |

**（v6.0 补充）** 批布局记录必须长期保留，因为 4.6 的确定性契约要求"给定会话轨迹与参数，可重现同一批边界序列"。若批布局丢失，历史会话的命中序列无法复现，审计无法验证。

合成上下文原文短期保留（7 天，用于即时调试）；长期可追溯通过"元数据 + 会话历史重建 + 哈希比对"实现，不依赖原文保留。

## 19.5 注入来源审计

每条注入记录：来源（会话历史/记忆索引/外部输入/用户指令）、内容哈希、呈现层脱敏标记、价值评分、token 成本、写入时间、是否被截断/延后/丢弃、写入时 Z2 状态快照。

## 19.6 合成上下文长期可追溯

每次合成记录：P/S0/R/S1/槽各段来源与哈希、批布局、Z2 状态快照、注入元数据。长期可追溯路径：

```
1. 从长期保留的合成上下文元数据中读取哈希与来源
2. 从会话历史 + 批布局记录重建对应时刻的合成视图
3. 计算重建视图哈希，与元数据中哈希比对
4. 差异告警并进入审计流程
```

原文比对仅可能在 7 天窗口内执行；7 天后使用哈希比对。

## 19.7 会话历史保护

只读；日志哈希链校验（11.3.6）；Z4 转移不得修改会话历史；审计日志独立存储；会话历史保留策略与合成上下文保留策略分离。

# 第 20 章 效果—成本权衡、风险与缓解

## 20.1 方案对比

| 方案 | 记忆效果 | 缓存成本 | 适用 | 实验可比性 |
|---|---|---|---|---|
| 直接改历史（理论最优） | 最高 | 最高 | 离线、高价值、低频 | 理论基线 |
| **本架构（云端）** | 中高，略降 | 低，Z3 重算 | 云端默认 | 主方案 |
| 本地拆分索引 | 高 | 低到中 | 本地默认 | 单列实验，不与云端同表直接对比 |
| 不注入/严格保缓存 | 低 | 最低 | 低成本会话 | 对比基线 |

## 20.2 效果模型（v6.0 补充定量锚点）

```
记忆效果 =
    理论最优效果
  − 尾注位置非最优损失
  − 注入预算截断损失
  − S0 批量延迟损失
  − R 窗口外转移损失
```

v6.0 为"尾注位置非最优损失"给出定量锚点（附录 H，exp1）：

| 放置方式 | 命中率 | 尾窗重算占比 | 相对理论最优的效果损失 |
|---|---|---|---|
| 前部插入（理论最优位置） | 0.254 | 74.6% | 0（但缓存代价最高） |
| 尾部追加（本架构） | 0.836 | 16.4% | 待测（需任务成功率实验） |
| 不注入 | 0.928 | 7.2% | 最大（完全无记忆） |

**关键洞察**：前部插入的命中率只有 0.254，意味着它的**每次调用成本约为尾注的 3 倍**。因此"理论最优"在单位成本收益上很可能劣于尾注，这正是 H1 要验证的命题。阶段二的预实验必须同时记录成本与效果，不能只看效果。

## 20.3 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| **R 推进单位未实现（I3 违反）** | 稳态重算占比从 15.7% 升至 68.8% | **第 2 章不变式 I3 + 12.8 的运行时检测 + 21.5 消融矩阵** |
| 缓存边界不可精确控制 | 注入边界误判 | Z2 状态机、12.6 保守后界判定表、低置信强制后移 |
| 服务商生效门槛误判（如把粒度当门槛） | 短前缀场景缓存收益为 0 | 5.4 的门槛/粒度分离定义；16.6 的二项独立验证 |
| 块粒度变化 | 估计误差 | 12.7 候选集外检测与 GCD 补充 |
| P 段漂移字节 | 整段失效 | 四重校验、告警、L4 |
| tokenizer 版本变化 | 缓存键或观测变化 | 7.3 区分观测快照与真实缓存键、L4 |
| 真实缓存键变化（工具集/采样参数） | 非漂移不命中 | 7.3 第四项校验、参数记录 |
| S0 频繁修改 | R 反复重算 | S0/S1 拆分、频率约束、预算审批、`max_tokens_S0` |
| **S0 在缓存覆盖区更新（情形 C）却被当 L2** | 整窗失效却无人审批 | **9.3.3 三态审批 + 12.6 的 B_mod** |
| R 窗口过长导致单次重算过大 | 超出 `max_recompute` | 8.5 的 W 区间规则 |
| R 窗口过短导致命中率低 | 缓存收益下降 | 8.5 的 W 下限规则；18.8 的配置校验拒绝启动 |

| 尾注效果非最优 | 记忆略降 | 价值排序、批处理、消融调优 |

### 21.3.1 "Z2 估计误差"的可测化定义（v6.0）

v5.0 的 20.6 写"Z2 估计误差 ≤ 10%"，但**真实缓存点不可直接观测**（2.3 的事实），因此该指标在字面上不可测。v6.0 给出可测替代：

```
定义：在一个受控探针中，人为构造已知缓存点 CP_true。
方法：发送前缀长度恰为 CP_true 的请求，然后在本轮中修改该位置之后的内容；
      观测 cached_tokens 是否等于 CP_true（块对齐后）。
指标：|CP_estimate − CP_true| / CP_true
```

若无法构造受控探针，则退化为以下**代理指标**（v6.0 推荐）：

```
边界安全率 = Pr(B_mod ≤ CP_true) 的估计
            = 在 N 次采样中，"本轮可修改边界落在真实缓存点之前"的比例
目标：≥ 99%（允许 1% 的激进判定）
失败阈值：< 95%
```

该代理指标可观测（每次请求都能算 `B_mod`，而 `CP_true` 可由"本轮是否发生 P 段之后的意外失效"间接判定）。

### 21.3.2 "Z4 触发频率"指标的修订（v6.0）

v5.0 的 20.6 写"Z4 触发频率 ≤ 每 10 轮 1 次"。该指标与"Z3 重算占比 ≤ 30%"互相抵消：若系统健康，Z4 本应极少触发（指标自动满足，无区分力）；若不健康，Z4 频繁触发又与主指标冲突。

v6.0 改为**与主指标同口径**：

```
Z4 动作的重算占比 = Σ Cost_request(Z4 动作触发的轮次) / Σ Cost_request(全部轮次)
```

阈值 ≤ 5%。这样"Z4 是否值得"直接由它贡献的重算量衡量，与 11.3.3 的动作成本分级一致。

## 21.4 统计功效设计（v6.0 补充计算表）

### 21.4.1 因子设计与样本量削减

变量组合数多，全因子设计样本量爆炸。采用分数因子设计 + 分层抽样：

- **核心因子**（全因子，每配置 ≥30 会话）：R 窗口（3 档）× S0 更新频率（3 档）× 服务商（2 家）= 18 配置。
- **次要因子**（正交表覆盖）：注入频率、注入价值分布、S1 频率、模拟块粒度、模拟最小缓存长度，采用 L18 正交表，每行 30 会话，共 540 会话。
- **总计**：核心 18×30 + 次要 540 ≈ 1080 会话。若效应量大，可压缩至 540；若效应量小，按功效计算扩样。

### 21.4.2 样本量的解析计算（v6.0 新增）

v5.0 声称"样本量 = f(效应量, α, β, 方差)"并给出"每配置 ≥30 会话（保守下限）"，但 30 会话在 α=0.05、功效 0.8 下只能检出 d≈0.74 的效应量，而 20.6 的"任务成功率下降 15%"（如 70%→55%）对应 d≈0.35。二者不匹配。

v6.0 给出双样本均值比较的样本量表：

```
n / 组 = 2(z_{α/2} + z_β)² / d²,    α = 0.05 → z = 1.96,  1 − β = 0.8 → z = 0.84

n = 2 × (1.96 + 0.84)² / d² = 15.68 / d²
```

| 效应量 d | 每组样本量 |
|---|---|
| 0.20 | 392 |
| 0.30 | 175 |
| 0.35 | 128 |
| 0.50 | 63 |
| 0.70 | 32 |
| 0.80 | 25 |

**结论**：
1. "30 会话"只能检出 d ≥ 0.72 的大效应，适合**预实验**（H1 的初筛）；
2. 正式验证"任务成功率下降 15%"（d≈0.35）需要**每组 128 会话**；
3. 因此阶段六的正式实验规模应为**核心 18 配置 × 128 会话 ≈ 2304 会话**，而不是 v5.0 的 1080。

**成本考虑**：2304 会话的实测成本较高。可行的折中是：
- 预实验（阶段二）：每配置 30 会话，只检出大效应，验证方向性（H1）；
- 正式实验（阶段六）：只对**主比较**（本架构 vs 严格保缓存）扩到 128/组，其余配置维持 30/组做方向性判断。

### 21.4.3 基准定义

- **基准 1**：理论最优（直接改历史，不保缓存）。
- **基准 2**：不注入或严格保缓存。
- **主比较**：本架构 vs 基准 2（证明效果/成本比优势）；本架构 vs 基准 1（证明效果损失可控）。

### 21.4.4 统计方法

- 均值、方差、95% 置信区间；
- 消融对比：bootstrap 重采样（≥1000 次），报告差值置信区间；
- 多重比较：Bonferroni 校正或 FDR 控制；
- 显著性阈值：校正后 p < 0.05。

# 第 22 章 结论

本架构将缓存感知的记忆注入问题形式化为双视图正交设计：内容职责视图（四段：P/S0/R/S1，另有一个注入槽运行时位置）回答"改什么、改多频繁、谁稳定"；运行时行为视图（Z1/Z3 内容区与 Z2/Z4 运行时机制）回答"缓存如何命中、重算落在何处、溢出如何管理"。

v6.0 在此基础上补上了第三个维度——**变更代数**（6.5），并把它写成可验证的不变式（第 2 章）。核心设计可归纳为 15 条：

1. **内容视图为四段 + 一个注入槽位置。** P 段四重校验（字节哈希、tokenizer 版本、token 序列哈希、真实缓存键快照）并禁止漂移字节；tokenizer 版本变化按"观测快照 vs 真实缓存键"区分处理。
2. **不变式 I3（R 段批边界对齐）是本架构成立的必要条件。** R 窗口只能整批前进，批内内容逐字节冻结。违反该不变式时，稳态重算占比从 15.7% 升至 68.8%（同一轨迹、同一参数）。
3. **S0 低频靠前、S1 高频尾置，使更新频率与重算成本匹配。** S0 变更成本区分三态（未覆盖/部分覆盖/全覆盖），情形 B 与 C 均按 L4 处理；S0/S1 均有 token 长度上限。
4. **R 段窗口内保留原文，窗口外由 Z4 整批转移至 S0 摘要或记忆索引。** 窗口预算 W 按 21.3 的阈值反解并受上下文上限约束，不再使用固定的"上下文 × 0.4"。
5. **注入槽为动态 token 预算，空位不消耗 token。** 淘汰只能从尾部发生（I5），槽满时执行批断而非逐条删除。
6. **Z2 以状态机形式观测缓存点，含五个稳定态 + 两个特殊态（TTL_EXPIRED、RECALIBRATING）。** 波动度改用绝对量 d（块数）而非相对 CV；四类规则有明确优先级；状态按 `(provider, model, tools_hash, system_hash, params_hash, layout)` 分域。
7. **Z4 的每个触发条件只允许触发其成本级别的动作**；推进缓存点须通过成本收益判定，且仅在批淘汰成本持续超标时才考虑。
8. **成本模型分"请求规模"与"边际成本"两个口径**，前者用于记账、后者用于决策，禁止混用。
9. **价值模型采用乘性成本惩罚**，保证 value 上界为 0.80，所有"自动解锁"门槛均经可达性校验。
10. **三边界与四范围严格类型化**：可修改边界用估计上界、重算范围用观测值、替换范围用设计量，三者不可互换。
11. **回顾性注入统一为 L5 审批 + 白名单 + 重算预算**，value 只作下限否定条件，不作准入条件。
12. **审批角色、存储、审计哈希链与外部锚定明确**；审计写入与决策采纳须原子。
13. **会话历史长期保留、不得删除**；访问控制与呈现层脱敏仅作用于注入与日志输出路径；脱敏检查前移到批切分（CP7），因为批一旦冻结就无法再改。
14. **服务商适配区分"可命中前缀下限"与"计费粒度"**：二者是不同的量，混用会同时低估短前缀风险与高估命中精度。DeepSeek 的实测（约 256 的下限、64 的粒度、向下取整）可作为该区分的范例。
15. **实验设计补入"R 推进单位"作为必选对照**，统计功效按效应量给出样本量表，A/B 级指标阻断、C 级指标只观测。

最终策略为：**云端默认四段两区两机制尾注，本地默认拆分索引；会话历史不改不删，合成上下文可改；缓存点是状态机观测量，注入槽是动态 token 预算；P 段只读，S0 批量，R 段按批冻结，S1 高频尾置且可预测替换，Z4 溢出整批转移。**

记忆性能与经济消耗不追求单点全局最优，而采用缓存感知的受约束最优：**改尾部不改前缀哈希，且尾部的改动被约束在可以精确预测的失效范围内**——缓存保持命中；代价是注入位置非最优、效果略降，但通常远小于缓存不命中的成本。

v6.0 与 v5.0 的实质差别不在于增加了多少公式，而在于**把"怎么改"从实现自由度变成了规范约束**。v5.0 花 57 条修订打磨公式与表格的一致性，却留空了决定一切的那一维。这不是审校不够仔细，而是**建模层次**的问题：一个只描述"内容职责"与"运行观测"的模型，天然看不见"变更方式"这一维。v6.0 把它补上，代价是三处新增的不变式与一批随之调整的阈值；收益是这份规范第一次可以被独立实现者复现出相同的命中序列。

# 附录 H：实验与验证数据（v6.0 新增）

本附录给出支撑 v6.0 全部定量结论的**可复现实验**。全部实验可用随文档发布的脚本一键复现（`python exp/run_all.py`），原始输出见 `reports/experiments_all.txt`。

## H.1 仿真内核

### H.1.1 内核做什么

把每轮请求的 prompt 按 `P ‖ S0 ‖ R ‖ S1 ‖ slot` 拼成字节串，然后：

1. 用**最长公共前缀（LCP）**与历史请求求交，得到本轮可命中前缀长度；
2. 按服务商模型换算：`cached = 0 if len < min_cache_len else floor(lcp / block) * block`；
3. 命中率 = `Σcached / Σprompt`，重算占比 = `1 − 命中率`。

**这套模型只依赖"前缀缓存按 token 序列哈希匹配"这一条机制事实（3.1），不引入任何关于效果质量的假设。**因此测量结论与模型质量无关，只与建模的请求序列有关。

### H.1.2 内核的局限（必须声明）

| 局限 | 影响 | 已尝试的缓解 |
|---|---|---|
| 无真实 tokenizer | 块对齐损失用字符长度近似 | 结论对块粒度敏感度低（见 H.3 的块粒度消融） |
| 无真实模型调用 | 无法测量任务成功率、召回准确率 | 本文所有"效果"类指标均未实测，标注为 C 级 |
| 会话轨迹为合成 | 不覆盖真实工具调用形态 | 用 `g`（每轮新增）与批大小两个参数覆盖主要形态 |
| 服务商行为为简化模型 | 未覆盖多级缓存、TTL、写入延迟 | 这些由 12 章的状态机处理，不进入本附录的定量结论 |

**结论的适用范围**：本附录的所有数字都是"同一内核、同一轨迹下不同配置的相对比较"。它们支持**方向性结论**（如"批边界 vs 逐 token 差 4 倍"）与**量级判断**，不支持"某服务商的真实命中率是 15.7%"这类绝对断言。

## H.4 附录 H.4：DeepSeek 实测（对应 D-8 / 5.4.1）

| 测量项 | 实测结果 | 与 v5.0 声明对比 |
