# 身份与人格：职业身份的可变性 vs 人格的一致性

> v0.1 · 2026-10-30 · 由 issue #712（会话窗口归因）实现过程中暴露的设计缺口总结而来

---

## 0. 一句话

**一个智能体可以有多份职业身份，但只能有一个人格。**

职业身份是**会话级、可轮换、可授权**的；人格是**跨会话、恒定、不可授权**的。
把两者混为一谈，会产生两类相反的故障：

| 混淆方向 | 故障形态 |
|---|---|
| 把职业身份当人格 | 换一个会话就像换了一个人——**人格漂移**，用户会觉得「不是同一个助手了」 |
| 把人格当职业身份 | 所有会话共享一套权限与位置——**越权与串台**，A 会话做的事被算到 B 头上 |

---

## 1. 问题的出现方式（实证）

2026-10-30 的 issue #712 报：模型把**另一个会话**里说过的话当成当前用户刚说的。深挖后发现三层叠加：

1. **事件面只有名字、没有职位**：`remember_event` 把 tenant/session/harness/unit 落了，
   `actor`（谁说的）**完全没落**（恒 None）；`token_id`（编号）/`role`（职位）/`parent`（汇报线）
   /`expires_at`（任期）也没落。
2. **注入面把元信息丢了**：`session_recall` 的 `recent` 条目只留 role/text/t，
   会话归属、密级、身份全被裁掉——模型没有依据判断「这条是谁在什么位置说的」。
3. **取窗顺序错了**：先截窗口再按会话过滤，导致本会话消息被别会话挤出——
   过滤器本身没错，**窗口错了**。

第 3 条是纯 bug；第 1、2 条是**设计缺口**。设计缺口比 bug 更值得写下来，
因为它会反复出现：只要「身份」在系统里只是一个字符串，归因就永远靠猜。

---

## 2. 核心区分：两层身份

### 2.1 人格（persona）——跨会话恒定

人格回答「**我是谁**」，与任务无关、与会话无关、与授权无关。

- 它**不能被会话改写**：一次会话不能改变「我是灵枢」这件事；
- 它**不能按权限收窄**：一个只读会话的灵枢，仍然是同一个灵枢；
- 它**是遗忘的例外**：人格层属保护层，常规遗忘/淘汰不触及——
  这是层保护的**语义理由**，不只是安全策略。

在灵枢里对应：`self` / `anchor` 层。

### 2.2 职业身份（position）——会话级、可轮换

职业身份回答「**我此刻以什么身份、在什么位置、代表谁做事**」。

- 它**随会话建立**、随会话结束而失效；
- 它**可以轮换**：同一个灵枢可以在 A 会话里做记录员、在 B 会话里做审校员；
- 它**受授权约束**：能做什么由授权决定，授权变了身份的权力面就变了；
- 它**是归因的锚点**：一条记忆说「这是谁做的」，指的就是这个，不是人格。

在灵枢里对应：`knowledge` / `contextual` 等工作层 + 事件面的 `meta.actor` 等归因字段。

### 2.3 两者的关系

```
人格（恒定，一份）
   ├── 职业身份 A（会话 1，任期 1 天，权限 X）
   ├── 职业身份 B（会话 2，任期 1 小时，权限 Y）
   └── 职业身份 C（会话 3，只读，权限 Z）
```

**多份职业身份都引用同一个自我。** 这是「多会话不人格分裂」的结构性保证——
不是因为模型记性好，而是因为**结构上就只有一个人格可引用**。

## 3. 职位说明书七要素（从公司组织学借来的判据）

「一个大公司怎么确定一个职位的负责人？」——不是只记名字，而是**职位说明书**：

| # | 要素 | 回答什么问题 | 灵枢里的对应 | 是否写入事件 |
|---|---|---|---|---|
| 1 | **名称** | 谁 | `actor` | 是 |
| 2 | **编号** | 哪一份（区分同名） | `token_id` | 是 |
| 3 | **作用/职责** | 干什么 | `role` | 是 |
| 4 | **所属** | 归谁管 | `tenant`/`harness`/`unit`/`parent` | 是 |
| 5 | **任期** | 什么时候在任 | `session`/`expires_at` | 会话必落，到期可落 |
| 6 | **任职条件** | 凭什么能上任 | `auth_mode`/`theory_ok` | 按需 |
| 7 | **权限** | 能被授权做什么 | `clearance`/`layers_allow`/`ops_allow` | **不写** |

### 3.1 第 7 条为什么不写进事件——这条最重要

**事件记「她当时是谁、在哪个位置」，不记「她当时有多大权」。**

理由：权限是**当前态**，不是**历史事实**。

- 若把 `clearance=secret` 固化进 2026-10-30 的事件，而该作者在 11 月被降级，
  历史事件仍然宣称「她当时有 secret 权」——这是**假的历史**；
- 更危险的是反向：若日后提权，旧事件会显得「当时就该能读」，掩盖越权痕迹。

因此权限由两样东西承担：
1. **密级字段** `sensitivity`——它是**数据的属性**，不是人的属性；
2. **读取时的判据**——当前这个人能不能读它，每次读都重新判。

**凡是「人 × 时」的快照，只能记身份与位置；凡是「能不能」，必须在读取时算。**

## 4. 推论：四条设计规则

### R1 人格层不可被会话改写

任何允许「会话内修改 self/anchor」的接口，都是在允许**人格漂移**。
若要改人格，必须是**跨会话的、显式的、可审计的**操作（人工裁定档），不能由某次会话顺手完成。

### R2 职业身份必须可归因到「会话 × 编号 × 位置」

只有名字（`actor`）不够——同名不同人、同人不同位置都会让归因失效。
最小归因四元组：**会话 + 编号 + 名字 + 所属**。

### R3 跨会话可见性由「授权」决定，不由「亲疏」决定

「这是别的会话做的」本身**不构成**不可读的理由。可读性只取决于：数据密级 × 当前身份权限。
因此应分档而非一刀切：私有/秘密档严格绑定会话；共有档跨会话可见**但必须标注来源**。

### R4 标注来源不是可选项

若共有档跨会话可见却不标注，模型就无法区分「自己刚说的」与「别的会话说的」——
这正是 #712 报的故障。**标注成本极低，缺失的代价是错误归因。**

## 5. 与既有设计的关系

本理论与既有决定**不冲突，而是给它们补语义理由**：

| 既有设计 | 原本的理由 | 本理论补充的理由 |
|---|---|---|
| `self`/`anchor` 属层保护（`is_protected` 恒真） | 安全（自我层不可被误删） | **语义**：那是人格，本就不该被会话改写 |
| 会话绑定只在 private/secret 档（issue #35） | 隐私 | **分档**：私有是「人 × 时」的快照，共有不是 |
| 写归因三态（`session_auto`） | 来源可辨认 | **R2**：职业身份缺一维则归因不可用 |
| 双单元复核（`reviewed_by`） | 防自证 | **R1**：人格级改动需跨单元，不能由会话内单人完成 |

---

## 6. 不适用条件（诚实边界）

1. **不覆盖「人格本身该不该变」**——本理论只说「不该由单次会话改」；
   至于人格能否随长期经历演化，属另一问题。
2. **不覆盖多租户隔离**——`tenant` 是行政边界，与人格无关。
3. **不主张把七要素全部落进事件**——第 7 条明确不落，第 6 条按需。
4. **不解决「模型是否遵守标注」**——本理论只保证**注入材料信息齐全**；
   模型如何使用是能力问题，不是结构问题。
5. **直连模式没有令牌编号**——`auth_mode=direct` 的 Principal 无 `token_id`，
   此时「编号」以 `session` 代之（会话本身就是一种编号）。令牌模式才有真正的令牌编号。
6. **代理/委派的身份传递未定稿**——`parent` 链上的身份继承规则
   （子代理是否继承职业身份、是否独立成一份）尚需单独裁定。
