# 从 LLM 推理框架反推记忆系统调优

## ——DeepInfer 技术原理的同构移植

> **性质**：原理分析 ｜ v0.1 ｜ 未改仓库任何文件
> **方法**：以[《上下文不足…原理分析》](上下文不足_LLM与记忆系统同构_原理分析_v0.1.md)确立的「LLM 架构 ≅ 记忆系统」三重同构为工具，把 DeepInfer 的**性能设计原理**逐项映射为记忆系统的**待优化点**。
> **立场修正**：本文不做「能不能用 DeepInfer」的评估（那是工程采购问题）。既然两者是同构物，**它为了压榨吞吐所做的每一个设计决策，在映射下都是我们的一处待优化点**。这是同构命题的第一次实战兑现。
> **诚实边界**：全部 DeepInfer 事实取自其 `doc/inference_deployment_qa.md` 原文（实取，含具体数字与表格）；灵枢侧现状取自本仓代码与实测。**凡标注「需核」的，本轮未取证。**

## 一 · 为什么这条路成立

三重同构给出的是：功能同构、问题同构、方案同构。
那么必然推论是：**「在 LLM 侧被验证过的调优手段」，在记忆侧存在结构对应的调优手段。**

但这条推论必须配一条**严判据**，否则会乱搬。本文用这条：

> **可移植，当且仅当两侧「约束的根源」同构——都是有限资源下的取舍。**
> **不可移植，当且仅当某一侧存在另一侧根本没有的物理约束。**

按这条判据，DeepInfer 里**大量**优化是为硬件拓扑服务的：HBM 容量、PCIe 带宽、SM 占用、RDMA、EP/DP 拓扑、GPU 空转。记忆系统里没有对应物，**这些一律不搬**（把「用 RDMA 拉 KV」搬成「多线程读 md」是荒唐类比）。

真正可搬的是**信息论与调度论层面**的原理：谁该存、谁该算、算力按什么分配、等待期填什么。下面八条全部属这一层。

## 二 · 八条原理的提取与同构映射

每条格式：**DeepInfer 的做法 → 它解决的本质矛盾 → 记忆系统的对应矛盾 → 灵枢现状 → 可移植动作**。

---

### R1 · 双目标张力，用阶段分离解耦

**做法**：目标同时是「高吞吐」与「低延迟」，两者互相拉扯。解法是 **VE / Prefill / Decode 分离部署**，让 TTFT（首 token 时延）与 TBT（token 间时延）**能独立控制与优化**。

**本质矛盾**：两个目标共享同一份资源，且最优配置相反，所以在同一资源池里必然互相拖累。

**记忆侧的对应矛盾**：**写入吞吐 vs 检索延迟**。批量归档要吞吐（一次吞很多），即时问答要延迟（不能等批）。混在一个通路里，批量写入会拖慢检索（锁竞争、索引抖动）。

**灵枢现状**：写入与检索是同一个 MCP 进程、同一份索引。有 `op=scrub` / 睡眠周期做后台整理，但**没有「阶段分离」的显式边界**。

**可移植动作**：把「批量写入（归档/蒸馏/重整）」与「在线检索」在**路径上**分开——至少让批量写入不阻塞检索的服务路径（异步落盘 + 索引增量可见）。**需核**：当前批量重构是否会阻塞在线检索。

---

### R2 · 按阶段特性分配不对称资源

**做法**：极度不对称——
- **Prefill：EP2 到 8 / DP2 到 8，取「HBM 允许的最小值」**
- **Decode：EP64 到 128 / DP64 到 128（Wide-EP），取「GPU 允许的最大值」**
- **VE：单卡够用，且推荐用便宜卡**

理由：prefill 是计算密集（瓶颈在 HBM），decode 是访存密集（靠超宽并行摊薄每步访存）。

**本质矛盾**：不同阶段的瓶颈在**不同资源**上，用同一套配置会同时浪费两侧。

**记忆侧的对应矛盾**：**写入侧瓶颈在 IO/校验，检索侧瓶颈在打分/排序**。用同一套参数（扫描上限、批量大小、缓存策略）服务两者，必然一侧过配一侧欠配。

**灵枢现状**：写入极快（0.011 到 0.019 秒，零 LLM），检索是主成本。但配置面上**是否有写入侧与检索侧的独立参数**？**需核**。

**可移植动作**：为写入侧与检索侧各设独立预算（写入侧的批大小/校验强度 vs 检索侧的扫描上限/候选数）。**核心原则照抄：小的一侧取「够用即止」的最小值，重的一侧取「资源允许」的最大值。**

### R3 · 缓存介质分层，且「专用存储集群」有三个理由

**做法**（原文表格）：

| 内容 | 介质 | 副本 | 管理者 |
|---|---|---|---|
| in-flight block KV + state KV | **推理 GPU 显存** | — | prefill/decode 实例 |
| SWA KV | **本地主机内存** | 单副本，3FS 上无 | 实例；跨机命中走 400G VLAN |
| Paged block KV | **专用 3FS 存储集群** | 无应用级副本，靠 3FS 自身冗余 | kvcache-store |

**为什么不用分层存储而用专用集群**（原文三条理由，这是全篇最精彩的一段）：

1. **让每台 prefill 机器都能命中任意前缀**——从而避免「**前缀亲和性**」与「**负载均衡路由策略**」之间的冲突；
2. 把**存储节点的自动扩缩与计算节点解耦**；
3. **使 KV cache 不受计算节点故障影响**——因为**计算节点故障率比存储节点高一个数量级以上**。

**本质矛盾**：缓存如果与计算共命运，那么「路由为了均衡而打散」与「缓存为了命中而亲和」就是结构性冲突；且计算的高故障率会传染给缓存。

**记忆侧的对应矛盾**（三条全部可映射）：

1. **「记忆亲和」 vs 「负载均衡」**：若把记忆按会话/租户亲和地放在实例上（提高局部性），就与「把请求均匀打散」冲突；
2. **记忆存储的扩缩 vs 检索计算的扩缩**应能独立；
3. **检索节点的高故障率不应污染记忆真源**。

**灵枢现状**：**第 3 条灵枢做得很好**——「原文即真源，索引只是派生物、随时可重建」，这正是「缓存与计算解耦」；且 `--serve` 多实例共享同一份契约。

**但第 2 条是缺口**：灵枢是**单库单索引**，没有「存储层与计算层独立扩缩」的概念。库大了只能整体扛。

**可移植动作**：不需要真去做分布式存储。**可移植的是那条判据本身**：「凡缓存，必须能被独立重建，且其丢失不损失真源」——灵枢已满足；**并把「计算节点故障不影响记忆可读」写成显式不变式**（当前是隐含的）。

### R4 · 显式「存/算」分区，且让两者对齐同一粒度

**做法**：每个 `StateBlock` 被**显式切成两区**：
`[stored region: SWA] [dropped region: YOCO consumer SWA]`
- stored region 是必须跨请求持久的窗口；
- **dropped region 不存，恢复靠 prefill 重算**；
- 还包含压缩边界累加器 `ca_state`/`ica_state`——**因为压缩窗口边界天然对齐到 128 token 存储粒度，所以没有跨边界依赖**。

**本质矛盾**：不是所有中间状态都值得存；但「不值得存」的东西若要重算，就必须保证重算的边界与存储的边界对齐，否则会产生跨边界依赖，重算变得昂贵或不可行。

**记忆侧的对应矛盾**：**哪些记忆必须持久，哪些宁可重算？**且「重算」的边界必须与「持久」的边界对齐。

**灵枢现状**：**这几乎是灵枢的核心不变式**——「原文即真源（持久），索引/缓存是派生物（可弃可重建）」。分区是有的。

**但灵枢缺「边界对齐」这一层**：灵枢的派生物（索引分片、桶、摘要）与原文之间，**是否有「对齐粒度」的显式约定**？若索引按节点对齐而摘要按块对齐，重建时就可能出现跨边界依赖。**需核**。

**可移植动作**：给「原文 / 索引 / 摘要」三者确立**统一的粒度约定**（例如都按节点 id 对齐），并把「无跨边界依赖」写成可断言的性质（守卫测试）。

---

### R5 · 有界重放：把重算成本降为常数

**做法**：**SWA bounded replay** 只重算最近 128 个 token，并把注意力窗口**截断在重放段内**——重放位置 s 时，位置 i 的 query 只对 `[max(s, i-127), i]` 的 key 计算，得到**近似的** SWA KV。
**关键收益：重算成本降为常数，与上下文长度和层数无关。**

原文还给了另一个更狠的例子：CED 架构里 decoder 的 block KV 可从 encoder 末层 hidden state 投影，精确重建要把**最后 2,560 tokens 跑过 20 层**；改为**只重算最后 128 tokens**，结果**只用于 decode、永不进入 prefix cache**——**总 prefill 计算几乎减半**。

**本质矛盾**：精确重建的成本随规模线性（甚至超线性）增长；而多数消费场景**只需要有界精度**。

**记忆侧的对应矛盾**：**检索缓存缺失时，是否全量重扫？**全量重扫的成本随库规模线性增长。

**灵枢现状**：有 `max_scan`、桶收敛（S1b）、`MAX_SCAN=200` 等**上限式**保护——思想相同（截断），但**不是「有界重放」**：截断是把搜索面砍掉，有界重放是**只重建最近一小段并让窗口自洽**。

**可移植动作**（这是本轮最可落地的改进项之一）：
> 当检索的索引/缓存陈旧或缺失时，**不做全量重建**，而只重建「最近一个窗口」并**把该次查询的可视窗口也截断在同一窗口内**——用一致性换常数成本。
> **且照抄那条铁律：有界重放产出的近似结果，只允许用于「当前这次消费」，绝不回写成为持久真值。**

后半句尤其重要，见 R6 的映射。

### R6 · 两级命中判定，缺一级就回退一个粒度

**做法**（原文命中策略）：

> 原则是：**命中长度由 block KV cache 决定，最后一个块是否需要重算由 SWA KV cache 决定**——SWA 缺失就退一个 block 重算。

具体：长度 L 的输入，受 YOCO 截断约束，最大命中长度至多 `L - 134`（128 窗口 + 6 投机回溯）。在该上限内**先查 block KV**得命中长度 L1（128 的倍数），**再查 SWA KV**：若 `[L1-128, L1]` 内存在 SWA KV，命中 = L1；否则命中 = `L1 - 128`（128 是重算窗口）。

**本质矛盾**：有两类缓存，可靠性不同、粒度不同。不分级判定 → 要么误用陈旧数据，要么白白放弃本来可用的那部分。

**记忆侧的对应矛盾**：**原文（可靠、慢变）与索引（派生、易陈旧）是两级**。应该先判「原文可达到哪里」，再判「索引是否覆盖到那个位置」，不覆盖就回退一个粒度重扫那一段。

**灵枢现状**：已有读面代际（`code_generation` / `disk_generation` / `stale_on_disk` / `restart_required`）——**这是版本级陈旧检测，但不是粒度级回退**。当前语义接近「全用或重建」，缺的是「退一个桶」。

**可移植动作（本轮可操作性最强的一条）**：
> 把检索改成**两级命中判定**：一级查真源可达性，二级查索引覆盖度；覆盖不足时**只回退一个桶重扫**，而不是全库重建。
> 并在返回体里**显式带出「本次命中停在哪一级」**——这本身就是可审计性的一部分（呼应四可里的「可追溯」）。

### R7 · 按边际回报分配算力，且它有一个负收益区间

**做法**：draft token 的接受概率因请求与位置而异，**定长验证会把验证算力浪费在低概率 token 上**。DSpark 用 Confidence Head 预测每个 draft token 的接受率，调度时**把验证算力分配给「边际回报最高」的 token**；生产上一次产 5 个 draft，按 profiled 硬件吞吐曲线与接受率排序，选**最大化有效吞吐的前缀子集**去验证。

**收益与代价（原文实测表，这是全篇最值得抄的一段）**：

| 并发（seqs/rank） | 定长验 5 | 变长平均验证长度 | 定长接受长度 | 变长接受长度 | 吞吐增益 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 16 | 5 | 4.44 | 3.32 | 3.24 | **-1.5%** |
| 32 | 5 | 3.65 | 3.25 | 3.17 | +1.6% |
| 48 | 5 | 3.94 | 3.3 | 3.26 | +3.6% |
| 60 | 5 | 3.58 | 3.3 | 3.21 | +5.4% |
| 72 | 5 | 3.24 | 3.29 | 3.12 | +6.7% |
| 96 | 5 | 3.24 | 3.3 | 3.15 | **+11.0%** |

**本质矛盾**：验证算力有限、候选质量参差，平均分配必然浪费；**但重排本身也要成本**，所以只在「候选多到值得重排」时才划算——**低并发时反而是负收益**。

**记忆侧的对应矛盾**：**候选验证（终排 / 证据防火墙 / 资格判定）的预算分配**。检索返回 N 条候选，全验就是「定长验证」。

**灵枢现状**：有四层证据防火墙、`judge_ranking` 白箱终排、`judge_qualification` 资格判定。**是否按边际回报分配，需核。**

**可移植动作**（照抄它的姿态比照抄它的算法更重要）：
> 给候选验证设一个**门槛**：候选数低于阈值 → **直接全验，不排序**（因为重排成本大于收益）；高于阈值 → 按「预计能否改变最终排名」排序，只重点验证高边际回报者。
> **并且把适用区间写进文档**——公开自己的负收益区间，比只报最好成绩更可信。

### R8 · 异步流水：先问「谁在等谁」，再把等待期填掉

**做法**：decode 第 N 步是 `schedule(N) -> forward(N) -> sample(N) -> post-process(N)`。其中 schedule 与 post-process 是纯 CPU，但 **post-process(N) 之前必须做一次 GPU-CPU 同步**以取 sample(N) 的结果。后果：**GPU 在 post-process(N) 与 schedule(N+1) 期间完全空转**。

解法：GPU 跑 `forward(N) -> sample(N)` 时，CPU 并发跑 `schedule(N+1) -> launch_forward(N+1) -> post-process(N-1) -> launch_sample(N+1)`，GPU 全程无空闲。**关键让步：允许 post-process 处理 N-1 的结果，即允许「延迟一拍」。**

**本质矛盾**：流水线里必然有「我在等对方」，等待期是纯浪费；但要把等待期填掉，必须允许**结果晚一拍**。

**记忆侧的对应矛盾**：写入路径（校验 → 落盘 → 更新索引）与检索路径之间，**索引更新是否阻塞检索**？检索是否必须等索引完全一致？

**灵枢现状**：有读缓存（`MDCG_READ_CACHE`）、热路径缓存（`MDCG_HOTCACHE`）、派生物常驻。**但「索引可以比真源晚一拍」这个容忍度是否显式存在，需核。**

**可移植动作**：
> 允许索引比真源**晚一拍**，但检索必须能说出「我读到的是哪一拍」，并**据此降级判定**。
> 这一条与 R6 天然咬合——灵枢已有代际号（`code_generation` / `disk_generation`），**只差把「代际差」用作延迟一拍的判定依据**，而不只是用来提示重启。

## 三 · 判据回收：这三层明确不搬

| 层 | 为什么不搬 |
|---|---|
| **硬件拓扑层** | EP/DP 拓扑、Wide-EP、GDR/RDMA、PCIe、HBM、SM 占用、CUDA copy engine——记忆系统没有对应物理约束。把它们类比成「多线程读 md」是荒唐的 |
| **数值精度层** | MXFP8、低精度计算、528 B/token 的 KV 格式——记忆是文本，无浮点精度问题 |
| **超大规模调度层** | 四个负载均衡器、autoscaling、故障容错、64 卡最小部署单元——我们单库单实例，无此规模 |

**能搬的只有第三类之外的「信息与调度原理」**：谁该存、谁该算、算力怎么分、等待期填什么、缓存怎么分级。八条里 R1 到 R8 全部落在这个区间。

## 五 · 必须承认的不对称（本文最大的诚实边界）

DeepInfer 的每一个决策都被**真实负载校准过**：155 万亿 tokens/天、$38/GPU-hour、能测出「低并发时变长验证是 -1.5%」这种细节，能测出「TTL 3 天让 chatbot 少 0.5% 到 1% 命中率」。

**我们没有这种压力测试台。**

所以本文八条移植**全部是基于原理的推测，不是基于我们的实测**。它们的可信度取决于同构命题本身是否成立，而不取决于我们跑过。

**推论（这才是本轮真正的行动项）**：
> 灵枢缺的不是「优化点子」，而是**「能证伪优化点子」的负载台**——一个能给出「不同库规模 / 并发 / 命中率 / 延迟」曲线的压力测试面。
> 没有它，本文的八条永远停在纸面推演；有了它，任何一条都能被证伪，包括我们自己提出的。

## 六 · 不适用条件

| 场景 | 为什么不适用 |
|---|---|
| 想据此引入硬件级优化（EP/DP、RDMA、低精度） | 判据已排除：无对应物理约束 |
| 想一次上全部八条 | R7 自己就证明了「优化有负收益区间」；无负载台时无法判断某条在我们身上是否负收益 |
| 库规模很小（几轮对话） | 全量扫即可，两级命中/有界重放都是纯开销 |
| 想把本文当「已落地方案」 | 本文是移植分析，**未做任何实现与实测** |

## 八 · 一句话结论

> **DeepInfer 的价值不在于我们能跑它，而在于它把「有限资源下如何取舍」这件事，用真实负载压到了极致——而记忆系统面对的是同构的取舍。**
> 八条原理里，最该立刻拿走的是**两级命中 + 原子度回退**与**有界重放 + 近似不回写**：它们不但可移植，还顺手补强了我们的「可审计」主张。
> 但最该承认的是：**他们有 155 万亿 tokens/天的校准台，我们没有。** 所以下一步不是照抄八条，而是**先给自己造一个能证伪优化点子的负载台**。
