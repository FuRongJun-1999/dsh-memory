# 令牌与角色权职分离 v0.1

> 把管理权限从「环境变量开关」改为「令牌 + 角色职责矩阵 + 派生链」。
> 实现：`md_cg/tokens.py`、`md_cg/security.py`、`md_cg/mcp_server.py`、`md_cg/mdcos.py`
> 测试：`python -m md_cg.test_p21_tokens`（31 项，含 MCP 进程层）

## 1. 为什么改

改造前，管理权限来自环境变量 `MDCG_CAN_ADMIN=1`：

```
MDCG_CAN_ADMIN=1  →  can_admin=True  →  可 review_decide / forget / protect
```

问题有三：

1. **无凭据**：任何能设置该进程环境的调用方都能自授权限，没有可追溯的授权主体；
2. **不可区分**：写权限是一根整体开关，无法表达「验证单元不得改事实层」；
3. **不可委派**：子代理只能拿同一把钥匙，权职分离无从谈起。

## 2. 三层模型

| 层 | 机制 | 落点 |
|---|---|---|
| ① 令牌 | 身份与权限的唯一凭据；明文只在签发时返回一次，落盘只存 `sha256` | `~/.mdcg/_tokens.json`（0600） |
| ② 角色 | 职责矩阵：可写层 / 可执行 op / 密级上限 / 可否管理 | `tokens.ROLE_SPECS` |
| ③ 派生 | 设计者令牌派生子令牌，**权限只能收窄**，子令牌默认不可再派生 | `tokens.derive()` |

令牌格式 `mdcg1.<role>.<token_id>.<secret>`：`role` 便于人读，但**权威来源是令牌记录**——
校验时比对记录中的 role 与 `sha256(secret)`，不一致即拒绝。

### fail-closed

| 情形 | 行为 |
|---|---|
| `MDCG_TOKEN` 合法 | 按令牌角色注入身份 |
| `MDCG_TOKEN` 非法/过期/吊销 | **拒绝启动**，退出码 `3`，不降级为可用 |
| 无 `MDCG_TOKEN` 且无 `MDCG_LEGACY_ENV_AUTH` | 降级为 `guest`：只读、`internal` 密级、不可管理 |
| `MDCG_LEGACY_ENV_AUTH=1` | 兼容旧部署的 env 直连（`auth_mode=legacy_env`，不推荐） |

## 3. 角色职责矩阵

五大单元（`record / reflect / verify / output / sustain`）的 `unit / effect / duty`
与 `identity.POSITIONS`（智能论 v3.4 §十三）**同源**，`test_p21_tokens` 有断言防漂移。

| 角色 | 单元 | 效 | 可写层 | 可执行 op | 密级上限 | 管理 | 可派生 |
|---|---|---|---|---|---|---|---|
| `designer` | 设计者权限载体 | 主 | `*` | `*` | secret | ✅ | ✅ |
| `record` | 记录单元 | 全 | knowledge, contextual, structural, unresolved, rejected, goals | info, route, read, write, goal, recent | internal | ✗ | ✗ |
| `reflect` | 反思单元 | 新 | contextual | info, route, read, write, recent, metacognition | internal | ✗ | ✗ |
| `verify` | 验证单元 | 稳 | rejected, contextual | info, route, read, write, verify | internal | ✗ | ✗ |
| `output` | 输出单元 | 通 | —（只读） | info, route, read, recent, whitebox | internal | ✗ | ✗ |
| `sustain` | 维生系统 | 存 | self | info, read, write, sustain, scrub, evolution, self_state, metacognition | internal | ✗ | ✗ |
| `guest` | 未认证访客 | — | —（只读） | info, route, read, recent, whitebox | internal | ✗ | ✗ |

别名：`recorder→record`、`reflection→reflect`、`verifier→verify`、`viewer→output`、
`admin/root→designer`、`anon/anonymous→guest`。

## 4. 核心私有内容保护

「其他单元不应越权修改核心私有内容」由**两道闸门**共同保证：

1. **密级闸门**：`private` / `secret` 内容只有 `clearance` 达标的身份可写。
   除 `designer` 外的角色密级上限一律 `internal`，因此**天然无法写入核心私有内容**。
2. **层闸门**：`anchor`（身份锚点）与 `self`（灵枢自身）保护层，
   只对 `layers_allow` 含该层或 `"*"` 的角色开放。

写入路径统一走 `Principal.require_layer_write(layer, sensitivity)`，
在 `MdCGSecure.add / add_rejected / add_unresolved / propose / add_goal / set_goal_status`
六处生效。越权即 `AccessDenied`，不做静默降级。

另有一道 **op 闸门**：`_cg_call` 入口调用 `Principal.require_op(op)`，
使「只读角色执行 write / review」在进入业务逻辑前就被拦下。

## 5. 单智能体的子代理权职分离

即使是单智能体环境，也用**子代理 + 子令牌**把职责分开，从而校验偏差与盲区：

```python
from md_cg import tokens

# 外部用户为唯一主智能体签发「设计者权限载体」
d = tokens.issue("designer", actor="codebuddy", label="设计者载体")

# 主智能体为各单元派生受限子令牌（权限只能收窄）
v = tokens.derive(d["token"], "verify",  actor="codebuddy-verify",  ttl=3600)
r = tokens.derive(d["token"], "reflect", actor="codebuddy-reflect", ttl=3600)
o = tokens.derive(d["token"], "output",  actor="codebuddy-output",  ttl=3600)
```

由此得到的性质：

- **验证单元写不了被验证内容**：`layers_allow=['rejected','contextual']`，
  写 `knowledge` 层直接 `AccessDenied`，因此「自己写、自己验」在结构上不成立；
- **记录单元不能自我验证**：无 `verify` op、无 `rejected` 以外的裁决权；
- **输出单元不产生副作用**：`can_write=False`，连审计节点都写不了；
- **维生系统改不了事实**：只能写 `self` 层运维域；
- **委派链封口**：子令牌 `delegable=False`，不能继续往下派生；
  父令牌吊销时**级联吊销**整条链。

这样，主智能体无法用「同一个身份」既产出又验收，偏差与盲区有独立单元交叉检查。

## 6. 操作手册

```bash
# ① 签发设计者载体（明文令牌只返回这一次）
python -m md_cg.tokens issue --role designer --actor codebuddy --label "外部用户授权载体"

# ② 派生各单元子令牌
python -m md_cg.tokens derive --token <设计者令牌> --role verify --actor codebuddy-verify --ttl 3600

# ③ 校验身份（打印 role / 可写层 / op 作用域）
python -m md_cg.tokens verify --token <令牌>

# ④ 清单与吊销
python -m md_cg.tokens list
python -m md_cg.tokens revoke --token-id tk_xxxxxxxxxxxx

# ⑤ 打印角色职责矩阵
python -m md_cg.tokens roles
```

MCP 接入（`~/.codebuddy/mcp.json`）：

```json
{
  "mcpServers": {
    "mdcg": {
      "command": "python",
      "args": ["-m", "md_cg.mcp_server"],
      "env": {
        "MDCG_ROOT": "D:/Program Files/2_ai/AEIS/data/mdcg",
        "MDCG_TOKEN": "mdcg1.designer.tk_xxxxxxxxxxxx.xxxxxxxx"
      }
    }
  }
}
```

令牌文件路径可用 `MDCG_TOKEN_FILE` 覆盖（默认 `~/.mdcg/_tokens.json`）。

## 7. 迁移与兼容

- 既有直接构造的 `Principal(...)`（测试、脚本）行为不变：
  `role="system"`、`layers_allow=None`（不限制），仅新增字段。
- 旧部署可临时设 `MDCG_LEGACY_ENV_AUTH=1` 继续用 env 身份，
  `whoami.principal.auth_mode` 会标注 `legacy_env` 以便识别与清理。
- `test_p2_mcp.py` 已自动带上该开关以保持回归。

## 8. 诚实边界

- **令牌文件即信任根**：`~/.mdcg/_tokens.json` 被写入者可自行追加令牌。
  本方案把「可自授权限」从进程环境收敛到文件系统权限（0600），
  未引入外部 KMS/签名链——那是下一步。
- **明文令牌仍出现在客户端配置里**：MCP 客户端需要它。若需更高强度，
  应改为「客户端持私钥 + 服务端校验签名」。
- **角色矩阵是策略不是证明**：`layers_allow` 收窄的是**写层**，
  读权限仍由 `clearance` 单维控制；跨租户隔离依赖 `MDCG_ROOT` 与 DEK。
- **`op` 闸门是入口检查**：未覆盖 MCP 暴露的全部 33 个细粒度工具，
  它们走 `cg`/`stg` 基元时同样受检，但直接调用 `MdCGSecure` 的脚本需自行遵守。
