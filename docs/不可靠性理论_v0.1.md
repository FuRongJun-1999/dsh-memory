## 零、定位与适用范围

### 0.1 定位

本理论回答一个问题：**当一个系统由不可靠的组件构成时，如何让整体仍然可托付？** 它不是可靠性工程（那假设组件大体可靠、失效是例外）；它把次序反过来——**不可靠是常态而非例外**，可靠性是系统施加于不可靠组件之上的协议性质，不是组件的固有属性。

这一立场在仓内已有理论前驱：《智能论3.4》元公理2（熵变公理，`docs/theory/智能论3.4.md:637`）断言系统天然趋向信息差扩大，协议降熵定理（同文件 :751）断言维持存在必须靠结构缩小信息差；蜂巢理论对齐稿据此裁定「fail-closed 是理论立场不是工程偏好」（`docs/hive/蜂巢设计_理论对齐_v0.1.md:60`，锚点 A20）。本稿把同一立场从「协作协议」推广到「一切组件假设」。

## 一、公理（不可靠假设集）

以下七条公理构成假设集。**凡不含「系统可能不正常」假设的设计约束皆非法**——即：任何只陈述「正常路径如何走」而不回答「此处说谎/半途死/误配/被注入/变慢时怎么办」的规格，一律退回。

- **公理 1（常态公理）**：任何组件在任何时刻都可能不正常。不存在「已验证所以此后可靠」的组件；验证结论本身带时效（理论对应：stable 租约带 TTL，`docs/theory/智能论3.4.md` 3.2.2，蜂巢对齐 A4 :44；工程对应：令牌 TTL 夹紧 N123，`md_cg/tokens.py:458`）。
- **公理 2（说谎公理）**：任何组件可能返回与事实不符的成功陈述。实证：验证器在套件 rc=0 且零计数时判全绿、以 pass 写 verdict——「未验证不写入」被空跑绕过（N9，v17.md:58；修复门 `hive/verify_runner.py:165-166` 补 `passed > 0`）；LLM 执行器自报成功 ≠ 验证通过（蜂巢对齐 D-1「done ≠ verified」:73）。**本公理同样适用于持久化面的写入者**：能写 result.json 的组件就能直写一份满足判据的假产物——`passed > 0` 门约束的是验证器的执行（套件真跑过），不约束盘面上已有产物的真伪；恢复判据 classify_result 读的也只是盘面字段（`hive/src/scheduler.rs:235-240`），直写盘面即可满足。故**盘面产物与审计留痕本身是说谎者候选**：审计面现仅防静默丢失（N126 吞错），对毒化/伪造零防线；对应该防线的完整性锚见 P11。
- **公理 3（半程死亡公理）**：任何组件可能在任意两步之间死掉，且死前可能留下半成品。实证：serve stop 只杀单进程致执行器树成孤儿、持凭据继续外呼（N92，v17.md:95）；半截 spec 覆写致任务契约永久毁（N88，v17.md:67）。
- **公理 4（误配公理）**：任何配置——环境变量、config 文件、env 键——可能缺失、为空、双源分叉或被静默覆盖。实证：jobs 池双源分叉致任务永久 pending 且观测面全绿（N89，v17.md:49）；空串键静默覆盖宿主 env（N91，v17.md:102）。
- **公理 5（注入公理）**：任何输入通道可能携带越权指令或敏感数据外发路径。实证：编排子任务可读取并外发部署凭据（N141，v17.md:83）；context_files 通道无 scope/PII 防线，全文进 prompt 发往外部网关（v8 N69，v17.md:100）。
- **公理 6（缓慢公理）**：任何组件可能在任意长的时间窗内无响应，且「无响应」与「已死」不可区分。实证：超时强杀分支不看产物、落 status=timeout + result.ok=true 矛盾终态（N146，v17.md:88）；心跳判活与 1s 检测粒度是工程妥协（蜂巢对齐 :165「诚实边界」）。
- **公理 7（时钟公理）**：读出时间的那个钟本身不可靠——系统判租约、判新鲜、排次序所依赖的「时间」是某个组件读出来的数，该数可能跳变（NTP 校正、虚拟机挂起恢复）、倒流或停滞，且「钟错了」与「时间真的到了」在判据面上不可区分。诚实声明：本公理无台账失效案例，属预防性建模（公理 1 对「读时间的组件」的直推，承重面引证如下；失效形态展开见 2.9）。承重面实证：令牌过期判定以壁钟 time.time() 落 expires_at（`md_cg/tokens.py:371`，派生 TTL min 夹紧 `:458`）；心跳新鲜窗按壁钟差值判死（`hive/serve_start.py:189`，窗宽与刷新粒度 `:51`）；stable 结论租约（`docs/theory/智能论3.4.md` 3.2.2）。失效方向：壁钟前跳→租约提前失效/活者被判死；壁钟后跳→失效永不到来/死者被判活。

**由公理组直接推出的三条推论**（在仓内均有裁决先例）：

1. **完成 ≠ 被验证**；不可验证的共识等同于无共识（《智能论3.4》元公理3 共识不变公理 :648；蜂巢对齐 A2 :42、D-1 :73）。
2. **恢复与终态判据必须锚在盘面产物上，不锚在状态字段或进程存活上**（蜂巢对齐 D-2「产物说了算」:76-80；`hive/src/scheduler.rs:11-12`「崩溃恢复：产物说了算——单一实现 classify_result」）。锚盘面有一个完整性前提：**产物必须过完整性锚（P11）**——伪造的产物比丢失的产物更危险，丢失使判据自然不满足，伪造则以完整一致态的形貌主动通过判据（公理 2 扩展句）。
3. **验证者必须与被验证者结构隔离**——自我改进系统若不能同时保住验证资格，其自我改进在结构上不成立（`docs/hive/蜂巢双实例互验_设计定稿.md` §1.1；《智能论3.4》3.3 验证单元权力制衡 :176）。

### 1.1 公理的使用规则（设计评审清单）

对任何新设计/新写面，依次过七问，任一问无答案即退回：

1. 此处组件**说谎**（返回假成功）时，谁先发现？（无发现者 = 违反公理 2，须补 P1/P4）
2. 此处组件**半程死亡**时，盘面留下什么？恢复者按什么判据接手？（无产物判据 = 违反公理 3，须补 P2/P10）
3. 此处的**配置**有几个来源？谁是唯一胜出者？（多源无裁决 = 违反公理 4，须补 P3）
4. 此处的**输入**若为恶意指令/敏感数据，外发路径有几条？各过几道闸？（单道闸 = 违反公理 5，须补 P8/P5）
5. 此处的**等待**有无上界？超时后终态由谁定？（无界等待或按进程存活定态 = 违反公理 6，须补 P6/P3）
6. 以上五问的答案**是否可被测试证伪**？（不可证伪 = 设计未完成，对齐蜂巢对齐 C26「能红+反向对照+明确执行者」写作纪律，:136）
7. 此处的**时间判据**（TTL、新鲜窗、排序键）读的是哪个钟？壁钟跳变/倒流时判据向哪个方向失真、失真可检吗？据此判据落盘的产物与留痕有没有完整性机制？（未问 = 违反公理 7 或公理 2 扩展句，须补 P6 时钟边界 / P11 完整性锚）

## 三、防线原语

十一条原语。每条给：定义 / 灵枢落点 / **代价与适用边界**（无代价声明的原语视为未定义）。

### P1 fail-closed（否决式融合）

- **定义**：校验不通过或校验器自身失灵时，一律拒绝而非放行；「检查未执行」不得冒充「检查通过」。
- **灵枢落点**：`hive/verify_runner.py:165-166`（suite_ok 补 `passed > 0` 门——rc=0 不等于「跑了」，N9）；`md_cg/mcp_server.py:3630-3652`（启动探针四处 fail-fast return 2）；`md_cg/datapath.py:60/:78`（设备路径守卫抛 ValueError）；preflight 门面 fail-closed（未装配返回 ok:False+装配错误透传，溯源矩阵 #29，`docs/theory/理论_机制_代码_实验_缺口矩阵_v0.1.md:55`）；理论立场=否决式融合任一通道可否决（蜂巢对齐 A20 :60）。
- **代价与边界**：用可用性换正确性——config 笔误会拒绝拉起而非带病上岗（对照 N91 空串静默上岗的反面教材，v17.md:102）；对**观测/审计/清理面** fail-closed 反而有害，允许 fail-soft 但**必须留痕**（`hive/orch.py:313-316` 清单落盘失败 log 留痕；反例 N126 审计吞错零告警——该反例的语义归属已按本条闭合：审计/观测通道归 P9 侧 fail-soft+留痕，余下为实现跟进，见「六、开放问题与实现跟进项」第 3 条）。判据必须是「实判据」而非代理判据——`passed>0` 防的就是 rc=0 这类代理判据被空跑绕过。

### P2 原子写 + fsync

- **定义**：多读者/多写者共享文件面上的任何状态落盘，必须经「同目录唯一临时名 + fsync + 原子替换」，禁止裸 open("w") 截断覆盖。
- **灵枢落点**：`hive/exec.py:104-156` write_result（mkstemp+flush+fsync+os.replace，PermissionError 递增重试 50 次、FileNotFoundError 重建自愈）；`hive/orch.py:270-310` _atomic_write_json（同一模板，v10 N82 先例）；接线面 `hive/orch.py:316`（children 清单）与 `:683`（spec 写回），一模板三收 N142/N88/v8 N70（v17.md:64-71）。
- **代价与边界**：Windows 撞读者瞬态句柄时最坏阻塞约 12.5s（10ms×递增至 50 次，`hive/exec.py:103` 注释）；rename 原子性只在同目录成立（mkstemp 必须同目录）；POSIX 0600 权限位仅多用户形态相关，win32 同用户部署不构成缺口（v17.md:111 台账读码口径）；fsync 有真实 IO 代价，仅用于「语义终态」文件，观测流（jsonl 追加）不必逐条 fsync。

### P3 唯一真源 + 确定性裁决

- **定义**：每个被多方消费的决策只允许一个决策函数、一份真源；资格判定必须是确定性规则（词面/结构），不得交给概率组件。
- **灵枢落点**：jobs 池解析单点化——MCP 面 _jobs_dir 改经 serve_start._jobs_from 同一决策函数同一合并语义（N89 修复，v17.md:50）；恢复/终态判据单一实现 classify_result「产物说了算」（`hive/src/scheduler.rs:11-12`、`:235-240`）；四态资格判定 ACCEPT/REJECT/DEFER/BLINDSPOT 为确定性判定序，BLINDSPOT=「无法建立可靠归属，停止猜测」（`md_cg/mdcg.py:211`；溯源矩阵 #2）；写入闸白名单+纵深（`md_cg/mdcg.py:1248`）。
- **代价与边界**：唯一真源同时是故障焦点与攻击焦点，真源自身必须受守卫（N135 热缓存 env 登记不全违反同文件自书纪律即此面破口，v16.md:18）；确定性判定覆盖不了语义理解，「四态判定不交给 LLM」的导航税尚未量化（溯源矩阵 #13，标注为理论盲区91）；纯点串类白名单正则须显式排除（N85，v17.md:104）。

### P4 判据冻结（验证者 ≠ 被验证者）

- **定义**：验证的判据与执行权必须结构隔离：验证者不参与修改，判据在被验对象变更前冻结；裁决看证据出处结构，不看多数票。
- **灵枢落点**：双实例互验设计定稿——git worktree 双副本、单次迭代内主实例+专职验证实例+仲裁实例角色固化、判据面/候选面分离（`docs/hive/蜂巢双实例互验_设计定稿.md` 表0-1 与 §7.6）；理论条款=3.3 验证单元权力制衡「验证单元权力集中=单点故障」（`docs/theory/智能论3.4.md:176`；蜂巢对齐 A5 :45）；verify 层 falsified 会移入 rejected 负记忆且受保护节点拒删（N130 闸，`md_cg/mcp_server.py:199-205`，v16.md:5）；令牌面「验证单元不得改事实层」由角色矩阵表达（`docs/hive/令牌与角色权职分离_v0.1.md` §1，v0.2 增补裁决权/管理权分离）。
- **代价与边界**：双副本双倍编译与运行成本、角色固化牺牲灵活性；**验证任务自身的造假可能尚未自动化防住**（蜂巢对齐 盲区4 :171），错后路径依赖维生终裁（使用者）；「验证者独立终审」在理论文档侧已有流程先例（《智能论3.4.md:7》GLM 终审+验证单元独立终审），工程侧仍是设计定稿待排期。

### P5 分层防御（无单一机制）

- **定义**：任何单道闸都被假定为可穿透；关键面必须有**相互独立**的多道闸，且逐通道审计「每道闸在该通道是否真的生效」。
- **灵枢落点**：read_file 通道三层——scope 白名单 / HIVE_READ_ROOTS / _sensitive_read 敏感名单 / PII 脱敏（`hive/exec.py:363` 生效条件、`:800-802` 返回体逐层过 _redact_pii）；反例教材：context_files 通道仅 _sensitive_read 一道，其余防线对该通道零生效即穿透（v8 N69，v17.md:100）。
- **代价与边界**：层间冗余有维护成本；**层数≠安全性**——若各层共享同一失效模式（如都用同一份名单），是伪分层；概率层（正则脱敏）只能降概率不能阻断（`hive/exec.py:976-979` 注释自认「正则脱敏是概率防线」；+86 前缀/分隔符/中文邻接形态全漏，N86，v17.md:105）。

### P6 超时降级（一切等待有界，降级判据仍信产物）

- **定义**：任何等待（心跳、锁、任务、租约）必须有超时与超时后的降级动作；降级/强杀后的终态判定仍以盘面产物为准。
- **灵枢落点**：HEARTBEAT 判活与 stop 段「未转假也照常退出循环」（`hive/serve_start.py:195`）；树杀/组杀 `taskkill /T /F` 与 `os.killpg(os.getpgid(pid),15)`，前提 start_new_session 单独成组（`hive/serve_start.py:215-223`、`:267`；N92 修复，v17.md:41）；令牌 TTL 派生只能收窄——子令牌过期取与父记录的 min（N123，`md_cg/tokens.py:458`）；stable 结论带 TTL 降级（蜂巢对齐 A4 :44）。
- **代价与边界**：超时必误杀正确但慢的任务——所以强杀后**不得无条件贴 timeout 标签**，须先查产物（反例 N146：kill 分支不看产物落 status=timeout+result.ok=true 矛盾终态，v17.md:88）；unix 真实群杀行为在 win32 本机不可动态验证，只能 mock 接线+源断言+读码论证并如实标注（v17.md:42 诚实边界）——跨平台行为差异本身是 S8 源的活例；**一切等待界都以时钟读数计，时钟粒度与时钟正确性是 P6 的隐含前提（公理 7 / 2.9）**——心跳新鲜窗按壁钟差值判死（`hive/serve_start.py:189`，窗宽 15s、每拍 <1s 刷，`:51`），NTP 校正或虚拟机挂起恢复引起的壁钟跳变可让活者被判死（误触发树杀/互维拉起）或死者被判活（孤儿树存活）；令牌 TTL 同为壁钟读数（`md_cg/tokens.py:371`），min 夹紧（`:458`）只收窄派生、防不了钟本身失真——故凡依赖时间判据的等待面，在跨机与虚拟化形态下须补单调钟或外部时间锚，并声明时钟粒度假设（对照 0.3 跨机盲区声明）。

### P7 信任本地计算（平台承诺必须实测后采信）

- **定义**：平台/运行时/文档承诺的语义（编码、路径归一、信号、原子性）不得直接采信，以本机实测与进程内自证为准；探不过的语义按不可靠处理。
- **灵枢落点**：进程内强制 UTF-8 stdio 三流（issue #39，`md_cg/mcp_server.py:3610`）；启动探针把「GetFullPathNameW 对保留设备名的暗改写」转化为 fail-fast（`md_cg/mcp_server.py:3610-3616`，批次51）；WinError 5/32/87 等行为差异全部来自本机实弹复现而非文档（v17.md:33-44 红绿场记录）；同一模板在 unix 臂的行为以「mock 接线+源断言+读码论证」三段式落地并标注不可动态验证（v17.md:42）。
- **代价与边界**：每个新平台/新 OS 须重做实弹验证，成本随平台数线性增长；「本地实测」覆盖不了未触发的时序窗口（N146 亚秒级窗口未做动态复现，读码论证并如实标注，v17.md:88）——P7 降低 S8 概率，不归零。

### P8 净化投影（最小披露）

- **定义**：一切向低信任域（外部网关、子代理、日志）投影的内容，默认只投「必要最小集」；敏感面以名单闸+脱敏+标注块三件套处理，被拦内容以 skipped 标注替代正文。
- **灵枢落点**：_sensitive_read 名单闸（精确名/目录段/前缀族/后缀族，N141 补 config.local.json 与 .token，`hive/exec.py:941-977` 读核在位）；_redact_pii 值脱敏与 _redact_deep 递归（`hive/exec.py:986-997`）；context 命中敏感返回 skipped="敏感凭据拒读" 标注块、不读正文不拒整个 spawn（`hive/exec.py:363`）。
- **代价与边界**：正则是概率防线（N86 漏 +86/分隔符/CJK 邻接形态，v17.md:105）；**净化必须逐通道审计**——read_file 单点的 PII 脱敏对 context_files/返回体通道不自动生效（v8 N69 + `hive/exec.py:800-802` 返回体补脱敏的先例）；名单法有误伤面（绿场验证 config.json/token.txt 不误伤，v17.md:33），扩名单须带零回归用例。

### P9 可观测性优先（观测面与决策面同源）

- **定义**：系统状态必须可被外部观测（元认知孵化的前提，蜂巢对齐 A8 :48）；观测面必须与决策面走同一数据源，否则「观测全绿」本身就是新的不可靠源。
- **灵枢落点**：progress.jsonl 五类离散条目（`hive/exec.py:60`、`:507`）；health_os 全域读数面（`md_cg/mdcos.py:3117-3119`）；实例间只传离散事件标记不传连续权重（蜂巢对齐 A18 :58）；反面教材 N89——spawn/poll/doctor 五观测面与实况全面相悖（任务永久 pending 且全绿），修复即「观测与 serve 同一决策函数」（v17.md:49-50）；观测面自身须容错——单个坏 result.json 打崩 poll 整面即观测盲区（N90，v17.md:101）。
- **代价与边界**：观测面扩了攻击面与解析面（N90/N85 的注入载体都是观测/登记面）；「状态暴露强制」有聚合成本（多任务全局视图缺，A8 差距栏 :48）；观测留痕不等于审计——留痕被静默吞掉等于零观测（N126）；**审计取证还有完整性前提：留痕可被伪造时取证同样归零**——审计 jsonl 现无任何完整性机制，任何写者可追加伪造记录且取证面读到的就是最后写者的版本（公理 2 扩展句；对应该防线=P11 完整性锚）。上报通道自身的容量与速率防线见 5.2 约束 E4。

### P10 let-it-crash 与隔离恢复（二选一，禁悬空态）

- **定义**：组件级故障只有两种合法处置——**fail-fast 崩出去**（坏状态不扩散）或**隔离恢复**（按盘面产物恢复到一致态）；禁止第三态：带病继续且不留痕。
- **灵枢落点**：fail-fast 面——启动探针 return 2（`md_cg/mcp_server.py:3630-3652`）、config 解析失败拒拉起（蜂巢对齐 A20 :60）；隔离恢复面——serve 启动先 recover_orphans 清残局、产物说了算单一实现（`hive/src/scheduler.rs:11-12`、`:146-153`、`:235-240`）；互维守护 mutual_watch（pid 探活→冷却防风暴→幂等拉起→验戳新鲜闭合，双亡 both_dead→外部告警不假装成功；溯源矩阵 #30，`docs/theory/理论_机制_代码_实验_缺口矩阵_v0.1.md:56`）；反向教材——stop 段树杀缺失使执行器成孤儿持凭据外呼（N92，v17.md:40）。
- **代价与边界**：crash 面对长任务是可用性中断，故必须有恢复判据（产物说了算，推论 2）；恢复判据不信产物则恢复本身制造矛盾终态（recover_orphans 与 classify_exit 两套判据的历史病灶，蜂巢对齐 D-2 :77；N146 是同族残面）；双亡检测是诚实上限——自动拉起救不回双实例同死，须外部告警兜底；**「产物说了算」还有完整性前提：恢复判据读的是不可伪造的产物**——伪造的一致态产物会让恢复精确地恢复到攻击者选定的状态，比没有产物更糟（推论 2 完整性前提；对应该防线=P11）。

### P11 完整性锚（判据面/证据面必须不可伪造）

- **定义**：凡被引用为判据或证据的持久化面（result/verdict/审计留痕/WAL），必须带完整性机制——HMAC、签名或外部锚（写后不可改的外部面）；无完整性机制的判据面，其上的任何判定都只是「对写入者的信任」，不是验证（公理 2 扩展句：盘面产物与审计留痕本身是说谎者候选）。
- **为何单独立原语（P2 防丢失，本条防伪造）**：P2 只保证产物不是半成品，不保证产物不是伪造品。仓内先例与缺口恰好共同证明该面真实存在：蜂群 WAL 已有 HMAC-SHA256 逐条验签（WAL-HMAC）——`swarm/rust_swarm.py:100-102` verify_wal_signatures（畸形/被篡改行计 bad、验签器不因坏输入崩溃）、`:129-131` 重算 HMAC 后 compare_digest，且 Python hmac 独立交叉复核 Rust 手写 SHA256；但同一机制的密钥面存在缺省缺口（N143：API 缺省=公开常量 `swarm/rust_swarm.py:24`、CLI 缺省=空串，v17.md:85）——机制装了、密钥没管，防伪造能力即形同虚设。反观 hive 侧被引用为判据的 result.json 与 md_cg 审计 jsonl 均无完整性机制，`passed > 0` 门（`hive/verify_runner.py:165-166`）与 classify_result 判据（`hive/src/scheduler.rs:235-240`）读盘面字段即可被直写满足。
- **灵枢落点**：WAL-HMAC 先例（上述）；N143 密钥生命周期缺口（v17.md:85，留档池在案）；推论 2 与 P9/P10 的完整性前提声明；审计面（`md_cg/mdcos.py:381`、`md_cg/crypto.py:401`）防静默丢失（N126）之外的伪造面为本条待建设面。
- **代价与边界**：**密钥管理本身成为新的不可靠源**——密钥的生成/分发/轮换/存储每一环都回到公理 1–4（缺省、泄露、双源、半程），N143 是活的例子；验签有每条记录的真实计算开销（WAL 逐条 HMAC 重算）；**无法防持有密钥者**——完整性锚证明的是「写后未被改」，不证明「写入者诚实」，故必须与 P4 组合：签发判据产物者与裁决者不得同权。

### P12 附：原语组合规则（单用不足，成对生效）

十一条原语单独使用都有已知穿透案例，合法使用方式是组合：

- **P1+P2**（一切语义终态写面）：先 fail-closed 校验，再原子落盘——只 P1 无 P2 则校验过了写裂（N88），只 P2 无 P1 则写得很原子地落了假成功（N9）。
- **P2+P11**（一切终态判据写面）：P2 保产物不是半成品（防丢失/撕裂），P11 保产物不是伪造品（防毒化）——只 P2 无 P11，N143 已示范：完整性机制在（WAL-HMAC 验签在仓）、缺省密钥使它对持有公开常量者形同虚设。
- **P3+P9**（一切决策面）：决策函数单源化的同一提交里，观测面必须改到同源——N89 修复先补观测同源才算闭合（v17.md:50），只改决策不改观测 = 「修好了但看起来没修」。
- **P4+P10**（一切自我修改面）：验证资格用双实例隔离（P4），改动失败用产物判据恢复（P10）——缺 P4 自证，缺 P10 改坏后回不去。
- **P6+P3**（一切超时面）：超时强杀（P6）之后终态必须回到确定性裁决（P3 产物说了算）——N146 证明跳过 P3 的 timeout 标签制造矛盾终态（v17.md:88）。
- **P8+P5**（一切投影面）：净化（P8）必须逐通道铺满（P5 的通道审计）——v8 N69 证明单通道净化对旁路通道不自动生效（v17.md:100）。

## 五、待建设面的设计约束（只写约束，不写实现）

以下四个待建面，任何后续实现必须满足对应约束才算合规；实现方案本身另案裁决。

### 5.1 记忆软总线（跨实例记忆消息传递）

- **约束 B1（消息化）**：跨实例只传离散消息，不共享内存态、不传连续内部状态（依据：A18 离散事件同步，蜂巢对齐 :58；S3 源的全部实证）。
- **约束 B2（最终一致）**：多副本收敛目标为最终一致；任何写必须可回读验证（写后回读，D-4 纪律，蜂巢对齐 :100）；不承诺线性一致，冲突窗口必须可观测。
- **约束 B3（冲突解决按裁决链与信任加权）**：冲突不得以多数票或「最后写者赢」默认裁决；须走确定性裁决链（P3：资格判定→证据出处结构），信任加权只能在**候选排序**起作用、不得作用于**资格判定**（依据：R1 裁决「自适应权重作用于候选排序，不得作用于资格判定」，蜂巢对齐 :123；A5 伪多数对策 :45）。信任权重数值化前置条件=D-5：无实测数据不做数值化（蜂巢对齐 :103-108）。
- **代价声明**：最终一致牺牲读即时性；裁决链使冲突收敛延迟高于简单策略；信任数据前置使加权长期不可用（诚实接受）。

### 5.2 错误上报通道（新写面）

- **约束 E1（双闸）**：一切新写面必须过双闸——层写权限闸（require_layer_write 语义）+ 保护闸（self/anchor 层、immutable 拒写）；先例=N131 merge 路径补与 add 同序同错型双闸（`md_cg/mdcos.py:2117`）。
- **约束 E2（字段白名单脱敏）**：上报字段必须白名单化，禁通配放行（姊妹面教训：N125 '*' 通配，v16.md:19）；白名单键透传不得无约束（v8 N68 教训，v17.md:99）；上报内容过净化投影（P8）。
- **约束 E3（不静默）**：上报通道自身失效必须可检（反例 N126：审计吞错零告警使取证面归零）；「增益失败不阻塞但不静默」为先例口径（v16.md:172）。
- **约束 E4（上报速率与容量防线）**：上报通道必须有四件套——**速率限制**（单位时间窗内单源上报条数上界）、**配额**（每源/每通道累计配额，超配额拒绝并计数可见）、**去重**（同源同型同内容的重复上报折叠为计数）、**严重度分级**（info/warn/critical 分阈值或分通道）。缺一即该通道可被灌成洪水：上报洪水不损数据但淹没真实告警——告警疲劳是观测面的软杀伤，直接违反 P9「观测必须可读」的存在理由（E3 的「不静默」若不配上限，静默的反面就是噪声，两者同属观测失效）。
- **代价声明**：双闸与白名单增加每条上报的延迟与演进成本（新字段须先登记）；不静默要求 stderr/health 计数双通道，占观测面容量；E4 的限流/配额/去重计数器是共享可变面，其自身并发安全归 5.3 线程模型约束。

### 5.3 线程模型

- **约束 T1（二选一）**：任何共享可变面，要么加锁（明确锁序），要么消息化（单写者所有权移交），禁止「注释声明单线程」式的口头豁免——实证：mcp_server「单线程 stdin 循环：无并发竞争」注释未覆盖 sustain 后台线程，丢更新与 RuntimeError 均为实测（N138，v16.md:90）。
- **约束 T2（缺省语义一并裁决）**：后台线程的部署开关缺省值必须与线程模型裁决一并评估，不得默认全开（N129/N138 缺省语义，v16.md:19/:90）。
- **代价声明**：加锁引入死锁/锁序维护成本并可能拖慢前台；消息化引入延迟与队列容量问题；两者都比「不加」贵——这正是不可靠理论的定价：并发正确性是买来的。

### 5.4 0.5.1 发布承诺

- **约束 R1**：0.5.1 发布前，上述 5.1–5.3 约束须以「可核对判据」进入对应面的验收清单（判据形式对齐蜂巢对齐 C26：能红+反向对照+明确执行者，:136）。
- **口径声明**：仓内 package.json 版本现为 0.5.0（`package.json:3`）；「0.5.1 发布承诺」出自本次四路调研提问口径，仓内文档未见 0.5.1 承诺原文——本约束以提问口径登记，待使用者确认承诺细则。
- **代价声明**：承诺将发布时点与约束验收绑定，可能推迟发布；不绑定则约束沦为建议（违反本章「只写约束」的效力前提）。
