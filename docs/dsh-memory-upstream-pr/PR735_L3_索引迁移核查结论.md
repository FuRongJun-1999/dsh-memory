## 二、索引里到底有什么（实测键集）

在临时合成库里写一个带冒号条件的节点，`close()` 落 `_index.json`，读回来的条目里
与「条件」沾边的键只有三个：

```
condition_space        ← frontmatter 原样快照（dict，不是派生短语列表）
has_neg_conditions     ← bool（有没有「不适用条件」行）
postcondition_terms    ← 「验证方式」要素的索引键（**另一个 CCG 要素**，不是生效条件）
```

**没有** `cond_terms`、`cond_phrases`、`condition_terms` 这类派生键。
换句话说：`_cond_terms()` 的切分结果**从来不落盘**，它只是一次函数调用的返回值。

> 注：`postcondition_terms` 很容易被误读成「生效条件的短语」。它是 §5.1 六要素表
> 第 5 行「验证方式 → 后置条件词」的索引键（`nodefile.CCG_INDEX_ROLES`），
> 由 `ccg_element_terms()` 切分，**与 `_cond_terms` 是两条独立的切分面**
> （`nodefile.py::cond_terms` 的注释明确写了「为什么与 `cond_terms` 不同」）。
> 我第一版断言把它算进「条件短语」判了 FAIL —— 那是我的断言写错，不是代码问题。

## 三、三个被点名的文件，逐一看调用点

### `mdcg.py` —— 判定时现读正文

```python
# :4743-4748（judge_qualification）
cond_text = MdCG._ccg_line(content, "生效条件")          # ← 读的是 content
if not cond_text and fm.get("condition_space"):
    cond_text = nodefile.condition_space_text(fm["condition_space"])  # ← fm 原值
if cond_text and cond_text.strip() != "无条件":
    terms_ = MdCG._cond_terms(cond_text)                 # ← 这里才切分，每次现算
```

`_cond_terms` 的**全部调用点只有 1 处**（`:4747`），就在判定函数体内。
它不读 `self.index`、不读 `_index.json`。

### `mdcos.py` —— 不调用 `_cond_terms`

`grep cond_terms mdcos.py` → **0 处**。
它只在 `:1297-1311` 把请求转给 `MdCG.judge_qualification`（外加一个 `ccg_exempt` 短路）。
`mdcos.py` 自己出现的 `condition_space` 全在写入/映射面，与短语切分无关。

### `backfill.py` —— 只写正文行，从不写索引

`grep cond_terms backfill.py` → **0 处**。
它做的事是「把 frontmatter 里已有的结构化声明**渲染成正文 CCG 行**」：

```
生效条件来源链（backfill.py:14-20，注释原文）：
  ① state_attributes.comment.生效条件（成文声明）
  ② nodefile.condition_space_text(frontmatter.condition_space)（四槽合成）
  旧版曾回退到 condition_space.observation_position 单槽 + 「观测位置：」前缀
  —— 那是把坐标的一维当成整条生效条件，真实库落了 109 条弱等价行
```

它写的是 `.md` 正文行。**目录形态没变、行格式没变**，所以本次改解析口径后
`backfill` 的产物不需要重跑，`condition_fix` 台账口径也不受影响。

> 顺带一个与 PR #735 第 7 条改动直接相关的呼应：PR 补上了
> legacy「观测位置：X」前缀的剥离，而 `backfill.py` 里正好有
> `is_legacy_position_condition()` 与 `LEGACY_CONDITION_BASIS` 用来定位这批旧行。
> 两边口径现在是一致的。

## 四、决定性实验：把索引抹掉，判定结论不变

最直接的反证 —— 给同一个 `content` 判两次，第二次**不给任何索引派生字段**：

```
node_dict  = {"frontmatter": {"verification_basis": "probe"}, "content": CONTENT}
node_dict2 = {"frontmatter": {},                              "content": CONTENT}  # 无索引字段
```

两者对「条件段」的判定完全相同（都在 `verification_basis` 那一步才分叉）。
⇒ 判定链读的是 `content` 本身，索引条目**不参与**。

再补两条静态实证：

- `inspect.getsource(judge_qualification)` 里出现 `_ccg_line` 与 `condition_space_text`；
- 同一段源码里**不出现** `entry` / `_index` 字样（无索引读取）。

`rebuild_index()` 前后条目数不变，索引形态也不因口径改动而变化。

## 五、边界（诚实）

1. 探针跑在**本机这份源码**（`md_cg/mdcg.py` 435,868 B，与上游 `main` @ `01c7f2de` 同尺寸），
   不是上游 CI 环境。
2. 我用的是**合成库**（临时目录 1 个节点），不是任何真实用户的库。
   「索引里没有条件短语」这一条是**结构性事实**（键集由 `_node_entry` 单点构造），
   不随库的规模变化；但我没有在 746 节点真实库上重扫一遍键集分布。
3. `postcondition_terms` / `rejection_terms` 这两个索引键**确实会被切分口径影响**
   —— 但它们走的是 `element_terms_from_text()`，**不是 `_cond_terms()`**。
   本 PR 没有改 `element_terms_from_text`，所以这两个键也不需要迁移。
   如果将来要改它，那才是需要 rebuild 的情形。
4. 我只核了「生效条件」这一要素的索引面。`consistency.py:324 condition_terms`
   （冲突检测用的另一套词面）是**独立实现**，本 PR 未触及，也不读 `_index.json` 的
   `cond_terms`（不存在这个键）。
