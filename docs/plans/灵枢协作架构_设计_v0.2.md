## 二 机制回流：对外域 → 对内域（本版核心）

**同构原则**：同一套机制，两个信任域。**对外跑通的，对内照同一形状落**——只在"权威面"与"归属"上分域。

| 对外域机制（**已跑通**）                                        | **对内域同构落法**                         | 同构依据                          |
| ----------------------------------------------------- | ----------------------------------- | ----------------------------- |
| **难度档** `base` = 1／3／6／10                             | 团队任务用**同一张表**（口径单点）                 | 表在 `bounty_board.py`，对内复用同一常量 |
| **质量化完成分** `max(1, round_half_up(base×2E/(round+1)))` | **团队交付**用同一公式；`round` = 该任务已发生的返工次数 | 中性点＝返工 1 次 ⇒ 不奖不罚             |
| **E：逐条验收通过率**（`/verify partial p/t`）                  | 团队交付**按验收条目逐条判**；分母进**快照**并随态迁移继承   | 防事后操纵分母                       |
| **招标模式**（`/bid` → `/select`）                          | **内部任务竞标**：多人对同一任务投标，维护者定标          | 招投标法：一人一投、截止后不得改、废标           |
| **落选分**（0／1／2／4）                                      | 内部**未中标者**的认可；**0 分也留痕**            | 否则与「未参与」同形，不可观测               |
| **价值向量**（贡献者 × 项目）                                    | 团队贡献向量（**同一输出契约**）                  | 可复算                           |
| **结算适配器**（向量出口，**站外结算**）                              | 团队内外的资金换算**均在站外**                   | V2：资金发生在站外                    |

**回流的先后**：**先回流"判定与留痕"类**（难度／质量化／E／落选），**后回流"竞标"类**（招标需多人同时可投，对内先确认并发上限）。

## 四 回应两项外部诊断

### 4.1 「架构太自洽 ⇒ 自闭环宇宙」

**诊断**：高野心架构的典型死法是**完美地长成一座没人住的宫殿**。

**对策（可观测）**：

- **指标换成外部量**：**外部采用数**（非自家端接入数、非自评读数）；
- **跨域晋升**：对外域的**外部贡献**（如外部 issue 交付）应能**晋升进对内域**的经验层 —— 通道不能只从内向外；
- **留一条外部入口**：对内域的机制**不得**以"只有我们知道怎么用"为前提。

### 4.2 「裁判席独立」

**诊断**：同一主体既做评测又做被测产品，**公信力风险是绝症级的**。

**对策**：**V5 ＋ V6 直接落**——本站是**贡献验收 ＋ 声誉账本**（不是插件评测榜单），但**对自家产品方向的验收必须公示利益关联**；若将来做评测，升级为「**永久不评自家**」。

## 七 子代理与项目评分（对内域的评分机制 · 本版第二处增量）

> **问题**（使用者指出）：**之前一直没有好的机制对「子代理」和「项目完成情况」进行评分。**  
> **本节定位**：把对外域已跑通的**验收—结算链**，落到蜂巢的**执行单元**上。

### 7.1 对内域缺的是什么（对照）

| 对外域（悬赏站，已跑通）          | 对内域（蜂巢，现状）                             |
| --------------------- | -------------------------------------- |
| 任务载体：issue，含**验收标准**栏 | **spec.json**（**可承载验收条目**，但从未用于验收）     |
| 交付：`/deliver` ＋ 证据包   | result.json（有 content／error，**无验收判定**） |
| **验收四闸**              | ❌ **缺**                                |
| `/verify`（判定 ＋ E）     | ❌ **缺**                                |
| `/settle`（结算入账）       | ❌ **缺**                                |
| append-only 账本        | ❌ **缺**（只有 jobs 目录）                    |

⇒ 缺的是**一整条「验收—结算」链**，**不是缺评分公式**。

### 7.2 评分对象与归集键

评分挂在 **`identity × task × unit`** 上——蜂巢 id 契约的四槽**已提供该键**。  
例：`dsh端_悬赏站计分_输出单元`（本会话产出的多个 job 归集到同一行）。

### 7.3 评分输入（全部可从现状取，无需新基建）

| 输入               | 取自                                       | 说明                   |
| ---------------- | ---------------------------------------- | -------------------- |
| **完成度**          | result.json：有无 content、error 是否为空        | 二值                   |
| **返工次数** `round` | 同一 (identity,task,unit) 下的**重投次数**       | 同对外域「已发生返工次数」        |
| **验收条目通过率 E**    | **spec.json 的验收条目**逐条判定                  | 与 issue 的验收标准栏**同构** |
| **执行类型**         | spec 有无 `command`（确定性执行 ／ LLM 委托）        | 确定性执行**证据强度更高**      |
| **是否 handoff**   | `result.need_continue` ／ `handoff_ready` | 满上下文交回 ⇒ 计「分段」而非「失败」 |

### 7.4 结算：沿用同一公式

```
Δ = max(1, round_half_up(base × 2E/(round+1)))
base = 按「单元 × 任务难度」定档（下表为**默认值**：可直接执行，改一处即全站生效；**标定入口**＝按实测完成率与返工分布回填）
```

| 单元       | 建议 base | 理由          |
| -------- | ------- | ----------- |
| **验证单元** | 6       | 独立复核，判据最难伪造 |
| **反思单元** | 6       | 需发现自身盲区     |
| **维生系统** | 6       | 跨切面，影响全局    |
| **输出单元** | 3       | 执行性产出，可机械核对 |
| **记录单元** | 3       | 同上          |

**默认值可直接执行**（与对外域同款「口径单点」：改 `UNIT_BASE` 一处即全站生效）；**标定方式**＝积累实测后按完成率与返工分布回填，**不阻塞落地**。

### 7.5 落到哪里：账本策略

- **对内账本**：`hive/jobs/_scoreboard.json`（append-only，按 (identity,task,unit) 归集）；
- **跨域晋升**：对内评分达阈值的产出，可**晋升进脑库**成为经验／方法论 —— 这是 §4.1「跨域晋升」的通道；
- **不写入对外账本**（`dsh-bounty/ledger.json`）—— 两个信任域**各记各的**（v0.1 命题）。

### 7.7 落地状态（2026-10-11 补）

**已实现**：`hive/scoreboard.py`（评分器）＋ `hive/test_scoreboard.py`（守卫：**12 断言 ＋ 9 定点变异**，逐条恰好命中期望红项）。  
**输出**：`hive/jobs/_scoreboard.json`，两级——`by_unit`（子代理级：identity×task×unit）／`by_task`（**项目完成情况**）。  
该路径**已被 `.gitignore` 覆盖**（`/hive/jobs/` 是运行态数据）⇒ 评分**不进公开面**。  
**实测（87 个在役 job）**：Δ 合计 148；状态分布 done 70 ／ error 15 ／ timeout 2；另 15 个历史格式目录（`h<时间戳>_<hex>`，id 契约 v2 之前）未计入。

**顺带暴露三条命名卫生问题**（只**报不合**，**不自动合并**——合并是使用者的决定，猜错即改分）：

1. **identity 大小写变体**：`DSH端` 与 `dsh端` 并存 ⇒ 同一端被拆成两行；
2. **task 近名**：`协作架构` ⊂ `灵枢协作架构`（同一工作两种叫法）；
3. **15 个 legacy 目录**不合 id 契约（历史遗留，未计入评分）。

**一条边界（实测教训）**：Windows 文件系统**大小写不敏感** ⇒ 两个 job 目录名若**仅 identity 大小写不同**会被当成同一目录（后者覆盖前者）。  
故 identity 变体只可能来自 task/unit 不同的真实 job —— 归集时**按 (identity, task, unit) 三元组**是安全的。

### 7.6 双向（本版第三处增量）

v0.2 前六节写的是「对外 → 对内」；**使用者指出这是双向的**：

| 方向          | 内容                                                                                                                |
| ----------- | ----------------------------------------------------------------------------------------------------------------- |
| **对外 → 对内** | 难度档／质量化／E／招标／落选／价值向量／结算适配器（§二）                                                                                    |
| **对内 → 对外** | ① 蜂巢的**确定性执行凭据**（spec→result 可复算）可作对外域的**证据强度**输入；② **对内验收记录**可作对外域的**独立复核凭据**（V5／V6 的素材）；③ 内域标定出的**阈值与口径**回流到对外域 |

⇒ **同构不是「一边抄另一边」，而是两边互为真源。**
