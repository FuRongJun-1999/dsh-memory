### 1.3 六要素与索引

**（a）六要素本来就有"图的索引角色"** —— `docs/theory/智能论3.4.md:3053-3059` 表头「要素 \| 标记 \| 内容 \| **图的索引角色**」，**只有 4 行**（功能名/生效条件/子功能/执行）。配套 `:3043-3045`「**注释 = 节点的名（以名举实）：图的检索 = 条件词 → 节点**……无注释 = 节点无名 = 图断裂」；`docs/theory/白箱智能是什么？.md:423/804` CCG =「以『条件词 → 节点』为检索面的代码能力索引」。

**（d）索引现状**：`_index.json = {nodes, buckets, _fingerprint}` 扁平快照（`md_cg/mdcg.py:1646-1651`）；与条件空间有关的只有 `time_window`(:1572) 与 `observation_position`(:1590) 两个标量。**无六要素轴、无时间轴、无因果轴。**

**（d）结论**

**理论对「时间」与「因果」的授权 = 边类型取值 + 节点/边字段 + 推导语义（因果推理）；检索方式是「条件路由下的边遍历」。** 把它们提为**索引结构**属**新增设计**（理论只有 `:3053-3059` 那张索引角色表与 `:3060-3061` 的时序边可作锚点），而**可执行模型应照抄契约层 S3**（种子=已过 S1/S2 门控者、沿 edges 扩散 N 跳、跳数衰减、不得引入未过门控节点）。**方案见 §六。**

## 二、设计目标（可判）

1. **睡眠成为一条有真源步骤序列的周期**（本仓从"欠定义"到"有设计正身"）。
2. **自迭代获得驱动源**：只在纪律允许的范围内自动（确定性 + 可预演 + 可回滚；**LLM 依赖动作永不自动**）。
3. **按六要素的索引重建落地**：六要素从"4 行索引角色 + 只当资格门槛"升级为**6 行 + 真正的重建轴**；并补**时间**与**因果**两条图检索面。
4. **自动整理不碰主库**：一切改动先落在**影子副本**上，周期合并（裁定 1）。
5. **可观测**：每轮睡眠/自迭代都有台账与判据读数（补 `缺口矩阵 #27` 的"无治理前后数字"）。
6. **不破既有纪律**：索引仍是派生物、可重建、逐字节确定；不自动删节点；不改 `forget` 的显式语义。

## 四、副本迭代与周期合并（裁定 1；v0.3 改为 **git 机制**）

> 裁定原话（第一轮）：「周期性改库不用担心。在开启时，使用一个副本进行迭代整理。完成后才周期性合并。周期设为一小时一次，且在睡眠时间开启，可由用户调整。」
> 裁定原话（第二轮）：「**合并还是得做验证，留下修改历史，和最新版本。沿用 git 的方式，自动进行。**」

### 4.1 形态：影子工作树 + **独立 git 目录**（`.git` 不落进数据根）

```
主库 <root>/                          ← 生产读写面；睡眠周期绝不在此迭代
  anchor/ structural/ knowledge/ contextual/ self/ rejected/ unresolved/ goals/
                                      ← 唯一真源（LAYERS 8 目录下的 .md，mdcg.py:38-39/:1609-1642）
  _index.json / _index_log/ / _access.log / _keys.json / trash/ / _deletions.jsonl / …
                                      ← 派生 / 运行态 / 密钥面（一律不进版本库）
影子 <state_root>/sleep/shadow/       ← git worktree（分支 sleep/<ts>），每轮物化
历史 <state_root>/sleep/lib.git       ← git 目录放在数据根**之外**，用 --git-dir 显式指定
```

**三条切法都是硬约束倒推的（逐条见 §4.2）**：
1. **git 只覆盖真源面**（那 8 个 LAYERS 目录的 `.md`）；派生/运行态/密钥一律不入版本库。
2. **不用"在数据根里放 `.git`"**，改用 `git --git-dir=<state_root>/sleep/lib.git --work-tree=<root>` + **显式 pathspec 白名单**（只 `add` 那 8 个目录）——于是 `<root>/_keys.json`、`mkstemp` 临时件、`*.lock` **结构性不可能**被 `git add -A` 误收。
3. **影子是 `git worktree`**：迭代在影子上做 → 每轮一个提交（=**修改历史**）→ `--no-ff` 合并回 `main`（=**最新版本**）。

### 4.2 为什么不能"直接 `git init` 数据根"：九条硬冲突与逐条应对

| # | 硬冲突（证据） | 本设计的应对 |
|---|---|---|
| 1 | **无根级锁**，写方是长驻 serve + hive + sustain + 批处理 ⇒ git 只能看到"移动中的树"（`mcp_server.py:4058`、`hive/exec.py:953`、`sustain.py:639-641`；锁粒度=`fsutil.py:106-165`） | 「物化 / 对账 / 合并」三段**串行**且持**根级锁**（§八 P0-1）；迭代段完全不碰主库 |
| 2 | 数据根**无 `.gitignore`**，`mkstemp` 临时件与 `*.lock` 会漏进工作区（`fsutil.py:58`、`:124`、`mdcos.py:561`） | 用**显式 pathspec 白名单**而非 ignore 面；临时件/锁件不在白名单内 ⇒ 进不去 |
| 3 | **`<root>/_keys.json` 就在数据根下**（DEK 信封，`crypto.py:66`/`:259-261`）⇒ `git add -A` 会提交密钥 | 同 2：白名单只含 8 个真源目录 ⇒ **密钥结构性不可达**；另设机械判据（§4.5） |
| 4 | 若数据根落进仓内：`files` 含 `md_cg`，而 R1 明列 `_index.json`/`_keys.json`/`_index_log/` 为包内禁止件、R4 只放行 `lib/`、R2 点名 `md_cg/knowledge/orphan` ⇒ 三道门禁同时拦（`check_publish_artifact.py:49-67`、`:46/549-553`、`:197-220`） | 数据根**本就在插件包之外**（`datapath.py:13-24`），本设计不改这一点；git 目录另落在 `state_root` |
| 5 | 整库 `git checkout` 回滚会让所有长驻进程走"指纹失配 → 全库扫描"（1.4 万文件；签名只含 `(mtime_ns,size)`，`mdcg.py:1284-1299`） | **回滚不走 `checkout`**：回滚 = `git revert` 出一个新提交 + 语义重放回主库；且回滚须显式发起 |
| 6 | `_index_log/` 与 `_audit.jsonl` append-only 且无界（已实测 15.9MB/7.4 万行，`conformance.py:252`），`_index.json` 7.97MB 每次重建全量 diff | 它们**不在版本库里**（同 2）；版本库只承担真源 md 的历史 |
| 7 | **冲突是语义的而非文本的**：同 id 覆盖须过 `protect.guard_write`/`is_immutable`（`protect.py:244-268`）、层迁移须过 `lifecycle.can_transition`（`mdcos.py:2555-2559`）、密文按 `(tenant,actor)` AAD（`crypto.py:311-330`）——`git merge` 的自动合并会**绕过这些闸门** | **两层分工**：git 只做「历史 + 版本」；**准入不经 git 的文本自动合并**，而是先算**语义差异集**逐项过四闸（保护 / tombstone / 并发 / 生命周期），通过者才重放到主库，随后让 git 把这次变更记成历史。冲突项**挂起不自动解决** |
| 8 | Windows `os.replace` 与 git 索引互造 `PermissionError`（已实证需 20 次重试，`fsutil.py:26-44`） | 三段 git 操作在**根级锁**内做（同 1），不并发于写方 |
| 9 | 纪律面：无既有登记位；L1 口径是"产物落点为只读判定" | git 目录落 `state_root`（非仓非包）；并把「睡眠周期的 git 前提」登记进运维文档（§十-1） |

**已具备的保护（不冲突，可依赖）**：`_scan_nodes` 只走 `LAYERS`（`mdcg.py:1609-1612`）、`census` 只剪枝 `ARCHIVE_DIRS`（`census.py:31`）、`codeindex/docindex/refindex` 的 `SKIP_DIRS` **已含 `.git`**（`codeindex.py:28`/`:401`、`docindex.py:36`、`refindex.py:324`；注释明写"否则一次参数写错就能把版本库元数据索引进认知图"）⇒ 数据根附近出现 `.git` 是**被预期过**的，不会被误索引/误当节点。

### 4.3 仓内现成实现：`hive/wm.py` —— 照它的形态抄，不新造

`hive/wm.py` 就是"影子分支 + 自动合并"的**同构实现**，三条设计裁决都已定过：

- `cmd_snapshot`（`wm.py:116-233`）：凭证闸 → 拷白名单产物 → `checkout -B task/<id>` → `add` → `commit` → `finally` 无条件 `checkout main`。
- `cmd_merge`（`wm.py:332-349`）：`git merge --no-ff`，**冲突诚实报错、不自动解决**。
- `cmd_revert`（`wm.py:352-359`）：`git revert`（merge commit 自动 `-m 1`），"历史不丢"。
- 既有裁决：**git 操作面只在串行主代理侧**、worker 零 git 依赖、冲突手交人工（`docs/hive/蜂巢工作记忆_项目计划.md:12-35`/`:80-85`）。

本设计**照抄其形态**（分支 `sleep/<时间戳>`、`--no-ff`、冲突不自动解决、git 面串行），只把工作树换成数据根真源面、把"合并准入"换成 §4.2 第 7 行的语义四闸。

> 边界说明：`wm.py` 的对象是**蜂巢任务产物**（`hive/jobs/<id>`），不是认知图；其计划文档明写"工作记忆=易变层，认知图=长期层"（`docs/hive/蜂巢工作记忆_项目计划.md:42`）。本设计借的是**形态**，不是它的数据面。

### 4.4 四阶段协议（v0.3：把 git 与语义闸串起来）

| 阶段 | 动作 | 判据 |
|---|---|---|
| **① 物化**（持根级锁） | `git worktree add`（分支 `sleep/<ts>`）→ 取真源面 → 记录**基准水位**（`_index.json` 指纹 + `_index_log` 各分片 stat + `_deletions.jsonl` 偏移） | 影子可独立开库；主库真源面**逐字节未变**（可判） |
| **② 迭代** | 在影子上跑 §3.1 的 2–7 步（归纳/升层/去污染/权重/索引重建/记录） | 影子内每步读数与台账完整 |
| **③ 对账 + 提交**（持根级锁） | 算**语义差异集** `Δ = {id → (before, after)}`，逐项过四闸：<br>· 保护闸（`protect.py` 三层；衰减须有 floor，见 §7.3）<br>· tombstone 闸（主库在迭代期间被 `forget` 的 id **不得复活**：读 `_deletions.jsonl` 增量）<br>· 并发闸（主库在迭代期间改动过的同一 id → **主库优先**，记 `conflict` 挂起）<br>· 生命周期闸（`lifecycle.can_transition`）<br>→ 通过者在影子上 `commit`（**一条睡眠周期 = 一个提交**，message 含本轮台账摘要） | Δ 为空 ⇒ 整轮跳过（零提交、零写入） |
| **④ 合并**（持根级锁） | ①语义重放 Δ 到主库（走正常写路径 + `evolution.record` 每条 before/after）→ ②`git merge --no-ff sleep/<ts>` 回 `main` | **幂等**（批次 id 落台账）；**可回退**（`git revert` + 语义重放——**已裁只给 revert，§〇.3-13；不提供 `reset --hard`**）；冲突项挂起并出清单 |

**为什么"语义重放"排在 `git merge` 之前**：git 是**记录者**不是**裁决者**（§4.2 第 7 行）。先过闸再重放，最后让 git 把这次变更记成历史——**"留下修改历史与最新版本"由 git 保证，"改得合法"由仓内既有闸门保证**。

### 6.3 时间路（`temporal`）——含 **τ 口径详解**（v0.3 更正）

> **先更正**：v0.2 这里写的是 `exp(-|Δt| / τ)`。**这个写法作废。** 仓内对衰减核有明文禁令——`md_cg/whitebox_kb/aeis_core/time_core.py` 的 docstring 逐字写着：「全库一切时间演化必须经本模块。核形状唯一（指数族）……**任何在本模块之外出现的衰减核实现（`exp(-t/τ)`、`×(1-factor)`、EMA 保持率）都是 bug**——由 `tools/time_core_lint.py` 按 E5 口径机械化审计」。即 `exp(-|Δt|/τ)` 是被**点名**的违例形态；**参数应是 γ（衰减率）而不是 τ**，且必须调用该模块的函数。

**（a）τ 是什么**：它是"时间邻近度"的**时间常数**——回答"两条记忆在时间上算不算近"。数学上：`w(Δt) = e^(-γ·Δt)`，则在 Δt = 1/γ 处权重降到 1/e ≈ 0.37；若习惯用半衰期 t½，则 `γ = ln2 / t½ ≈ 0.693 / t½`。所以 τ（或其倒数 γ）是"多久算远"的刻度，**不是可随手取的常数**。

**（b）仓内已用法定形态**（`time_core.py` 三个函数，本路该用第二个）：
- **`cred_factor(gamma, dt, floor=0.0, ceil=1.0) -> e^(-γ·dt)`** —— docstring 逐字：「适用于 x0=1、x_inf=0 的**新近度加权形态（如知识飞轮 recency factor）**」← **正是本路的用法**；
- `cred(x0, x_inf, gamma, dt)`：向终值回归的完整形态（本路不需要终值）；
- `cred_step(x, factor)`：离散形态 `x·(1-factor)`，`γ = -ln(1-factor)` 每周期（常驻循环逐轮用它）。

**（c）γ 的取值不应自行发明——仓内已有三把尺子**（照"真源唯一"纪律，取值应锚定）：

| 既有常量 | 值 | 出处 | 换算 |
|---|---|---|---|
| 无观测**半衰期**（P_trust 向初值回归） | **30 天** | `md_cg/links.py:53`（`factor = 0.5 ** (days / DECAY_DAYS)`，`:500`） | γ = ln2/30天 ≈ **0.0231 /天** |
| 「陈旧」判定（抽检口径） | 30 天 | `md_cg/scrub.py:56`（`STALE_DAYS`） | 与上者同刻度 |
| 「长期未验证」判定 | 14 天 | `md_cg/scrub.py:57`（`UNVERIFIED_DAYS`） | γ = ln2/14天 ≈ 0.0495 /天 |

⇒ **已裁（§〇.3-12）：缺省 γ = `ln2 / 30天`（半衰期 30 天）**，与 `links.py:53` 的半衰期同刻度；`UNVERIFIED_DAYS=14` 留作可选严格档（`MDCG_TEMPORAL_GAMMA` 可覆盖，见下）。

**（d）三个子决定（签收时一并定）**：
1. **Δt 取哪一对时间**：**已裁（§〇.3-12）取 a) `created_at`**（写入时刻，最稳、主链必有）；b) 双时间轴 `valid_from/valid_until`（成立时间窗，须先定"窗口 vs 时刻"的比较规则）与 c) 时空图 `temporal_coordinate`（理论字段，但 **md_cg 主链未落此字段**，见 §1.4(c)）均留作后续可选档。
2. **γ 是否可配**：**已裁（§〇.3-12）缺省 `ln2/30天`**；建议 `MDCG_TEMPORAL_GAMMA` 可覆盖，与既有 `MDCG_SPREAD_DECAY`（`md_cg/mdcg.py:3183`）同形。
3. **平滑核 vs 硬窗口**：本路取**平滑核**（`cred_factor`）；若更想要"只取 N 天内"，那是**过滤**（走既有的 `validity=True` 时间过滤路径，`md_cg/mdcos.py:738`），不是本路的替代品——两者可并存。

## 七、权重刷新与衰减（裁定 4）

> 裁定原话：「**显然是分数**，被经常调用的记忆其权重被刷新，不被调用的记忆，其权重衰减。这个也是本来就有的理论设计。」

### 7.1 按裁定定形态

- **形态 = 分数乘子**（不是并列键）：`score ← score × w_refresh(node)`，其中 `w_refresh` 由"访问刷新 + 时间衰减"合成。
- **刷新来源**：`access_count` / `last_access`（现只记账、且**不在索引条目里** — §1.5(c) 卡点）。
- **衰减核**：**必须复用** `md_cg/whitebox_kb/aeis_core/time_core.py` 的 `credit` 族（该模块 docstring 明令「任何在它之外出现的衰减核实现都是 bug」）；形态与 `智能论3.4.md:2122-2125` 的 `exp(-γ·t)` 同族。
- **刷新/降权的门槛与步长**：照抄 AEIS `consolidate_cycle` 的既有取值（`rehearsal_threshold=0.7`、`degrade_threshold=0.2`、`gain=0.01`、`access_count % 10 == 0` 才 +gain），因为这些是本仓**已成文**的参数，不自行发明。

### 7.2 实现路径（**v0.3 按裁定：进主分数**）

> 裁定原话：「**进主分数。**」⇒ 取消 v0.2 的"先新路零位移、后乘子"两段法，直接做成**主分数乘子**。

**主分数形态**：`score ← score × cred_factor(γ, Δt) × refresh(access_count, last_access)`，`refresh` 按 §7.1 的 AEIS 既有门槛与步长实现。落位取"分池权重乘数"**同一乘子位**（`md_cg/mdcg.py:3575-3577` 的 `raw = clamp(raw * pooling.weight_of(...))`）——**不新开乘子链**。

**三个卡点必须先解**：
1. **数据可得**：把 `access_count` / `last_access`（或派生的 `refresh` 分数）**加进索引条目**（`_node_entry` 现无这两个键，`md_cg/mdcg.py:1532-1563`；先例是同为扁指标量的 `time_window`/`observation_position`，`:1572`/`:1590`）——否则检索只能读盘，违反"检索不写少读"。
2. **双侧同改**：Python `_score`（`md_cg/mdcg.py:3561-3581`）与 Rust `sort_path`（`rust/src/retrieval.rs:201-220`）必须同改，并保留逐位对拍守卫（先例 `docs/eval/优化第一批…_v1.0.md:218-221`）。
3. **published 读数必变且须披露**：主分数一动，README/`VERSION.json` 的公开检索数字即变——**改前基线必须先落盘**（仓内惯例：把改前 commit 检出到独立 worktree 跑同一守卫），否则"变了多少"无法归因；变更幅度**如实披露**，不得只报新数。

> 与 §5.4 的三条硬要求**是同一套**（双侧同改 / 披露读数 / 前置判据），两处改动应**同批**做、共用一套对拍守卫。

### 7.3 必须补的第二道闸（移植隐患）

AEIS 的 `decay_cycle` **没有 floor**，而 md_cg 的保护判定是**即时读 `importance ≥ 0.70`**（`md_cg/protect.py:135-151`）⇒ **衰减穿过 0.70 会让节点自动失去保护**。移植时必须：

- 给衰减项加 **floor**（照 `md_cg/weights.py:459` 的 `IMPORTANCE_PROTECT=0.70` 用法）；
- 保留 `weights.recalc` 已有的"`after ≥ 0.70` 自动补写 `protected`"（`:531-534`）行为；
- 记忆里那条语义边界：**不可遗忘 ≠ 不可覆盖**，衰减属"降级/搬迁"族，须走 `guard_move` 语义（`md_cg/protect.py:272-282`），且"降级不得误实现为删除记录"。

### 7.4 回滚与预演（照既有三件套）

`weights.recalc(apply=False)` 预演 → `_maintain.jsonl` 逐节点 before/after → `weights.rollback` 反向 apply。**衰减/刷新机制必须自带同款三件套**（AEIS 侧没有预演/回滚，这是移植时的净增工作量）。
