## 〇、摘要与结论先行

**一句话**：使用者的命题在架构上等于——**同一套任务生命周期（认领 → 租约 → 交付 → 验收 → 结算）跑在两个信任域里**；阶段序列不变，变的是每个阶段「凭什么信」。对内信任**预置**（自家 agent，权威面＝认知图），对外信任**累积**（陌生人/外部 agent，权威面＝issue 线程）。

**三层嵌套**：个体层（一个 agent 的记忆与上下文）⊂ 团队层（对内协作：蜂群＋团队记忆）⊂ 项目层（对外协作：悬赏站＋公共声誉）。**嵌套的不是三套系统，是三样结构**：同一套 append-only 账本、同一套「机器闸在前、人审闸在后且不得自动通过」的闸序、同一套 CCG 六要素记忆节点。嵌套后**唯一改变的是信任域与权威面**。

**五组件落在哪一层**：

| 组件 | 个体层 | 团队层（对内） | 项目层（对外） |
|---|---|---|---|
| **蜂群** | 单个 agent 的上下文 | 蜂巢三层调度（进程／DAG／群体）+ 群聊交互面 | 外部 agent 作为**外部执行者**提交交付 |
| **项目管理** | 个人待办 | `spec.depends_on` 静态 DAG + 失败硬传播 | 悬赏站六态状态机 + 租约 + 争议 |
| **资源分配** | 上下文预算 | worker 名额／租约时长／排序键 Ｋ_in | 并发认领上限／难度配额／声誉加权 |
| **群聊** | 无 | **人可对话的团队入口**（本设计新增面） | 外部认领者**不进群聊**，只走命令面 |
| **团队记忆** | 个人长期记忆（私密） | 团队 L0／项目 L0／L1 卡片／L2 细节（session 硬隔离） | 公开账本（append-only）+ 内部可检索镜像 |

**复用而不重造（三份已有的资产）**：
- 蜂巢的**三层调度**已成文（微观进程已闭环／中观 DAG 本期／宏观群体规划中）——本设计**不重造调度语义**；
- 悬赏站的**六态＋四闸＋双层账本**已独立成仓——本设计**把它的骨架提升为两域共用的生命周期**；
- 三层记忆（L0/L1/L2 + `session` 硬隔离）已有**实测支撑**——本设计**把它递归一层**，得到团队层与项目层。

**本稿不做什么**：不落实现代码；不校准任何未实测的数值（计分、并发上限、租约阈值一律标「建议值待裁」）；不宣称任何未验证读数。

## 一、四边现状：我们手里已经有什么

### 1. 执行面（蜂巢 hive）——调度已闭环到中观，宏观仍是图纸

**已有什么**：三层调度模型已成文（`docs/hive/蜂巢迭代_宏观与群体调度_v0.1.md`）。微观层（进程调度）已闭环：worker 池、`claimed.lock` 原子领取互斥、心跳、`kill_tree`、崩溃恢复（`recover_orphans` + M1 产物判据），回答「哪个进程跑它」。中观层（任务 DAG）为**本期施工**：`spec.depends_on` 静态依赖门禁——提交侧沿链 DFS 检环 + 依赖存在性校验，调度侧终态检查，失败**硬传播**（依赖非 done ⇒ 下游直接 `error` 且不执行），回答「它什么时候能跑」。宏观层（群体调度）**仍在规划**：群体注册表、能力路由、死锁探测器，I-2 起分期，跨机明确列为盲区60 不出界。接口面是**文件协议即接口**：spec.json 进、result.json 出，终态判据唯一锚在 `result.json` 的 `error` 字段（不锚状态字段、不锚返回计数）；**worker 无状态**，零 git，身份隔离靠 `session` 命名（`hive_job_*` / `hive_orch_*`）。身份契约是四槽 id（identity / task / unit / 编号）+ **五单元闭集**（记录 / 反思 / 验证 / 输出 / 维生），运行时拓扑为「1 副代理（设计者视角，融合裁决位唯一）+ 5 单元」（`docs/hive/子代理配置标准_v0.5.md` §8）。

**缺什么**：中观只覆盖静态 DAG，**不支持运行时动态加边**；裁决轮次无熔断（k_rev 未落，I-4）；宏观的**信任度量无实测数据**（D-5 BLINDSPOT 延续，同见 `docs/hive/蜂巢设计_理论对齐_v0.1.md` 诚实边界）。蜂巢自 2026-09-22 起处于**实测迭代期**（`hive/README.md:21`；同文件 `:23` 记「曾转『迭代中的产品』暂停常规派发，同日使用者裁定进入实测迭代」——**暂停是历史沿革，迭代是当前状态**，本设计稿自身的三章即在该期内经蜂巢派发完成），约束 D-005（rust 纯 std 零 crate）与「文件协议即接口」不破。

**出处**：`docs/hive/蜂巢迭代_宏观与群体调度_v0.1.md`、`docs/hive/蜂巢设计_理论对齐_v0.1.md`、`docs/hive/子代理配置标准_v0.5.md`。

### 2. 协作面（悬赏站 dsh-bounty）——对外协作的完整骨架已独立成仓

**已有什么**（本仓只剩指针页 `docs/plans/悬赏板设计_v0.1.md`，实现与规则 2026-10-10 迁至 `<悬赏站仓>`）：**六态状态机** open→claimed→delivered→verified→settled，另有 expired / disputed，映射 GitHub labels（`bounty:{open|claimed|…}` + `difficulty:{easy|medium|hard|expert}`），**expired 立即回 open 不驻留标签**；**验收四闸**——① CI 全绿（机器判，不可辩）② 复现读数（改前 vs 改后逐项对照）③ 守卫 + 定点变异（注入必失败 ⇒ 守卫必红并点名）④ **维护者人审（不得写成自动通过）**；**租约式认领**——`/claim` 校验（无锁 / 本人并发数 ≤ 上限）→ 上锁 + 记到期时间，72h 未交付 → expired 回板；命令面 `/claim`、`/deliver`、`/withdraw`、`/dispute`，命令只认行首最前的词，**被拒命令记在尝试者头上**；**声誉双层**——公开面 = `docs/bounty/ledger.json`（append-only 事件流）+ `board.md`（荣誉榜，**由账本机械生成**），内部面 = 同一账本的可检索镜像（v0.1 只落公开面，**内部面待接线**）；计分为建议值待裁（easy 1 / medium 3 / hard 6 / expert 10；虚假交付 −5；超时 −1；争议败诉不扣本金但记录在案）；**状态权威面 = issue 线程本身**（评论里的 `<!-- bounty:v1 {…} -->` 标记），**不是数据库**。结算 = 声誉制，**不涉资金**——资金与账号是不动边界。

**缺什么**：内部信任镜像未接线；声誉分口径无实测校准；跨仓/跨机的群体间协作无载体。

**出处**：指针页 + 编排侧已取证的跨仓事实（`<悬赏站仓>` = FuRongJun-1999/dsh-bounty）。

### 3. 记忆面（大脑库 md_cg）——认知图是权威面，三层记忆已实测

**已有什么**：认知图节点结构 = **CCG 六要素**（功能名 / 生效条件 / 子功能 / 执行 / 验证方式 / 不适用条件，见 `docs/工作纪律_认知图条目_v1.1.json` 第 16 条记忆闭环）+ **条件空间**（identity / conditions.apply / negative.reject 的正负条件分离）+ **验证基底**（`verification_basis` 白名单：compiler / test / measurement / formal_proof / data / textbook / public_kb / other，写非法值即抛异常）。团队记忆为三层（`docs/hive/主代理子代理记忆架构设计.md`）：**L0 全局态**（主代理独占，`session=main`，<30 条、importance ≥0.9）、**L1 卡片层**（子代理产出，固定 5 栏卡片）、**L2 细节层**（过程产物，默认不召回）。**session 是硬隔离**：实测 `session=None` 返 16 条、`session="main"` 仅 **1 条**、`session="subA"` 5 条——主代理物理上拿不到子代理细节。防爆三闸门实测有效：预算 1200 tokens 时 200 条产出**只纳入 25 条、实耗 1170（97.5% 利用率）、其余 25 条进 `skipped`**（硬截断，不是「尽量少读」）。溯源靠 `derived_from`，裁决靠 `review_decide` 生成带 `record_hash` 的审计记录。

**缺什么**：L2 细节层只增不减，需主动 `scrub`（全架构唯一需运维处）；条件空间未声明时一致性检测返回 BLINDSPOT（不假装确定）；并行写入的冲突检测必须后置到收口检查点 `final_check()` 才无条件检出。

**出处**：`docs/hive/主代理子代理记忆架构设计.md`（含独立复现 27/27、多进程双端 12/12 实测清单）、`docs/工作纪律_认知图条目_v1.1.json`。

### 4. 交互面（缺失）——协作只对 agent 可见，人没有团队入口

**现状**：以上三边都是**机器可消费**的——蜂巢吃 spec.json，悬赏站吃 issue 评论，认知图吃节点写入。人要看进度，只能读目录、读账本、读 md 文件；**没有任何一个「可直接对话的团队入口」**：不能对团队说「你们的验证闸为什么判红」，团队也不能主动向人报告关注信号。

**对照 DS Bot**（外部 DSH 插件，仅作设计对照，不采纳其代码）：主 bot 高权限管所有群与 bot；群聊**序列化发言**（上一人 posted 或 passed 后下一人才开始），顺序按 roster（admin 优先）；`@Name` 传唤，回复里的 `@` 会叫下一个（per-member / per-round 上限，admin 的调用够得更远）；成员无新信息则 `[PASS]` 沉默；**每个成员在群里有一个自己的隐藏 Session**（群永不读成员私聊）；上下文由独立 context steward 二分决策（switch 开新 part / compact 就地压缩）；记忆段冻结以保住 provider 前缀缓存。

**代价（三处，非风格问题）**：① **时序不可观测**——DS Bot 的 roster 序、`[PASS]` 沉默、传唤链是**结构信息**，只看 result.json 的终态会把它全部压平；② **裁决无人入位**——四闸的第四闸是维护者人审、对内域的对应物是设计者裁决，缺入口意味着这两处最后只能由 agent 自裁自决，正撞上「验证单元不得写事实层」的既有禁令；③ **关注信号无收件人**——设计者视角的产物是判定单与 signal，无群聊面时它没有落地对象，盲区无处上报。**即：三边齐备而交互面缺失，协作的观测位与裁决位同时落空。**

## 二、架构命题：同一套架构，两个信任域，三层嵌套

### 2.1 命题翻译

使用者的原话是：「灵枢大脑库负责个人层面的长期记忆，和内部进行团队记忆。而灵枢项目管理系统则是对外协作，和灵枢大脑可以使用**同一套架构**，只是进行**嵌套**了。」

架构翻译：**同一套任务生命周期（认领 → 租约 → 交付 → 验收 → 结算）跑在两个信任域里**。阶段序列不变，变的是每个阶段「凭什么信」。逐条对齐如下。

| 维度 | 对内域（自家 agent） | 对外域（陌生人 / 外部 agent） | 复用 / 替换 |
|---|---|---|---|
| **状态机** | 蜂巢 job 终态（pending / claimed / running / done / error / timeout / killed）+ 中观依赖门禁 | open → claimed → delivered → verified → settled，另有 expired / disputed | **骨架复用、词表映射**：可认领→已认领→已交付→已验收→已结算两域同构；`error/timeout/killed` 对内即对外 `disputed/expired` 的功能等价物 |
| **租约** | `claimed.lock` 原子领取（互斥，**不带到期限**） | `/claim` 校验 + 上锁 + 记到期时间 | **必须替换**：对内是「锁到进程结束」，对外必须「锁到 deadline」——对外域无租约即无限占位 |
| **超时** | 任务级 + 步级双层超时（秒级，已有） | 交付期 72h（小时级）→ expired 回 open | **机制复用、量纲替换**：执行超时 ≠ 交付租约 |
| **验收闸** | 确定性门禁（`result.json` error 字段 / `expect_*` 断言 / `exec_cmd.py`）+ 编排侧裁决（融合位唯一） | CI 全绿 + 复现读数 + 守卫定点变异 + 维护者人审 | **骨架复用**：机器闸在前、人审闸在后且**不得自动通过**；对内域「人审闸」= 设计者视角裁决 |
| **账本** | 认知图（append-only 节点 + `derived_from` 溯源 + `record_hash` 审计） | `ledger.json` append-only 事件流 + `board.md` 机械生成 | **结构复用、权威面替换**：事件流 + 机械榜单两域同构；权威面一个是本机库、一个是 issue 线程 |
| **计分／信任** | **已有**：连接层信任值 `p_trust`（`md_cg/links.py`；初值 0.8，可升可降、**可被反例击穿**、受上限约束不可刷高、30 天无观测向初值回归、全程留痕）＋元认知信任面 `p_trust/p_gap`（由 confirmed/weakened 事件聚合） | 难度分 easy 1 / medium 3 / hard 6 / expert 10（建议值待裁），虚交 −5，超时 −1 | **结构复用、载体替换**：两域都是「概率估计＋可降＋留痕」；差别在对内信任挂在**认知图链接层**（持久、可衰减、可聚合），对外声誉挂在**公开账本**（append-only、可公示） |
| **争议** | 一致性检测 DEFER → 设计者裁决 → `record_hash` 留痕 | `/dispute` + 争议败诉不扣本金但记录在案 | **通路复用、裁决人替换**（设计者 ↔ 维护者），后果不同（记忆更正 ↔ 声誉记录） |

两域的差异可归纳为一句话：**对内域信任是预置的**——状态权威面是本机认知图，失败成本是浪费算力，验收闸靠确定性门禁加编排侧裁决；**对外域信任是累积的**——状态权威面是 issue 线程本身，失败成本是声誉与协作关系，验收闸靠 CI、复现读数、守卫变异加人审。

### 2.2 三层嵌套图

```
│  信任 = 累积（陌生人 / 外部 agent）  失败成本 = 声誉与协作关系  │
│  ┌─ 团队层（对内协作）────────────────────────────────────┐  │
│  │  蜂群 + 团队记忆                                     │  │
│  │  权威面 = 认知图（<大脑库根>）  账本 = 认知图节点事件流 │  │
│  │  信任 = 预置（自家 agent）  失败成本 = 浪费算力        │  │
│  │  ┌─ 个体层（一个 agent 的记忆与上下文）──────────┐    │  │
│  │  │  L0 全局态（session=main）                   │    │  │
│  │  │  L1 卡片层 · L2 细节层（session=subXXX）     │    │  │
│  │  │  CCG 六要素 + 条件空间 + 验证基底            │    │  │
│  │  └──────────────────────────────────────────────┘    │  │
│  └──────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

**边界条件与越界禁令**：

- **个体 → 团队**：`session` 是硬隔离，主代理只见 L0；子代理**不得自行 recall 全局态**，只能接收主代理裁剪注入的最小充分上下文（`docs/hive/主代理子代理记忆架构设计.md` 阶段 2）。
- **团队 → 项目**：**跨群体只同步已验证产物**（A15，`result.json` ok）；未验证不强制同步，跨群体协议 = 文件投放 + 终态回执，零连续状态（`docs/hive/蜂巢迭代_宏观与群体调度_v0.1.md` 理论锚点）。
- **项目 → 个体（反向禁令）**：外部可见面**不得含本机路径与私密内容**——工作纪律第 9 条（敏感信息隔离：含隐私/私有内容只写私有库，不上传公开库，推送描述不写敏感词）与第 14 条（内容政策合规：公开产物过内容政策 + 隐私双清单），出处 `docs/工作纪律_认知图条目_v1.1.json`。
- **个体 ← 项目（反向禁令）**：**个人记忆不得直读外部账本**。外部账本由陌生人写入，是未验证输入；它只能经收口检查点复核 + 裁决通路，变成带 `derived_from` 的认知图节点后才进团队记忆。
- **越界的判据**：外部内容出现在本机路径里 → 违第 9 条；外部账本直接成为 L0 结论 → 绕过验收闸；未验证 result 进跨群体同步 → 违 A15。

### 2.3 为什么必须同构

**收益一：一套状态机两处实现，语义可迁移。** 两域的阶段序列相同，对内域调试出来的终态语义（`error` vs `timeout` vs `killed` 的区分）可以直接翻译到对外域的 `disputed` / `expired`，不必为对外协作另造一套心智模型。悬赏站今天的 `expired 立即回 open` 与蜂巢的恢复语义是同一个动作。

**收益二：声誉与信任可跨层聚合。** 对外域的公开账本是 append-only 事件流，对内域的认知图同样是 append-only 节点流。结构一致 ⇒ 同一套读取器能同时读出「这个外部 agent 的历史交付」与「这个内部单元的历史产出」，聚合才有可能。若两域账本异构，聚合就必须先做语义对账——而语义对账的输入恰恰是它想产出的东西，循环。

**收益三：个体经验可直接晋升为团队知识。** L1 卡片（CCG 六要素 + 条件空间 + 验证基底）与认知图节点同构，故一条子代理结论从 `session=subA` 升到团队记忆**不需要转格式**，只需补 `derived_from` 与 `verification_basis`。这是「个体层 ⊂ 团队层」在数据面成立的前提。

**不同构的代价**：两套语义 ⇒ **对账不可能**。内部账本用重要度、外部账本用难度分，二者无共同量纲，任何「谁的贡献更大」的聚合都只能靠人工口径；更严重的是验收语义分叉——对内域「执行器自报成功」与对外域「CI 全绿」若被当成两种不同的正确性，同一批产物在两个域会得到两个结论，信任就无法跨层传递。

### 2.4 「只是嵌套了」到底嵌套了什么

被嵌套的是**三样结构**，且仅此三样：

1. **同一套账本结构**：append-only 事件流 + 机械生成的榜单。公开面 `ledger.json` → `board.md`（由账本机械生成，人不手改）；对内域是认知图节点流 → 索引/榜单。**榜单永不手写**是同一条纪律。
2. **同一套验收闸骨架**：机器闸在前（CI / `expect_*` 断言 / 复现读数 / 守卫变异）、人审闸在后且**不得自动通过**。对外的第四闸是维护者人审，对内的对应闸是设计者视角裁决——位置相同，裁决人不同。
3. **同一套记忆节点结构**：CCG 六要素 + 条件空间（正负条件分离）+ 验证基底。无论节点来自自家单元还是外部交付，入库形态一致。

**嵌套后唯一改变的是信任域与权威面**：内部域的权威面是本机认知图（`<大脑库根>`），外部域的权威面是 issue 线程（评论里的 `<!-- bounty:v1 {…} -->` 标记）——两者都是**文本载体而非服务内部状态**，这与蜂巢「文件协议即接口」同一条纪律；信任域从预置变为累积，失败成本从算力变为声誉。

命题因此可以收成一句可施工的话：**先有骨架，后有域；域切换只允许改权威面与信任来源，不允许改阶段序列、闸门顺序与节点结构。** 违反这一条的改动，等价于在同一个系统里埋下两套语义——第一节四边现状里那些「已取证」的结构（六态、四闸、session 硬隔离、CCG 六要素），就是这条约束目前唯一可核对的锚点。

## 三、统一任务生命周期：一条状态机，两个权威面

对内（蜂巢 job）与对外（悬赏 issue）不是两套状态机，是**同一条骨架在两个权威面的投影**。骨架：未占 → 已占（lease） → 已交付 → 已验证 → 已收口，加两条旁路：租约到期回收、争议挂起。差异只在两处——对内缺的是依赖 DAG 与失败硬传播，对外不能缺的是争议仲裁与人审闸。

### 3.1 统一状态机

以悬赏站六态（open / claimed / delivered / verified / settled + expired / disputed，`<悬赏站仓>`）为骨架，逐态给出对内投影：

| 骨架态 | 对内投影 | 进入条件 | 退出条件 | 超时行为 | 失败行为 |
|---|---|---|---|---|---|
| open | `pending` | 提交过 spec 校验（必填/白名单值 fail-fast）+ 依赖完整性与成环校验通过 | `claimed.lock` 原子领取 | 无；但依赖集失败会立刻转失败 | 依赖不完整或成环 → 提交即拒；提交后依赖目录被删 → `error`「依赖不完整」 |
| claimed | `claimed` | 锁落盘 | 进程起（→running）或 result.json 落盘 | 心跳缺失 → `recover_orphans` 重投 | 领取方崩溃 → **重投而非判失败**（无产物=无事实） |
| delivered | `running` 终结、result.json 已落盘、**未收口** | 执行器写 result.json | 编排侧/验证档判定 | 无独立窗口，复用任务级 `timeout_s` | result 的 `error` 非空 → `error` 终态 |
| verified | 机器三闸全绿 | 断言/回归、复现读数、守卫＋定点变异依次过 | 第④闸给出裁决 | 受任务级 timeout 约束 | 任一机器闸红 → `error`，不可辩 |
| settled | `done` 终态 + 记账 | 收口 accept 且结果入账 | 终态无退出 | 不适用 | 不适用 |
| expired | `timeout` / `killed` | 租约到期未交付、执行超时、被抢占 | 终态（**不回 pending**） | 即本体 | 硬失败 |
| disputed | **不设** | — | — | — | — |

三处必须写明的判读：

**① 对内必须补的：依赖 DAG 与失败硬传播。** 任一依赖终态 ∈ {error, timeout, killed} ⇒ 本任务直接 `error` 且**不执行**（级联取消闭包，不设"跳过依赖继续"的软模式，避免静默错执行）；任一依赖仍 pending/claimed/running ⇒ 本拍跳过。实现选择是**不新增状态**（仍留 pending，由调度器每拍求值），代价是外部看不出 pending 是在等领取还是等依赖；补救是派生一个只读的 `blocked_by` 视图——**派生字段不是状态**，不得参与判定。

**② 对外必须保留的：disputed 与人审闸。** 对内不设 disputed，因为失败硬传播且无第三方申诉面：验不过即失败。同时须诚实标注一处差别：对内并非无人裁决——认知图写入过闸门产生 DEFER 审核队列，裁决权归设计者；但那是**一条写入的处置态**，不是任务状态，两者不可混用。

**③ 状态属于"需求"还是"实例"，决定 expired 的走向。** 对外认领者失败，需求还在 → expired 立即回 open、不驻留标签；对内一个 job 就是一次执行实例，死了就死了 → 终态。这是同一骨架在两面最锋利的分歧，也是"嵌套"的证据：外层是需求生命周期，内层是实例生命周期。

### 3.2 权威面与幂等

- **对外权威面 = issue 线程本身**：评论里的 `<!-- bounty:v1 {…} -->` 标记，不是数据库。公开账本 `docs/bounty/ledger.json`（append-only 事件流）是记账权威；荣誉榜 `board.md` 由账本**机械生成**。
- **对内权威面 = 文件协议**：spec.json 是意图权威（唯一写者=提交者，落盘后不可变）、result.json 是终态权威（唯一写者=执行器）、调度状态由 scheduler 唯一写。
- **认知图留痕是镜像，不是权威**：`session=hive_job_<id>` 的 L1 卡片层与 L2 细节层（docs/hive/主代理子代理记忆架构设计.md），由 result.json 派生。

「同一状态能否同时在两处表达」的判据四条，全中才允许：

(a) **可写者唯一**：每个状态字段只有一个角色有写权；
(b) **镜像单向生成**：镜像由权威面机械推导，无独立写路径（不存在"改荣誉榜来改分"的路）；
(c) **判定只读权威面**：能否认领/收口/计分只读权威面，镜像缺失或落后只影响可观测性、不改变判定；
(d) **冲突以权威面为准并留痕**：漂移记一条事件、重算镜像，不反向覆盖权威面。

**禁止双写真相**：任何"两处都可写、事后对账"的设计直接违反 (a)。

幂等三层：对内 job_id 唯一 + 原子写（tmp+fsync+rename）使读方永不见半态，已满足；但**提交幂等性弱**——重复 submit 产生新 job（已记观测，不阻塞）。对外命令行首最近命令词 + 被拒命令记在尝试者头上（为刷单可查）；重复 /claim 应幂等拒绝而非二次上锁。跨面：同一交付重复 /deliver 只认首次证据快照，后续 no-op 并留痕。

### 3.3 租约的统一

- **对内租约 = 三元组**：`claimed.lock`（占位）+ 心跳（存活证明）+ 超时强杀与崩溃恢复（回收）。回收分岔：claimed 无心跳 → 重投；running 崩溃 → 诚实标 error（可能已有副作用，不静默重投）。
- **对外租约 = 72h 到期回 open**：/claim 校验无锁与本人并发上限 → 上锁 + 记到期时间。

**租约是资源的占位，不是权限**，因此时长必须与资源挂钩。设名额 N、平均租约 L：期望吞吐 R ≈ N / L。L 过长 → 名额被死占，R 降、饥饿升；L 过短 → 频繁回收重投，浪费 ≈ 1 −（有效执行时长 / L）。故 L 的下界是任务 P95 完成时长（不腰斩正常任务），上界是可承受的饥饿窗口。

对内 `timeout_s ∈ [5, 3600]` 缺省 600（docs/hive/子代理配置标准_v0.5.md §0，经 hive_spawn 注入；**CLI 直提绕开 MCP 注入，其任务级超时默认值未取证**（复核记录见 §九·2）），对外 72h——四个数量级之差不是随意：对内是分钟级机算且失败可重投，对外是人 + 异步 review，天然天级。推论：**长租约任务应先过更严的准入校验**（对内=依赖完整+成环；对外=难度与声誉门槛），因为长占位的错误代价更高。蜂巢 worker 并发名额数值、对外"本人并发认领数 ≤ 上限"的阈值，均**未取证**。

### 3.4 验收闸的统一骨架

骨架一句话：**机器闸在前、人审闸在后、且人审闸不得自动通过**；前序闸红即不进后续闸（fail-closed，与令牌 fail-closed 同向）。

| 闸 | 对外投影 | 对内投影 |
|---|---|---|
| ① | CI 全绿（机器判，不可辩） | 断言 / 回归 |
| ② | 复现读数（改前 vs 改后逐项对照） | 复现读数（`step_<i>_stdout.txt` head、可复跑命令、elapsed_s/tokens） |
| ③ | 守卫＋定点变异（注入必失败 ⇒ 守卫必红并点名） | 守卫＋定点变异（判据面 + 定点注入） |
| ④ | 维护者人审 | 编排侧裁决：每轮必出 accept / reject / needs_rework 三态之一并留痕 |

**什么样的任务可砍第④闸**——判据必须同时满足五条，任一条不满足即不可砍：

1. **可判性**：存在机器可执行的**充要**判据，不存在"读数对但意图错"的空隙（判据即目标，不是目标的代理指标）；
2. **无外部性**：不改对外契约（接口、协议、字段、状态机、计分规则），只改内部实现；
3. **可逆性**：失败可完全回滚、无残留副作用、无不可逆外发；
4. **无判断载荷**：不涉及取舍（性能 vs 成本、兼容 vs 简洁）——不存在两个都"对"的方案需要选一；
5. **非敏感面**：影响面不含权限、密钥、门禁、账本、状态权威面。

并且：**砍闸 ≠ 自动通过**。免闸必须显式留痕（谁判的免闸、命中哪几条判据），否则等于把闸静默删除。第④闸永不自动通过——即使保留，也必须由裁决位显式给出三态之一，"没意见就过"视为闸失效。

## 四、资源分配：把租约变成可核算的资源

### 4.1 资源维度盘点

| 维度 | 对内现状（蜂巢） | 出处 | 对外现状 | 值班诚实项 |
|---|---|---|---|---|
| worker 名额与并发 | worker 池 + `claimed.lock` 原子领取（单执行者互斥）；**名额数值未取证** | hive/README.md、docs/hive/蜂巢设计_理论对齐_v0.1.md（源码行号引用） | /claim 校验无锁 + 本人并发认领数 ≤ 上限；**阈值未取证** | 两处上限都无取证数值 |
| 模型额度与上下文预算 | `context_budget_tokens` 缺省 200000、`reasoning_effort` 缺省 high、`max_tool_rounds` 默认 5；`context_strict=true` 时超预算即 error | hive/hive_mcp/mcp_server.py（`DEFAULT_*`）、docs/hive/子代理配置标准_v0.5.md §0/§1 | 无 | CLI 直提绕过 MCP 注入，rust 侧无 effort/预算默认 |
| 租约时长 | `timeout_s ∈ [5,3600]`，缺省 600；直提默认 300 | 同上 §0/§1 | 72h | — |
| 优先级 | spec 字段白名单内**无 priority** → 调度面无可显式排序键 | docs/hive/子代理配置标准_v0.5.md §1、docs/hive/蜂巢迭代_宏观与群体调度_v0.1.md §五 | 无显式优先级，仅 difficulty 标签 + 新鲜度 | 缺口，非"未取证" |
| 磁盘与产物面 | `jobs/<id>/{spec.json,status.json,result.json,progress.jsonl,step_<i>_stdout.txt}`；result.json 只留 head 4000 字符；中间件整合后清理 | 同上 §5.4、§7 | issue 线程 + `docs/bounty/ledger.json` + `board.md` | — |
| 心跳观测 | `elapsed_s` / `tokens`；进展卡条目 start/tool/final/handoff/error | hive/wm.py、hive/README.md | 无 | token 为执行器自报 |
| 身份/会话预算 | `session=hive_job_<id>` 硬隔离；L0 召回 800–1200 tokens；L1 默认不读 | docs/hive/主代理子代理记忆架构设计.md | — | — |

### 4.2 分配判据与排序键

四类判据：**难度分**（easy 1 / medium 3 / hard 6 / expert 10，`<悬赏站仓>`注明"建议值待裁"）、**声誉加权**（对外，只作排序与门槛）、**依赖位置**（中观 DAG 的关键路径）、**新鲜度/饥饿补偿**。

关键路径的定义要可算：`crit(t)` = 从 t 出发到根的最长下游链帧数——即 t 的延迟会推迟多少个下游任务，它就是"顺序错误重试熵"的量化。

对内调度面每拍排序（候选集 = pending 且依赖已满足）：

```
K_in(t) = ( -crit(t), prio(t), wait_norm(t), job_id )
wait_norm(t) = (now - created_at) / L_lease(t)；wait_norm > τ 时整条抬到 crit 之前
prio(t) = w_d ∈ {1,3,6,10}
```

`job_id` 作稳定破平，保证排序确定性可复现。饥饿补偿**只对等待超过一个租约周期**的任务生效，避免长尾永久垫底。

对外认领排序：

```
K_out(i) = ( eligible(i), reput(claimant)/w_d(difficulty), wait_norm(i), issue_id )
eligible = 未锁 ∧ 本人并发 ≤ 上限 ∧ reput ≥ g(difficulty)
```

`reput/w_d` 是**匹配式**加权：低声誉者在低难度上排前，高声誉者接高难度时不被难度反压到底——不是惩罚，是配对。`g(d)`、`w_d`、`τ`、并发阈值全部为建议值待裁，**无实测数据**（承接 D-5 BLINDSPOT）。

### 4.3 防饥饿与防抢占滥用

对外五道：本人并发上限（防单人吃满）、expired 立即回 open 不驻留标签（防死占）、最多 3 轮修改 + 超时回板（防无限占用）、声誉可降（虚假交付 −5 / 超时 −1，防劣质占位）、难度配额轮转（防高声誉垄断高难度）。

对内三条，并纠正一个常见误解：**worker 名额公平性不能靠锁来实现**——`claimed.lock` 是先到先得，无队列公平。公平只能落在**排序面**（4.2 的 K_in），锁面只负责互斥。长任务长期占名额的饥饿，靠双层超时（步级 `timeout_step_s` / 任务级 `timeout_s`）回收。额外收益：失败硬传播同时是**资源回收机制**——依赖一红，整条下游链立即转 error 释放名额外，不空转等待。

**抢占的代价与记录**：蜂巢已有 kill 通道 / kill_tree 作抢占原语（hive/test_stop_tree_kill.py 取证存在）。代价三项——(a) 沉没成本：已耗 token 与 elapsed_s 不回收；(b) 重复执行：除非 `need_continue`/`handoff` 可续，且 `auto_continue` 恒为 false，续跑须主代理显式裁决、不自动；(c) 状态抖动：反复抢占使进展卡与终态难判。**抢占必须留痕**：一条事件记录抢占者身份、依据、被抢占 job_id、已耗 elapsed_s/tokens、是否可续。防滥用靠依据白名单化——只允许依赖失败传播、租约超时、死锁探测判定停滞三类触发，**禁止"高优先级随意踢低优先级"**。

### 4.4 成本可见性

借鉴对照组 DS Bot 的用量页（按时间 / bot / 模型统计 token；其序列化发言 + per-member / per-round 上限说明"发言次数本身也是被记账的资源"，仅作对照，不采纳其代码）。

对内记账口径：四键聚合（时间窗 × 群体或 serve 实例 × job_id × model）× 三类计数（prompt / completion / reasoning）。**reasoning 必须单独记**——docs/hive/子代理配置标准_v0.5.md §1 实测：reasoning_tokens 计入 max_tokens，`completion_tokens ≈ reasoning_tokens` 是假成功指纹；不记 reasoning，"高思考低产出"任务在账面上会显得便宜。时间维取心跳 `elapsed_s`，token 维取 result.json / 心跳观测。

对外记账口径：声誉账本是 append-only 事件流，**成本不进账本**——对外结算＝声誉制、不涉资金，唯一可审计物是交付证据（PR / 可复跑读数）。若要成本面，只能从 CI 时长与证据条数派生，且必须标为"间接指标"。

**诚实边界：只报 token 不报钱。** 三条理由：① 单价随网关、档位、时段变化，且中转网关价格不可知——换算是不可验证的假设，违反可验证共识；② 账面 token 是执行器自报，未与 provider usage 对账，是"自报值"不是账单；③ 对外不涉资金是不动边界。若确需金额，须外部单价表 + 显式标"估算"，且**不得用于任何裁决**。

### 4.5 资源分配与声誉的联动

联动画（对外）：

| 声誉 | 资格门槛 g(d) | 并发上限 | 租约 | 排序 |
|---|---|---|---|---|
| 低于下限 | 仅 easy（g=0） | 1 | 标准 72h | 同难度内靠后 |
| 达门槛 | medium 0.2 / hard 0.5 / expert 0.7 | 默认上限 | 标准 | 同难度内按 reput/w_d |
| 高 | 全难度 | 上限 +1（非无限） | hard/expert 可申请加成 | 同难度内靠前 |

即：**低声誉限并发、高声誉不锁资格**；租约加成与难度成正比（难度越高，复现与读数的证据工作量越大）；高难度的"优先"只在**同难度内**成立，不赋予跨难度插队权。

**不联动的理由同样必须写明**：

1. **对内不是「引入」声誉——信任值本来就在**（本稿初版此条有误，已订正）。连接层 `md_cg/links.py` 已实现**跨节点信任** `p_trust`（落盘 `~/.mdcg/_links.json`，0600），四条不可动摇性质：**① 是概率估计不是承诺**（可上调、可下调、可被反例击穿）；**② 有上限 `p_trust_cap`**（受版本对齐度与节点完整度约束，不能靠高频交互刷高）；**③ 有衰减**（`DECAY_DAYS=30` 无观测向初值回归）；**④ 全程留痕**（audit 记录每次变更的证据与依据条款）。数值与状态位：`P_TRUST_INIT=0.8`、`CAP_ALIGNED/INCOMPLETE/MISALIGNED/ISOLATED = 0.8/0.6/0.3/0.0`、`UP_STEP=0.05`／`DOWN_STEP=0.20`（**宪章第七条：降快于升**）、`DEGRADE_BELOW=0.50`、状态位 `probation/normal/degraded/isolated/withdrawn`；另有元认知信任面 `p_trust/p_gap` 由 confirmed/weakened 事件聚合。
   **故本条的问题不是「是否引入」，而是「如何把既有信任值接到资源分配上」**。worker 无状态**不构成障碍**——信任值不挂在 worker 上，而挂在**认知图链接层**（持久、可衰减、可聚合、有上限）。
2. **声誉不得决定"能不能做"，只决定排队顺序与配额**。否则刷分即资源垄断；且声誉可降（悬赏站已定）使"高声誉=永久特权"不成立。
3. **防刷分导致垄断三条硬闸**：高难度保留配额（高声誉者不得同时占满全部 expert）；排序加权饱和有上界（高声誉拿到的是"同等条件下先"，不是"无条件先"）；每周期从公开账本整体重算，不做增量信任累积（防历史刷分当资产）。
4. **两个既有缺口都属「通道未打通」，不是「能力不存在」**：
   - **(a) 对外 → 对内未接**：悬赏站内部信任镜像未接线（v0.1 只落公开面）⇒ 外部声誉目前进不了内部信任面。
   - **(b) 对内 → 资源分配未接**：既有实测已确认——全仓**无信任分级体系**（无晋升/降级阈值）、健康分不影响信任、修正信号不改信任（`docs/swarm/蜂群同错检测实验协议_v0.1.md` §2.5）；蜂群运行时的信任值变化来源仅「实例程序自身的德指令」与「实例故障时沿用上轮」，跨实例传播只有路由 payload 的 `@trust` 占位符一种形式。
   - **且阈值本身未标定**：`UP_STEP/DOWN_STEP/DECAY_DAYS/PROBATION_SECONDS` 均为**未标定占位值**（蜂群互联 §4.3：「只声明结构，不宣称权重数值」）。
   **结论**：可接线的**基座已存在**，缺的是「读信任值 → 进排序键/配额」这段通道与阈值标定。在此之前，基于信任值的配额仍**不得进判定路径**（缺口在接线，不在能力）。

回到使用者命题：对外悬赏站与对内蜂巢是**同一套架构的嵌套**——外层挂在"需求"（issue 线程为权威面，租约以天计，闸后有人审）；内层挂在"实例"（文件协议为权威面，租约以分钟计，闸后是编排裁决）；两层共用同一条状态骨架、同一套"单点权威 + 只做镜像"的幂等纪律、同一个"机器在前人审在后"的闸序。L0/L1/L2 与 session 硬隔离，是这条命题在记忆面的同一投影：外层记的是协作史与声誉，内层记的是作业留痕与全局态。

## 五、群聊：人可对话的团队入口

### 5.1 定位：群聊是交互面，蜂巢是执行面

分工只有一句：**群聊负责把人的意图变成 spec，并把状态展示给人；调度语义一条都不许落在群聊里。** 调度归蜂巢三层——微观问「哪个进程跑它」（`claimed.lock` 互斥），中观问「它什么时候能跑」（`spec.depends_on` 静态 DAG + 失败硬传播），宏观问「哪个群体跑它」（群体注册表与能力路由，规划中）。群聊既不产出 `claimed.lock`，也不产出 DAG。

**理由有两条。**

其一，**两类语义的载体不同**。群聊的载体是自然语言对话，其天然能力是澄清、追问、确认；DAG 的载体是 `spec.json` 里的 `depends_on` 字段，需要提交侧无环检测、存在性校验、调度侧终态检查三处强制点。把依赖关系表达成「大家按顺序说话」，等于把可机械校验的约束降级成需要参会者自觉遵守的礼节——而礼节的失效是静默的。

其二，**反例就摆在对照组**。DS Bot 的群聊有序列化发言（上一人 posted 或 passed 后下一人才开始），这条规则确实保证了「一次只有一人在说」，但它是**发言权互斥**，不是**任务依赖**。时间序不等于依赖序：它无法表达「B 必须在 A 完成后开始」，原因有三——(a) 发言顺序是 roster 序（admin 优先），是与内容无关的固定拓扑，A 说完只代表轮到 B，不代表 A 的产物可用；(b) 没有失败传播，A 在发言中失败不会使 B 被级联取消，B 会照常执行并在错误的输入上产出结论；(c) 没有终态概念，DS Bot 无法区分「A 说完了」与「A 的产物已被验证」。三者合起来的结果是：**它能表达人对人的会议，不能表达机器对机器的流水线。**

因此灵枢的边界是：**人可以对群聊说话，群聊不可以对蜂巢下调度指令。** 群聊唯一的出口是 spec——由 admin 写成 `spec.json` 并走 `hive_spawn` / `submit`（工作纪律第 17 条：执行性任务统一走蜂巢留痕）。

### 5.2 发言纪律（逐条对照 DS Bot）

| DS Bot 规则 | 灵枢处置 | 理由 |
|---|---|---|
| 序列化发言（一次一人） | **采纳，但改造为显式发言令牌** | 采纳「互斥」这一性质；改造其判据。DS Bot 靠「上一人 posted 或 passed」隐式推断发言权交还，成员崩溃或长时间思考时无法区分「在说」与「死了」。灵枢改为显式租约：主持人发放发言令牌并记到期时间，超时即收回——与蜂巢 `claimed.lock`、悬赏站 `lease` 同构，一套机制三处复用 |
| 发言顺序 = roster 序（admin 优先） | **不全采纳** | roster 是固定拓扑，与任务无关。灵枢的顺序由**当前任务的 DAG 与未决项**决定：谁持有待裁决信息谁先说；admin 的优先仅保留在**收口位**（合并结论、写 L0） |
| @ 传唤 + per-member/per-round 调用上限 | **采纳，附加条件** | 上限必须保留，否则群聊退化成广播风暴，注意力预算被无差别消耗。附加条件：传唤必须携带**待决项或信息缺口**（对应卡片「未决项：」槽），无理由的传唤按噪声记账在发起者头上——对齐悬赏站「被拒命令记在尝试者头上」的防刷单口径 |
| [PASS] 沉默 | **采纳** | 这是本组最有价值的一条，本质是**注意力经济的社会版**：没有新信息就不占用带宽。灵枢补一条：PASS 也要落盘（一条极短记录），否则「没说话」与「没参与」在事后不可区分，审计面出现空洞 |
| admin 中介（默认只 admin 回） | **采纳中介，剥离裁决** | admin 是使用者的代理，职责是**中介与裁剪**：把人的话变 spec、决定叫谁、给成员裁剪上下文。它不做技术裁决——同条件异值的冲突交由 CCG 冲突检测给出 `DEFER`，再由融合裁决位（副代理／设计者视角）裁决；权限面动作归 designer 令牌（`review_decide` require_admin）。DS Bot 的「主 bot 高权限管所有群」是单点，灵枢把「中介权」与「专业裁决权」「权限面终裁权」三者分离 |

### 5.3 人的位置：唯一 root 是使用者

使用者是全系统唯一 root，admin 只是其代理。分层如下（**每层写「不能做什么」**，因为权限设计的失效总发生在越权侧）：

| 层 | 可做 | **不可做** |
|---|---|---|
| **使用者（root）** | 定目标、定边界、终裁权限面与不动边界（资金与账号） | 不得绕过留痕直改盘面产物（否则证据链断裂） |
| **admin（使用者代理）** | 意图→spec、裁剪上下文注入、决定叫谁、主持收口、写团队 L0 | 不得代行技术裁决（归融合裁决位）；不得放开资金与账号边界；不得读取成员的个体私聊 session |
| **成员（内部子代理／五单元）** | 读裁剪注入的上下文、发言、写**自己 session** 的卡片与细节 | 不得召回他人 session；不得写 knowledge 层（验证单元的 `layers_allow` 不含 knowledge——`md_cg/mdcos.py:5322` 明载 verifier 的 `layers_allow=rejected/contextual`，`md_cg/security.py:94` 定义该可写层白名单；写入直接 `AccessDenied`，「自己写、自己验」在结构上不成立）；不得改公开面账本 |
| **外部认领者** | 经悬赏站命令面认领／交付／争议；读公开面账本与荣誉榜 | 不进群聊（见 5.5）；不得读大脑库任何 session；不得触发内部记忆写入；未过验收四闸的结论不得进 L1 |

### 5.4 会话隔离：群永不读成员私聊

DS Bot 让每个成员在群里拥有一个自己的隐藏 Session，群永不读成员私聊。灵枢的等价物**不需要新机制**：大脑库的 `session` 过滤是硬隔离——实测同一库内 `session=None` 返回全部 16 条，`session="main"` 只返回 1 条，`session="subA"` 只返回该成员的 5 条。群聊只需占一个独立 session（如 `chat:<群标识>`），物理上就看不见 `main` 与 `sub:*`。

逐条划定跨成员可见性：

**允许共享**：① 团队 L0 全局态（由 admin 裁剪后**注入**，不让成员自行 recall，理由见既有三层记忆设计阶段 2）；② `spec.json` / `result.json`（经**文件协议**共享，不经记忆库）；③ 公共规则（卡片规范、工作纪律公开面）；④ 公开账本与荣誉榜。

**禁止共享**：① 他人私聊／他人 session 的任何条目；② 个人长期记忆（大脑库私密面）；③ 含敏感信息的文档——按**工作纪律第 9 条**只留私有库，不进群聊上下文、不进团队卡片、不进公开面，推送描述不写敏感词；④ 未过验收四闸的外部交付结论，不得进团队 knowledge 层；⑤ 内部信任镜像的分值与权重，不得出现在群聊或公开面。

### 5.5 与悬赏站的接驳：外部认领者不进群聊

**结论：不进。** 理由三条：① 群聊是内部交互面，参会者共享被裁剪的内部上下文，外部主体进入即引入**上下文投毒与隐私越界的双向面**；② 外部协作需要的不是共处一个会话，而是**结构化接口**——`/claim`、`/deliver <PR 或证据>`、`/withdraw`、`/dispute <理由>` 四条命令加公开账本已足够，状态权威面在 issue 线程本身；③ 六态状态机（open→claimed→delivered→verified→settled，另 expired / disputed）与验收四闸是**可机器判定的**，把判定权交给群聊对话只会引入不可复现的裁量。

替代接驳面：外部认领者的全部可见输出 = issue 线程 + `docs/bounty/ledger.json`（append-only）+ `board.md`（由账本机械生成）。内部对外的全部输入 = 同一账本。**两侧不共享上下文，只共享账本事件。** 若未来开只读外部频道，前置条件是：只读、只对单一 bounty 会话、无写记忆权限、无 @ 传唤权。

## 六、团队记忆：三层结构 + 内外双层账本

### 6.1 三层记忆在团队层与项目层的嵌套

直接复用 `docs/hive/主代理子代理记忆架构设计.md` 的 L0 全局态 / L1 卡片层 / L2 细节层，加 `session` 硬隔离与 `derived_from` 溯源。使用者的命题是「同一套架构，嵌套一层」，具体落法是**递归套用「主代理-子代理」关系**：

- **团队层**：admin 是团队主代理，其「子代理」是各个项目；团队 L0 记跨项目的目标、阶段、待决与决策链。
- **项目层**：项目编排者是项目主代理，其子代理是五单元与 worker；项目 L0 只记本项目状态。
- **执行层**：worker 的 L1 卡片与 L2 细节。

寻址方式（`session` 为任意字符串，硬过滤已实测）：

| 层 | 写入者 session | 读取者用哪个 session / layer |
|---|---|---|
| 团队 L0 | `team:<团队>` | admin：`session="team:<团队>"`，`budget_tokens=1200` |
| 项目 L0 | `proj:<项目>` | 项目编排者：`session="proj:<项目>"` |
| L1 卡片 | `sub:<任务>` | 上层按 task 号**定向取**，不默认召回 |
| L2 细节 | `sub:<任务>` + `layer="contextual"` | 仅追问时按 id 精确取单条 |

**层级不越读**：项目编排者不得读团队 L0 之外的团队 session；admin 默认不读项目 L1。跨层连接靠 `derived_from`，不靠放宽过滤。

### 6.2 记忆的三条边界

| 层 | 谁能读 | 谁能写 | **禁止进入** |
|---|---|---|---|
| **个人长期记忆**（大脑库，私密） | 仅本人 session 的持有者 | 本人 | 群聊上下文、团队卡片、公开面——**按第 9 条**，含隐私内容只留私有库 |
| **内部团队记忆**（同一库，按 session 与单元隔离） | 该 session 持有者 + admin 裁剪注入 | 该 session 持有者；写 knowledge 层受 `layers_allow` 约束 | 个人私密条目；未验证结论；外部认领者的原始过程 |
| **对外公共记忆**（悬赏站账本，公开可查） | 任何人（含外部） | 仅命令面产生的状态变更 | 任何内部 ID／内部路径／内部信任分；**按第 14 条**，公开产物须过内容政策合规与隐私双清单 |

关键点：**同一套 `session` 机制同时服务私密与隔离**，边界差别不在机制而在谁能持有哪个 session 标识——这就是「同一套架构、嵌套一层」的实质。

### 6.3 内外双层账本

公开面 = `docs/bounty/ledger.json`（append-only 事件流）+ `board.md`（由账本机械生成，不手工编辑）。内部面 = 同一账本的**可检索镜像**，供内部信任权重使用；v0.1 只落公开面，**内部面待接线**。

> **注意（订正）**：这里的「内部信任权重」**不是待建设的新能力**——连接层 `md_cg/links.py` 的跨节点 `p_trust` 已是既有的对内信任载体（含上限、衰减、留痕四性质）。待接线的是**账本事件 → 信任值**这一条通道，而非信任机制本身。

内部镜像的用途判据（只此三类）：① **内部信任权重**——决定后续任务派发给谁；② **资源分配**——编排者的注意力与队列优先级；③ **经验晋升**——哪些外部结论值得进 L1（见 6.4）。镜像的查询结果不得成为对外的评分公示。

**单向性规则（三条，缺一则账本失去证据价值）**：
1. **镜像只读**：内部面不产生任何账本事件，不修改、不删除、不重排公开面。
2. **纠正靠追加**：公开面无「撤销」，判错只用新事件覆盖（争议败诉不扣本金但记录在案，本身就是追加语义）。
3. **镜像必须是公开面的纯函数**：镜像可从公开面完整重建；不得存在「只在内网可见」的原始事实。若镜像与公开面不一致，以公开面为准。

### 6.4 经验晋升通路

一个外部交付通过**验收四闸**（CI 全绿 → 复现读数对照 → 守卫＋定点变异 → 维护者人审，人审不许写成自动通过）并进入 `settled` 后，其结论可晋升为内部团队记忆：

**判据**：四闸全过 + 可复跑读数可复现 + 状态为 `settled`（非 disputed）。

**落点**：写 `session="team:<团队>"` 的 L1 卡片，`importance=0.7`（≥0.7 触发 `protected`，不可遗忘），`verification_basis` 取白名单值（CI／测试→`test`，复现读数→`measurement`，人审仍归 `other`），`derived_from` 指向账本事件 id 与验收记录。

**去重**：按卡片「功能名＋子功能＋生效条件」槽位比对。同槽同值→合并引用；同槽异值→`DEFER`，由主代理裁决是更正还是分支（「是更正还是分歧」正是主代理该回答的问题）。

**署名与出处**：卡片必须携带外部认领者身份与账本事件 id，**晋升不得抹除声誉归属**——声誉归外部，认知归内部，两者不冲突。

**未验证不写入**（工作纪律第 5 条）：未过闸的交付只停留在公开面的 `delivered` / `disputed`，不得生成 knowledge 层条目；确需留档的，只能写入 `layer="contextual"` 并在结论行显式标注「未验证」，且不得被当作已固化知识召回。

### 6.5 记忆的衰减与退役

退役 ≠ 删除。退役 = 标记 `retired` 并保留 id 与 `derived_from` 链，保证溯源不断。

**可退役判据**（满足其一）：① 结论已被更新卡片取代且溯源链完整；② 纯细节、无下游引用（L2 是只增不减的，需按大任务周期主动 `scrub`／`forget`，这是本架构唯一需要主动运维的地方）；③ 与任何未决项无关且长期零召回。

**不可退役判据**：① 公开面声誉事件；② 验收记录与裁决留痕（每次裁决生成带哈希的审核记录）；③ 任何被 L0 引用的卡片。理由：这些条目一旦可删，账本就退化为可变数据库，审计无从复现。**append-only 的意义就在这里——不是「记得多」，而是「任何时刻都能证明当时记的是什么」。**

## 七、分期路线与能红判据

分期原则：**先接线、再交互、后分配、最后对外深化**；每期的进入条件未满足不进下一期，每期的完成判据必须**能红**（可构造一个必失败的检验）。

### P0 · 接线（最高优先，改动面最小）

| 项 | 内容 | 能红判据 |
|---|---|---|
| 团队/项目 session 规约 | 定义 `team:<团队>` / `proj:<项目>` / `sub:<任务>` 三类 session 命名，并写进派发纪律 | 构造一次跨 session 读取（`session="proj:X"` 读团队 L0）→ **必须取不到**；取到即判据失效 |
| 内部信任镜像接线 | 悬赏站账本 → 内部可检索镜像（单向、纯函数） | 把镜像删掉后从公开账本重建 → **必须逐字段一致**；不一致即非纯函数 |
| 派发留痕对账 | 蜂巢 job（spec/status/result）与认知图 L1 卡片按 `derived_from` 对账 | 抽一条已完成 job → 其卡片必须能反查到 `result.json` 与 job_id；查不到即断链 |

### P1 · 群聊交互面（本设计新增的唯一组件）

| 项 | 内容 | 能红判据 |
|---|---|---|
| 最小入口 | admin 中介 + 意图→spec 出口 + 状态展示（只读） | 人的一句话能产出**一份合法 spec** 并走蜂巢留痕；产出不了即未通 |
| 发言纪律 | 显式发言令牌（租约式）+ `[PASS]` 沉默并落盘 + 传唤须携带待决项 | 注入一个「无待决项的传唤」→ **必须被记为噪声**；不记即纪律未生效 |
| 隔离 | 群聊占独立 session，物理不可见 `main` / `sub:*` | 群聊 session 召回**必须取不到**任何成员私聊条目 |

### P2 · 资源分配落地

| 项 | 内容 | 能红判据 |
|---|---|---|
| 排序键 `K_in` | 关键路径 `crit(t)` + 优先级 + 饥饿补偿 + job_id 稳定破平 | 同一候选集重复排序 → **逐位一致**（确定性）；不一致即破平失效 |
| 抢占留痕 | 只允许三类触发（依赖失败传播／租约超时／死锁判停滞） | 构造一次「高优先级踢低优先级」→ **必须被拒**；不拒即白名单失效 |
| 成本口径 | 四键聚合 × 三类计数，**reasoning 单独记** | 构造一个「高 reasoning 低产出」任务 → 账面**必须不显得便宜**；显得便宜即口径漏项 |

### P3 · 对外深化

| 项 | 内容 | 能红判据 |
|---|---|---|
| 经验晋升通路 | 过四闸且 `settled` 的外部交付 → 晋升为团队 L1 卡片（带出处与署名） | 构造一个 `disputed` 交付 → **必须无法晋升**；能晋升即闸失效 |
| 声誉→资源联动 | 门槛/配额/租约加成按声誉分层（**同难度内**优先，不给跨难度插队权） | 高声誉者尝试占满全部 expert 名额 → **必须被配额拦下** |
| 四闸对内的等价物 | 编排侧裁决「每轮必出 accept / reject / needs_rework 三态之一」 | 一次「没意见就过」→ **必须判为闸失效**并留痕 |

**四期共同的前置门**：P0 的 session 规约与派发纪律必须先落——否则后续所有隔离与对账都建立在未定义的口径上，等于在沙地上盖楼。

### 8.2 待使用者裁定（不自行决定）

1. **文档落点**：本稿现在落在哪一侧？（本仓 `docs/plans/` ／ 悬赏站仓 ／ 两边各一份并在各自索引登记）——跨仓设计的归属需要先定，否则后续引用会分叉。
2. **群聊形态**：DSH 插件（人可直接对话的界面）／蜂巢的只读状态可视面／**先只定协议不落界面**？——本稿按"交互面"设计，但**没有选形态**，因为形态决定了后续是插件工程还是脚本工程。
3. **资源分配范围**：只做 worker 名额与租约，还是**同时纳入模型额度与成本记账**？（后者需要 provider usage 对账，本稿的诚实边界是"只报 token 不报钱"）
4. ~~对内是否引入声誉~~ → **该待裁项已撤销**（使用者 2026-10-11 指出：「声誉不是引入的，我们本来就有，信任值」）。经复核 `md_cg/links.py`：连接层跨节点信任 `p_trust` 是既有能力（四性质：概率估计非承诺／有上限不可刷高／有衰减向初值回归／全程留痕），元认知面另有 `p_trust/p_gap`。**本稿初版「worker 无状态 ⇒ 无持久声誉载体 ⇒ 不宜引入」的论证前提有误**——信任值挂在认知图链接层，不在 worker 上。**真问题改为**：如何把既有信任值接入资源分配与门禁（接线缺口见 §8.1 与 ch4·4.5），以及标定其占位阈值。
5. **计分与阈值是否照建议值**：若不照，需要一套校准实验（本稿不含）。
6. **分期优先级**：P0→P3 的排序是否照本稿（先接线、再交互、后分配、最后对外）？

### 8.3 本稿的自我边界

- 本稿是**设计稿**：所有状态机、闸序、排序键都是**结构与判据**，不是实现；任何一期开工前须先过对应期的前置门（§七）。
- 本稿**没有实现代价评估**：三单元撰写共耗 ~476k tokens（见 §九·4），但那只是**写稿**成本，不等于实现成本。
- 本稿**没有做对抗性验证**：未构造"故意破坏"实验证明这些闸在真实攻击下有效——这是设计稿与实测之间的标准缺口，须由 §七 的能红判据在实施期补齐。

## 九、编排侧复核补正

三章正文由蜂巢三单元产出，编排侧逐条复核后做了 **3 处定点补正**，记录如下（**保留而非抹除**，以便追溯判断偏差的来源）：

**1. 蜂巢当前状态的表述错位（真实纠错）**
- 初稿（输出单元）称「蜂巢现处『迭代产品·暂时停用』态」。
- **实测订正**：`hive/README.md:21` 记「迭代状态：**实测迭代期**（2026-09-22 起）」；`:23` 写明「蜂巢于 2026-09-22 曾转『迭代中的产品』暂停常规派发；**同日使用者裁定进入实测迭代**」。
- **根因**：把历史暂停态当成了当前状态。**证据是活的**——本设计稿自身的三个章节就是经蜂巢派发在实测迭代期内完成的（§九·4），若蜂巢确在停用态，本稿不可能存在。
- **教训**：读文档时要区分「历史沿革」与「当前状态」，两者常写在同一段里。

**2. 「CLI 直提默认超时 300」缺证（撤销断言）**

**3. 初稿一处断言经复核**有据**（保留并补出处）**
