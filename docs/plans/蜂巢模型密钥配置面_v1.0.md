## 一、背景与病根（N200：一变量双角色）

### 1.1 病根陈述

`HIVE_API_KEY` 在改造前同时承担两个互不相干的角色：

| 角色 | 位置 | 生效形态 |
|---|---|---|
| **锚密钥链尾**（结果完整性锚 P11 的密钥来源） | `hive/src/keyres.rs` 旧版链第三环 `env("HIVE_API_KEY")` | 谁配了模型密钥，谁就能签锚 |
| **LLM 网关密钥**（执行器调 chat/completions 的凭据） | `hive/exec.py` 的 `_post_chat` | 执行器干活所必需 |

缺陷台账的原始判据（`docs/eval/缺陷挖掘_自主迭代_v23.md` 的「F. N200」段，high，留档·大设计决策）：一变量双角色 = **判据面与身份面混同**——「谁有权签锚」退化为「谁能调模型」；同时批次65 的 env 剥离把该键从每个执行器子进程无条件摘掉，导致 serve 派发的全部 LLM 任务确定性失败。

### 1.2 批次65 的显性回归（N185）

批次65 把 `HIVE_API_KEY` 列入 `ORCH_SECRET_ENV_KEYS` 三键、每次 `spawn_executor` **无条件** `env_remove`，且只在 `spec.orchestrate` 为真时重注身份两键——`HIVE_API_KEY` **永不重注**：

- 剥离面（旧）：`hive/src/exec.rs:85-86` 三键常量；`:134-135` 无条件 `env_remove`；`:137` 起仅 orchestrate 重注。
- 后果（现码同位置仍可见该约束）：`hive/exec.py` 的 `_post_chat` 经 `model_endpoint()` 取键，键为空即抛 `RuntimeError`（抛出点在 `model_endpoint` 内）→ 执行器在首次 API 调用前即退。
- 台账证据（材料，非本轮实跑）：v23 复核会话 A/B 实跑——哑 dumper 作执行器经 serve 跑，落盘 env 实测**无 `HIVE_API_KEY`**；同 spec 以仓内 `exec.py` 经 serve 跑 → `state=error`、`error="RuntimeError: HIVE_API_KEY 未设置…"`；同一 spec 带哑密钥直跑 `exec.py` → 走到网络调用（两臂唯一变量即 env 剥离）。

**结论**：标准部署下 serve 派发的全部 LLM 任务（`exec.py` 直路与 `orch.py` 编排路复用同一 `_post_chat`）在首次 API 调用前确定性落 error——**主能力全断，无需攻击者**。

### 1.3 本机实测现状（本轮只读观察）

| 观察项 | 读到的事实 | 证据 |
|---|---|---|
| 本机锚的实际来源 | `hive/config.local.json` 里 `HIVE_ORCH_TOKEN_FILE` 为**直值非空**、`HIVE_ORCH_TOKEN` 未设、`HIVE_API_KEY` 为 `{"env": "DEEPSEEK_API_KEY"}` ⇒ **锚链首环就命中身份令牌文件** | 逐键形态只读列举（未打印任何值） |
| 在役 serve 是否带上批次65 剥离面 | 最近三个作业均为 LLM 任务（`model=deepseek-flash`）`state=done`、`result.json` 带 `result_anchor`，创建时间 2026-09-27 14:55–14:58；而在役 `hive/target/release/hive.exe` 的构建时间为 **2026-09-26 12:44** ⇒ **运行中的二进制尚未带上剥离面** | `hive/jobs/*/status.json`、`hive/jobs/*/result.json` 只读摘要 + 二进制 mtime |
| 运行态 | 心跳新鲜（age ≈ 0.22s）、`workers=4`、`exec_mode=deterministic+llm` ⇒ serve 在跑，本批未动 | `hive/jobs/_serve.json` 只读 |

**故本机的真实影响是「功能回归风险」而不是已发生的密钥泄露**：

1. **锚泄露/混同面休眠**——锚密钥实际来自令牌文件，「链尾 = 模型密钥」这条混同路径在本机部署上根本没被用到；
2. **功能回归尚未落地**——在役二进制仍是批次65 之前的构建（LLM 任务照常 `done`），但**下一次 `--rebuild`/重启就会把「LLM 任务全断」带上线**（v23 台账同向记载：「该回归尚未落地、下次 --rebuild/重启后落地」）。

⇒ 本批的价值在于：**在该回归上线之前把契约修正掉**，而不是修一个已经发生的事故。

## 二、设计（三角色分离）

### 2.1 角色表

| 角色 | 键 | 是否默认进执行器 env？ | 判据/依据 |
|---|---|---|---|
| **模型（网关）密钥**（唯一默认项） | `HIVE_API_KEY` / `HIVE_API_BASE` | **是**（默认继承） | 普通配置：执行器调模型所必需。`hive/exec.py` 的解析段（`USE_SUBAGENT_LLM_KEY` / `_llm_switch` / `_endpoint_parts` / `_missing_key_msg` / `model_base` / `model_endpoint` / `_bind_llm_spec`）；`hive/README.md` 的 env 表 `HIVE_API_KEY` 行 |
| **身份锚 / 身份令牌**（独立） | `HIVE_ORCH_TOKEN` / `HIVE_ORCH_TOKEN_FILE` | **否**，唯一例外 `spec.orchestrate` 真值任务条件重注 | `hive/src/exec.rs` 的 `const ORCH_SECRET_ENV_KEYS` 两键常量 + `spawn_executor` 的条件重注段；同两键 = 锚密钥链两环 `hive/src/keyres.rs` 的 `resolve_key_from_env` |
| **子代理覆盖**（可选开关） | `HIVE_SUBAGENT_API_KEY` / `HIVE_SUBAGENT_API_BASE` | 是（普通配置） | `hive/exec.py` 的 `_endpoint_parts`；`hive/orch.py` 的 `sub["use_subagent_llm"] = True` 只写布尔开关 |

### 2.2 三条设计决策

1. **模型密钥 = 唯一默认项，默认继承给执行器**。收回批次65 对 `HIVE_API_KEY` 的剥离：它从 `ORCH_SECRET_ENV_KEYS` 出表（`hive/src/exec.rs` 的 `const ORCH_SECRET_ENV_KEYS`），两种任务形态一致到达执行器（`hive/src/exec.rs` 的 `spawn_executor` 头注段）。
2. **身份锚独立且不进执行器、orchestrate 例外**。剥离判据从「键名里带不带 API/TOKEN」改为**身份**（`hive/src/exec.rs` 中 `const ORCH_SECRET_ENV_KEYS` 之前的常量 doc 口径陈述）：执行器持身份令牌即可对任意任务自签合法锚（keyres 不可伪造性对最暴露进程失效）、或以 serve 身份认领 principal；编排任务（执行器 = `orch.py`）需要令牌派生收窄身份（`orch.py` 的 `load_principal` fail-closed），故按 `spec.orchestrate` 条件重注，且**重注面 = 剥离面 = 同一常量**（`hive/src/exec.rs` 的 `spawn_executor` 内重注循环，杜绝两处清单分叉）。
3. **子代理覆盖为可选开关**。spec 只承载布尔 `use_subagent_llm`，**密钥值与地址只从 serve env 读**（`hive/exec.py` 的 `_llm_switch`、`_endpoint_parts`）——spec 会落盘、进 log/result、被编排链与读取方看见，一旦允许携带值，写 spec 者就能让执行器把任意凭据发往任意地址。半套覆盖（开关真、子代理密钥缺）= 主密钥 + 子代理网关的跨网关错配，故**整组回落主配置**（`hive/exec.py` 的 `_endpoint_parts` 内整组回落分支）。

### 2.3 与 v24 裁决建议的关系（必须说清的口径选择）

`docs/eval/缺陷挖掘_自主迭代_v24.md` 的「5.1 N200 裁决建议」段给出三案，推荐 **方案 A（新增专用变量 `HIVE_LLM_API_KEY` + 条件注入）**、次选 **方案 B（按需重注原键）**、不建议 **方案 C（短时作用域凭据）**。

**本批既不是 A 也不是 B**，而是第三条路：**让模型密钥回到批次65 之前的地位（普通配置、默认继承），同时把它从锚链尾摘掉**（消掉双角色的另一半）。

理由：① 模型密钥本来就是执行器干活的必需品，机密等级与身份锚不同——批次65 把它当身份面是判据混同；② 零新变量、零新注入判据（A 会引入「任务类型决定是否注入」的第二个判据面，B 会让剥离面按任务类型而非进程类型变化）；③ 锚链收窄为身份两环后，执行器即使持有模型密钥也**无法自签锚**——「执行器不持 serve 密钥」这一不变量收敛为「执行器不持**身份**密钥」，与 `hive/src/exec.rs` 的常量 doc（`const ORCH_SECRET_ENV_KEYS` 口径陈述）一致。

代价（如实）：这是**契约变更**——把「`HIVE_API_KEY` 不在执行器 env」从既有契约翻转为「必须在」。三条既有断言随之同步（§三末尾逐条列明），这是本批唯一的测试期望例外。

## 五、验收步骤（用户怎么验）

### 5.1 只读看配置：`--show-config` 看什么

```cmd
:: 在 hive 目录下（或给 --config 指向你的配置）
python serve_start.py --show-config
python serve_start.py --status          :: 心跳 + 任务统计 + 同一份 config_summary
```

四栏读法：

1. **`source`**——确认密钥来源是你预期的形态：`直值` / `env:<系统变量名>` / `file:<路径>`。若你期望引系统变量却看到「直值」，说明密钥被写死在配置文件里了。
2. **`masked`**——形式为「少量前缀 + `len=N` + `sha256:<8位指纹>`」，用来比对「是不是我期望的那把 key / 有没有被换过」。**任何情况下都不出明文**（这是单点函数 `hive/serve_start.py` 的 `mask_secret` 的承诺）。
3. **`role` 与 `reaches_executor`**——本次改造的核心验收点：
   - `HIVE_ORCH_TOKEN` / `HIVE_ORCH_TOKEN_FILE` 必须是 `身份令牌` / `身份锚` 且 `reaches_executor=False`（note 会写「仅 spec.orchestrate 任务条件重注」）；
   - `HIVE_API_KEY` 必须是 `模型密钥` 且 `reaches_executor=True`（模型密钥是执行器干活的必需品）；
   - `HIVE_SUBAGENT_API_KEY` / `_BASE` 为 `子代理覆盖`（可选，未设也逐键列出并标 `empty`）。
4. **`problems` 与 `conclusion`**——缺模型密钥时会点名该配哪个键（并给出 `{"HIVE_API_KEY": {"env": "DEEPSEEK_API_KEY"}}` 这样的示例形态）或提示声明 `HIVE_LLM_DISABLED`；身份面两键皆缺时会提示「锚判据整体不启用（安全方向降级，行为=旧产物判据）」。

注意语义：`ok` 的含义是「**这份配置能拉起 serve 吗**」，故缺密钥时 `--show-config` 仍输出完整 JSON，但 `ok=false` 且 CLI 退出码为 **1**（沿用 `emit` 的既有 0/1 口径）——它是诊断面，不是失败。`--show-config` / `--status` 属只读动作：不改 env、不落盘、不探测/拉起任何进程。

### 5.2 何时生效（关键）

| 改动面 | 生效时机 | 依据 |
|---|---|---|
