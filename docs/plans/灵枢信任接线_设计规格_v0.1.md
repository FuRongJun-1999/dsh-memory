## 〇、结论先行

**一句话**：把既有信任值接进资源分配 ＝ **读向三条闸 ＋ 写向一条闭环 ＋ 一张档位表**。而它的定位是一句更根本的话——

> **信任值接的是「给谁做」（跨对端派发），不是「谁先做」（单机 worker 池排队）。**

**为什么只能是这个定位（三条硬约束合围）**：

1. `hive_spawn` 入参白名单 `SPAWN_ALLOWED_KEYS` **19 键，逐键点名后无 `priority`／无 `trust`／无 `quota`**，且未知键**显式拒绝**（不静默丢弃）⇒ 信任**不可能**作为 spec 键进入内核；
2. **D-005**（rust 侧纯 std 零 crate）不破 ⇒ 内核不得引入信任库或打分逻辑；
3. **「文件协议即接口」**（spec.json/status.json/result.json/kill 四文件 + 心跳）⇒ 任何跨面语义都必须能落到这些文件的键上，落不到就不存在。

三条合起来只剩一个落点：**信任决策在派发侧（编排者）完成**，以「派或不派／派给谁／给多大预算」的形式**在 spec.json 落盘之前物化**。**内核行为对信任零感知**——对它而言，一次被拒的派发与「本就不该派」的派发不可区分。

**三件产出**：

| 产出 | 内容 | 补的是哪个缺口 |
|---|---|---|
| **读向**（§二） | 资格门槛闸 ＋ 配额闸 ＋ **状态位硬闸**（`isolated`/`withdrawn` 一票否决） | 让信任能约束派发 |
| **写向**（§三） | 任务终态 → `observe` 的闭环：责任归属判据 ＋ `job_id` 幂等 ＋ 防自放大 ＋ 验签策略 | 补「修正信号不改信任」「健康分不影响信任」 |
| **分级**（§四） | 连续 `p_trust` → **既有状态位**档位（不自造第二套状态名）＋ 待遇绑定 ＋ 滞回与复检 | 补「全仓无信任分级体系」 |

**一条必须先说清的闭环必要性**：读向接线**单独上线会让信任单向消耗**。正信号（`done`）当前没有任何生产者，而 `UP_STEP=0.05` 在没有调用者时等于**常量 0**；负信号（`-DOWN_STEP=0.20`）照常生效 ⇒ `p_trust` 单调下行，跌破 `DEGRADE_BELOW=0.50` 自动降级，终局是**全群无派发资格**。**写向闭环不是配套，是读向不自杀的前提。**

**本规格不做什么**：不改 `md_cg/links.py` 内核（除 §三·3.4 与 §四·4.2 明确标注为「建议」的两项外）；不改蜂巢内核；不新增 spec 契约外字段；不含实现代码。**本规格自身是设计稿，不是实现。**

## 一、接线面盘点：可用的信任面与资源面

### 1.1 可用的信任面

信任面 = 连接层（蜂群互联层 1），实现于 `md_cg/links.py`（658 行），落盘 `~/.mdcg/_links.json`（0600），真源 `docs/swarm/蜂群互联_v0.1.md`。

**读向 API**：
- `load(path) -> dict`（`md_cg/links.py::load`）：返回 `{schema, links, updated_at}`；文件不存在或解析失败回落空结构，不抛错。这是读取 p_trust / status / p_trust_cap 的唯一读原语。
- `links_file(path)`：路径解析单点（`MDCG_LINKS_FILE` 环境变量 → 默认落盘路径），本设计不得另设第二路径口径。
- CLI action 面：`card / policy / evidence / publish / peers / export / import`（`links.py` action 集合）。上述七项**未逐行取证**具体字段与返回形态，本设计不引用其内部结构。

**写向 API（唯一入口）**：`observe(peer, *, evidence, positive=True, subsystem, peer_signature, path, signers_file, actor)`（`md_cg/links.py:350`）。
- **前置条件**：peer 必须经 `load(path)/_find` 命中已存在连接——**需先 handshake**；未命中或 `status == "withdrawn"` 抛 `LinkError`。
- **互斥锁语义**：`load → mutate → save` 全程持**连接级互斥锁** `_locked`（`fsutil.FileLock`，锁文件为 links 路径 + `.lock`）。无锁时两写者各持旧快照互覆，丢 `evidence_count` 与 audit。
- **验签失败处置**：按策略 `on_verify_fail` 处置（`reject` 抛 `LinkError`；其余置 isolate/degrade 后返回 `ok=False`）。
- **更新字段**：`p_trust = round(max(0.0, min(cap, before + delta)), 6)`（cap 取 `p_trust_cap`）；`evidence_count + 1`；`last_observed`；`decay = 0`；验签要求时写 `signatures.peer_evidence`；全程 `_audit` 留痕。**负证据跌破 `DEGRADE_BELOW` 且原状态 ∈ `IN_TRUST` → 自动降级 `degraded`**（宪章第七条）。
- 其他写向 action：`handshake`（建档，提交走连接级互斥）、`promote(:446)`、`degrade(:466)`、`isolate(:472)`、`withdraw(:478)`、`decay_all(:489)`。

**稳定契约 vs 未标定占位**——这是本设计取值合法性的分水岭：

| 类别 | 项 | 可用性 |
|---|---|---|
| **稳定契约** | 状态位 `STATUS=(probation,normal,degraded,isolated,withdrawn)`、`IN_TRUST=(probation,normal,degraded)`；上限 `CAP_ALIGNED=0.8 / CAP_INCOMPLETE=0.6 / CAP_MISALIGNED=0.3 / CAP_ISOLATED=0.0`；`DEGRADE_BELOW=0.50`；`P_TRUST_INIT=0.8`；observe 前置 / 锁语义 / 更新字段 / 状态机方向 | 可作为**档位边界与门槛**的直接依据 |
| **未标定占位** | `UP_STEP=0.05`、`DOWN_STEP=0.20`、`DECAY_DAYS=30.0`、`PROBATION_SECONDS=7天` | 模块 docstring 明写「**均为未标定占位值**」，蜂群互联 §4.3「只声明结构，不宣称权重数值」，标定属路线图 v0.3。**不得当作已标定的权重使用**，只能用作结构方向（升慢降快）的定性论据 |

**既有缺口（实测）**：全仓无信任分级体系（无晋升/降级阈值）；健康分不影响信任；修正信号不改信任；运行时信任值变化来源仅「实例程序自身的德指令」与「实例故障沿用上轮」。**本设计正是在补这个分级缺口**，且不改 links 内核。

### 1.2 可用的资源面

**蜂巢三层调度现状**：微观（worker 池 / `claimed.lock` / 心跳 / `kill_tree` / 崩溃恢复）；中观（`spec.depends_on` 静态 DAG + 失败硬传播，`scheduler::deps_gate`）；宏观（群体注册表 / 能力路由 / 死锁探测）——**宏观尚在规划中，未取证可用**。

**worker 无状态**：worker 只是执行槽位，不跨 job 持有任何记忆，因此**没有承载持久声誉的结构位置**。

**`hive_spawn` 入参白名单 `SPAWN_ALLOWED_KEYS`（19 键）**：`model`、`user_prompt`、`system_prompt`、`context_files`、`timeout_s`、`reasoning_effort`、`context_budget_tokens`、`context_strict`、`thinking`、`tools`、`max_tool_rounds`、`mdcg_root`、`web_search_backend`、`max_tokens`、`temperature`、`depends_on`、`identity`、`task`、`unit`——**逐键点名后确认：无 `priority`、无 `trust`、无 `quota`**（三者均不在列表内）。未知键**显式拒绝**，不静默丢弃。

**id 契约四槽**：`identity / task / unit / 编号`；前三槽必填、编号由 Rust 侧 `hive alloc-id` 独占分配（本面不自造 id，`HIVE_EXE` 不可用即显式报错，不静默降级）；`unit` 取**五单元闭集**。

**「文件协议即接口」的含义**：MCP 面与 serve 之间零 IPC、零共享内存，唯一通道是 `jobs/<id>/{spec.json, status.json, result.json, kill}` 四文件 + `_serve.json` 心跳。由此推出两条硬推论：①**任何跨面语义必须能落到这些文件的键上**，落不到就不存在；②**内核不需要、也不应理解新增语义**——它在 spec.json 落盘之后才开始工作。

### 1.3 两条约束推出唯一可行落点

约束 A：`SPAWN_ALLOWED_KEYS` 无优先级/信任/配额字段，且未知键显式拒绝 ⇒ **信任值不可能作为 spec 键传入蜂巢**，内核无法据信任改变领取或排队行为。
约束 B：D-005（rust 侧纯 std 零 crate）与「文件协议即接口」不破 ⇒ **内核不得引入信任库、打分逻辑或新状态语义**。

两条约束合起来只剩一个落点：**信任决策必须在派发侧（编排者）完成**，并以「派或不派、派给谁、给多大预算」的形式**在 spec.json 落盘之前物化**。信任不进 spec、不进内核，只改「谁来组装这次 spec」。

**分界线**：
- **编排者读信任**：经 `load` 得 `p_trust / status / p_trust_cap`，据此算 `eligible`、并发配额、租约时长、档位——**消费者是编排者，不是内核**。
- **蜂巢内核不读信任**：内核只看到既有键构成的 spec.json；对它而言，一次被拒的派发与「本就不该派」的派发**不可区分**。内核行为对信任**零感知**，故 D-005 与文件协议逐位不变。

### 1.4 对端与 worker 的区分（本章最关键）

信任值**不能接 worker 池**，三条理由：

1. **peer 是对端实体，worker 不是命名实体**。peer 有 `link_id`、有 `p_trust`、有状态位、有 audit 留痕——是**可被指名的持久对象**；worker 只是池中的槽位，无名、无对外标识。
2. **worker 无状态、无持久声誉载体**。信任要求「跨时间累积、可被反例击穿、有衰减」；worker 跨 job 不持有任何东西，声誉无处附着。
3. **单机 worker 池的公平性属排序面**（`K_in` 排序键），与「我信哪个对端」是**两个不同的量**。把信任接到 worker 池上，等于用「对端信誉」去解「本机排队公平」，两者无因果关系。

**判定表——哪些执行主体有信任值**：

| 执行主体 | 是否命名实体 | 是否存在于 `_links.json` | 有信任值？ |
|---|---|---|---|
| **对端**（`agent:node-x`、其他 serve、外部 agent） | 是（`peer_node_id`） | 是（需先 handshake 建档） | **有** |
| worker 池槽位 | 否（无身份） | 否 | 无 |
| `exec.py` / `exec_cmd.py` 进程实例 | 否 | 否 | 无 |
| 单次 job（`h_<身份>_<任务>_<单元>_<编号>`） | 是（有 id），但**任务是任务的实例，不是主体** | 否 | 无——信任不附着于 job |
| 五单元子代理（本机派发） | 是（单元身份） | 否 | 无——同属本机自派，走排序面 |

**一句话**：信任值接的是「**给谁做**」（跨对端派发），不是「**谁先做**」（单机 worker 池排队）。

## 二、读向接线：三条闸与一张档位表

读向接线的定位：**在派发侧把 `p_trust`/`status` 读出来，转成「派发资格 + 资源配额」**。它只消费信任面，不回写信任面（回写走 `observe`，属写向接线）。

### 2.1 闸一·资格门槛

```
eligible(peer, difficulty) = (p_trust ≥ g(difficulty)) ∧ (status ∈ IN_TRUST)
```

- `IN_TRUST = (probation, normal, degraded)`——直接引用 links 既有闭集，不自造。
- `g`：难度档 → 最低 p_trust 的映射函数（单调不减）。**g 的取值是建议值待裁**：本设计只固定其**结构**（单调、以 `DEGRADE_BELOW=0.50` 为下界锚点、以 `CAP_ALIGNED=0.80` 为上界锚点），**具体数值待使用者裁定**；任何把具体 g 写成已定的表述都是越权。
- 判定结果仅两种：**过闸 → 进入闸二**；**不过闸 → 不派，并留判定理由**（不降级为「勉强派」）。

### 2.2 闸二·配额

`p_trust` 档位 → **并发上限**与**租约时长**。语义纪律两条：

- **租约是资源占位，不是权限**。租约期内对端占用编排侧的并发名额与预算额度；租约到期名额自动回收。**租约不授予任何额外能力**，不改变 eligible 判定，不能用来「先占坑再补资格」。
- **长租约须更严准入**：租约时长与准入严格度**正相关**。一次性短任务可对中档开放；长租约（含长链、跨轮续跑）只对高档开放。**具体租约时长与并发上限数值均为建议值待裁**。

### 2.3 闸三·状态位闸

状态位是**先于 p_trust 数值的硬闸**（状态位由 `observe`/`promote`/`degrade`/`isolate`/`withdraw` 变更，不由数值内插）：

| 状态位 | 处置 |
|---|---|
| `isolated` | **直接不给派**（一票否决，不看 p_trust 数值） |
| `withdrawn` | **直接不给派**；且 `observe` 对其抛 `LinkError`（连接已退场，不再接受观测） |
| `degraded` | **降档处理**：跌破 `DEGRADE_BELOW=0.50` 即自动进入该位，落最低可派档；不得因历史高分豁免（宪章第七条：不因历史高分豁免） |
| `probation` | **观察期**：可派但**限低难度 + 限短租约 + 并发压到最小**；观察期内正证据累积可提交 `promote` 出观察期 |
| `normal` | 按档位表正常待遇 |

### 2.4 档位表（连续 p_trust → 离散档位，与既有状态位对齐）

**不自造第二套状态名**——档位是对 `p_trust` 连续量的读向切分，**必须回落到既有状态位**；档位只描述「资源待遇」，不描述「状态」。

| 档 | 判据（读向切分） | 资格 | 并发 | 租约 | 排序位置 | 退出条件 |
|---|---|---|---|---|---|---|
| **不派** | `status ∈ {isolated, withdrawn}` | 无 | 0 | — | 不入队 | 经 `handshake`/`promote` 回 `IN_TRUST` |
| **受限档** | `status = degraded`（p_trust < 0.50）或 `status = probation` | 仅最低难度 | 最小（1） | 最短 | 末位 | 正证据累积 + 显式 `promote` → 常规档；**衰减不升档** |
| **常规档** | `status = normal` ∧ `p_trust ∈ [0.50, 0.60)` | 中低难度 | 中 | 中 | 中位 | 升：p_trust ≥ 0.60 + 显式 promote → 高档；降：`p_trust < 0.50` 由 `observe` **自动**降 `degraded` → 受限档 |
| **高档** | `status = normal` ∧ `p_trust ≥ 0.60`（上限 `CAP_ALIGNED = 0.80`） | 全难度 | 高 | 最长 | 首位 | 降：负证据使 `p_trust < 0.60` 退常规档；跌破 0.50 自动降级 |

**两条结构性澄清**：①**升档只走显式 `promote`，降档可由 `observe` 自动触发**——这是「降快于升」（宪章第七条）在读向的直接体现，本设计**不引入自动升档**；②**`decay_all` 只把 p_trust 向初值回归，不恢复状态位**——衰减到高分不等于出观察期、不等于解除 degraded。
（`g(difficulty)` 的具体数值、并发上限、租约时长三项**均为建议值待裁**；表中「最小/中/高」「最短/中/最长」为结构序，不是已定数值。）

### 2.5 与排序面的关系

读向接线**只做资格与配额**（决定「能不能派、最多同时派几个、占多久」），**不改 worker 池的内部排队**——那属中观排序面（本机公平性，`K_in` 排序键）。

两者同时存在时的优先级：

- **硬闸 = 读向接线**。过不了闸一/闸三的执行主体**不进入候选集**，排序面对它无话可说；闸二封顶后，超出配额的候选**直接出局**，不是「排后面」。
- **软排序 = 排序面**。在通过硬闸的候选集**之内**，按什么次序派发（p_trust 降序、`last_observed` 新鲜度、任务亲和等）是软排序，允许平局与调参。
- **边界纪律**：排序面**不得**因为某对端「排队久/任务急」而放宽硬闸；读向接线也**不得**把配额下沉成排序权重（那会把硬约束软化成可让步的偏好，等于取消闸二）。一句话：**硬闸决定谁有资格，软排序决定谁先上**。

## 三、写向闭环：任务终态回写信任

### 3.1 闭环的必要性

已接线的只有**读向**：`p_trust` → 派发决策（给谁做）。**写向**（任务终态 → `observe`）当前没有生产者。两处已取证事实指向同一件事：`docs/swarm/蜂群同错检测实验协议_v0.1.md` §2.3 记「health 只进报告，不回馈 trust 计算，不参与任何路由/晋升/降级决策」，§5.2 缺失清单 M3「修正信号无任何信任/路由后果」、M4「健康→信任回馈缺失」；同文 §2.1 进一步记「信任是自报值，协调器零否决权」，运行时信任变化只有「实例程序自身的德指令」与「实例故障沿用上轮」。

后果不是「信任不更新」，而是**单向消耗**。读向接线一旦启用，真实交互持续产出负信号（error/timeout），而正信号（done）没有任何通道进入 `observe`，于是：

- 唯一上行来源是 `handshake` 初值（0.8）与衰减（`DECAY_DAYS=30` 向初值回归）；
- 下行来源是每一次失败（`−DOWN_STEP=0.20`）与人工 `degrade`；
- `UP_STEP=0.05` 在没有调用者时等于**常量 0**。

`p_trust` 因此单调下行，跌破 `DEGRADE_BELOW=0.50` 后 `observe` 内的反例击穿段（`md_cg/links.py:350` 函数体内）把连接自动置 `degraded`；而 IN_TRUST 集合内没有「值回升 → 自动退出 degraded」的路径（见 4.4）。终局是全体 degraded——分级体系上线后等价于**全群无派发资格**。闭环不是锦上添花，是读向接线不自杀的前提。

### 3.2 回写规则（终态 → observe 映射）

判据是**责任归属**，不是终态名字本身。（终态字面值以第二章／蜂巢 `result.json` 枚举为准；本表给语义类。）

| 终态 | 回写 | positive | 理由 |
|---|---|---|---|
| done（产物齐备、结构校验通过） | 是 | True | 唯一可作正证据的终态；`result.json` 落盘且字段完整 ⇒ 有可复算的观测对象 |
| error（对端执行失败，终态含 error 键） | 是 | False | 对端未履约；与蜂巢 health 的 error 判定口径同源 |
| timeout（对端在 `timeout_s` 内无进度/无心跳） | 是 | False | 履约能力缺失；判据落在「无进度」而非「超时」本身 |
| timeout（对端持续推进、预算给少） | **否** | — | 责任在编排者：`timeout_s` 由本节点给，预算不足不是对端过失 |
| error（本节点输入缺失／DAG 前置失败） | **否** | — | 属编排者自身故障，回写即污染 |
| killed-by-intent（编排者主动 kill／预算回收／抢占） | **否** | — | 终止指令来自本节点，对端无过；回写等于把自己的调度决定记成对方过失 |
| killed（宿主崩溃、OOM 等） | **否** | — | 无可归因主体；无主体即无证据 |
| needs_review（产物待复核、未裁决） | **否** | — | 无真值裁决；对未验证结论记账＝用未验证结论充当证据（对齐既有纪律：拿不出证据不写 verification_basis） |
| 同一 `job_id` 的中间尝试 | **否** | — | 只回写**最终**终态，见 3.3 |

### 3.3 幂等与防自放大

`observe` 自身无幂等判据：每条调用无条件 `evidence_count+1` 并施加 ±步长。步长是固定值，所以「同一任务重复 observe N 次」＝一条事实被批发成 N 条证据：0.60 的对端 4 次重复正证据即回满 cap 0.80；负向更危险，`DOWN_STEP=0.20` 使 4 次重复负证据把 0.80 打到 0.00。重复观测是**唯一的刷高／击穿通道**，必须由幂等键封死。

- **幂等键＝`job_id`**。蜂巢 id 契约四槽（identity/task/unit/编号）已保证任务可命名；崩溃重建后重跑同一轮时**轮次号不变**（蜂巢既有幂等口径），故重跑不产生新 `job_id`——这正是键必须落在 `job_id` 而非「尝试序」的原因。
- **落点在回写侧（编排者）**，不能在连接层强制：连接层无法区分「新证据」与「重复投递」。设计方向：回写前查本节点侧的「已观测集合」（账本与 `_links.json` 同目录、同 0600 口径），命中即跳过并返回 `skipped=True`（幂等命中是正常路径，不是报错）。
- **键须进签名载荷**：evidence 经 `md_cg/links.py` 的 `evidence_payload(peer, evidence, positive)` 参与验签，`job_id` 必须出现在 evidence 的规范化文本中，否则事后替换 `job_id` 重放即可绕过账本。
- `p_trust_cap` 是上游兜底但**不能替代幂等**：它只让已在上限的连接刷不动，对已跌破上限的连接不设防。

### 3.4 证据与署名

evidence 必带（结构化、可复算、供对端复核）：`job_id`（幂等键兼对账主键）、终态、`result.json` 路径（仓内相对路径，如 `<大脑库根>/hive/jobs/<job_id>/result.json`）、`elapsed_s`、LLM 类 worker 另带 `tokens`（含 model）以便成本与时长对账，以及归因字段（`attributed_to`: peer/self/unknown），与 §3.2 的责任判据同源。

`peer_signature` 签的是**来源**，不是**评价**：对端对 `result.json` 摘要签名，验签后本节点能主张「这条结果确实由该节点产出」，但**不**证明结果正确（证据来自该节点 ≠ 证据为真）。对端未签时按 `default_signer` 走。

`on_verify_fail` 在任务回写场景应取 **degrade**：

- 取 `reject`：这条终态证据完全不进 delta、不进 audit，与留痕义务冲突，丢掉的恰是最需留痕的异常；若策略确为 reject，回写侧必须自行落拒收留痕（对齐 `md_cg/evidence.py` 的拒收留痕先例）。
- 取 `isolate`：一次验签失败是密钥/配置事故的概率远高于是恶意；而 `isolated` 会同时把 `cap` 与 `p_trust` 置 0，**无自动回升入口**，等于不可逆冻结，代价与证据强度不成比例。
- 取 `degrade`：保留记账与留痕，方向符合「降快于升」；`observe` 返回 `ok=False` 表示该条不产生 delta，异常本身仍进 audit。

并且：验签失败**不等于**对端行为异常，应记为带 `reason=verify_fail` 的异常事件，并区分「对端未签」「签名验不过」「本地无注册签名器」三种成因——把基础设施故障记账成对端过失，是自裁的镜像错误。

**谁有权回写**：派发侧编排者，本节点唯一写入者，`actor` 入 audit。被评对端**不得**回写自己的正证据：写入位置是本节点的 `_links.json`（对端写不了我的信任根），代理写入就是替我下判断；对端若能自评，`p_trust` 即可自放大，与 cap 纪律、宪章第七条正面对撞；且与已证失败同源——自报制的缺陷就是缺裁决链，回写权交给被评方等于把该缺陷复制到跨节点面。权限依据走派生律：回写权派生于「编排者 + 维生职责」的版本条款，**不**派生于对端自身；对端签名只作来源证明，不作评价权。

### 3.5 反例通道

触发条件（缺一不回写）：① 责任归对端（§3.2 判据）；② 有可复算的观测对象（`result.json` 或明确的「无进度」证据）；③ 该 `job_id` 未入已观测集合。

「一次失败是否该击穿」直接由常量算出：

- 自动降级条件是 `p_trust + delta < DEGRADE_BELOW`，负 delta＝−0.20 ⇒ **击穿线是 `p_trust < 0.70`**。
- 初值连接（`P_TRUST_INIT=0.8`）：一次对端可归因失败 → 0.60，**不降档**；两次 → 0.40，降档。即「初值连接容忍一次对端可归因失败，不容忍两次」。
- `p_trust` 已在 0.65 的连接：一次失败即 0.45，直接降档。

上限（防以量代质）：单次 −0.20（4 倍正步长）；同一 `job_id` 只记一次；同一失败事实的多种症状（timeout + error + killed 同时出现）**只记一条**——重复记账等于绕开幂等键；`p_trust` 由 `max(0.0, …)` 夹下界。

不豁免：历史高分不豁免**记账**（每条负证据都进 audit、都改值），只是未必跨过状态位阈值。对端申辩走复核通道，复核结果由维生单元显式落一条 audit，**不自动回滚** `p_trust`（自动回滚等于给对方一条免罚通道）。

## 四、分级体系：补齐「无信任分级体系」缺口

### 4.1 为什么需要分级

已取证缺口：全仓无信任分级体系（无晋升/降级阈值）。连续值适合观测与留痕，不适合直接做资源决策：**不可解释**（0.61 与 0.79 的待遇差别说不清，无法回答「这次为什么被拒」）；**不可对账**（审计要可枚举的结论，连续值只能事后重算，无法写进依据条款）；**不稳定**（单次 ±0.05/±0.20 抖动会让并发、租约反复横跳）。分级提供**滞回**：档位是决策面，`p_trust` 是观测面。

### 4.2 分级设计（复用既有状态位，不新造）

档位名**直接复用** `STATUS=(probation, normal, degraded, isolated, withdrawn)`，`withdrawn` 不入级（退出态，30 天冷静期）。

| 档位 | 状态位 | 进入条件 | 退出条件 |
|---|---|---|---|
| 隔离 | `isolated` | 严重/持续异常；`isolate`（`md_cg/links.py:472`）置 `cap=0`、`p_trust=0` | 既有实现无自动回升入口 ⇒ 事实冻结，解冻须维生/设计者显式裁定 |
| 降级 | `degraded` | 负证据使 `p_trust < DEGRADE_BELOW=0.50`（`observe` 内自动）；或 `degrade`（`links.py:466`）；或验签失败 `on_verify_fail=degrade` | 复检显式复位（见 4.4），非衰减自动完成 |
| 观察期 | `probation` | 新 `handshake`（含 peer_theory / position_map / declared_charter）；版本不符亦降为观察期 | `promote`（`links.py:446`）：观察期满（`PROBATION_SECONDS=7` 天，未声明宪章翻倍） |
| 正常 | `normal` | `promote` 成功 | 负证据击穿 → `degraded`；异常 → `isolated` |

与常量的对齐：`P_TRUST_INIT=0.8` 与完整节点 `CAP_ALIGNED=0.8` 同值（新连接从上限起步）；`DEGRADE_BELOW=0.50` 即降级档上界；`CAP_INCOMPLETE=0.6` 在 0.50 之上 ⇒ 不完整节点仍可达 normal 档（值低于完整节点）；`CAP_MISALIGNED=0.3` **本身低于 0.50** ⇒ 版本不符的连接在信任值上永远够不到 normal 区间，即公理差＝折价到降级带，与既有 `_cap_for` 默认行为一致，不改动。注意 `probation` 与 `normal` 的值域相同（0.50–cap），区别只在 `probation_until` 是否到期 ⇒ 档位必须是「状态位 + 观察期」二维，不能只用值定义。

一处需补的判据：`promote(links.py:446)` 当前只校验 `probation_until` 到期。若分级以档位派发资源，「纯时间到期即转 normal」会让**从未被观测**的对端拿到全量待遇——观察期退化为「等待」而非「观察」，与隐式学习冲突。建议前置再加两条：观察期内无未结负证据、`evidence_count ≥ 1`。这是建议，非既有行为。

### 4.3 档位 → 资源待遇绑定表

核心澄清必须贯彻：**信任值接的是「给谁做」（跨对端派发），不是「谁先做」（单机 worker 池排队）**。peer 是对端实体（`agent:node-x`、其他 serve、外部 agent）；worker 不是命名实体、无身份、无持久声誉载体。下表每列都由**派发侧（编排者）**在生成 `spec.json` **之前**消费：

| 档位 | 资格门槛 | 并发/在飞 | 租约 | 排序（K_in） |
|---|---|---|---|---|
| `normal` | 可派发写类、长任务、`destructive` unit | 全额配额 | 可获租约、可续租 | 最前 |
| `probation` | 限只读/短任务；不得 `destructive` | 限流（在飞受限） | 租约不可续，终态即释放 | 次之 |
| `degraded` | 仅「观察任务」（只读、可丢弃、探测性） | 极少在飞 + 超时兜底 | 无租约 | 末尾 |
| `isolated` | 不派发（不建连） | 0 | 无 | 不参与 |

不变量：待遇沿档位**单调不增**（`normal ≥ probation ≥ degraded ≥ isolated`）。在飞上限、配额、租约时长的**具体数值**属第二章资源面，本篇不另定，只声明档次到待遇的映射方向，避免与第二章矛盾。

接线纪律：本表**不进蜂巢内核**。`hive_spawn` 入参白名单 19 键中无 `priority`/`trust`/`quota`，未知键显式拒绝（不静默丢弃）⇒ 决策只能落在**派发侧**，不改 `SPAWN_ALLOWED_KEYS`，不加 `spec.json` 契约外字段，从而不破 D-005（rust 纯 std 零 crate）与「文件协议即接口」。单机 worker 池内的公平性属**排序面**（K_in 排序键）：排序面管「谁先做」，信任面管「给谁做」，两者只在编排者处汇合，互不越界。

### 4.4 衰减与复检

`decay_all`（`links.py:489`）只对 IN_TRUST（`probation`/`normal`/`degraded`）生效，按 `factor = 0.5^(days/30)` **向 `P_TRUST_INIT=0.8` 回归**，再按 `cap` 夹取。两个口径必须写明：

- **长期无观测回到哪个档？** 值回到 0.8（cap 允许时），**档位不动**——`decay_all` 只写 `p_trust`/`decay`，不调用 `_set_status`。于是会出现 `status=degraded` 同时 `p_trust=0.80` 的连接。这是**档位与值解耦**的风险：只看值则滞回失效，只看状态位则衰减对档位无影响。故口径定为：**档位只由状态位给出；档位复位必须显式复检，不能由衰减自动完成**。
- 复检建议：`decay_all` 批次后，若 `p_trust ≥ 0.70` 且 `status=degraded` 且无未结负证据 ⇒ 允许维生单元显式 `promote` 回 `normal` 并留痕。0.70 与 §3.5 击穿线同值，保证「复位线与击穿线不重叠」，避免抖动。
- `CAP_MISALIGNED=0.3` 的连接：回归被 `min(cap, …)` 夹在 0.3，恒定低于 0.50 ⇒ 既永不进 normal 带，也不会自动进 degraded。版本差是**上限**问题，复检解决不了。

观察期进出：`PROBATION_SECONDS=7` 天（未声明宪章翻倍，宪章术语表）；出口是 `promote`（观察期满），非到期自动转（当前实现由调用方触发）。观察期内若负证据把值打到 <0.50，仍会转 `degraded`——`probation` 属 IN_TRUST，不豁免反例。

### 4.5 审计与可追溯

每次**档位变化**必须可追溯，且既有留痕通道够用，不新开：`_set_status` 写 `status:<old>-><new>` + `clause` + `reason`；`observe` 写 `by`/`evidence`（截断 200 字符）/`positive`/`delta`/`p_trust`；`audit` 只增不改。分级只需补三条纪律：

1. **派发决策也要留痕**。现有 `audit` 只记连接变更，不记「这次为什么拒绝派发」。每次消费档位生成 `spec.json` 时，应落一条决策记录（对端、档位、待遇、`job_id`、所依据档位的时间戳），否则 4.1 的「可解释」不成立。
2. **不一致必须显式**。4.4 的 `degraded` + `p_trust=0.80` 这类解耦状态，必须在查询面把 `tier` 与 `p_trust` 并列输出并附 `tier_stale` 布尔；静默只给一个字段，审计就对不上账。
3. **诚实边界不变**。`_links.json` 即本节点信任根，能写它者即可篡改分级与信任；分级不改变这一点，只让篡改**可对账**（档位离散、变更留痕），而非不可能。声明权 + 校验权（拒绝派发／拒绝合作）仍是唯一执行力。

## 五、能红判据：每条接线的「构造一个必失败检验」

判据纪律：每条接线配一个**可构造的必失败检验**——把该判据删掉，检验必须变绿（即缺陷被放出来）。检验不通过即该条未生效。

| # | 接线 | 能红判据（构造必失败检验） |
|---|---|---|
| R1 | 闸一·资格门槛 | 造一个 `p_trust < g(difficulty)` 的对端请求高难度任务 → **必须被拒且留判定理由**；若派发成功，或"被拒但无理由留痕"，闸失效 |
| R2 | 闸二·配额 | 造一个受限档对端并发提交 2 个任务（上限 1）→ **第 2 个必须被挡**；挡不住即配额失效 |
| R3 | 闸三·状态位硬闸 | 造一个 `status=isolated` 但 `p_trust` 数值很高的对端 → **必须不给派**；给派即硬闸失效（数值不得覆盖状态位） |
| R4 | 写向·责任归属 | 造一个**编排者自己预算给少**导致的 `timeout` → **必须不回写**；若回写，即把自身过失记成对端过失，判据失效 |
| R5 | 写向·幂等 | 同一 `job_id` 的回写**重复投递 3 次** → `p_trust` **只变一次**、`evidence_count` 只 +1；变多次即幂等失效（这是唯一的刷高/击穿通道） |
| R6 | 写向·不得自评 | 让被评对端提交自己的正证据 → **必须被拒**（或记为越权事件）；能写进即自放大通道打开 |
| R7 | 分级·滞回 | 造 `p_trust` 在档位边界附近抖动（±1 步长）→ **档位不得反复横跳**；横跳即未提供滞回，分级退化为连续值 |
| R8 | 分级·档位与值解耦 | 造一个 `status=degraded` 且 `decay_all` 已把 `p_trust` 拉回 0.80 的连接 → **档位必须仍是 `degraded`**（须显式复检才复位）；若自动回到 `normal`，则衰减成了免罚通道 |
