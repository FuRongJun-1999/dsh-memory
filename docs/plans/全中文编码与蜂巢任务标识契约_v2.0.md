## 一 决定与它的真实作用面

使用者裁定两件事：**①路径全面 UTF-8 兼容中文**；**②蜂巢任务标识改用语义四槽组合，不再用毫秒+pid**。

关键判断（本文档的立论）：**这两件事的性质完全不同**。

- ① 不是"新建能力"，而是"把已有能力钉成不依赖环境变量的硬约束"——三个面的编码层**已经**是 UTF-8 端到端（§二 实测），但撑住它的是**环境变量 + 每个入口自己记得设**，而仓里有 224 处裸 `open()`（§三）。
- ② 不是"编码问题"，而是**一道故意的安全闸**在挡路——`valid_job_id` 只收 ASCII，放宽它是全案唯一的**安全面**改动（§四.4）。

## 三 脆弱点（必须钉住的东西）

1. **系统 locale 是 GBK。** 本机 `locale.getlocale()` = `('Chinese (Simplified)_China', '936')`，而 Python 裸 `open()` 的缺省编码取 `locale.getpreferredencoding(False)` ⇒ **不设 UTF-8 模式时，裸 `open()` 在本机走 cp936**。
2. **今天没炸，靠的是环境变量。** 本机环境里设了 `PYTHONUTF8=1` 与 `PYTHONIOENCODING=utf-8`。入口也已显式钉：`scripts/run_tests.py:88`（给子进程覆盖）、`scripts/linux_verify.sh:9`（export）、TS 桥层 `src/lib/mdcg_client.ts`（同名注释见 `hive/hive_mcp/mcp_server.py:852`）。
3. **裸 `open()` 224 处**（`md_cg/` `hive/` `scripts/`，未传 `encoding=`）。ASCII 数据无碍，一旦内容或路径含中文，就看第 1 条的脸色。
4. **已有乱码实证**：本会话中 mdcg 的 stderr 打出过 `[mdcg-mcp] 鈿� 瀵嗙骇閰嶇疆…`——这一类通道未对齐编码的现成样本。
5. **零处归一化**：全仓无 NFC/NFD 归一化。中文受的影响小，但混排拉丁带音调与 CJK 兼容表意文字（U+FA10 等**确实**会 NFD 分解）会咬人；macOS 按 NFD 存储名字，而 `depends_on` 判据是**字符串相等** ⇒ 不归一化即静默失配。

## 四 硬约束（要落成什么）

### 四.1 路径与文件名一律 UTF-8 + NFC

- 一切落盘的可读文本固定 UTF-8；一切用户可见的路径/文件名/id 固定 **NFC**。
- 归一化在**写入边界**执行一次（提交面/落盘点），比较前亦归一化；判据单点，不得各处自持。

### 四.2 进程自保证 UTF-8（不依赖使用者 profile）

- 每个入口（`hive/hive_mcp/mcp_server.py`、`hive/orch.py`、`hive/exec.py`、`scripts/*`、TS 桥）在最早处检查 `sys.flags.utf8_mode`；未开则设置 `PYTHONUTF8=1`/`PYTHONIOENCODING=utf-8` 并**重启自身**，不可重启时 **fail-fast 报错**（同 N200「无模型密钥启动前置报错」的形状：不静默降级）。
- 这一条落地后，§三.3 那 224 处的**大部分风险直接消失**（UTF-8 模式下裸 `open()` 即 UTF-8），比自己逐个补 `encoding=` 便宜一个数量级。

### 四.3 机械守卫：裸 `open()` 不许新增

- AST 扫描生产模块（`md_cg/` `hive/` `scripts/`，排除 bench）里未传 `encoding=` 的 `open()` 与无 `encoding=` 的 `Path.read_text/write_text`，白名单化存量，**新增即红**。
- 与 §四.2 互为兜底：自保证是运行期防线，守卫是提交期防线。守卫须自带定点变异自证（本仓惯例）。

### 四.4 id 契约 v2（安全面改动，最需谨慎的一节）

**形态**：`h_<身份>_<任务>_<单元>_<编号>`，例 `h_zcode端_灵枢迭代_反思单元_0001`。

| 槽 | 例 | 必填 | 来源 | 说明 |
|:--|:--|:--|:--|:--|
| 身份 | `zcode端` | **是** | 提交面显式声明（env/入参） | 提交者/端别；**不允许静默推导**（猜错且静默正是 H-1 那半边缺陷的形状） |
| 任务 | `灵枢迭代` | **是** | 显式声明 | 工作流或迭代名；目录可作它的父段（成 5 段） |
| 单元 | `反思单元` | **是** | 显式声明，**闭集** | 见下「五单元闭集」 |
| 编号 | `0001` | 分配得出 | Rust 侧分配器 | 该 (身份,任务,单元) 前缀下的序号，**定宽 4 位**，溢出 **显式报错**（不加宽——加宽会破坏定宽前提） |

**五单元闭集（本契约的关键收窄，使用者 2026-09-29 裁定）**：单元槽**不是自由文本**，取值限定为**蜂巢五单元**，真源是 `md_cg/identity.py:55-67` 的 `POSITIONS`：

| pos | 单元 | effect | duty |
|:--|:--|:--|:--|
| `record` | 记录单元 | 全 | 保存观测、过程、结果和误差 |
| `reflect` | 反思单元 | 新 | 发现差异、遗漏条件和新的路径 |
| `verify` | 验证单元 | 稳 | 判断规则、执行结果和结构是否有效 |
| `output` | 输出单元 | 通 | 与外部系统协作并表达边界 |
| `sustain` | 维生系统 | 存 | 维护存在、预算、回滚和整体结构 |

- 好处：任务的身份里直接带**它归哪个职能单元**，而词表有既有真源、不会漂移；提交面校验即 `∈ POSITION_ORDER`。
- 守卫：**沿用仓内既有的同源断言形态**（`md_cg/test_p21_tokens.py:218`「与 `identity.POSITIONS` 同源校验」）——id 词表与 `POSITIONS` 必须逐项一致，任一侧增删即红。
- `POSITION_ORDER`（`identity.py:67`）同时给出**规范顺序**，可用于校验与排序，不必在 id 契约里另立一份。
- 注意：**副代理不是第六个单元**（`docs/hive/子代理配置标准_v0.5.md:151`：副代理是融合位 𝓕 本身，五单元是 𝓕 的功能分解）⇒ 词表恰为 5，不得为副代理增设槽值。

**编号分配算法＝独占创建即分配**：对目标名执行 `fs::create_dir`（Rust）/`os.mkdir`（Python）——目标已存在时**必然失败**，失败即编号加一重试（有界重试，超限显式报错）。性质：
- 碰撞**结构上不可能**，不再依赖「毫秒恰好不同 ∧ pid 恰好不同」；
- **H-1 的碰撞那半因此被消解而非被修补**——不需要进程内计数器、不需要提高熵；
- 复用的是仓内既有原语同款（`claimed.lock` 的 `create_new` 独占）。
- `now_ms()` 保留为 `status.created_ts` 的时钟源，**退出 id**。

**字符集闸放宽（`job.rs:63-67` 与 `mcp_server.py:152` 这对双胞胎须同改）**：由「ASCII 字母数字 + `_`」放宽为「Unicode 字母/数字 + `_`」，**同时保留并新增拒收项**：

| 拒收 | 理由 |
|:--|:--|
| `/`、`\` | 路径分隔（原始缺陷载体：`kill ..` 池外写、`poll ../victim` 池外读） |
| 单独的 `.` 与 `..` | 相对路径 |
| `:` | Windows 盘符 |
| 控制字符、零宽字符、双向控制字符 | 同形异义与不可见注入 |
| 首尾空白、尾点 | Windows 会静默剥掉 ⇒ 两个不同 id 落到同一目录 |
| Windows 保留设备名（`CON`/`NUL`/`AUX`/`PRN`/`COM1`…） | 本仓 v0.5.1 刚修过这一类（issue #39），勿回退 |

**这是全案唯一的攻击面改动**：必须有守卫（合法/非法两侧用例 + 跨语言对照，沿用 H-6 的 18-id 对照形态），必须做定点变异，且守卫要覆盖 `kill`/`poll`/`depends_on` 三条拼路径入口。

### 四.5 排序口径：把代理换成真值

id 不再含时间后，「字典序 = 提交时序」这条**代理**失效，四个消费者须改为**直接按 `status.created_ts` 排序**（每个 status 都已有该字段）：

| 站点 | 现语义 | 改后 |
|:--|:--|:--|
| `hive/src/main.rs:223` `find_active_by_hash` | 名升序取首个 = 最老活跃同哈希 | 活跃同哈希中 `created_ts` 最小者 |
| `hive/src/main.rs:473` poll 列表 | 名升序 | `created_ts` 升序 |
| `hive/src/main.rs:696` doctor | 名升序 | `created_ts` 升序 |
| `hive/src/scheduler.rs:213`/`:300` 领取顺序 | 名升序 = FIFO | `created_ts` 升序 = FIFO（**语义保持**） |

### 四.6 控制台：**明确不做兼容**（使用者 2026-09-29 裁决）

先摆事实（实测，真 `hive.exe` + 中文池路径）：CLI 写出的字节是**裸 UTF-8**。同一串字节两种读法——

| 读法 | 结果 |
|:--|:--|
| 按 UTF-8 解码（管道 / 文件场景的正确读法） | `…\Temp\控制台试验_hucyqfhm` |
| 按 cp936 解码（= 代码页 936 的窗口所见） | `…\Temp\鎺у埗鍙拌瘯楠_hucyqfh` |

机制：输出到管道或文件时没有"代码页"这一层，写读双方约定 UTF-8 即可；问题只出在**目标是 Windows 控制台**时——控制台按**自身代码页**解释收到的字节。Python 不出这个问题是因为 PEP 528 让它对控制台改走宽字符 API `WriteConsoleW`（绕过代码页）；Rust 的 `println!` 走 `WriteFile` 直写字节，没有这层翻译。

**裁决：不做控制台兼容。** 不实现 Rust 侧的 `WriteConsoleW` 分支，也不要求使用者 `chcp 65001`；把正确性收进**约定**而不是**显示层**：

1. **取用通道固定为 Python**：本仓一切读写与判定走 `python -X utf8 …`（沿既有工程纪律第 15 条「命令统一走 python + 显式 UTF-8」）。Python 对控制台本就正确，走它即绕开问题。
2. **README 明写约束**：全仓文本与路径一律 UTF-8（无 BOM），并显式向 AI / 接入方声明「这里是 UTF-8、请走 python、别拿控制台当取用通道」（已落 `README.md` 的「编码约定」节）。
3. **Rust CLI 的控制台渲染不在承诺面**：CLI 输出为裸 UTF-8 字节；管道/文件读法即正确。控制台里看到什么，属显示层，不承诺。

**代价与残余**：若有人偏要在代码页 936 的窗口里直接读 CLI 输出，会看到乱码——这是**已知且接受**的边界；文档已写明规避方式（走 python、或把输出重定向到文件后按 UTF-8 读）。### 四.7 明确不改的面

- **`h` 前缀保留**：`valid_job_id` 的 `starts_with('h')`、`list_jobs` 的 `h` 前缀过滤、以及全部依赖它的守卫不动。去掉它要牵动一大片，收益为零。
- **存量零迁移**：旧 `h<13位毫秒>_<4hex>` 与新形态**同时满足**放宽后的闸、都以 `h` 开头被 `list_jobs` 收；§四.5 改按 `created_ts` 排序后两种形态共存无碍。
- **依赖无环性依据不动**：`scheduler.rs:690-697` 的注释写明依据是「**无法引用提交时尚不存在的任务**」即**存在性闸**（`main.rs:282-298` + H-6 新增的 MCP 侧 `_dep_gate`），**不是** id 的时间序。语义 id 不危及 I-1。（该注释「由 job_id 时间序结构性保证」的措辞与此表述有出入，宜一并订正。）
- **MCP/编排面共用一处生成器**：现状是 `mcp_server.py:339` 自造 `h{ms}_{uuid4[:6]}`，本契约要求两侧共用同一分配语义；「谁持唯一实现」是 §五 待裁项。

## 六 不适用条件

- 本稿不覆盖插件宿主与前端渲染的编码面；只论本仓三面（Rust 内核、Python 认知图与执行器、TS 桥）。
- 存量库与存量任务的**内容**不在范围内（只论路径、文件名与任务标识）；需要搬动既有存量数据的条目另开批次。
- 归一化形态一旦定为 NFC，原本按 NFD 存储的存量名字**不做自动迁移**——那需要单独的迁移方案与中止条件。
- 本稿不含实现；签名前不动码。
