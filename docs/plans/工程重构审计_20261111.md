## 二、按严重性排序的详细分析

### P0-1 · 架构判据已存在，但只覆盖 0.34% 的代码（A-01 / A-02 / A-13 合并）

**这是本次审计最重要的发现：项目不缺架构，缺的是「把已写好的架构判据接到真实代码上」。**

**证据链**

1. 架构判据确实存在且正确。`md_cg/iface/_verify.py:55` 定义分层：
   ```
   _LAYERS = ("adapter", "iface", "govern", "kernel")
   ```
   `:66-67` 定义语义「数字越小越靠上，下层引用层号更小的即反向依赖」；`:60-64` 定义宿主类型禁入表，并特别把 `mcp_server` 列入（`:61` 注释：「本仓 `md_cg/mcp_server.py` 即宿主接线面」）。

2. 判据真的会红。`_verify.py:83-94` 的 `_check` 逐项捕获断言；`:69-78` 从真值表推导待扫层；`:272-282` 用 `ast.walk` 解析；`:308-311` 支持注入 root 以便夹具在临时目录自证。实测运行：
   ```
   $ python -X utf8 -m md_cg.test_kernel_iface_contracts
   PASS 导入图单向（kernel/govern/iface）
   PASS 导入图守卫夹具自证
   PASS 守卫覆盖每个内层（防判据空转）
   ===== W1 守卫：14 通过，0 失败 =====   (EXIT=0)
   ```
   而且它的「夹具自证」项证明它抓得到违规 —— 这不是恒绿断言。

3. 但覆盖面几乎为零。实测被扫层的规模：

   | 层 | 文件数 | 行数 |
   |---|---|---|
   | `md_cg/kernel/` | 1 | **19** |
   | `md_cg/govern/` | 1 | **16** |
   | `md_cg/iface/` | 3 | 832 |
   | **判据覆盖合计** | 5 | **867** |
   | **`md_cg/` 根目录（未覆盖）** | 827 | **254,222** |

   覆盖率 = 867 / 255,089 ≈ **0.34%**。

4. 空壳自述属实。`md_cg/govern/__init__.py` 开头即写「灵枢 1.0 治理层（govern）—— W1 骨架，无实现」，`__all__ = ["GOVERN_LAYER", "LIFECYCLE_STATES"]` 只导出 2 个常量。`kernel/__init__.py` 同样只有 `LAYER_ORDER` 与 `KERNEL_LAYER`。

5. 而真实治理实现全在根目录，且体量可观：

   |---|---|---|
   | `consistency.py` | 1138 | govern/kernel |
   | `conformance.py` | 666 | govern |
   | `audit.py` | 602 | govern |
   | `rollback.py` | 601 | govern |
   | `writelimit.py` | 519 | govern |
   | `writegate.py` | 244 | govern |
   | `revise.py` | 111 | govern |
   | **小计** | **3881** | — |

6. 更严重的是 `mreview/` —— 它是**真实存在的治理流水线**（`mreview/__init__.py` 自述 M1 机械层 / M2 蜂群 / M3 定位 / M4 落地治理），但它既不在 `_LAYERS` 里（不叫 `govern`），又反向依赖根模块 **24 处**：
   ```
   mreview/govern.py:52    from ..mdcos import ALL_ROLES, WORK_ROLES
   mreview/locate.py:64-68 from ..conformance / crosscheck / nodefile / refindex / writelimit
   mreview/pipeline.py:32-35,727  from ..crosscheck / tokens / writepipe / security / mdcos

   ```
   即：**治理层写在 `mreview/` 里，却依赖本该在其下方的检索实体**。`_LAYERS` 看不见 `mreview`，所以这 24 处反向依赖永远不会被点名。

7. 守卫作者的预言已经应验。`_verify.py:71-74` 原文：
   > 「为什么从 `_LAYERS` 推导而不是手写……手写清单会与 `_LAYERS` 漂移——**事实就是漂了**，『iface 层引 adapter』这类反向依赖在 `_violations` 里判得出来，却因为层名不在手写清单里而**从不被扫**，形成第二个『判据有、守卫不接电』的盲区。」

   结论：这个病症当时在 `_LAYERS` 内部被修好了，但**同一病症在 `md_cg/` 根目录这一更大尺度上原样存在**，因为根目录压根没有层名。

**影响**

- 项目方认为「实现太乱」，根因不是缺少规则，而是**规则的作用域与实际代码位置不重合**。在修复这一重合之前，任何「按层重构」都无法被验证是否真的改善。
- `adapter > iface > govern > kernel` 这个四层设计目前**完全悬空**：adapter 层的实体（`mcp_server.py` / `mdcg.py` / `mdcos.py`）不在任何层包里，`govern`/`kernel` 层是空壳，`iface` 层只被 `test_kernel_iface_contracts.py:15` 引用。

**建议（渐进式，不推倒重写）**

1. **先把判据扩到全仓，再搬家**。给 `_verify.py` 增加一个 `_SCAN_ROOTS` 参数，使其能对 `md_cg/` 根目录下**未归类模块**执行「只允许依赖白名单」检查。这一步零文件移动，只让现状可度量 —— 产出「根目录 → 子包」的越权边清单，作为后续搬迁的施工图。
2. **把 `mreview` 登记进 `_LAYERS`**（或显式声明它属 `govern`），让那 24 处反向依赖立刻变红，再逐条按 P0-3 的顺序消解。
3. **把架构判据提为独立 gate 步骤**（`python scripts/check_import_direction.py`），进 `.github/workflows/`，让 PR 上能点名违规而非只靠全量套件红绿。参照 `iface/_verify.py` 已有的「夹具自证」模式，确保新守卫不是恒绿。

### P0-2 · 治理层「目录是空壳、实现散落根目录」的双账本（A-02）

**证据**

- 空壳侧：`md_cg/govern/__init__.py` 全文 16 行，`__all__ = ["GOVERN_LAYER", "LIFECYCLE_STATES"]`，`LIFECYCLE_STATES = ("active", "dormant", "retired", "tombstoned")`。自述「本包为 W1 骨架（M1）：只放类型与协议…… M4 才把 revise/retire/rollback 真刀切换过来」。
- 实现侧：`revise.py`(111)、`rollback.py`(601)、`audit.py`(602)、`conformance.py`(666)、`writelimit.py`(519)、`writegate.py`(244)、`consistency.py`(1138) 全在 `md_cg/` 根。
- 该 `__init__.py` 甚至明确写了「届时 `rollback` 必须覆盖正文——该能力已由 `md_cg/rollback.py` 实现」——**文档自己承认了实现位置的偏差**，却把对齐推到 M4。

**影响**：这是「层」概念失效的直接原因。读代码的人打开 `govern/` 看到 16 行常量，会以为治理层未开始；而真正的治理逻辑有 3881 行藏在根目录里，且与 155 个其他源模块平级。

**建议**

渐进落地，**每步一个 PR、每步保持 `run_tests.py` 与架构守卫全绿**：

`run_tests.py:56-59` 注释说明其设计意图：`tests/` 是「悬赏验收直接运行入口，『**已逐文件裁决可改**、且在 `md_cg/` 里没有同名副本的测试』……若本清单漏收，该测试就完全不在 CI 里」。

## 四、建议的重构顺序

原则：**先 measurable（可度量）→ 再可验证（守卫接电）→ 再搬家（纯转移）→ 最后解耦（改依赖）。** 每个阶段独立成 PR，每阶段结束时 `python scripts/run_tests.py` 与架构守卫必须全绿。

### 阶段 0 · 建立基线（半天，零风险）

**目标**：让「现状有多乱」变成可度量数字，后续每一步都能证明改善了。

**步骤**
1. 跑 `python scripts/run_tests.py` 记录当前全量基线（804 个目标）。
2. 跑 `python -X utf8 -m md_cg.test_kernel_iface_contracts` 记录 14 项全绿基线。
3. 把本报告的 A-01 覆盖数字（867 / 255,089 = 0.34%）写成一份 `docs/dev/架构健康基线_20261111.md` 存档。
4. 记录 `git rev-parse --short HEAD`。

**如何验证行为不变**：本阶段只读 + 写文档，无代码改动。

**风险**：无。

### 阶段 1 · 补齐缺失门禁（1–2 天，收益最高）

**目标**：把已有但未接电的验证面接上。不碰任何业务代码。

**步骤**
1. **新增 `ts-tests` workflow**（对应 P0-4）：`npm ci --include=dev` → `npm test`。这是纯增量，`package.json:106` 已定义好命令。
2. **新增 `scripts/check_lib_fresh.py`**（对应 P1-6）：src↔lib mtime 单调检查，接入 `package.json:108` 的 `gate`（本地守卫，不进 CI）。
3. **把 `test_kernel_iface_contracts` 提为独立 gate 步骤**：在 `package.json` 的 `gate` 中显式加一项，使架构判据能点名失败而非淹没在 804 目标里。

**如何验证行为不变**：新门禁首次运行时，**若为绿，说明现状无回归**；若为红，说明发现的是既有缺陷（用阶段 0 基线判定），应先登记再修，不可为了变绿而弱化门禁。

**风险**：新增 CI job 会增加 PR 时长。TS 测试 63 个、`tsx` 直跑，预计可控。若过慢，可先只跑 `hooks*` / `roleplay*` / `context-window` 等高价值子集并登记其余。

### 阶段 2 · 扩展架构判据覆盖面（3–5 天，P0 核心）

**目标**：让架构守卫从覆盖 0.34% 提升到覆盖 100%，**这一步只让问题可见，不修问题**。

**步骤**
1. `md_cg/iface/_verify.py` 增加 `_SCAN_ROOTS`：对 `md_cg/` 根目录下未被归类的模块，执行「只允许依赖白名单（纯 stdlib + `iface.contracts`）」检查。
2. 把 `mreview` 登记进 `_LAYERS`（声明其属 `govern`），使 24 处反向依赖立刻变红。
3. **先记录红线基线**（允许「已知违规清单」显式登记），避免门禁一上来就恒红导致被关掉 —— 这正是 `_verify.py:71-74` 警告的失效模式。该模式在本仓已有先例可复用：`test/chaos_injection/registry.py:77,85` 的 `EXPECTED_GAP`（已知缺口基线）与 `scripts/run_tests.py:64` 的同名概念。
4. 产出「根目录 → 子包」越权边清单，作为阶段 3 的施工图。

**如何验证行为不变**：`_verify.py` 的 `_test_import_direction` 是**静态 AST 分析、零副作用**（`:15` 自述「不执行、不 import、零副作用」）。扩展它不改变任何运行时行为。对比阶段 0 基线：`run_tests.py` 结果应完全一致。

**风险**：若把「已知违规」一次性全设为 hard-fail，门禁会红且被绕过。**必须用显式基线清单渐进清零**，这是阶段 2 的关键纪律。

### 阶段 3 · 纯转移：把治理实现搬进治理层（1–2 周）

**目标**：消除 `govern/` 空壳与根目录实体的双账本（P0-2 / P0-3）。

**步骤**
1. **先下沉纯常量**（P0-3 建议 1）：`ALL_ROLES` / `WORK_ROLES` 从 `mdcos` 迁到 `kernel/`（当前 19 行、零依赖，天然适合）。`mdcos` 与 `mreview/govern.py:52` 改为从新位置取。**这一步同时反转「被治理方定义标准」。**

3. `govern/__init__.py` 升格：导出上述模块公共符号，与 `LIFECYCLE_STATES` 并存。
4. 每迁一个模块，跑 `run_tests.py -k <相关>` 对应目标集。

**如何验证行为不变**
- 迁移前后 `run_tests.py` 全量结果必须逐目标一致（用阶段 0 基线 diff）。

### 阶段 4 · 拆解巨型单体（持续，按收益排序）

**目标**：把 A-05/A-06/A-07 三个上帝体降到可维护规模。

**顺序（按拆解成本从低到高）**

- 每个文件都有密集的既有测试（`test_c8_search_rrf_gates`、`test_issue*` 系列直接 import 这两个模块），迁移前用 `run_tests.py --list | grep <模块>` 锁定目标集，迁移后复跑。

**风险**：最高的阶段。缓解手段：**一次只拆一个关注点**、坚持 re-export shim、每个 PR 只动一个巨型文件。**不要尝试一次重写任何一个。**

**步骤**

**验证**：无行为变更；`run_tests.py` 与全部守卫保持绿。

### 阶段排序理由（为什么不是先拆大文件）

项目方直觉是「三个 7000 行文件最该先动」。但本次审计认为**应后置**，理由有三：

1. **拆之前必须先有判据**。当前架构守卫覆盖 0.34%，如果先拆大文件，拆完没人能证明「依赖方向真的改善了」——只能靠人肉 review。先做阶段 2，拆完即可由机器裁决。
2. **`mdcos` fan-in = 205、`mdcg` fan-in = 83**。在这两个数字下降之前，任何拆分都是在 205 个调用点上做手术。而阶段 3 的「治理实现迁入层包」会自然降低根目录耦合，为阶段 4 创造安全窗口。
3. **阶段 1 的 `ts-tests` 是零风险的纯增量**，却堵住了 `src/` 侧唯一的验收真空。投入产出比远高于任何拆解。

**一句话结论**：本项目的重构不是「收拾乱麻」，而是「给已经画好的图纸通电」——先接电（阶段 1–2），再搬家（阶段 3），最后拆解（阶段 4）。
