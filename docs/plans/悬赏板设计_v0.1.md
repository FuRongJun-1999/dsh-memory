# 灵枢悬赏板 · 设计稿 v0.1（2026-10-09）

> 参考：**ClawHunt**（`clawhunt.store/marketplace`）——AI agent 悬赏市场。
> 设计者裁定（2026-10-09）：**灵枢＝发布方** ｜ **结算＝声誉制（不涉资金）** ｜ **落点＝大脑仓 `dsh-memory`**。
> 本稿只落本地，**未经设计者点头不 push 到公开面**。

## 〇、一句话

把公开仓的 issue 池变成**可认领的悬赏任务**：外部人或 AI agent 认领 → 交付 → 过我们现成的确定性验收闸 → 记入**可追溯的声誉账本**。

## 一、为什么值得做（我们缺什么 / 有什么）

| 面 | 现状 | 结论 |
|---|---|---|
| 认领机制 | 公开面**零认领**（无 ISSUE_TEMPLATE／无 CODEOWNERS／无 assignee 流程）；但**蜂群内部早有** `hive/jobs/*/claimed.lock` 租约 | **把内部已有的认领-租约外化到公开面** |
| 验收机制 | 已有四闸：CI（该仓 8 workflow）／复现机器人（`repro-bot.yml`）／PR 审核细则（两闸）／守卫+变异惯例 | 验收我们**比 ClawHunt 强**（确定性读数 vs 纯人审） |
| 激励 | 无 | 加声誉面（ClawHunt 用 karma 分，我们用**可追溯信任图**） |
| 声誉底座 | `md_cg/trust.py`（信任机制）已在 | 认知图做内部镜像，公开面另有账本 |

**差异点**：ClawHunt 的结算靠 USDC 托管、声誉只有分数；灵枢的声誉可以进**可检索、可追溯的认知图**——「这个贡献者做过什么、交付质量如何」是能查的，不是一串数字。

## 二、状态机（六态 · 映射 GitHub labels）

```
bounty:open ──/claim──▶ bounty:claimed ──/deliver──▶ bounty:delivered ──验收──▶ bounty:verified ──▶ bounty:settled
                              │                                                      │
                              └── 72h 超时未交付 ──▶ bounty:expired（自动回 open）    └── 争议 ──▶ bounty:disputed
```

- `bounty`（入选标记，维护者打）· `difficulty:{easy|medium|hard|expert}` · `bounty:{open|claimed|delivered|verified|settled|expired|disputed}`
- 交付走 **PR**（修码类）或 **评论证据块**（分析/复现类）

## 三、命令面（MVP 只做 GitHub 评论命令）

| 命令 | 谁用 | 效果 |
|---|---|---|
| `/claim` | 认领者 | 校验（无锁／本人并发认领数 ≤ 上限）→ 上锁 + 记到期时间 |
| `/deliver <PR 链接或证据>` | 认领者 | 转 `bounty:delivered`，等验收 |
| `/withdraw` | 认领者 | 主动释放（不影响声誉） |
| `/dispute <理由>` | 双方 | 转 `bounty:disputed`，我方仲裁并留痕 |

## 四、验收（四道闸，逐道可查）

1. **CI 全绿**：该仓 8 个 workflow 在该 PR 上全绿（机器判，不可辩）
2. **复现读数**：属「可复现缺陷」类 ⇒ 用复现机器人贴原始读数（把 `repro-bot.yml` 从身体仓移植）
3. **守卫 + 定点变异**：修码类必须带守卫件与「注入必失败 ⇒ 守卫必红并点名」的变异自证（本仓既有惯例，写进验收标准）
4. **维护者人审**：我方打 `bounty:verified`（含判定理由）

**防作弊**：交付必带可复跑读数；最多 **3 轮**修改；超时回板；声誉**可降**（虚假交付/刷单记负分）。

## 五、声誉账本（双层）

- **公开面**：`docs/bounty/ledger.json`（append-only 事件流）＋ `docs/bounty/board.md`（荣誉榜，workflow 生成）
- **内部面**：认知图 `trust` 面镜像（我方心跳轮从 ledger 增量同步）——让灵枢「认识」贡献者，供跨端协作的信任权重使用
- **计分（建议值，待裁）**：easy 1 ／ medium 3 ／ hard 6 ／ expert 10；负分：虚假交付 −5、超时未交付 −1；争议败诉不扣本金但记录在案

## 六、MVP 范围（第一版只做这些）

1. `.github/workflows/bounty.yml`：注释命令处理 + `schedule` 超时回收
2. 标签体系（上表）
3. `.github/ISSUE_TEMPLATE/bounty.yml`：发布模板（含「验收标准」必填栏）

5. **试点**：先给 3–5 条现成 issue 打 `bounty` 标签，人工跑通全链（谁认领、怎么验收、账本怎么记）
