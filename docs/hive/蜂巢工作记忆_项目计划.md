## 1. 三个决策点（已落定）

### ① 载体形态：真 git 起步（A 路）

- **git 操作面只在主代理侧**（`hive/wm.py`，python stdlib 封装 git CLI）。
- worker/执行器/rust 三处**零 git 依赖**：执行器保持「读 spec.json 写 result.json」无状态契约；rust 保持纯 std（D-005 不破）。
- B 路（自研 git 兼容对象存储，blob/tree/commit SHA 内容寻址，纯 std 可写）作为后路记录在案（第 7 条兜底）；swarm 已有手写 SHA256 先例，zlib 可用 stored 块规避压缩依赖。

### ② 并发写模型：一任务一分支

- 分支命名 `task/<job_id>`；job_id 取 result.json 的 `job_id` 字段，缺失用目录名。
- **物理隔离 = job 目录本身**（蜂巢天然工作区）：worker 的写权限被结构性限制在自己的 job 目录内（位置效应落码），worker 全程不碰 git。
- 工作记忆仓只收**产物白名单快照**：`spec.json + result.json`（必须）+ `progress.jsonl`（可选，进展卡——worker 侧零 git 依赖写入的交接面，见 §3）+ `log.txt`（可选）+ `--artifacts`（可选，逗号分隔）。
- snapshot/merge 是**主代理串行操作面**（非 worker 并发面）：合并冲突处理权归主代理，wm 对冲突诚实报错（`conflict:true` + hint），绝不自动解决。

### ③ 提交语义分级：写入 → 提交 → 合并，闸在中间

| 闸 | 凭证 | 落码 |
|---|---|---|
| snapshot（提交） | `result.json` 终态 `ok:true` | 第 5 条「未验证不写入」的任务级落码；失败/超时任务物理上无法入库 |
| merge（合并主线） | 主代理显式执行 `wm.py merge` | 两阶段审查机械化；merge 须在 main 上执行（操作契约） |
| revert（回退） | 免费，任意提交点 | 生成反向提交，历史不丢（全记） |

commit message 规范：`task <job_id> verdict=ok model=<model> duration_s=<n>`——可审计。

## 3. 命令面（v0.1）

```cmd
python hive\wm.py init     [--wm DIR]                                  :: 建仓（幂等）
python hive\wm.py snapshot --job hive\jobs\<id> --wm DIR [--artifacts a.json]  :: 凭证闸+提交
python hive\wm.py merge    --branch task\<id> --wm DIR                 :: 主代理合并
python hive\wm.py log      --wm DIR [--branch B] [--limit N]
python hive\wm.py revert   --commit SHA --wm DIR                       :: 免费回退
python hive\wm.py status   --wm DIR
python hive\wm.py progress --job hive\jobs\<id> [--limit 50]           :: 读进展卡（未快照）
python hive\wm.py progress --wm DIR --job-id <id> [--limit 50]          :: 读进展卡（已快照，两级查找）
```

默认仓位置：`hive/wm-repo/`（运行态，已 gitignore）；`HIVE_WM_DIR` 可覆盖。
输出统一单行 JSON（对齐 hive CLI 风格）；`wm-repo` 内 `jobs/<job_id>/` 即产物快照树。

**`progress` 读取面（v0.4 §5.3 换人续跑落地，2026-09-16）**：worker 在自家 job 目录写
`progress.jsonl`（`start`/`tool`/`final`/`handoff`/`error` 逐条），**全程零 git 依赖**——
符合「worker 无 git 面」的结构约束；进展卡由主代理在 `snapshot` 时纳白名单入库。
已快照 job 的卡只存在于 `task/<job_id>` 分支（snapshot 后 HEAD 归还 `main`），
故 `--wm` 源走**两级查找**：先工作区，落空再 `git show task/<ID>:jobs/<ID>/progress.jsonl`，
返回体 `source`（`job`/`worktree`/`wm_branch`）与 `ref` 标明读取出处；卡缺失如实报缺不伪造。
坏行跳过不炸（诚实降级）；`handoff`/`auto_continue` 透出交回信号，**续跑裁决权在主代理，
本命令不自动续跑**（`auto_continue` 恒 `false`）。

## 5. 设计边界（诚实）

- snapshot 串行契约：并发多任务快照由主代理串行调度（合并权本就归主代理）；worker 间没有 git 并发面。
- 快照中途失败可能残留 staging 目录（`wm-repo/jobs/<id>`），下次 snapshot 自动覆盖，不影响 main。
- 冲突现场保留（不自动 abort），hint 给出 `merge --abort` 出口——处理权在主代理。
- 工作记忆内容推 GitHub 前必须过第 14 条双清单（盘符绝对路径/密钥/个人标识），默认只存本地/推私有仓。
