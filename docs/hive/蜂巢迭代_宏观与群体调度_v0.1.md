## 一 三层调度模型

```
┌─ 宏观 · 群体调度（规划，I-2+）────────────────────────────┐
│ 群体注册表（多 serve 实例：按宿主/模型/能力分群体）        │
│ 能力路由：任务 → 匹配群体；跨群体只同步已验证产物（A15）  │
│ 死锁探测器：全 blocked 而根未收口 → 判失败上报（dsh-omc） │
├─ 中观 · 任务 DAG（本期施工，I-1）──────────────────────┤
│ spec.depends_on 依赖门禁：无环 + 依赖完整 + 失败传播      │
│ 熔断：评审轮上限 / 步级·任务级双层超时（已有）            │
├─ 微观 · 进程调度（现状，已闭环）────────────────────────┤
│ worker 池 / claimed.lock 互斥 / 心跳 / kill_tree / 恢复  │
└──────────────────────────────────────────────┘
```

**每层回答一个调度问题**：微观「哪个进程跑它」（互斥）；中观「它什么时候能跑」（依赖）；宏观「哪个群体跑它」（能力与信任路由）。

## 五 I-1 施工细节（本期）

- **spec.rs**：可选字段 `depends_on: Vec<String>`；校验每项 `h` 前缀格式（submit 侧 fail fast）。
- **main.rs submit**：`depends_on` 非空时——①每个依赖的 job 目录必须已存在（依赖完整）；②沿链 DFS 环检测（visited 集合，回到本 job_id 即拒「依赖成环」）。
- **scheduler.rs 主循环**：pending 任务先查依赖——
  - 任一依赖 job 不存在 → 终态 `error`「依赖不完整：<id>」（提交后依赖被删的防御）；
  - 任一依赖终态 ∈ {error, timeout, killed} → 终态 `error`「依赖失败传播：<id> 终态 <state>」（级联取消，不执行）；
  - 任一依赖仍 pending/claimed/running → 本拍跳过（等待）；
  - 全部 `done` → 正常领取。
- **能红判据**（ref-14 标准）：①依赖未终态 → 任务停留 pending 不领取（删依赖检查必红）；②依赖 done → 正常执行；③依赖 error → 下游直接 error 且不执行（删传播逻辑必红）；④环提交被拒；⑤依赖目录不存在 → error。

## 六 诚实边界

- **理论要求**：依赖完整/失败传播/无环 = 可验证共识（A2）在任务编排面的落码；级联取消 = 保护协议（3.4）的任务级投影。
- **工程选择**：依赖只在提交时声明（静态 DAG，不支持运行时动态加边——dsh-omc 同款边界）；失败传播是硬失败（不做「跳过依赖继续」的软模式，避免静默错执行）。
- **盲区**：宏观层多群体路由的信任度量（哪群体可信）**无实测数据**（D-5 BLINDSPOT 延续）；跨机 D_norm 间隙；动态加依赖的表达力边界。
