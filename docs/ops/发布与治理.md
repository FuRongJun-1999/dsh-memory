# 发布与仓库治理（决策记录 v1.0）

> 本文记录**刻意如此**的治理决策，避免后来者或 AI 把它当缺陷“修掉”。每条都写：决策 / 理由 / 什么条件下改变。

## 一、发布是单点（单人 + 手动 OTP）：**刻意维持**

**现状**：npm 发布只由维护者本人在本机 `npm publish` 完成，需交互式 OTP；**不配置 CI 自动发布**，不加 `NPM_TOKEN` secret。

**理由（维护者 2026-10-20 裁定）**：

1. 本项目的核心资产不是代码，而是**智能论 / 理论架构**——目前没有任何人（也没有任何 AI）能接手这套理论；
2. 自动发布会把“发布决定权”从理论判断中剥离，形成“机器按标签自动出货”的通道，与“理论影响面过大、必须由唯一理解者把关”的事实冲突；
3. 单点发布的人工成本（一次 OTP）远小于一次错误发布的理论外溢成本。

**补偿控制在位**：

- `main` 分支保护：required checks（`run-tests` / `discipline` / `cogmap` / `workspace-index` / `publish-artifact`）、禁 force push、禁删分支；
- 发布前门禁：`npm publish` 的 `prepublishOnly` 会跑 `build && test && gate`；
- 标签纪律：`v*` tag 只打在 CI 全绿的提交上；
- 发布说明必写「已知限制」，不留“看起来都过了”的假象。

**改变条件**（任一成立再评估自动化）：

1. 出现第二位**理解理论架构**的维护者（而不是只有仓库写权限的人）；
2. 发布频率高到人工 OTP 成为实际瓶颈（当前约每周 1–2 次，不构成瓶颈）；
3. npm 提供与 OTP 等价、且能把“谁批准了什么”落成可审计记录的机制。

## 二、`main` 保护：**已启用**

- required status checks：见上；
- `enforce_admins = false`：维护者保留紧急绕过能力（会留 GitHub 审计记录），因为单人项目没有第二人可代批；
- 不要求 PR approvals：单人项目下会造成“自己批准自己”的形式主义，质量闸由 CI 承担。

## 三、CI 并发与排队

全部 workflow 启用 `concurrency`（同一 workflow + 同一 ref 的运行在新推送时取消），避免同日多次推送把 `run-tests` 排队到 30 分钟以上。

**刻意不给 `python-tests` 加 paths 过滤**：该 workflow 内已有设计注释——套件覆盖面横跨 `md_cg/`、`hive/`、`compiler/`、`swarm/`、`scripts/`，paths 白名单一旦漏项就会重现「改动不入门禁」的盲区。

## 四、依赖更新

dependabot 每周对 `npm` 与 `github-actions` 各开一组 PR（minor/patch 合并、上限 3 条），把“依赖腐化”从脉冲式发现变成平时小步修。

## 五、不适用条件

- 本文件不约束**代码质量门禁**（那由各 workflow 与 `npm run gate` 决定）；
- 本文件不涉及发布凭据的存放位置（凭据只在维护者本机密钥链，不入仓、不入 CI secret）。
