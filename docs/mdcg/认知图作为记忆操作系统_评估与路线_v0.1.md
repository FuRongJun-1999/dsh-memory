## 二、OS 视角评估：差什么

把「记忆操作系统」拆成 OS 必备件，逐项对照：

| OS 要件 | md_cg 现状 | 差距 |
|---|---|---|
| **文件系统**（持久化）| ✅ md 目录 + 原子写 + 跨进程锁 + 分片日志 | — |
| **索引/目录服务** | ✅ 条件分区 + 可重建 `_index` | — |
| **系统调用面**（对外 API）| ⚠️ Python 库（`MdCG` 类）| **无 MCP 工具面 / CLI / 守护进程**；无版本化契约 |
| **进程与会话模型** | ⚠️ 有文件锁 | **无租户/会话/身份**；多 agent 并发语义未定义 |
| **权限与安全** | ❌ | 无访问控制（对比 noema：sensitivity cap + tombstone + payload-free 审计）|
| **设备驱动**（数据源）| ❌ | 未接 AEIS 记忆库 / DSH 会话 / 视觉语音产出 |
| **调度与生命周期** | ✅ flush/close/compact/rebuild | 无常驻服务、心跳、自愈 |
| **可观测** | ✅ health + `_reflection.jsonl` + `_access.log` | 无指标导出/告警/看板 |
| **与既有系统关系** | ❌ | AEIS 主库仍是 sqlite（`aeis_memory.db` 59MB）——**两套记忆并存，未统一** |

## 三、关键判断

**md_cg 目前是「引擎（engine）」，不是「操作系统（OS）」。**

三处结构性差距（按优先级）：

1. **系统调用面缺失** —— 它是 Python 库，不是服务。要成为 OS，必须暴露**稳定的对外接口**（首选 MCP 工具面，因为灵枢本身就是 MCP 服务、DSH 与其他 agent 天然可调）。
2. **与灵枢/AEIS 未统一** —— 认知图（md_cg）与 AEIS 记忆（sqlite）**并行两套**。OS 的前提是**单一权威存储**。
3. **进程/权限模型缺失** —— 多 agent 并发写、租户隔离、访问控制都还没有（文件锁只解决了互斥，没解决"谁可以写什么"）。

> 另：md_cg 已从 `llm-adapter-poc/` 实验工作区提取到工作区顶层 `md_cg/`（2026-09-09），一次性脚本留在原目录待清理。

## 四、路线（引擎 → OS）

| 阶段 | 做什么 | 验收 |
|---|---|---|
| **P1 接口** | md_cg → MCP 工具面（remember/recall/search/verify/reflect/health/forget）；DSH 插件可直连 | MCP 客户端可调用；与现有 dsh-memory 工具面兼容 |
| **P2 统一** | AEIS 现有记忆（`aeis_memory.db`）迁移到 md_cg | **全量字段等价**（非抽样）+ 幂等 + 可回滚；沿用本次知识库 md 迁移经验 |
| **P3 进程** | 常驻服务 + 会话/租户 + 权限（参考 noema：tenant.lock / sensitivity cap / tombstone / payload-free 审计）| 多 agent 并发写零丢失；越权写入被拒 |
| **P4 驱动** | 接入实际数据源（DSH 会话、视觉/语音产出）| 端到端：一次会话 → 记忆 → 条件路由召回 |

## 五、结论

- **引擎层已经成熟**：五层 + 条件路由 + 资格四态 + 认知循环 + 负记忆 + 并发/只读契约，**P0/P1 全绿，3058 节点实战**。
- **OS 层刚起步**：缺**系统调用面（MCP）**、**单一权威存储（与 AEIS 统一）**、**进程/权限模型**。
- **最优先**：把 md_cg 暴露成 MCP 工具面 —— 这一步完成后，它才真正从"库"变成"可被多个 agent 共同依赖的操作系统"。
