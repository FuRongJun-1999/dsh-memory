## 2 四条解读

### 2.1 **B 不是净改进 —— 它是把偏置从一端推到另一端**
B 在「现值 +0.53、滞后 −0.40」上是数量级改善，但在**通用能力轴**上全面下降：历史 −0.27、四态 −0.18、缘由 −0.16、逐字 −0.09。
其中**四态 / 缘由 / 逐字不是「历史题专属」**，它们的下降说明代价不只落在历史问上。
桶分布更直白：B 让 **long 桶从 0.6207 掉到 0.2069（−0.41）**，只换来 short 桶 +0.05 ⇒ **`fact_time` 系统性惩罚长链**。
⇒ **两个口径都不能直接采用**：A 偏「旧」（平列后 id 字典序让最早版本恒胜），B 偏「新」（最新版本挤掉正确的历史版本）。
这与根因件（`task-31`）的结论一致：缺的是**「事实生效时点 / 版本序」按时点条件化**，而非全局偏向新或旧。

### 2.2 ★**新发现的硬缺陷：变更链两组皆 ≈0（与本次口径无关）**
A=0、B=0.0357，而同口径的官方首轮灵枢 `chain=0.643` ⇒ **本 harness 的 adapter 在「变更问」上失效**。
变更问要**按序号列出每一次变更前后的值**（`CHAIN_K=60 / CHAIN_MATERIAL_CHARS=80000`），两组皆崩说明：
**不是 `created_at` 口径造成的，而是 adapter 的检索面拿不到/装不下整条链**。
⇒ **在该轴上本 harness 目前不可用于判断**；这是必须先修的 harness 缺陷，不是引擎结论。

### 2.3 「同口径 ≠ 同实现」再次被证实
本 A 组（0.3617 / 0.4468）与官方首轮 lingshu（0.489 / 0.298）**同量级但不等**，且本 A 组滞后**更差**。
官方首轮用的 adapter **不在公开仓内**（README §8 明说 `common.py`/`adapters/*` 由使用者自备），故两组**不可横比**，
本表只能作**同实现内的 A/B 因果对照**，不能当「灵枢在官方榜上的分数」。

### 2.4 与外部提交的差距仍在
外部提交（RRF3 v1.1 + ChronicleDM）：现值 0.979 / 历史 0.927 / 变更链 0.982 / 滞后 0.021。
B 只在「现值 0.894 / 滞后 0.043」上逼近，**历史 0.520 / 变更链 0.036 差距仍大**——且变更链的差距**主要来自本 harness 缺陷**，须先修再评。

## 3 建议的下一步（按依赖排序，均需裁定后才动 `md_cg`）

1. **先修 harness 的变更链覆盖**（不是改引擎）：查 adapter 在 `CHAIN_K=60` 下为何只覆盖到极少 seq；修好后重跑 A 组，拿到**该轴的真实基线**。
2. **再做「时点条件化」**：解析问题里的时点（「第 k 次提交」）并据此选择/排序版本，目标是**现值↑ 且 历史/四态/缘由 不降**——判据就用本量具（~1 秒/轮）+ 官方判分器双证；**不得**用「只看现值」的单轴判据。
3. **红线**：`probe_judge.py` 一行不改；任何改动若使历史/四态下降，视为**未通过**（本 A/B 就是这条判据的反例）。
