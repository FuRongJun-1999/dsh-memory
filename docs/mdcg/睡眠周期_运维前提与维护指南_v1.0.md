# 睡眠周期 · 运维前提与维护指南（v1.0）

> **这一页回答一件事：开了睡眠周期之后，你的记忆库多了什么、在哪里、怎么维护、怎么关、怎么退。**
> 依据：`docs/plans/睡眠与自迭代_功能优化设计_v0.4.md`（规格冻结版）§四 / §4.7。
> 使用者裁定（2026-10-01，第三轮）：「进行登记，让用户知道怎么维护记忆」。

---

## 一、睡眠周期是什么（一句话）

灵枢的**自迭代**（八步闭环的第 5 固化 / 6 记录 / 8 方向性自检）与**睡眠整理**合成一条周期引擎：在**睡眠时段**内，用**一个副本**做归纳 / 升层 / 巩固 / 权重与索引重建，完成后**周期性合并**回主库，并**留下修改历史**。

**为什么用副本**：整理期间主库的**真源面**（八个层目录下的 `.md`）逐字节不变——长驻进程（serve / 蜂巢 / 会话）继续正常读写，整理结果只在合并那一刻以**受闸门约束**的方式落回。

---

## 二、版本库在哪里（唯一的"新增物"）

| 项 | 位置 | 说明 |
|---|---|---|
| **版本库（git 目录）** | `<state_root>/sleep/lib.git` | **在数据根之外**。用 `git --git-dir` 显式指定，**不在你的记忆库里放 `.git`** |
| **影子工作树** | `<state_root>/sleep/shadow` | 整理实际发生的地方；每轮以 `git worktree` 建在分支 `sleep/<时间戳>` 上 |
| **台账** | `<state_root>/sleep/` 下的轮次记录 | 每轮九步的逐步读数、语义差异集 Δ、冲突清单 |

**版本库只覆盖真源面**：那八个层目录下的 `.md`。以下**结构性进不去**（用显式路径白名单而非 ignore 面保证）：
`_keys.json`（密钥信封）· `_access.log` · `_index.json` · `_index_log/` · `*.tmp`（临时件）· `*.lock`（锁件）。
⇒ **密钥与运行态从设计上就不可达**，不是"记得排除"。

## 三、维护动作（你要知道的四条）

### 1. 看历史

```bash
git --git-dir=<state_root>/sleep/lib.git --work-tree=<root> log --oneline
```

一条睡眠周期 = **两个提交**：先是**内容提交**（语义重放落主库的那一刻，台账里记作 `round_commit`），随后是 `--no-ff` 的**合并提交**（只记拓扑，其树与内容提交同）。

### 2. 看某一轮改了什么

```bash
git --git-dir=<state_root>/sleep/lib.git --work-tree=<root> show <round_commit>
```

逐节点的 before/after 另有 `_maintain.jsonl` 同族留痕（与权重重算共用一套）。

### 3. 回退（**只提供 `revert`**）

```bash
git --git-dir=<state_root>/sleep/lib.git --work-tree=<root> revert <round_commit>
```

**要 revert 的是该轮的「内容提交」**（台账 `phases.merge.round_commit`）——合并提交只是拓扑记录，对它 `revert -m 1` 对内容零影响（git 会报 nothing added to commit）。

**裁定（第三轮）：只给 `revert`，不提供 `reset --hard`。** 理由：`revert` 出一个**新提交**——历史不丢、可追、可再次审计；`reset --hard` 会抹掉历史，与「留下修改历史」的裁定相反。
回退是**显式发起**的动作，睡眠周期**永不自动回退**。

### 4. 冲突怎么处理

合并阶段若发现**主库与影子改了同一个 id**（或命中保护闸 / tombstone 闸 / 生命周期闸），该项**挂起**：**不自动解决**、**不写入主库**，出一个冲突清单等人处理（与蜂巢工作记忆 `hive/wm.py` 的既有裁决同款：冲突手交人工）。

> 一句话：**git 只做记录者，准入由仓内既有闸门裁决**。所以「合并成功」不等于"git 没冲突"，而是"过了语义四闸"。

### 5. 手动跑一轮（不等 tick）

手动入口是**同一条周期**的入口，不是旁路——它过的是同一套**四道门**：

```bash
python -X utf8 -m md_cg.sleep --once              # 立即一轮：过四道门并落台账
python -X utf8 -m md_cg.sleep --once --dry-run    # 只预览：跑盘点与四道门，不物化、不记账
python -X utf8 -m md_cg.sleep --status            # 只读：含 last_cycle（上一次为何没迭代）
```

- `--once` 与常驻 tick 调的是同一个 `run_cycle`；**门没过就只记一条台账**，并显式打印
  一行 `本轮未迭代原因：…`——**该行与台账同一文案源**（「门拦」/「物化未完成」/「幂等」
  三类可辨，见 §九）。
- `--dry-run` **只与 `--once` 同用**（单独使用直接报错并返回 2，不执行任何动作）。
- `--status` 的 `last_cycle` 段给出最近一条台账记录的 `t` / `batch` / `round` /
  `candidates` / `skipped`、②③④ 的 skip 文案与 `phases.materialize` 摘要——
  **「上一次为什么没迭代」从 CLI 直接可看**，不必翻 `_sleep.jsonl`。

## 四、开关与可调项（全部可调）

| env | 缺省 | 语义 |
|---|---|---|
| `MDCG_SLEEP` | `1`（开） | 睡眠周期总开关；设 `0` 即整条周期不再启动 |
| `MDCG_SLEEP_INTERVAL` | `3600` | 周期（秒），缺省一小时一次 |
| `MDCG_SLEEP_WINDOW` | `23:00-07:00` | **睡眠时段**（本地时间）；**支持跨午夜**；留空 = 全时段；**窗口外只记账、不迭代** |
| `MDCG_SLEEP_MERGE` | `auto` | 合并策略：`auto`（自动执行四阶段）/ `ask`（合并前询问）/ `never`（只留副本不合并）。**`auto` 下冲突仍挂起** |
| `MDCG_SLEEP_GITDIR` | 空 | 覆盖版本库位置（缺省 `state_root()/sleep/lib.git`） |
| `MDCG_SLEEP_SHADOW` | 空 | 覆盖影子工作树位置（缺省 `state_root()/sleep/shadow`） |
| `MDCG_SLEEP_SCRUB_APPLY` | `0` | 第④步「去污染实改」的闸门；**缺省只盘点不落盘** |
| `MDCG_TEMPORAL_GAMMA` | `ln2/30天` | 时间邻近度的衰减率（半衰期 30 天，与既有 `links.py` 同刻度）；可调 |
| `MDCG_CHAIN_TYPES` | 空 | **因果路沿哪些边类型扩散**（逗号分隔，大小写不敏感）。留空 = 缺省集 `causal,sequential,applies_to`。**这一项决定因果路在语料库上有没有东西可走**：从文档/叙事语料切出来的节点只有 `reference` 与父章节结构边，**没有 causal 边**，所以对这种库要显式设成 `MDCG_CHAIN_TYPES=reference,part_of`（或含 `sequential`）——否则因果路恒空。只接受 `chain.EDGE_WEIGHTS` 里已登记的类型，未登记形态会被剔除并回落缺省集 |
| `MDCG_SUSTAIN` | `1` | 常驻自维持循环总开关（睡眠周期挂在它上面） |

> **整条关掉**：`MDCG_SLEEP=0`；**连常驻循环一起关**：`MDCG_SUSTAIN=0`。

> **调度前提（v1.1 补）**：睡眠周期**没有自己的进程**——它挂在常驻 `sustain` 循环的
> **第六档 tick** 上（缺省 `MDCG_SLEEP_INTERVAL=3600` 秒一次）；**进程不在就不跑**，
> 也没有补跑机制（错过的 tick 不追）。跑一轮要过**四道门**：总开关
> `MDCG_SLEEP` / `MDCG_SLEEP_MERGE=never` / 睡眠窗口 / 稳态候选数为 0。
> 手动入口 `--once` 过的正是这同一套门（见 §三.5）。

## 五、自动的边界（哪些永不自动）

| 动作 | 可自动 | 依据 |
|---|---|---|
| 归纳 / 升层 / 权重重算 / 索引重建 | ✅ | 确定性、可预演、可回滚；索引是派生物 |
| 去污染**实改** | ⚠ 缺省关（`MDCG_SLEEP_SCRUB_APPLY=0`） | 在副本上可放行，合并前可复核 |
| **任何依赖 LLM 的固化** | ❌ **永不自动** | 依赖 LLM 的动作交人工另批 |
| **任何不可回滚的删除** | ❌ **永不自动** | 五环承诺：遗忘只能由显式 `cg(op=forget)` 发起 |
| 方向性自检 | ✅ 只产**记录** | 理论纪律：自检结果**不自动触发修改** |

**「合并前可复核」在缺省配置下由什么保证**：缺省 `MDCG_SLEEP_MERGE=auto` 会在**同一轮**内把已过闸的改动一并落主库，所以严格的「合并前人工看一眼」窗口只由 `MDCG_SLEEP_MERGE=ask` 提供。另外**去污染实改缺省就是关的**（`MDCG_SLEEP_SCRUB_APPLY=0`），所以缺省配置下最具侵入性的那一档根本不会落盘——要用它，请显式开启并配 `ask` 档。

**窗口值写错了会怎样**：`MDCG_SLEEP_WINDOW` **留空**＝全时段（这是唯一的显式全时段入口）；**非法形态**（例如 `23:00-99:99`）按同表 `INTERVAL`/`MERGE` 的既有回落口径**回落缺省 `23:00-07:00`**——不会因为打错字而变成全天迭代。

## 六、健康读数（每轮都留）

每轮睡眠在台账里留：①盘点候选数 ②本轮语义差异集 Δ 的大小 ③过了四闸多少、挂起多少 ④是否空轮（候选 0 ⇒ 只记账不动手）⑤九步逐步读数（未接线的步骤显式标 `skipped`）。

`cg(op=sustain, action=status)` 可看到最近几轮；命令行侧另有
`python -X utf8 -m md_cg.sleep --status` 的 **`last_cycle`** 段（最近一条台账记录的
`t`/`batch`/`round`/`candidates`/`skipped`、②③④ skip 文案、`phases.materialize` 摘要
与 `not_iterated_reason`）——**「上一次为何没迭代」不必翻台账文件**。

## 七、前提一句话总结

> 睡眠周期会在 `<state_root>/sleep/lib.git` 建一个**只覆盖真源面**的版本库，用它做**副本迭代 + 周期合并**，合并准入走仓内既有语义闸门（不是 git 的文本合并），回退只给 `revert`，冲突挂起等人处理。**密钥与运行态结构性进不去这个版本库。**

## 八、P2 / P4 落地后的检索与权重变化（2026-10-01 · 发版披露）

> 依据：`docs/plans/睡眠与自迭代_功能优化设计_v0.4.md` §5.1–§5.4 / §七。
> **这一节是「默认检索读数变了」的对外说明**——改动前基线与改动后读数见
> `scripts/p2p4_probe.py`（同一命令在改前 worktree 与改后工作区各跑一次）。

### 1. 六要素后两行进默认检索（§5.4）

`# 验证方式`（后置条件词）与 `# 不适用条件`（拒绝域词）现在进**索引条目**
（`postcondition_terms` / `rejection_terms`，与 `time_window` 同款「免读文件」扁指标量），
并进**默认检索路径**：

- 问「**怎么验证的 / 用什么方法证明**」或查询词命中验证手段 ⇒ 召回声明了该手段的节点；
- 问「**什么条件下不适用 / 何时不适用**」⇒ 召回**声明了拒绝域**的节点，结果卡带
  `boundary_hit` 标记（`meta.boundary` 里有独立计数）；
- **普通问句下拒绝域仍不作召回键**（反例命中只由资格判定处置）——灵敏度一字不动。

**拒绝域双语义**：边界命中（`boundary_hit`）与资格 `REJECT` 是**两件事**，
分开计数、分开呈现；「问它什么时候不适用」不会把节点自己打成 REJECT。

**口径提醒（务必知道）**：`mdcg_recall` 的缺省**融合口径是 `max`**（因因果路缺省进路），
这影响**所有**默认召回调用，**与库里有没有边无关**；要 `sum`（经典 RRF 求和）请显式传
`fusion="sum"`。（这是设计稿 §6.2 的既定口径，本批**补披露**，行为未变。）

### 2. 权重刷新与衰减进主分数（§七）

检索分数现在是：`score ← score × cred_factor(γ, Δt) × refresh(访问计数)`。

| env | 缺省 | 语义 |
|---|---|---|
| `MDCG_FRESHNESS` | `1`（开） | 刷新/衰减乘子总开关；**设 `0` 即回到改动前口径**（与既有部署逐位一致，是「可回退」的第一道闸） |
| `MDCG_FRESHNESS_NOW` | 空 | 参照时刻（unix 秒）。**只为守卫/探针的确定性**；留空 = 系统时钟 |
| `MDCG_TEMPORAL_GAMMA` | `ln2/30天` | 衰减率（与时间路同一读取点） |

三条必须知道的语义：

1. **老记忆会被降权**（这正是「召回被旧的历史记忆干扰」的处置）：未被调用的记忆按
   `ln2/30 天` 半衰期衰减，下限 `0.001`（floor，不会归零到不可召回）；被经常调用的
   记忆按 AEIS `consolidate_cycle` 的既有门槛刷新（`access_count % 10 == 0` 且
   `last_access > 0` 才 +1%）。
2. **保护线不会被衰减穿过**：受保护节点（`importance ≥ 0.70`）的衰减乘子有下界
   `0.70 / importance` ⇒ `importance × 乘子 ≥ 0.70` 恒成立，节点不会因衰减
   **自动失去保护**。
3. **不可遗忘 ≠ 不可覆盖；降级不是删除**：`freshness.recalc(apply=True)` 只写
   `freshness_weight` 与 `freshness_state="degraded"` 标记，**从不删节点**；要跨层
   降级走既有 `_move_layer`（内含 `protect.guard_move`，受保护节点需显式 `override`）。

**粒度说明（本批的一处取舍）**：Δt 以**整日**为粒度（向下取整）。理由：γ 的单位本来
就是「天」；仓内有「同查询两轮结果逐位一致 / 可复算」的硬纪律，不量化则分数会随
系统时钟逐轮微变；量化后两侧（Python / Rust）在同一「天」桶上恒同值。量化损失上界 =
γ × 1 天 ≈ 2.3%。

**回滚（三件套，与权重重算同款）**：预演 `freshness.recalc(apply=False)` →
逐节点 before/after 落 `_maintain.jsonl`（`action="freshness"`）→
反向 `freshness.rollback(batch=...)`。AEIS 侧**没有**预演与回滚，这是移植时的净增。

### 3. 读侧语言面的已知边界（**不要**把对拍 10/10 当成已对齐）

| 侧 | 缺省路集 | 说明 |
|---|---|---|
| Python | **6 路**：lexical / bucket / entity / graph / chain / temporal | 生产读面 |
| Rust | **4 路**：lexical / bucket / entity / graph | 评测/嵌入读面，**尚未**实现 chain/temporal 与六要素后两行索引键 |

`scripts/rank_parity.py` 现在仍报 10/10，**只因其语料无 edges / 无时间参数 /
无六要素后两行声明**（缺省差异在这类语料上不可观测）——它是「两侧同口径下逐位一致」
的证据，**不是**「两侧已对齐」的证据。P4 乘子的两侧逐位对拍另配了**有判别力**的夹具
（同分不同龄的节点，见 `md_cg/test_p4_freshness.py` 的 G12）。

## 九、行为口径更新（v1.1 · issue #60/#61）：**物化成功即迭代**

> 这一节说明「读数与调度口径变了什么」。三条变更都能在台账与 CLI 上直接对拍。

### 1. 「物化成功」与「真源面未变」拆成两个读数

此前 `materialize()` 的 `ok` 把两件事混在一起：物化窗口内主库真源面被**别的写方**
改动过（活跃库里这是常态），`ok` 就是假，调用方据此**跳过整轮迭代**——越有料越不
整理（自我否决）。现在二者分开：

| 读数 | 含义 |
|---|---|
| `phases.materialize.ok` | **物化动作是否成功**（影子挂上了没：不 busy、能独立开库） |
| `phases.materialize.face_stable` | **主库真源面在物化窗口内是否逐字节未变**（= 原 `ok` 的真值） |

### 2. 物化成功即迭代；真源面漂移交**并发闸**（主库优先）

`face_stable=False` **不再阻止**迭代。迭代期间主库被改动/新增的**同一 id**，由第 ③ 段
对账的**并发闸**（物化时记下的 `baseline_face` 水位）逐项判「**主库优先**」、挂起不
自动解决（同 §三.4）。`source_face_delta` 与 `baseline_face` 两个读数**原样保留**。

### 3. 台账 skip 文案分类，不再混成一句（v1.2 补「物化超时」一支）

②③④ 步的 `skipped` 现在明确区分「门拦」与「物化未完成」（CLI 的
`last_cycle.not_iterated_reason` 与 `--once` 打印的那一行**同源**，即下表文案本身）：

| 台账文案 | 含义 |
|---|---|
| `窗口外（MDCG_SLEEP_WINDOW=…；只记账不迭代）`／`MDCG_SLEEP=0（总开关关）`／`MDCG_SLEEP_MERGE=never（只记账不迭代）`／`稳态：盘点候选数为 0（只记账不动手）` | **门拦**：按设计不动手 |
| `物化未完成：根级锁被占（另一进程在周期内）`／`物化未完成：<error 摘要>` | **物化未完成**：想动手却没做成（取不到根级锁／影子未挂上） |
| `本轮未迭代` | `ledger_steps` 的**缺省兜底**（`run_cycle` 的三条路径都显式给文案，不落这条） |
| `物化超时：<error 摘要>` | **物化超时**（issue #63）：git 子进程超时已被 kill——**操作没完成**，与「git 的裁决失败」分开（见 §十） |

## 十、常驻循环的卡死防护与观测（v1.2 · issue #63）

> 这一节说明「循环卡住会怎样、怎么第一时间看出来、怎么处置」。三层无界
> （时间 / 输入 / 观测）在本批一并收口，读数与处置全部落在**既有面**上。

### 1. 三层无界，三处消灭

`SustainLoop._run()` 是**单线程串行六档**（心跳 → 自愈 → 自净 → 演化 → 整理 →
睡眠）：任一档**无界阻塞**，整条循环停摆（issue #63 实测停 **9.5 小时**：六档
全停、`loop.state=dead`、心跳年龄无限增长）。三层根因与修法：

| 层 | 根因（现场判据见 §十.4） | 修法 |
|---|---|---|
| ① 时间无界 | `sleep._git()` 调 git **无 `timeout=`**——子进程无界等待 | `timeout=_GIT_TIMEOUT_S`（**120s**，模块常量单点可调）：超时即 kill |
| ② 输入无界 | 同处**未指定 `stdin`** ⇒ 子进程**继承父进程 stdin**——DSH 常驻宿主的 **JSON-RPC 活管道**（不写入也不关闭） | `stdin=subprocess.DEVNULL`：读 stdin 的子进程立即 EOF（先例形态 `md_cg/run_tests.py:105`） |
| ③ 观测无界 | tick 台账在 `run_cycle` **返回后**才写 ⇒ 卡住期间 `phases` 为空，外部读不到卡在哪档 | 六档进 / 出各刷**既有心跳戳**：`current_tick` / `last_tick_done` / `last_tick_error`，另给 `stale_tick` 告警 |

**超时语义（可区分）**：git 超时抛 `SleepGitTimeout`（`SleepError` 子类），消息含
「git … 超时（120s）已被 kill」+ 命令名；它与 git 的 rc≠0 失败
（`git … 失败: <stderr>`）是**两条**文案面。物化档的台账文案同样分两支：
`物化超时：…` vs `物化未完成：…`（issue #60 的 mat_fail 文案族续）。

### 2. 读数：`cg(op=sustain, action=status)` 新增进度四字段

| 字段 | 含义 | 读法 |
|---|---|---|
| `current_tick` | 此刻正在跑的档：`{name, started_at, pid}` + `running_s`（已运行秒数）；空闲为 `null` | 卡住时这一条直接回答「卡在哪档、多久了」 |
| `last_tick_done` | 上一档完成读数：`{name, t, ok}`（`ok=false` = 该档抛了异常） | 与 `last_tick_error` 配套看失败态 |
| `last_tick_error` | 最近一次档内异常：`{name, t, error: 类名+摘要}`——**容忍 ≠ 静默**（六档异常一律记入此处；由**单点包装**实现，`_run` 的六档 try/except 形态逐字未改——既有守卫 `md_cg/test_sleep_p1.py` G3a 把它钉死） | 非 null 即至少有一档在报错 |
| `stale_tick` | 告警：`current_tick` 年龄 > `max(2×该档 interval, 1800s)` 时给出 `{tick, age_s, limit_s, alert}`（alert 含档名与已运行时长） | 非 null = **疑似卡死** |

写点即**既有心跳戳**（`<net_dir>/heartbeat.<name>.stamp`）——不新增状态文件；
每档**进入时**就刷一次（卡住场景下「没有下一次写」是常态，所以必须在进入时
落盘），退出时清 `current_tick` 并记 `last_tick_done`。同进程读内存、跨进程
回落戳内字段。

### 3. 处置：`stale_tick` 报出来之后怎么办

`stale_tick` **只告警、不杀线程**（线程不可安全强杀；强杀会留下半截写）。
处置 = **人工重启常驻进程**（宿主侧重启 serve / 重新拉起灵枢插件）；重启后从
心跳戳与 `<state_root>/sleep/_sleep.jsonl` 台账接着看。

**残留锁（有界自清，2026-10-06 落地）**：git 子进程被 kill 后可能留下 `index.lock`
——现由 `sleep._clear_git_lock` **有界**自清（三闸口径）：①只碰本模块影子仓
（单属仓，无第三方合法持锁面）；②时机两处——`_git` 每次调用**前置巡检**清
**超龄锁**（mtime ≥ 300s ≫ 全调用 120s 超时上界，即崩溃残留），超时 kill 后
**force 清**当场残留（此刻仓内锁只可能来自被 kill 进程）；③其余一律不动——
超时消息如实带「已自动清理 / 未动，若后续报 lock 请人工核删」处置读数。
清理动作记一行 `git_lock_cleared` 台账（含 age_s/force）。守卫
`python -X utf8 -m md_cg.test_sleep_gitlock`（8 断言，含「新锁不误删」反向腿）。

### 4. issue #63 的现场判据（四条，引录）

1. **停摆形态**：六档全停（心跳 / 自愈 / 巡检 / 演化 / 整理 / 睡眠），
   `loop.state=dead`、心跳年龄无限增长——单线程串行的放大效应。
2. **时间无界**：`sleep._git()` 无 `timeout=`——子进程无界等待。
3. **输入无界（受控复现）**：父 stdin 为「活管道（不写入不关闭）」时，读 stdin
   的子进程 **6 秒后仍悬挂（poll=None）**；`stdin=DEVNULL` 时 **0.02s 立即 EOF
   返回**。
4. **观测无界**：tick 台账 / `phases` 在 `run_cycle` 返回后才写 ⇒ 卡住期间外部
   **无法知道卡在哪档**（`phases` 空）。
