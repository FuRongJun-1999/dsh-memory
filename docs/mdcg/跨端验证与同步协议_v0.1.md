# 跨端验证与同步协议 v0.1

## 一、角色与职责（使用者裁决 2026-09-17）

| 角色 | 实体 | 职责 | 权限 |
|---|---|---|---|
| **主代理** | DSH 端 designer（actor=dsh-memory） | 编排、改码、**持有任务台账**、判定验证是否闭合 | 须含 `task` op |
| **验证端** | zcode（在 **4_ai 验证面** `<verify-face>/dsh-memory`） | 独立复算与反证，产出**回执** | **无权设 task**；只出回执，不改台账 |

> 台账归属是硬边界：`task` 由主代理写。验证端若要表达结论，走**回执**（第三节），不写任务实体。

## 二、同步通道（不经网络，不触第 14 条）

1. 主代理在 2_ai/dsh-memory 提交（pathspec 部分提交）。
2. 验证端从主代理仓**直接 fetch**（本地路径即远端）：
   `git -C "<verify-face>/dsh-memory" fetch "<main-repo>/dsh-memory" main`
   （**占位符**：本机真实路径不入公开文档——第 14 条；执行时按本机部署替换）
   然后 `git checkout -B verify/<verify_id> FETCH_HEAD`（或 merge）到隔离分支。
3. **验证面 = 已提交状态**：工作区未提交的在途改动**一律不进入验证面**——这是把「我的脏工作区」与「被验证的产物」分开的关键。
4. 4_ai 的独立性即互斥保证：验证端不写 2_ai，主代理不写 4_ai；两侧测试副产物（如 _md_cg_p27/、verify_cache.json）互不干扰。
5. 需要对公众发布时，主代理才 `push origin main`，且**推送前必须过第 14 条双清单**。

## 三、握手格式（蜂巢任务即信道）

**请求（主代理 → 验证端）**：一条 task 台账卡 + 交给验证端的 spec 模板。

```
[VERIFY-REQ] verify_id=<verify_id> commit=<sha> repo=<verify-face>/dsh-memory
acceptance=<逐条可判的验收判据>
commands=<验证端将执行的确定性命令（argv 形式，零 LLM）>
```

**回执（验证端 → 主代理）**：验证端用蜂巢 `submit --spec` 派发确定性任务，spec 的 `user_prompt` 以如下行**开头**，结论落在该任务 `result.json`：

```
[VERIFY-RESULT] verify_id=<verify_id> commit=<sha> verdict=PASS|FAIL|PARTIAL
evidence=<命令输出摘要 / 失败项清单 / 与基线的差异>
```

> 为什么用蜂巢：第 17 条已强制「执行性任务经蜂巢派发」，spec/status/result 三件套天然留痕——于是**回执不需要额外机制**，它就是一条已留痕的任务。

## 四、机械判定：怎么知道「验证完了」

主代理侧一条**只读巡检**（L1 可直跑，须输出一行留痕）：

1. 记水位 w：发起请求时刻 `hive/jobs` 的最大 `created_ts`。
2. 枚举 `created_ts > w` 的任务，筛出 `spec.json` 的 `user_prompt` 以 `[VERIFY-RESULT]` 开头者。
   **防自证**：本端（actor=dsh-memory）派发的任务一律不算，只认非本端派发的回执。
3. **判定为「验证已回」的充要条件**：存在 `[VERIFY-RESULT]` 任务，其 `verify_id` 与 `commit` 与请求**逐字一致**，且 `result.json` 已落盘。
4. 命中 → 主代理据此写台账：`task action=status`（通过迁 `done` 且 result 必填；不通过迁 `blocked` 并记缺失维度）。
5. 未命中 → 状态是「**未收到回执**」；措辞不得是不可判定的「等验证中」。
6. **基线采集位置（迭代二修补 · 经编外复核两轮修正）**：在**同一验证面**上取两个期望——**基线 commit 的期望 vs 候选 commit 的实测**；禁止从发起端工作区取任何期望值（发起端工作区结果只用于「发起端是否引入回归」的自测，不得写入验收判据）。
   > 复核指出的原文缺陷：「期望值与实测值同源采集」表述含糊、有**同义反复风险**，故改为按两个 commit 显式命名。
   > 引用回归结果时必须逐字附 **SUMMARY 原文 + 失败清单原文**，不得只报「全绿/几红」这类概括——实测 `scripts/run_tests.py` 的 SUMMARY 计数不自洽（「84/85 通过，3 跳过」），概括式引用必然失真。
   > 归因（智能论三问协议 · `CommonTrustProtocol/docs/条件论失败分析协议.md`）：首轮判据写死「期望 3 红」= 在**发起端工作区**观测、却声明适用于**验证面** → 失配维度 = **观测位置 + 条件边界**；机制缺的条件声明 = 「基线采集位置 = 验证面」。
   > 证据：回执 job `h1789634407680_445c` 在 4_ai 纯净树得 **85/85 零红**，而发起端脏树有 3 红（源于 20+ 项未提交在途改动，与提交产物无关）。
   > 附：本节判定已机械化实现于**主代理侧仓外运维件** `<main-ops-dir>/poll_verify_receipt.py`（**刻意不入公开仓**：内含本机绝对路径，触第 14 条）。

## 五、TTL 与措辞纪律

- 每条请求带 deadline（建议 24h）。
- 到期未回：主代理在会话中**明确报告「未收到验证回执」**并给出水位与检索证据；不得暗示已通过。
- 严禁把「我自己的自测通过」表述为「已验证」——自测是主代理自身的验证门禁，不是第三方验证。

## 六、不适用条件

- 不适用于纯查询/无仓库改动的任务（无产物则无需交叉验证）。
- 不替代第 5 条（主代理自身须先过断言/回归）与第 14 条（推送前双清单）。
- 不授权验证端写台账、改 2_ai 工作区、或代主代理提交。
- 4_ai 的 .venv 与依赖环境由验证端自持；主代理不假定两侧环境一致，差异须在回执 evidence 中显式声明。
