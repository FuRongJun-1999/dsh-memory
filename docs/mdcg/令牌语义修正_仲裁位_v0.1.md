## 一 问题：语义塌缩（实测取证）

- 编排者职能 = 拆解派发 + **裁决子代理冲突**（orch.py 收口，理论位=智能论 3.9 仲裁实例；v0.3 标准对应裁决者/verify 位的判定单职能）。
- 裁决要过 `MdCGSecure.review_decide` 的库层 `require_admin` 闸门，而 `can_admin` 只有 designer 角色为真 → **编排者被迫持 designer 角色**（tokens.py:225 `ORCH_ROLE = "designer"`，取证 2026-09-16）。
- 后果：子代理链上出现 role 字面为 designer 的令牌，与「链上零第二设计者」治理意图字面冲突。裁定 A（实质权力唯一）是**过渡合法化**：收窄投影（ops 6 项、无 core 层、不可 forget/anchor/self/goals），但 role 名仍称 designer——**名实不符**。

## 二 理论对齐

- 智能论 3.9：**仲裁实例**是协议内部正式职能位（处理分歧、执行恢复）——裁决权属仲裁位，不属设计者位置（1.4.3 互斥）。
- v0.3 标准的裁决者模板（判定单七字段）即该职能的提示词投影；五单元矩阵中与其最贴近的是 **verify（稳）**，但仲裁实例还需 write（收口归档）——故独立成位比塞进 verify 更诚实。
- 令牌 v0.1 §5 已确立「单智能体子代理权职分离」先例：主智能体（唯一设计者载体）派生受限子令牌。本稿把「编排者」纳入同一范式。

## 三 设计

### 3.1 新增角色 `orchestr`（仲裁位）

进 `tokens.ROLE_SPECS`（与五单元同源风格，effect 取「裁」，对应 3.9 仲裁实例）：

| 字段 | 值 | 说明 |
|---|---|---|
| unit | 仲裁实例（3.9） | 非五单元，独立职能位（模板对应 v0.3 裁决者主轴+编排收口） |
| effect | 裁 | 与全新稳通存并列，出处=3.9 |
| 可写层 | contextual, unresolved, rejected | 收口归档所需；**无 knowledge**（升层仍走设计者/收口纪律既有通道）与 **无 anchor/self/goals** |
| 可执行 op | info, route, read, write, review, recent, consistency | 即现 ORCH_OPS_ALLOW |
| 密级上限 | internal | 同五单元 |
| 管理 | ✗ | **can_admin=False（关键变化）**：不可 forget/protect/动 anchor |
| 可派生 | ✗ | 委派链封口 |

### 3.2 权限模型配套：拆开「裁决权」与「管理权」

- `review_decide` 闸门：`require_admin` → **`require_op("review")` + `require_layer_write(被裁决节点所在层)`** 复合。
- `can_admin` 语义收窄回本位：仅 forget / protect / anchor 写 / 令牌管理 等存在级操作。
- 影响面（施工时逐点核对）：`mdcos.py`（review_decide 及 require_admin 其他调用点）、`md_cg/mcp_server.py` 的 review 面、`test_p21_tokens`（31 项断言扩展+修订）、`hive/orch.py`（principal role 日志与校验）、`tokens.py ORCH_*` 常量（`ORCH_ROLE = "orchestr"`）。

### 3.3 兼容与迁移（顺序铁律：先改模型，后重签，再换链）

1. 施工：新增角色 + 闸门拆分 + 断言（先行能红测试：orchestr 派生后 review_decide 可过、forget/anchor 写必拒）。
2. 重签：`orch --token <579ce0> --out`（同一维生根，无需新授权——派生链不变，仅角色语义修正）。
3. 换链：`hive/config.local.json` 的 `HIVE_ORCH_TOKEN_FILE` 不变（文件路径同位，内容被覆盖）→ `--restart`。
4. 旧投影令牌（tk_2700d603a5a0，role=designer 收窄版）由维生 revoke 收口。
5. 文档同步：本稿状态改「已落地」；`令牌与角色权职分离` 升 v0.2（矩阵加 orchestr 行）；hive/README 令牌段同步。

### 3.4 验证判据（能红 + 反向对照，ref-14 标准）

- 正向：orchestr 令牌 `review_decide` 成功（编排收口裁决可用）；`forget` 拒（AccessDenied）；写 `anchor/self/goals` 拒；写 `knowledge` 拒；`derive` 再派生拒。
- 反向对照：旧模型（require_admin 一刀切）下 orchestr 裁决必被拒（旧行为可红）；role 字面校验（令牌串 `mdcg1.orchestr.` 前缀 + 记录 role 一致）。
- 端到端：编排实测第三轮（失败子任务收口 + 冲突裁决场景），编排者持 orchestr 令牌完成裁决且认知图审计记录 actor=hive-orchestrator。

## 四 诚实边界

- **令牌文件即信任根**不变（v0.1 §8）：文件写入者仍可自授权限，收敛到 0600 是现状上限。
- orchestr 的「裁」仍是**协议内部裁决**：判定不一致的终裁在维生（12 节），orchestr 不终裁——与其令牌能力一致（无 sustain op）。
- 五单元同源断言（test_p21_tokens）需要扩展而非修改：orchestr 是 3.9 职能位投影，不冒充五单元。
