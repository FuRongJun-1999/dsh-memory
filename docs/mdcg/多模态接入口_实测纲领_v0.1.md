## 一 为什么「多模态」这一条排在实测的最前面

设计者把多模态架构定位为**灵枢与世界模型的接入口**——这把文档 §4.4 的性质改变了：

- 文档里 D1（原始像素交付）原本只是「交付层四层改造」中的第四项，且 §7.1 把它排在**阶段 3（最后）**；
- 但若它是**接入口**，那么它的**前置三件**就不是「最后做」，而是**所有跨模态实测的准入条件**——在图像进不了库、也进不了注入面之前，任何「灵枢能不能用世界模型的输出」的实测都无从谈起。

⇒ **本纲领的排序与文档 §7.1 不同，理由在此**：文档按「瓶颈律 + 改动面」排；本纲领按「**接入口是否已通**」排。**凡属接入口本身的缺口，优先取证。**

**★A2（**更正**）：图像块存在且只许走 user message / tool result —— 这两点成立；但「默认被 offload 成占位文本」**判错了，方向反了**。**

原判（编排侧，仅读了 `offloaded?: true` 的注释）：**原图交付不是默认路径，而是被 offload 挤掉的那条**。

**子代理实读 `requiredImageOffload` 的实现后推翻**（`<D>/dsh-llm/lib/types/content.js:183-226`）：


且触发链是**「报错 → 宿主补记 → 重试」**，不是默认投影（`dsh-llm-deepseek/lib/index.js:1435-1438`）：


⇒ **正确的判定：原图交付是默认路径。** 正常路径先走 Files API 上传（`prepareFileIds`，`:1445-1458`），Files 失败才降级内联 base64；`offloaded: true` **只**在收到 `IMAGE_OFFLOAD_REQUIRED` 之后才由宿主写入。默认预算也宽松（DeepSeek 侧：`maxImagesPerRequest = 600`、`maxRequestFilesBytes = 128 MiB`、`maxInlineRequestImageBytes = 20 MiB`）。

**★A2 的根因（我的判据错在哪）**：我把 `offloaded?: true` 的**注释**（它描述的是「这条路径上会发什么」）读成了**默认行为**——而注释没说的恰恰是「什么时候会走到这条路径」。**⇒ 判据：注释描述的是「该分支的行为」，不是「该分支是否被默认走到」；判断默认路径必须读**条件判断**（这里是 `if (excessCount === 0 && excessBytes === 0) return 0`）。** 这与 A1 同根：**用描述性材料（类型定义 / 注释）代替了判定性材料（分支条件 / 事件枚举）**。

**⇒ A1/A2 更正对实测排序的影响（重要）**：原判「D1 落地 ≠ 原图到模型」**不成立** ⇒ **原图交付这条路比我以为的宽**。而「插件能不能把图送进去」的答案是**能（经 `agent/pre-step`）**，不是不能。⇒ 线 A 从「交付面基本被堵」变成「**交付面有两条可用通道，且默认就是原图**」——**这实质改变了批 3 的必要性排序**（见 §六）。

| `entity_id` / `state_attributes` | **md_cg 无此字段** | 不得发明；身体库侧才有，属第二段 |

**★为什么「文本面」与「attachmentId」互为充要（判据，非偏好）**：
- md_cg 检索打分**只读 `content` 与 `tags`**、索引快照**不含二进制** ⇒ **只存不透明 id，该节点在默认检索里恒不可达**（覆盖度 0 ⇒ 跳过）；
- 且 `attachmentId` 是**不透明标识**（注释原文「Opaque storage identifier; never a filesystem path or bearer URL」）⇒ 对模型/用户**零语义**；
- 反向也不成立：**不能只存文本面不存 id**——文本面会被去重闸门 MERGE 并入既有节点，一旦被并，**同一张图的第二次出现就无法定位到具体附件**。

**★与不可信边界的关系（必须回答的那一格）**：

- **R1（走文本轨）**：图像节点取回时，**其落库的文本面走既有文本轨**（`escapePromptBraces` → `renderUntrustedMemoryBlock`）。理由＝文本面是任意用户输入/工具输出的沉淀，与既有记忆正文**同源同风险**，没有理由豁免。
- **R2（原图不另设注入格，本轮）**：**不给图像另设注入格**。代价逐条：①若该格文本仍进 `assembly.contexts`，裸 `{{` 会让宿主每轮 assemble **throw**（`prompt_safety.ts` 已写死该伤害路径）⇒ 会话永久不可用；②若走别的通道（如 `agent/pre-step`），则**绕开了这条护栏本身**，需重建等价转义与等价边界声明；③图像本体/EXIF/文件名都是**不可信内容**，无边界标记时模型无从区分数据与指令。⇒ **若未来必须交付原图（D1），必须先为该格重建两道护栏的等价物，作为独立设计项、须设计者裁。**
- **R3**：`attachmentId` 是 opaque ⇒ 注入文本里只可作标识符，**不得被拼成路径或 bearer URL**。

**能红条件**：①若实测显示「图像节点入库后默认检索命中率**不升反降**」（占位文本稀释 lexical 覆盖度）⇒ 「文本面必须可检索」这条被推翻；②若 `user/message` 的 `ImageBlock` 并未真的出现（A5 被推翻）⇒ 整个 B1 无对象；③若去重闸门把同一张图的多次出现全部 MERGE 成一个节点 ⇒ 「tags 承载引用」不足。

**削掉的判别力（如实）**：放弃「原图进库可被像素级复现」（本仓无二进制列，本来就没有）；`reasoning` 一律不进 ⇒ 放弃「从历史推理草稿找回中间假设」；`tool-call` 一律不进 ⇒ 放弃「从历史调用参数找回调用习惯」；`file` 本轮不进 ⇒ 放弃附件类记忆。

### 八-3 · B3 模态进检索（第二段，身体库侧）——**方案空间 + 推荐**

**★子代理新取证的一处关键事实（批 1 未列）**：**非文本 modality 不止 image**。实测库内 `(layer, modality)` 分布含 `('anchor','protocol')`、`('structure','structure')` ⇒ **方案 A 的「排除非文本」会连带把不可遗忘的锚点层与结构层从文本检索里删掉**：实测 `search_content("超时")` 改前命中 4 条（structure／knowledge-text／knowledge-image／anchor），**按 `modality=='text'` 过滤后只剩 1 条**。**这是 A 最重的副作用。**

| 方案 | 改动面 | 对既有召回 | 代价 |
|---|---|---|---|
| **A 排除式** | `LingshuStore.search_content` 加模态过滤（约 1 函数／2 处 SQL） | **返回集严格变小**（实测「红色杯子」5→2 条） | **削召回最重**：图里描述的事实**加上**锚点/结构层一起永久退出文本检索 |
| **B 加权式** | 评分步引入模态权重（约 1 函数／2 处） | **集合不变、只变名次**（实测 image 榜首 0.4286 → 降到 0.2143） | 新增一个**无理论出处的权重旋钮**（须经验标定），且图仍被文本压制 |
| **C 双轨式** | **文本路零改动**；另设模态专属入口（给 `query_nodes(modality=)` 接生产调用方） | **零 diff**（实测改前=改后逐位不变），同时新增模态入口 | 多一个入口要维护；若走语义路则依赖当前**未装配**的 `semantic_space` provider |

**推荐：C（双轨式）**。判据三条：①**唯一不改既有文本口径**的方案（A/B 都动 `search_content` 这个全仓唯一文本检索真源）；②**把 0 调用方的既有能力点亮**（`query_nodes(modality='image')` 实测 2/2 正确、0 调用方），不新增真源、不动 schema；③**对世界模型接入口最友好**——world 侧要「按模态取图」，需要的正是一个**不改文本口径即可用的取图面**；A 会让「按模态取图」与「文本召回」互斥，B 让图永远排在文本之后。

**一行题（给设计者的「只需点头」）**：
> **模态是否进检索判据：A 排除式 / B 加权式 / C 双轨式（推荐）**

**★本项属口径变更，须设计者裁，本设计不含实施。**

**★world 侧「按模态取图 + 按区域锚取邻域」需要什么（判据）**：
- **按模态取图**：现有 `query_nodes(modality=)` **已够**（实测正确），但**缺索引**（`modality` 无索引）——千级库可忽略，规模化须补；
- **按区域锚取邻域**：现有 `spatiotemporal_query` **不够**，缺三样（均实测）：①**缺统一的扁平数值轴**——`ingest_frame` 把 image 的 bbox 存成**嵌套 dict** `{"visual":{"bbox":[...]}}`，`scene_model` 存扁平 `{x,y,z}`，`subgraph_replace` 存 `{image2d_x,image2d_y}`，`update_self` 存 `{self_axis}` ⇒ **四种形态并存**；对 image 节点传 `space_metric='visual'` **实测 `TypeError: unsupported operand type(s) for -: 'dict' and 'dict'`**；②**缺多轴/bbox 联合**（只支持单轴 `|Δ|≤radius`）；③**缺模态过滤**（签名无 `modality` 参数，且 `candidates` 硬编码 `limit=200`）。
- **另有一条新取证的缝**：world 侧 `world3d(action="build")` 走 `get_nodes_by_tag("vprim")`，而**全仓无任何 `vprim` 标签的生产写入方**（仅两处读、零处写）⇒ 「world 侧按标签取图重建世界」这条既有路**当前也无生产者**。**这解释了批 1 的「两侧没有共同的数据形态」**：world 侧等 `vprim` 标签、记忆库存 `modality='image'`，**两个键互不相识**。⇒ 最小接线是「让 world 侧取图改走 `modality='image'`」或「让 `ingest_frame` 同时打 `vprim` 标签」，**二者取一、须设计者裁**。

### 八-6 · B2 图像脱敏判据（**含 EXIF 核实，已回**）

**★第一半·EXIF 核实——判定＝剥离（代码级＋校验级双重证明）；我原先「仅应用方向」的担心被推翻。**

| 环节 | 实读 | 判据 |
|---|---|---|
| 归一化实现 | 走 **`sharp` 重编码**（`dsh-attachment-local` 依赖 `sharp@^0.35.3`） | 不是原地改写 |
| 元数据 | 归一化管线 `.rotate().toColourspace("srgb").resize()` → `jpeg()/webp()`，**全文件 `withMetadata`／`keepExif`／`keepMetadata` 零命中** | sharp 文档：未调用 `withMetadata` ＝ **strip all metadata** |
| 直通条件 | `canPassThroughNormalization()` 的必要条件**含 `!carriesMetadata`** | **任何带 EXIF 的源图都过不了直通、必被重编码** |
| 输出校验 | `verifyNormalizedImage()` **断言**输出 `carriesMetadata` 为假，否则 throw | **fail-closed**：归一化产物被证明元数据为空 |
| `originalDimensions` 的含义 | 在重编码**之前**用 `detected` 读出并记下（`orientation >= 5` 时宽高互换），仅在下采样时写入 | **是主动读取的记录值，不是改写后残留** ⇒ 与「重编码＋剥离」互为佐证 |

⇒ **GPS／设备序列号／拍摄时间戳／IFD1 内嵌缩略图随整块 EXIF 一并消失。**

**★两条我原先没看到的边界（同一取证暴露）**：
1. **`file` 通道是旁路、逐字节 verbatim、零归一化**（`saveFileVerbatim`；`FileAttachmentRef` 注释原文「Files are stored byte-for-byte with no normalization」）⇒ **带 EXIF 的图像若从 file 通道进来，EXIF 原样保留**。且 UI 按 MIME 白名单分流（仅四种图像 MIME 走 image 通道），**其余格式一律走 file 通道** ⇒ 这是一条**已定位、未实测**的旁路。
2. **非 EXIF 容器元数据**（PNG `tEXt/zTXt/iTXt`、GIF comment、WebP EXIF chunk）是否被 `carriesRetainedMetadata` 覆盖，**未取证** ⇒ 判据结论**不得外推**为「所有元数据都没了」。

**★B2 判据设计（要点）**：

- **判据只有一条（来源证明）**：可脱敏 ⇔ 该块是 `ImageBlock` 且 `attachmentId` 形如 `sha256:<64hex>`、`mediaType` ∈ 四种、`bytes/width/height` 齐备。**满足 ⇒ 只落引用，绝不落像素**（纵深防御：即便宿主某版本漏剥，记忆层也无像素可泄）。**不满足（`FileAttachmentRef`／裸路径／自行落盘的字节）⇒ fail-closed 拒绝**，与既有 `_seal_content` 的 `LockedError` 同构——**不静默降级为「原样落库」**。
- **脱敏判据清单**（逐项给「为什么敏感／怎么判／做不到时的降级」）：EXIF GPS／设备序列号／时间戳／IFD1 内嵌缩略图 ⇒ **均由「来源证明」一条覆盖**（EXIF 是整块丢弃、非选择性）；**截图内可见文本凭据** 与 **人脸/人像** ⇒ **本仓无 OCR/人脸能力**（`src/` 下 `image|attachment|multimodal` 零命中），**如实写「做不到」**，降级路径＝「图像一律不落库、只落引用」或整条跳过；**文件名** ⇒ 宿主已做 basename + 去控制字符 + 截断；**极端分辨率指纹** ⇒ **不判**（低风险且与展示需求冲突，如实承认不覆盖）。
- **与既有 `desensitize` 的关系＝另设一格，不扩展其签名**。三条理由：①**契约不兼容**（`desensitize(text: string): string | null`，定义域是字符串）；②**`null` 语义粒度不符**（现语义＝**整条消息跳过**，而复用会把「图像不可脱敏」升级成「整条消息不记」⇒ **改变既有写入行为**）；③**判据性质不同**（`SENSITIVE_PATTERNS` 是文本正则集；图像判据是来源/能力判定）。
- **fail-closed 的可见性（如实分两半）**：**能做的**＝诊断面可见（复用 `hook_audit` 的 `skipped` 通道 ＋ logger，落 `dsh-memory-hook-audit.json`）；**做不到的**＝**对话内可见**（用户看不到「为什么这张图没被记住」）——要做到须改注入面，**触口径、须设计者裁**。

**能红条件（会推翻本判据的读数）**：①带 EXIF GPS 的 JPEG 过 `prepareImageFile` 后**输出仍能读到 `exif`** ⇒ 「宿主已剥离」被推翻；②造一张「无 EXIF 但含 PNG `tEXt`」的 PNG，直通返回 true 且输出仍带 `tEXt` ⇒ `carriesRetainedMetadata` 有覆盖缺口；③`saveFile` 后字节 sha256 **≠** 输入 ⇒ 「file 通道 verbatim」被推翻；④`grep -ri "tesseract|opencv|face|ocr|onnx" src/` 有命中 ⇒ 「本仓无 OCR/人脸能力」被推翻；⑤任一 `dsh-attachment-local` 副本出现 `withMetadata`／`keepExif` ⇒ 「默认剥离」被推翻（**版本漂移**）。

**削掉的判别力（如实）**：①「只信 `attachmentId`」削掉了**对宿主版本漂移的判别力**（本机已见三代包：`0.1.0-rc.8`／`0.1.7-rc.2`／`0.2.0-rc.2`）⇒ **判据须带宿主版本下限**，否则「已剥离」是**版本相关的假定**；②「不做 OCR/人脸」削掉了「截图内凭据」与「人像」的全部判别力——**这是明确的不覆盖面**；③「只落引用不落字节」削掉了「离线可检索图像内容」；④「EXIF 整块剥离」判据依赖 `carriesRetainedMetadata` 覆盖完整，对非 EXIF 容器元数据**是假定而非证明**。

**★由此对 §八-4（A6）的一处影响**：A6 的「可先行、不阻塞于 B2」结论**更强了**——因为 B2 的结论是「宿主 image 通道已剥离 EXIF」，而 A6 若只落「引用 + 文本面」，则**图像字节根本不入库**（md_cg 无二进制列）⇒ **两条防线叠加**。但**硬边界不变**：一旦要落字节或交付原图，仍须先过 B2。

### 八-7 · 批 1.5 的净结论（一句话）

**接入口的第一段（DSH 事件 → md_cg）现在只有一处硬堵点（A6），且宿主侧全线已就绪；第二段（md_cg ↔ 身体库）的缝已定位到具体键（`vprim` 标签 vs `modality='image'` 互不相识）。** 两段各有**一个「只需点头」的题**：第一段＝「A6 最小修复是否实施」（含硬边界「只落引用不落字节」）；第二段＝「模态是否进检索判据：A 排除 / B 加权 / C 双轨（推荐）」。**两项均须设计者裁，本批不含实施。**

### 九-5 · 建设方案（要新建 / 要复用 / 成本 / 能红）

**要新建**（文件级）：`md_cg/bench_calib_zero.py`（五臂编排器＋剖面表）／`md_cg/calib_corrupt.py`（三个破坏原语：删／打乱／剥字段，seed 化确定性）／`md_cg/calib_probe.py`（写入探针的**结构保真维**）／`docs/eval/校准零号试验_读数_v1.0.md`（读数报告）／（前置）《秤》格式答案键。

**要复用**：交付链与生成器/判官 `md_cg/bench_e2e_locomo_qa.py` 的 `run_one`＋`retrieval`/`full_context` 臂构造＋提示词（**须逐臂逐字冻结**）；丙注入器 `bench_membench.py` 的两个 patch 函数；写入原语 `mdcos.add/forget/recall`；丁剥离原语 `backfill._remove_ccg_line`／`consistency._strip_ccg_segments`；沙箱 `test/chaos_injection/mdcg_support.apply_env`。

**成本分解**：**纯本地零 API** ＝五臂破坏注入＋结构保真探针＋机械层判据（逐字定位/回源/退役泄漏比对/字段在场）＋建库检索＋剖面计算。**必须调 API** ＝reader（每臂每题 1 次）＋judge（仅语义层）。**量级：最小版 100 题 × 5 臂 ≈ 1000 次调用**；含闭卷＋原文参照两个参照臂 ≈ 1400 次（与设计稿 §5.4「100 题三臂约 300 次 reader」同口径）。**机械层判据可替代部分 judge**（逐字/结构保真零 API）。

**能红条件（若设计错会看到什么）**：
1. **★乙丙不可分（最核心）**：若删 30% 与打乱检索序在剖面上给出**相同**读数（例如都只把交付净增量拉低 ≈10pp，而写入探针两臂**都满值**——因现探针只验节点在场、不验字段），则 **乙=丙 ⇒ 违反「乙≠丙≠丁」预注册判据 ⇒ 红**。**这正是 W5 零翻转读数预示的风险。**
2. **丁方向不出现**：剥掉时间/否定/来源字段后，结构保真与边界子测试两维**不降** ⇒ 红。
3. **甲净增量不为零**：甲仍显示正净增量（题池被先验污染）⇒ 红（须先跑先验陷阱过滤）。
4. **乙方向不齐降**：删 30% 后仅交付降、写入/检索探针不降（说明删的不是被检索命中的关键记忆）⇒ 红。

**风险与前置**：①**无《秤》格式答案键**（见九-4，最大）；②**呈现对照无载体**（呈现层内嵌、无独立可替换层 ⇒ 丁需先抽出呈现边界）；③**写入探针结构保真维缺失**；④**指标灵敏度风险**（W5 已实测「压力下判定零翻转」⇒ 须补细粒度检索指标如命中率/排序位次，而非只看 verdict）；⑤**判官可靠性**（语义层须过锚自证，否则「降」可能是判官噪声）；⑥**全部注入须走 `apply_env` 临时沙箱，绝不碰在役库**。
