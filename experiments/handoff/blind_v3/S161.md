## 它到底在管什么

Agent 会记住很多事。真正麻烦的不是「记不住」，而是**记错了、或者记的东西来路不明，而没人发现**。
所以这套东西的重心不在存储，而在三件事：

1. **留痕（血缘）**：这条记忆从哪来、谁写的、什么时候写的。
2. **能重来（重放）**：把当时发生的事按顺序再放一遍，看结论还站不站得住。
3. **能删干净（保留与删除）**：说了删，就是真删，包括当初留下的痕迹。

下面文档标题里的括注是我按字面给的白话解释，具体以文档正文为准。

## 我承诺什么，我不承诺什么

**我承诺：**

- 规格、清单、报告都放在仓库里，可以逐字节核对。
- 我说「通过了」的地方，你都能自己重跑一遍来验证。
- 我说「没做」的地方，不会在别处悄悄当成「做了」。

**我不承诺：**

- 不承诺生产可用、不掉电丢数据、不承诺任何大模型上的效果。
- 不承诺这份文档永远最新。上游的观察点是某一天的快照，不代表永久最新。

**两条自我约束（也是我对「别让信我的人吃亏」的落实）：**

- **不搬迁生产记忆，不复制原始会话、私有路径或执行日志。** 别人的东西不因为「方便」就被搬进来。
- **不修改测试来掩盖语义漂移。** 规格变了就是变了，要升版本、写理由、让人看见；改测试让它「继续通过」，才是真正会害人的做法。

## 自己验证（不需要装任何依赖，Python 3.11+，纯标准库）

在仓库根运行：

~~~text
python scripts/check_all.py
~~~

核心版本锁针对规范化核心契约：**更新必须升版本并说明理由。**

另有 [全目录清单](<scripts/spec-tree.lock.json>) 与 [只读检查器](<scripts/spec_tree.py>)：
逐个文件核对规格目录的名称与字节摘要，连样例和已生成报告一起核对。

关于这两样，有三句话要讲明白：

- **增删改文件都要人工审阅**，CI 不会自动重写清单。清单一致 ≠ 获准发布。
- 清单的意义是「悄悄改会被发现」，不是「改了就一定对」。
- 如果哪天你发现清单和实际对不上，请不要怀疑自己：那就说明有人（可能就是我）漏了流程。

## 我做了什么改动，以及为什么

| 改动 | 原因 |
|---|---|
| 把“设计开发中，不是已发布的1.0运行时”从引用块里的一句，升级成**开篇的状态表** | 你怕让人吃亏，那就是：**最容易被误读的信息应该最早出现**。原来“隔离闭环通过”和“不证明生产效果”被拆在两处，容易只读到前一半。 |
| 加了「三十秒版本」和「你属于哪类读者」 | “看不懂”通常不是术语难，而是不知道该读哪一段。分层后，路过的人 30 秒能走，要审的人能直达。 |
| 免责内容改成「我承诺什么 / 我不承诺什么」对照 | 原来这些句子散落在各处、读起来像法律条款；改成第一人称承诺书后，**免责从“推卸”变成“可信度来源”**。这是这份文档真正的资产。 |
| 「CI绿不等于运行时已完成」加粗并配上一句解释 | 这句话是全篇最容易被忽略、也最容易被引用错的一句。 |
| 把「不得修改测试来掩盖语义漂移」从文末一句，提到自我约束清单里 | 这正是你怕的那种“让信我的人吃亏”——**测试是唯一能自己发现你说谎的机制**，它值得靠前。 |
| 血缘哈希、上游提交、版本锁要求全部原样保留 | 这些是可审计的凭据，一个字符都不能动。 |
| 结尾加三行 | 把“想被认可”和“怕让人吃亏”说出口。不煽情，但让人知道这份严谨是有原因的，而不是为了严密而严密。 |
