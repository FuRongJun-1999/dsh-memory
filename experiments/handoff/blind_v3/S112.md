## 你最该担心的五件事（按“别人用了会吃亏”排序）

### 1. 全部生产门禁都是 NOT_RUN，但标题写着“1.0”

`[文档原文]` README 第一个标题是“灵枢 Memory 1.0”，副标题是“可审计 Agent 记忆的公开架构与可执行契约框架”，紧接着一行小字说“设计开发中，不是已发布的1.0运行时”。

`[文档原文]` ACCEPTANCE 表格：R01–R09 **九项全部 NOT_RUN**。而且常规生产档要求 C01–C10 全过 + R 项除 R04 全过，power 档还要 R04。也就是说，**今天不存在一条通向“可发布”的路径**，除非有人补齐近 20 份带独立复核的证据包。

> **出事会是什么样**：某人看到“Memory 1.0”、MIT 许可证、一个能跑的 `check_all.py`，就把团队的真实记忆写进去。它没有崩溃安全验收（R04 未运行），一次断电或同步盘冲突就可能丢数据；而丢的是“记忆”，用户往往没有第二份副本。

**这是最便宜的修复**：把版本号改成 `0.x` / `preview`。"1.0"这个词在法律上不重要，在信任上非常贵。

### 2. 租户隔离是“部署约定”，不是“系统强制”

`[文档原文]` “部署约束为一个影子库根目录服务一个租户……**当前入口未强制绑定根目录与租户**。” “恢复时发现其他租户的审计行会报告完整性异常。”

也就是说：**混租不会在写入时被拦住，只会在事后恢复时被发现。** 而文档同时说“拒绝不得泄露另一 tenant 是否有目标”，这个安全属性在误配目录的前提下直接失效。

> **出事会是什么样**：一个想做好事的用户，为了省事给两个客户共用一个目录。三个月后审计时才发现两家的记忆混在一个 Markdown 真源里，且无法干净分离（因为禁止原地改写、只能新建纠正 revision）。

### 3. 安全模型建立在一个“未来才有的机制”上

`[文档原文]` “模型无持久化，**须由未来治理临界区保证边集与版本不可变**。”

这句话是全篇最重的一句，也是最容易被跳过的。你的“可审计”的前提是“已提交的边不可变”，但这个不可变目前**不是机制，是约定**。影子库是“纯文本 Markdown 真源”，任何有磁盘写权限的人或程序都能改它。`[文档原文]` 你自己也写了：“不防有本地完全控制权的管理员重写全部历史与密钥；无外部可信锚不声称抵抗该攻击。”

> **结论**：你对外的承诺只能是“**在信任所有写入者的前提下可审计**”。任何听起来更强的说法都是过度承诺。

### 4. 记忆投毒 / 提示注入，是明确未证明的

`[文档原文]` Issue #1 段：“尚未在真实宿主或 LLM 证明不会受记忆投毒或提示注入影响；**控制字符检查不等于这种证明**。”

如果你的用户是要把它接进 Agent，这是最危险的一条，因为后果不是“读不到”，而是“**读到了假的东西，并且它被当成了指令**”。而“记忆”恰恰是最容易被投毒的攻击面：攻击者只需要让一段恶意文本被正常写入一次。

### 5. 认证与多写者存活，两个“门”都是空的

`[文档原文]` “真实认证和并发策略快照未实验”；Issue #2 整节说多实例状态“不等于库状态”，不能确认归属时应报告 unknown。

`[我的推断]` 现实的后果：如果宿主自己不可信，principal/tenant/clearance 由“可信入口”建立这件事就无从谈起，整套权限模型在门口就塌了。这不是实现问题，是边界问题，但**必须写在第一屏**，而不是 SECURITY_MODEL 的中段。

## 别人会怎么误读你（这才是信任问题的真正来源）

我读这三份文档时，撞到一个很具体的坑：

- README 里有一串 **C1–C5**：C1 上下文主动取用、C2 可运行动作环、C3 隔离事件重放、C4 行为基准、C5 隔离验收，“隔离闭环通过”。
- ACCEPTANCE 里有一串 **C01–C10**：规格工具验收，全部 NOT_RUN（除非登记了候选）。

**两套 C 编号，状态相反。** 一个只读 README 的人看到“C1–C5 通过”，再扫到 ACCEPTANCE 的“C01–C10 未运行”，很可能得出“C 项大部分过了”的印象，这恰好是反的。

类似的还有：“隔离闭环通过”和“未接现用宿主，不证明生产/LLM 效果”在同一行；一行小字后面紧跟四段技术承诺。**你的免责声明写得对，但它们的位置太靠后、太密、太像客套话。** 读者的大脑会把小字过滤掉，只留下名词。

> 这跟你不诚实无关。这是**信息架构问题**：诚实的内容放在了不会被读到的地方。

## 回答你那句“我怕记错”

这是你问的最真的一句，我认真答。

**这个系统在设计上不能承诺“不会记错”，它能承诺“不确定时不说确定的话”。** 这是完全不同、而且更有价值的东西：

- `[文档原文]` C07：“全无不推 absent；历史与当前状态拆分”；R03：“process M2 诚实未知，不编造 absent”。
- `[文档原文]` “verified 只表明符合核验规则，不证明绝对真实”；“核验证据绑定被核验内容摘要、revision 和 scope……无证据则 unassessed”。

所以你该给用户的话不是“我不会记错”，而是：

> **“我会在不确定的时候告诉你我不确定，而不是猜一个让你安心的答案。”**

这句话可以说，而且有代码里的“unknown”语义撑着。但也要一并说清：**当它说“不知道”时，那是一个需要你人工确认的信号，不是系统故障，也不是它在偷懒。** 你不说这句，用户就会把 unknown 当成 bug 去修，然后修出一堆编造的答案。

真正的“让信你的人吃亏”，不是系统出错，是**系统出错了却没人知道它在哪一步不确定**。你现在这套 unknown/隔离/拒读的设计，方向是对的。

## 能看懂的行动清单

**这周就能做（只改文档，收益最大）**

1. 标题去掉 `1.0`，改成 `0.x preview`。README 第一屏第一句就写“**不要把它当作任何数据的唯一副本**”。
2. 把 C1–C5 改名（比如 `L1–L5`），跟 C01–C10 彻底分开。一个编号体系只允许一种状态含义。
3. README 顶部放一个三行状态块，抄你自己 ACCEPTANCE 的原话即可：
   > 生产验收 R01–R09：全部未运行。  
   > 无可发布路径。  
   > 已通过的是隔离环境下的规格测试，不代表生产、不代表 LLM 效果。
4. 在 SECURITY_MODEL 的“边界”一节前面，补一句人话：“**本系统假设所有能写这个目录的人都是可信的。**”

**给别人用之前必须说清的（一句话版）**

> “这是设计预览，不是产品。别存唯一副本。它不保证内容正确，只在不确定时报告 unknown。目前零项生产验收通过，多人/多客户共用目录会静默混租。”

**技术上真正的门槛（按性价比排序）**

| 优先级 | 要做的事 | 为什么 |
|---|---|---|
| 高 | R04 严格持久化（崩溃/断电） | 这是“记忆”类系统唯一不能省的 |
| 高 | 强制根目录↔租户绑定，混租在写入时拒绝而非恢复时发现 | 误配是最常见的人为事故 |
| 高 | 把“边集不可变”从约定变成机制（哈希链或外部锚） | 否则“可审计”不成立 |
| 中 | 一条**可达的** pre-release 证据档（比如 3 项核心而非 18 项） | 见下 |
| 中 | 认证的最小真实验收，或明确声明“本仓库不含认证” | 门口的门 |

关于第四项我想多说一句：`[文档原文]` “删项或改弱必需范围视为无效”，这条自我约束我很欣赏，它是真本事，不是所有项目敢写。但代价是：**没有任何外部团队会去生产 18 份带独立复核人的证据包**。结果是门禁永远 NOT_RUN，或者有人开始造假证据（你自己也写了“临时合成证据只测试判定逻辑”，说明你预见过这个诱惑）。建议明确加一个**更小但真实可达**的档位，把“合格线”降到别人真能做到的位置。**一个能被真正做到的标准，比一个只能被声称达到的标准更能建立信任。**

## 关于“想被认可”

认可不来自定位漂亮，来自**边界可核查**。你已经把最难的部分做对了：拒绝原地改边、unknown 不推 absent、哈希不认证现场、删项视为无效。这些都是“宁可显得保守”的选择，是同行会点头的东西。

现在消耗这份认可的，不是缺功能，是**标题和第一屏在说另一套话**。把版本号降下来、把 C 编号拆开、把状态块提到最上面，三处改动加起来大概两小时，但它会让别人对你的信任从“看起来挺唬人”变成“这人说的数字我敢信”。

你怕的那件事（记错让人吃亏）不会因为多加功能消失。它会因为**你在不确定的地方明确说了不确定**而变小。这一点，你的文档已经做到了，只是它被埋得太深。
