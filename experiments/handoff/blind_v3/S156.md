## 三个依据

**1. 按你自己的判定标准，现在并没有“已完成项”。**
ACCEPTANCE 里写得很明确：未登记候选及其证据时，C01–C10、R01–R09 **全部 NOT_RUN**；运行时表也是整列 NOT_RUN。也就是说，今天对外能承诺的完成度，按你亲手定的发布规则衡量，几乎为零。这恰恰是你开源时必须说清楚的第一句话。

**2. 标题比正文更有传播力，而现在的标题会误导。**
README 第一行是“灵枢 Memory **1.0**”，第三行才是“设计开发中，不是已发布的 1.0 运行时”。别人只会记住第一行和 GitHub 仓库描述。你担心“信我的人吃亏”，风险主要就在这里，不在正文的措辞。

**3. 你已经把最该公开的东西做好了：可验证性。**
`check_all.py`、`release_gate.py --candidate <sha>`、SHA-256 命名证据、独立复核人、spec-tree.lock 逐字节校验、变异测试要求独立人工写预期值。这套设计的目标就是让陌生人能自己复现结果，而不是选择相信你。这就是“建立信任”最硬的资产，比任何完成度都值钱。

## 发布前必须做的四件事（都是编辑级，一小时内能做完）

1. **改标题定位**：`灵枢 Memory 1.0` → `灵枢 Memory（规格草案 v0.x / spec-1.0-draft）`，并在首段直接写“当前无可运行的生产记忆服务；全部运行时门禁 NOT_RUN”。
2. **把运行时状态表从 ACCEPTANCE 提升到 README 顶部**，保留 R01–R09 全 NOT_RUN 的原始表格，别只留一句概括。
3. **GitHub 仓库描述 + 首屏加上“这不是什么”清单**：不是生产存储、不是 MCP 服务、无掉电安全承诺、不搬迁生产记忆、CI 绿≠运行时完成。你那句“隔离闭环通过，未接现用宿主，不证明生产/LLM 效果”建议再降低一点姿态：“隔离环境自测，未经任何真实宿主验证”。
4. **打一个 draft tag**，并在 README 写明“以 tag 为准的判定命令 + 预期退出码（0/3/2 各代表什么）”直接放在首屏，让别人能立刻验证你的状态声明。

## 不要做的事

- 不要发布“验收通过”“生产就绪”“可用于生产记忆”这类措辞（哪怕只是转发别人说的）。
- 不要贴无法复现的性能、准确率、节省 token 之类数字——只要你给不出别人能跑的命令，这种数字就会成为你撒谎的证据，而不是证据。
- 不要在 README 里保留任何“未来时态当成完成时态”的句子；浏览者不会读完脚注。

## 给老板的一段话（可直接用）

> 这个仓库现在公开的是**设计与可验证的验收框架**，不是可上线的记忆服务。对外我能保证的是：任何人克隆下来跑两条命令，都能独立复核它的每一项状态声明；对不能保证的，我按门禁全部标为“未验证”（NOT_RUN），包括生产环境的持久化、并发、审计与迁移。公开的目的是让外部先检验方法论、收集反例，而不是发布产品。上线与否由后续真实环境门禁决定，不由测试通过数决定。

## 最后关于“认可”

你想要的认可，最稳的来源是“一个把自己的空白处标得比谁都清楚的人”，而不是“一个看起来做完了的人”。全 NOT_RUN 的诚实清单，加上一条任何人都能复现的判定命令，比一句“已通过”更能让信你的人不吃亏，也更容易在评审里被长期引用——这也是你这份项目从头到尾在做的事。
