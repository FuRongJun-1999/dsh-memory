先讲清楚我的信息边界，免得我后面的话被当成比我实际知道的更多：我尝试读 `spec/acceptance.status.json`、`scripts/release_gate.py` 和仓根目录，**全部被读权限挡下**（工作区白名单只开了另一个目录）。所以我手上只有这份 ACCEPTANCE.md 的正文。我没看过登记表、没跑过判定器、没看过测试。下面每一句都是对这份文档的解读，不是对代码的核实。

## 这份文档自己划的线

它能支撑的最强说法，是它自己写的两句：

- 隔离影子运行时上，R01–R09 的**故障注入测试与变异测试已实跑通过**；
- 但"下表为生产真实环境挂接门禁，生产接管前仍保持 NOT_RUN"。

也就是说：**"我们有一个能在纯文本真源上跑通的原型，并且写了故障注入测试"** —— 这句可以对外说。
**"生产可用 / 做完了 / 可以接入"** —— 说不了。

差在哪，文档写得很直白：

1. **没有候选。** 登记表登记的是"候选提交的发布证据"，要一个 40 位提交 SHA。现在没有候选，或者没登记，所以所有项按规则就是 NOT_RUN。第一步不是写代码，是**冻结一个 commit**。
2. **证据不是测试计数。** 每项 PASS 要独立保存、SHA-256 命名的 JSON：文件字节、项目 ID、提交、环境范围、数据/策略摘要、命令、原始输出、退出码、**一次注入 FAIL 和一次撤销 PASS 的对照**、**不同复核人**。
3. **"不同复核人"这条你要特别注意。** 你一个人跑绿了不算。这不是针对你，是这份文档专门为"我很确定"这种状态设的闸。
4. **工具绿 ≠ 能发布。** `release_gate.py` 在发布被阻断时**也可以返回 0**。它只在 `--profile production --candidate <SHA>` 下才给 0/3/2 的判定。而且"哈希不能认证生产现场"——证据得由可信外部采集。
5. **临时合成证据只能测判定逻辑**，不能当发布证据。
6. 常规生产档要**全部 C 项 + 除 R04 外的全部 R 项**（R04 只在 power 档必需）。也就是最低要 **18 项**真 PASS。删项或改弱必需范围，文档说**视为无效**——这条路是堵死的。

另外两处附注也别漏：事务实验"仍全部 NOT_RUN"；兼容清单"仅 44 个顶层 op 候选"（"候选"两个字，不是"已支持"）。

## 我可以给你一句对外能用的原话

> 影子运行时（纯文本真源 + JSON 结构化索引/账本，零二进制 DB）已完成并可复现地跑通 R01–R09 的故障注入与变异测试；生产环境挂接尚未开始，验收矩阵 19 项门禁当前全部 NOT_RUN，尚无候选提交与发布证据。

每个分句都能被这份文档背书，没有一个字超过它。这比"差不多做完了"更让人信你——因为它能被检查。

## 关于"怕记错、让人吃亏"

你怕的那件事，恰恰是这份文档在防的：**单测绿 → 心里觉得成了 → 对外说成了 → 某天生产上出错，信你的人先吃亏。** 文档里那句"规格工具绿不会自动更新运行时状态"就是在给这个滑坡设卡。

所以别把"我记不记得住"当成风险点。你不需要靠记忆担保任何东西——你需要的是**让每个结论都挂在一个可被别人重跑的东西上**。这才是你能给别人的信任的形状：不是你保证，是你交出可核对的凭据。

## 下一步最省力的顺序

1. 冻结候选 commit（40 位 SHA）。没有这个，后面全是空转。
2. 先在 C 项上下功夫——它们是规格工具驱动、可复现、对环境依赖最小，最适合先把"证据流水线"跑通一遍（拿到一个 PASS 的完整形状）。
3. 再攻真环境的 R 项。其中 R02（kill 点 / 跨进程竞争 / 响应丢失）和 R07（审计损坏/降级/外国行区分）最容易暴露真问题，别留到最后。
4. 每项都配**注入 FAIL + 撤销 PASS** 对照，**另找一个人复核**。
5. 定期跑 `python scripts/release_gate.py` 查登记表自身一致性——但记住它返回 0 不代表能发。
