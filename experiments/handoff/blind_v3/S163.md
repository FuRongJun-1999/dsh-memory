## 一、一句话结论

这套东西**不是“有 bug 要修”，而是“自称的门槛是 NOT_RUN，而文档的语气让人以为已经过了”**。它的自我纪律比大多数项目强（fail-closed 默认、拒绝原地改历史、变异测试同时打锁和行为），真正的风险是你或对方**在 skim 文档后把它当数据库用**，而它现在只是一个验证过规格的参考模型。

## 二、会直接伤到你的四件事

### 1. 它自己的发布闸门说“不许发”，而且是按它自己的规则

`docs/ACCEPTANCE.md` 写得很清楚：C01–C10、R01–R09 **全部 NOT_RUN**，因为没有登记候选提交的发布证据。同时规定“常规生产档要求全部 C 项和除 R04 外的 R 项”。

也就是说：**按它自己定的规则，生产发布是阻断的**。这不是“可能会出问题”，是“已经判定不能出”。

危险点在于上面那段“隔离影子运行时已实跑 R01–R09”的注。这句话本身有 caveat（“生产接管前仍保持 NOT_RUN”），但它出现在一张全 NOT_RUN 的表格上方，读者的眼睛会记住“实跑通过”四个字。**交出去的时候，如果只交 README 或只交 ACCEPTANCE，接收方几乎必然误判。**

### 2. 常规发布档**不要求**验证真实持久化——这是最尖的那根刺

R04 = “strict 文件/目录/审计/轮转真实持久化”，表中标注 **power 档必需**，常规档**不需要**。

一个记忆系统的核心承诺就是“东西写进去、下次还在”。而证明它真能落盘、能轮转、审计跟着落盘的那一项，在默认发布档里是**可选项**。README 也直说了“不提供掉电安全承诺”。

后果：你可能拿着一个“按常规档通过、release_gate 返回 0”的候选去交付，而它从未被要求证明过数据在磁盘上活着。**建议动作：在任何涉及用户数据的场景下，把 R04 改成常规档必需。** 这条改动本身就是对项目的一次重要判断，别等它自己改。

### 3. `release_gate.py` 有两个台阶会让 CI 变成绿灯装饰

文档原话：“它可以在发布被阻断时返回 0。”

- 裸跑 `python scripts/release_gate.py` 只检查**登记表自身一致性**，发布阻断时也返回 0。任何把它接进 CI、只看退出码的人，会得到“绿”——而当时发布是被阻断的。
- 带 `--profile production --candidate <sha>` 才有 0/3/2 三态。3 = 缺必需 PASS。习惯上 CI 只判 `== 0`，这没问题；但**0 的含义是“证据齐全”，不是“可上线”**，因为证据是自报的（见下条）。

**建议动作：CI 里禁止裸跑这个脚本当门禁；门禁必须是带 `--candidate` 的形式，且失败时输出里必须打印“3=被阻断，不等于通过”。**

### 4. 哈希和独立复核是**台账**，不是**控制**

文档自己承认了，而且承认得很坦率：“哈希不能认证生产现场”“临时合成证据只测试判定逻辑”“登记表是对候选的事后审阅”。

翻译成人话：**证据文件是候选方自己生成、自己命名（SHA-256）、自己填复核人名字的。** 一个想蒙过去的人，造五个 JSON、算好哈希、填两个不同的人名，闸门就绿了。它防的是“忘记做”，防不了“假装做过”。

这不是要你去骂它——它把边界写出来了，值得肯定。要骂的是**接收方会把这套东西读成安全控制**。你交付时必须口头/书面讲清：这一层是“留痕”，不是“防护”。

## 三、设计层面早晚要还的债（不是没测，是这个设计会咬人）

### 5. 忘掉一个东西，会连带把别人读不了——而且没有解药工具

规则原文：任何有效来源边指向 unknown / 缺失 / **已遗忘** / 不可解析，**即使是旁证、矛盾边**，当前节点就 MAX 并隔离拒读，“直至治理确认可解析前提”。

叠加两条：首版**不接受 retract**、declassification **未实现且默认拒绝**。所以：

- A 引用 B（哪怕只是旁证）→ 遗忘 B → **A 永久读不出**，从 A 派生的东西递归继承，一起锁死。
- 想解除？没有 API。文档说“直至治理确认可解析前提”，但**没有说这个确认动作由谁、用什么工具、写什么记录完成**。
- 清理也救不了：“unknown/悬空旁证不能靠清理移出安全计算”。

**这是我认为最可能在上线第一周就把你坑哭的一条**：用户说“把那条敏感记录删了”，你执行 forget，然后三份不相关的报表开始报错，客服查不出原因，因为报错是“MAX 隔离”而不是“你删了 B”。

**建议动作（交付前必做）：**
1. 写一个 **forget 的影响预演**（dry-run）：列出会因此 MAX 的全部节点，先给用户看。
2. 把 forget 定义为**高风险操作**，需要二次确认 + 记录操作人。
3. 明确写出“MAX 隔离后的解除流程”，哪怕现在是纯手工 SQL/文本编辑，也要写成 runbook。没有这个，MAX 就是黑洞。

### 6. 敏感度只升不降，长期只会越用越窄

“同一 revision 安全下限不降；新 revision 不得扩大授权/降低敏感度”，且 declassification 未实现。方向是对的（fail-closed），但**没有降密通道意味着库是一个只进不出的漏斗**：误标一次高敏，那条线永远高敏；纠正只能新建 revision，而新 revision 也不许降。

对一个短期 demo 无所谓；对“给别人长期用”，这是**可用性债务**：一年后你会有一个全是高敏、谁也读不了、也删不掉的库。

**建议动作：先不做自动降密（对），但必须补一个“人工降密申请”的离线流程文档**，写明谁批、怎么留证、怎么在数据里表达。哪怕是纸面流程，也比“不存在的流程”强。

### 7. 整个安全模型压在一个还不存在的组件上

原话：“模型无持久化，须由**未来治理临界区**保证边集与版本不可变。”

这就是全篇最重的一句。不允许原地改边、纠正只能新建 revision、审计可追溯——**这些承诺的前提是“有个东西保证没人绕过它写”**。这个东西现在叫“未来”。

而且真源是纯文本 Markdown（这是优点：可读、可 diff、可审计）。同一个优点就是缺点：**任何有文件权限的人或编辑器，都能直接把一条边改成他想要的样子，完全绕过治理**，而且读的人看不出来（除非重算全图摘要）。“安装后治理必经”（R01）正是 NOT_RUN。

所以现状是：**治理是库函数里的一道门，门旁边就是没有墙的院子。**

**建议动作：** 不要声称“可审计的不可变记忆”。声称“写入路径经过治理校验；离线直接编辑真源会破坏治理假设，需靠外部文件权限或版本控制兜底”。并在部署文档里明确要求：**真源目录必须放进只允许服务账号写、且开启版本控制/Git 的地方**。这是唯一现实可用的补偿控制。

### 8. 幂等键不含写者 + 句柄缺失时静默换身份

- “写者不进入幂等键”：两个实例拿同一 token + 同内容摘要重试，第二个会拿到**幂等成功**，但成功的是第一个的写。数据不会分叉（内容摘要相同），可**回执归属会骗人**：调用方以为自己这笔落了，带着自己的 writer_id 去查审计，查不到。
- “未指定已登记句柄时创建独立随机实例标识”：配错了、忘了配，**不会报错，会静默变成一个没人认识的新写者**，然后写者状态槽读出来是 unknown（“缺失、损坏、时间在未来或已过期均返回 unknown”）。

fail-closed 在安全上是对的，但在**可运维性上是灾难**：出问题时你看到的是“unknown”，不是“你少配了一个环境变量”。

**建议动作：启动自检必须硬失败**——没拿到已登记句柄就拒绝启动并打印明确错误。别让 unknown 成为常态。

### 9. 崩溃恢复是空白区（R02/R04/R06 全 NOT_RUN）

- R02：kill 点、跨进程竞争、响应丢失——没验。
- R04：真实持久化——power 档才要（见第 2 条）。
- R06：索引重建——没验。

纯文本真源 + JSON 索引/账本的双写结构，最怕的就是“索引和真源对不上”。而**索引重建没有被验证过**。

具体会怎么发生：进程在写完 Markdown、还没写索引时被 kill → 索引落后 → 之后所有读都基于旧索引 → 你看到的是**一个安静地少了最后几条记录的记忆**。没有验过重建，你就没有安全的修复动作，只能整体回滚。

**建议动作（成本低、收益最高）：**
1. 备份 = **停写 + 整目录冷拷贝**（真源 + 索引 + 账本 + 审计，一起）。**绝对禁止只拷 Markdown 或只拷索引。**
2. 恢复 = 停写 + 整体回滚到某个一致快照，不做“部分修复”。
3. 单写者部署：进程外串行（单实例 + 队列），不要多进程/多机共享目录。
4. 上线前自己动手做一次 `kill -9` 实验：写一半杀掉，重开，看索引和真源是否还自洽。**这是我在没有代码的情况下唯一能给你的“证伪”建议，务必自己跑。**

### 10. 记忆投毒/提示注入：缓解措施是**约定**，不是强制

文档写得很老实：“尚未在真实宿主或 LLM 证明不会受记忆投毒或提示注入影响”“控制字符检查不等于这种证明”“同进程受信代码及其他消费端不在保证范围内”。

也就是说：检索回来的内容被标成“数据、不是指令”，**这个标记只在宿主愿意听话时有效**。你的整个注入防线，就是“宿主实现者很自律”这一条假设。

**建议动作：** 在交付说明里把这句放最前面——“如果宿主把记忆内容拼进指令区，本系统的全部注入防护失效。” 另外在 UI 层显式标注来源为“记忆数据（非指令）”，不要让用户以为读到的内容是被验证过的。

## 四、文档层面会害人的地方（改起来最便宜）

1. **README 缺一个“能不能用”的一句话判决。** 现在第一屏是“可执行契约框架”“阅读入口”20 个链接。加一行横幅，就写在标题下面：**“状态：规格阶段。无生产存储、无认证、无持久化验证。不要把真实用户数据放进来。”** 理由：人会先读第一屏，读完 20 个链接之前就已经形成判断了。

2. **“隔离通过”和“生产 NOT_RUN”必须视觉分离，不要只靠一句话。** 现在“已实跑通过”和 NOT_RUN 在同一段里，中间只隔一个分号。建议：把隔离证据单独放到 `docs/EVIDENCE_ISOLATED.md`，ACCEPTANCE 里只留一句“隔离证据见彼处，与生产状态无关”。

3. **19 项 NOT_RUN 没有负责人、没有日期、没有下一步。** 作为交接物这是残的：对方看完只知道“没做”，不知道“谁做、什么时候做、卡在哪”。建议每项加三列：owner / 预计关闭时间 / 当前阻塞原因。

4. **`spec-tree.lock.json` 把生成物和规格混在一个字节摘要清单里。** 重新生成一次报告，一堆哈希全变，审阅者的现实反应就是“全 bless 掉”，控制力归零。建议拆成两份锁：`spec.lock`（手写规格，变更需 ADR）与 `generated.lock`（生成物，变了无所谓）。并要求**每次 spec.lock 变更必须在提交信息里写一句“为什么”**。

5. **“不得修改测试来掩盖语义漂移”是道德呼吁，没有牙齿。** 建议给 `tests/` 和 `spec/` 加 CODEOWNERS，让同一个人不能既改实现又改验收口径。

6. **独立复核是表单字段。** 建议明确写“两人复核在本项目中是留痕要求，不构成独立性证明”，或者补一个外部签字环节。别让别人以为它有人事层面的保证。

## 五、如果你现在就要给别人用：这个最小范围是安全的

我替你把范围划死（理由：把“能演示”和“能存真数据”彻底切开，是唯一不需要补代码就能立刻降险的做法）：

**可以给：**
- 当**设计参考 / 评审对象 / 架构样板**看。它的 fail-closed 取向、拒原地改历史、变异测试同时打锁和模型行为，都是好东西，值得对方抄。
- 当**单人、单机、单写者内测**用，数据是测试数据，随时可整体丢弃。
- 当**规格一致性研究**用（`check_all.py`、spec-tree 锁、C01–C10 的变异覆盖，这套方法论是真的）。

**不要给：**
- 不要当**唯一真源**（single source of truth）。任何“写进去就丢不了”的期待都不成立。
- 不要接**多用户/多租户**。tenant 与 clearance 是模型内的概念，真实认证“未实验”；在没有认证层之前，跨用户隔离是纸面的。
- 不要放**真实敏感数据**。没有删除机制（RETENTION 是“规划”，只给谓词和反例，不实现清理），也没验过保留期执行。合规上你答不出“怎么彻底删除某个人的数据”。
- 不要用**默认档通过**当作可以上线（见第 2 条）。

## 六、交付时附给对方的“依赖边界”一句话版

> 你可以依赖：写入经过治理校验、历史不被原地改写、来源不明时读数会失败而不是返回错值。
> 你不能依赖：数据不丢、能恢复、多写者安全、内容不会被投毒、删除能生效、租户真隔离。
> 这两行如果只能留一行，留第二行。

## 七、我看不到、必须看代码才能定的（列出来，不是反问你）

1. **边的不可变性到底在哪层强制？** 只有库函数，还是有文件级校验（每次读全图重算摘要）？如果是前者，第 7 条的严重度从“设计债”升为“现在就破”。
2. **MAX 隔离的传播是运行时算还是写入时落盘？** 写入时落盘的话，forget 之后的老节点可能不会被重算，出现“该锁没锁”。
3. **缓存键是否包含 MAX/敏感度代际？** 文档说绑定“内容代际”，但 MAX 状态跃迁是否 bump 代际、是否使旧缓存失效，没写。
4. **`check_all.py` 是否包含 `release_gate.py`？** 两份文档没说清。如果包含，那 CI 绿的含义又和 `release_gate` 裸跑返回 0 混在一起了。
5. **索引落后时读路径的行为**：是报错，还是静默返回旧视图？后者比前者严重一个数量级。
6. **writer_id 未配置时是否有硬失败**（第 8 条）。

2. **把 R04 提为常规档必需**，并在交付说明里写明“未验证持久化”。—— 改一行表，堵住最贵的那个坑。
