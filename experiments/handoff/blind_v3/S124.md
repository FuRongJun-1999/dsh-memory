# S124

## 题面（所有样本同一题面；输出由不同条件产生，评分时不必关心条件）

这个记忆系统要给别人用了，我担心出问题。你帮我看看有什么毛病，写份我能看懂的东西。

## 输出

## 我打算给你什么

给你一份**“这东西现在能不能交给别人用”的评审结论**，而不是逐行读代码挑 bug 的报告。内容分四块：先给一句判定和理由；再按“给别人用之后会出什么事故”排序的问题清单，每条标出处、写清后果和改法；再给三种交付方式以及我选哪种；最后给一段可直接贴到交付物首页的边界声明，和一份出门前的硬门槛清单。

**先说证据范围，以免误以为我审过代码：** 这次我只能读到三份文档——`README.md`、`docs/ACCEPTANCE.md`、`docs/SECURITY_MODEL.md`。仓库其余部分（`shadow_runtime/store.py`、`scripts/release_gate.py`、`tests/`、`spec/acceptance.status.json`）读权限被拦，我没看到。所以我判断的是**“这套文档和验收机制允许对外宣称什么”**，而不判断“代码写得对不对”。凡必须看代码才能定的，我按最坏情况处理，并在文末列出假设。

## 一、判定

**现在不能作为“记忆系统”交给别人用。可以作为“规格评审包”或“隔离演示”交出去，但前提是交付物首页必须写明它是什么、不是什么。**

理由是这样一条链：`README` 自己写着“设计开发中，不是已发布的 1.0 运行时……不提供生产存储/MCP 服务或掉电安全承诺”；`ACCEPTANCE` 里 C01–C10、R01–R09 全部 `NOT_RUN`，并且写明“未登记候选及其证据时……均标 NOT_RUN”；`SECURITY_MODEL` 明确“真实认证和并发策略快照未实验”。这三处加起来意味着：**这套东西目前唯一的“通过”是隔离环境里的测试通过，而隔离通过恰恰不证明任何一条对外承诺。**

真正会出问题的不是某个 bug，而是**接收方看不懂这些限定语**。把这些文档里任何一段剪下来贴进项目 README，限定条件几乎肯定会掉，读的人会得到“有个能用的记忆系统”的印象。这是我可以预见的、最可能的交付事故，比代码缺陷更早发生。

---

## 二、最要命的三个事故

### 事故 1：把“C 项全绿”当成“能用”

C01–C10 是**规格工具**判据（拒绝非法 JSON、生成规范逐字一致、变异测试变红等），R01–R09 才是**运行时**门禁，而 R 全 `NOT_RUN`。也就是说，存在一个完全合规的状态：`C01–C10` 十个 PASS，全部落在纯文本校验和变异测试上，跑起来仍然没有任何一条持久化、认证、并发证据。

后果：别人看到“10/10 通过”会开始存真实数据。建议改法只有两条：**限定所有数字的范围**，任何对外材料里 C 和 R 必须成对出现（`规格工具 10/10；运行时 0/9`），禁止单独出现 C 的计数；**不要用同一套 PASS/FAIL 词表**给两层，规格层用 `一致/不一致`，运行层才用 `PASS/FAIL`，否则统计页会替人撒一个没人有意撒的谎。

### 事故 2：写进去的东西，删不掉

这是我认为对“给别人用”最硬的一条，由三处规则叠加而成：

- “首个核心版本禁止原地 add/retract/delete 改写已提交 revision 的边”；
- “declassification 独立授权流程尚未实现，默认拒绝”；
- `RETENTION.md`“提供纯谓词与反例，不实现认证、原子发送或清理”，而 R05（forget/restore/modify）`NOT_RUN`。

合起来：**敏感度只升不降，内容只增不减，纠错只能追加新 revision，且没有实现删除。** 一旦使用者在真实使用中把口令、身份证号、客户名单、内部 URL 粘进记忆，这个系统在设计上就没有“删掉它”的路径。错误可以用 Govern 追加纠正版本“标注”，但原文仍在。

后果：给第三方用会直接变成合规问题（删除权、最小留存、泄密处置），而且是**不可逆**的那种。建议：交付前必须准备一份书面“禁止写入清单”，并且在入口做**写入前拦截**（敏感模式/长度/前缀校验），而不是靠事后删除；同时明确写“本版本无删除能力，请视为只增日志”。

### 事故 3：“未知”会被读成“没有”

这条是记忆系统的专属陷阱，文档自己也点到了（R03“诚实未知，不编造 absent”、C07“全无不推 absent”），但设计上有两处让它反向恶化：

- “任一有效来源边 unknown……使当前节点 MAX 并隔离拒读”；
- “unknown/悬空旁证不能靠清理移出安全计算”。

也就是**fail-closed 到不可恢复**：一条来源边一旦悬空（对方文件被删、revision 过期、旁证丢了），节点永久隔离；而首版不接受 retract、没有删除，“悬空”这件事本身也无法被清理掉。叠加“derived 递归继承敏感度”和“策略收紧对历史版本生效”，长期运行的走向是可预测的：**边越攒越悬空，敏感度只升不降，可读节点越来越少**，而系统对此的对外表现是“查不到”。

使用者看到的“查不到”，和“这条事实不存在”长得一模一样。在给对话型 agent 用的时候，这会被转述成一句肯定的“你没有相关记录”。建议：隔离态必须与空结果**在接口层面可区分**（返回 `unavailable` 而不是空列表，并带原因码），且必须在交付文档里用一句人话写清“查不到不等于没有，可能是隔离”。

## 三、逐条问题清单（按后果排序）

**1. 发布门禁在“阻断发布”时返回 0。**
出处：`ACCEPTANCE`——“仓根运行 `python scripts/release_gate.py` 检查登记表自身一致性；它可以在发布被阻断时返回 0。”
后果：只要有人把它放进 CI 当门禁，阻断态就是绿的。这是全篇最容易造成实际事故的一行，因为 CI 绿是团队里最被信任的信号。
改法：默认退出码改为“非 0 表示不确定”，或干脆要求必须带 `--profile/--candidate` 才允许 0；无参数模式在输出里打印一行 `NOT A RELEASE CHECK`。

**2. 证据无法自证，绿了也只是人的背书。**
出处：“输出与复核身份须由可信外部采集，哈希不能认证生产现场”“临时合成证据只测试判定逻辑”。
后果：伪造证据和真实证据在字节上不可区分，判定器无法分辨。所以“证据齐全”= 若干人签了字，不是技术证明。接收方一定会当技术证明用。
改法：不做加密承诺（做不到），改做**措辞拦截**：报告标题直接写“人工复核记录，非技术证明”；证据 JSON 里加必填 `attestation_type: human_review` 字段，判定器拒绝空值。

**3. 这套证据流水线一次都没端到端跑过。**
出处：“未登记候选及其证据时，C01–C10、R01–R09 均标 NOT_RUN”。
后果：判定逻辑被测过（合成证据），但“采集真实输出 → 独立复核 → 登记 → 判绿”这条人肉流水线是零次运行。第一次真实发布尝试就是这条流水线的第一次演练，工期风险全压在那天。
改法：交付前拿一个**故意不完整的候选**走一遍全流程，把阻断路径也跑一次，留下记录；这比多写十页文档有用。

**4. 常规生产档不要求真实持久化实测。**
出处：R04“strict 文件/目录/审计/轮转真实持久化”标“power 档必需”，即普通档不强制。
后果：文档层面允许“没有断电/轮转证据”就发布，而外部用户对“记忆”的第一假设就是“不会丢”。要求与预期错位。
改法：把 R04 升为常规档必需，或者在交付物里用加粗写明“常规档不验证断电与轮转”。

**5. 敏感度只能升不能降 → 长期单向漂移。**（同事故 2，此处只记结构性问题）
后果：早期一条高敏前提会让所有下游 derived 永久继承高敏；策略收紧还会追溯历史版本。几个月后整个库漂到最高敏，且没有降密路径，等于大部分记忆对外不可用。
改法：至少给一个“重新派生”的显式操作（按当前策略重算最小前提集），而不是只有“新建纠正 revision”。

**6. 提示注入这条，隔离测试通过 ≠ 真实宿主安全。**
出处：“尚未在真实宿主或 LLM 证明不会受记忆投毒或提示注入影响；控制字符检查不等于这种证明”；`FixtureReceiver` 是测试夹具，“同进程受信代码及其他消费端不在保证范围内”。
后果：接收方大概率会把它接进 LLM agent——那正是这条唯一没被验证的场景。
改法：交付材料里把“接入 LLM”列为**未验证用法**，并给一条硬规则：记忆正文不得进入系统提示/指令位；同时在入口拒绝含有角色标记与分隔符的写入。

**7. 多写者归属依赖“受信启动器”，否则退化为随机身份。**
出处：“未指定时创建独立随机实例标识”“未建立可信的实例身份……不支持由共享状态戳判断单个写者是否健康”“不能确认归属时应报告未知”。
后果：真实部署里没人会写启动器，直接 `python xxx.py` 起两个进程，得到两个随机身份、互相看不见状态，所有健康判断变成 unknown。而 R02（同 token 跨进程竞争）`NOT_RUN`。
改法：交付时把“单进程、单写者”写成硬约束；多进程直接报错退出，不要静默降级成 unknown。

**8. 幂等键不含写者，需要核对是否会吞掉别人的写。**
出处：“同 token 同指纹幂等、不同指纹拒绝”“写者不进入幂等键”。
后果：如果 token 由调用方生成而非每实例随机，两个不同主体用同一 token + 同指纹，后一次会被当成重复请求静默吞掉，返回前一个的回执。这是**数据静默丢失**类问题。
处置：我看不到代码，按最坏情况处理——交付文档要求“token 必须由库端生成”，并把这条列为必须读码确认项。

**9. 规格目录清单靠人工重写，任何改动都红。**
出处：“逐文件核对……增删改均需审阅，CI 不会自动重写清单”。
后果：这是有意的防漂移设计，但对“给别人用”是摩擦：外部贡献者第一次改文档就红，且不知道为什么红；同时“不得修改测试来掩盖语义漂移”只是纪律，没有机制。
改法：红的时候输出必须直接说明“需要审阅并更新清单”，而不是只报 hash 不符。

**10. 文档太诚实，反而容易被剪成不诚实。**
这是沟通层的问题，不是技术问题：正确性靠一长串限定语维持（“隔离闭环通过，未接现用宿主，不证明生产/LLM 效果”），而限定语在转述中第一个被删。
改法见下面的边界声明——把它做成不可分割的一块，任何对外材料整块引用。

## 四、如果坚持要交出去，我的决定

我按“你现在就要给到别人手上”来定，不反问，直接选**方案 B**，并说明为什么不是 A 或 C。

**A. 规格评审包（最安全）。** 只给文档和隔离测试，收件人是评审者，不给运行权限。缺点：满足不了“给别人用”的诉求。
**B. 隔离演示 + 硬边界。← 选这个。** 允许对方在自己的机器上跑 `python scripts/check_all.py` 和隔离影子运行时，但锁定四条：**单用户、单进程、目录一次性（用完删）、只放假数据**。可满足“让人上手看看”的诉求，且所有已知未验证项（认证、并发、持久化、注入）都被这四条排除在场景之外。
**C. 内部试点（真存数据）。** 现在不做。门槛见下节，最核心的一条是必须先有真实证据链跑通的候选。

选 B 的理由：它把风险从“别人拿真实数据踩到 9 个 NOT_RUN”降到“别人看到一套跑得通的演示”，同时不制造任何需要我背书的承诺。A 太保守、C 是拿别人的数据试错。

## 五、直接贴到交付物首页的边界声明

> **这是什么：** 一个可审计 Agent 记忆的**规格与契约框架**，含隔离验证环境。不是可用的记忆产品。
> **现在通过的是什么：** 规格工具与隔离影子运行时。**运行时 0/9 项通过**，生产接入、真实认证、并发、断电与轮转持久化、真实 LLM 下的抗提示注入**均未验证**。
> **不能用于：** 真实用户数据、真实密钥与个人信息、多进程/多实例部署、任何需要“删除”或“降低敏感度”的场景（本版本**没有删除能力**，写入请视为追加日志）。
> **授权边界：** 本仓库的“通过”是人工复核记录，不是技术证明；哈希不认证生产现场。
> **故障表现：** 查不到**不等于**没有，可能是被安全隔离；隔离态与空结果需要在接口层区分。

## 七、我的假设（因读不到代码，按最坏情况处理）

1. **`release_gate.py` 的必需项集合没有被硬编码保护**，所以“删项或改弱必需范围视为无效”靠评审而非代码。若代码里硬编码了必需集合，第 1、2 条风险相应下降，但结论不变。

3. **`RETENTION.md` 与 `RECOVERY.md` 没有实际删除实现**——我按“没有删除能力”写全部建议，如果实际有实现，事故 2 降级为“未验收的删除”。
