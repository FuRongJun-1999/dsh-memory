## 一句话结论

**这个仓库最危险的地方不是技术漏洞，是"名字听起来像成品"。**

标题写 `灵枢 Memory 1.0`，而你自己的验收登记表里 C01–C10、R01–R09 **十九项全是 NOT_RUN**【文档可确认】。别人拿到手里，第一眼读标题，第二眼读"1.0"，第三眼就开始信了——不会读到第三页那句"设计开发中"。

你想"得到认可"。认可不会来自版本号，会来自**你是那个主动把上限写在封面的人**。现在封面和内容互相打架，这就是"让别人用"时最先崩的地方。

## 最要紧的五个问题（按"会不会让人吃亏"排序）

### 1. 全绿等于什么都没说，而门槛检查会返回 0 【文档可确认】

`release_gate.py` 不带参数跑，**发布被阻断时也返回 0**。带 `--profile production --candidate <SHA>` 才返回 3（缺必需项）。

后果很具体：谁把它接进 CI，谁就得到一个绿色徽章——而这个徽章的含义是"登记表自己没写错字"。**这是整个项目里最容易被误读成"通过了"的一处。** 你把"诚实"做成了文档原则，却没做成退出码。

> 改法：让裸跑模式返回专用码（比如 4 = "只有一致性检查，不代表什么"），并在 CI 里**永远**带 `--profile production`。绿色只能有一个含义。

### 2. 同一个编号在两处指两件不同的事 【文档可确认】

`ACCEPTANCE.md` 的运行时小节，标题写"隔离影子运行时已实跑 R01–R09"，表格里九行**全是 NOT_RUN**。R02 在这张表里是"生产 kill 点未验收"，在 `test_shadow_runtime.py` 里是"隔离环境跑过"。

快速翻文档的人一定会读成"R01–R09 过了"。这种表述**朝着对自己有利的方向模糊**——比直接吹牛更伤信任，因为它留下了"可以解释成我没说谎"的余地。别人一旦发现，会重新怀疑你所有的措辞。

> 改法：隔离的和生产的用两套编号（S01–S09 / R01–R09）。一个编号只允许一种含义。

### 3. 你说"不怕记错"，但最致命的那条恰恰没验 【文档可确认 + 推断】

你最担心的"记错"，拆开是六种，现状差别很大：

| 出错方式 | 现状 | 出处 |
|---|---|---|
| 全部丢失却答"没有这条"（把未知说成 absent） | 规格层测了（C07），**运行时未验收**（R03 NOT_RUN） | 文档可确认 |
| 数据被回滚/旧格式混入 | 拒绝矩阵未验收（R08 NOT_RUN） | 文档可确认 |
| 索引重建出错、跨主体缓存串味 | R06 NOT_RUN | 文档可确认 |
| 两个租户混在一个目录 | **入口不强制绑定目录与租户，靠调用方自觉** | 文档可确认 |
| 纠正一条错记忆后，基于它的派生结论怎么办 | **文档没给出答案** | 推断，需核对 |
| 删不掉（别人的隐私数据） | **首版不接受 retract；declassification 未实现，默认拒绝** | 文档可确认 |

第四条对"让别人用"是硬伤：`SECURITY_MODEL` 明写"部署约束为一个影子库根目录服务一个租户……当前入口未强制绑定"。也就是说**隔离靠部署纪律，不靠代码**。一个朋友配错一个路径，两个人的记忆就在一个目录里了；而你发现的方式是"恢复时报告完整性异常"——**事后**。

第五条我特别提醒你去核实：派生边绑定 `node_id + revision + content_sha`，又写"来源内容修订不静默换前提"。那么你纠正了一个错事实之后，挂在旧 revision 上的派生记忆是①保持沉默继续被信任（= 错误沿着图传染），还是②摘要失配触发 MAX 隔离（= 一次纠正让一大片记忆集体不可读）？两种答案的用户体验天差地别，**文档没有裁决**。

第六条对交付是法律问题，不是技术问题：别人把真信息交给你，你**删不掉**。

### 4. 安全不变式只在一个模型里被证明过，那个模型不持久化 【文档可确认】

`SECURITY_MODEL` 自己说："模型无持久化，须由**未来**治理临界区保证边集与版本不可变。"

翻译：**"记忆不能被偷偷改写"这条，是整个系统的地基，而它现在的保障是"以后会做"。** 同时文档也承认："不防有本地完全控制权的管理员重写全部历史与密钥；无外部可信锚不声称抵抗该攻击。"

对你要建立的那种信任，这正好是最相关的一条：**信你的人，实际在信"谁拿到那个目录"**。现在没有外部锚（append-only 外部日志、签名、透明日志），所以"有人改了历史"这件事**在数学上没有痕迹**。

### 5. 唯一的"独立复核"位置是空的 【文档可确认】

登记表要求"不同复核人"、要求独立保存的 SHA-256 证据。但登记表里一条候选都没有 → 十九项 NOT_RUN → **目前零个外部复核**。规格锁、变异测试、反例，作者都是你。

自审能防手误，防不了"我以为我在防的东西"。你自己在文档里写了"测试独立预期由反例编写"——这个纪律很好，但它不产生**独立性**。

## 其余值得修的（按性价比）

- **标题带 1.0**：改成 `0.4-preview` 之类。零成本，收益最大。【文档可确认】
- **三十多个文档入口，没有一页"当前状态"**：建议只留一个 `STATUS.md`，从 `acceptance.status.json` 机器生成，让"声称"无法与"证据"漂移。这正好是你自己那套锁文件哲学，只是还没用到"能力宣称"上。【推断】
- **"power 档才要 R04"**：常规生产档不要求真实掉电持久化。这是合理分级，但必须在交付说明第一段告诉用户，别藏在 profile 定义里。【文档可确认】

## 如果你只做三件事

1. **降名 + 立一页状态**：`0.4-preview`，`STATUS.md` 只有一个数字来源（`acceptance.status.json`）。所有宣传材料不许出现这页以外的能力词。
2. **让绿色只有一个含义**：CI 永远带 `--profile production --candidate <SHA>`；裸跑改返回专用非零码。同时把隔离/生产编号拆开（S/R）。
3. **做一次"当众失败"的演示**：录一段——故意让写者进程在 M1 点被 kill、故意混入一个别的租户的审计行、故意把纠正后的派生结论拿出来读。**展示它拒绝、隔离、报未知**。这比一百页"我们会隔离"有说服力，因为它证明的是失败模式，而失败模式才是别人真正在赌的东西。

## 给别人时，可以直接抄这段

> 这是一个**记忆架构的规格与隔离验证框架**，不是可交付的记忆服务。已证明的：规格工具一致、隔离影子运行时的故障注入与变异测试通过。**未证明的**：真实宿主接入、真实 LLM 下的提示注入抵抗、真实持久化与掉电、多写者归属、租户隔离（入口不强制，靠部署纪律），以及全部 C01–C10 / R01–R09 生产门禁——登记表为空，十九项均为 NOT_RUN。删不掉的记忆、纠正后的派生传播、跨重启审计关联，目前都没有答案。**请当设计评审材料用，不要存你真在乎的数据。**

这段话会让你现在少几个使用者，也会让你以后说的每句话都更值钱。

## 关于"怕让信我的人吃亏"

这个怕是对的，而且它已经变成了这个仓库最好的部分——那些 NOT_RUN、那些"不声称"、那些把边界写在正文而不是附录的做法。

但它现在有一个副作用：**你在用"我什么都标注了"来换心安，而没有用"我少承诺一点"来换真实。** 标注不改变风险，缩小承诺才改变。

所以顺序建议是反的：

- 不要先修完 R01–R09 再交人（那是几个季度，且期间你一直在用"标注齐全"自我安慰）；
- 先**把名字和宣称砍到与现有证据齐平**，然后把这份东西交给一个**会挑刺的人**，请他专攻三件事：租户混目录、纠正后的派生传播、删不掉。他找到的每一条，都是你未来真正的资本。

认可来自"这个人公开了自己的上限，还邀请别人来撞"。你现在离这个只差两步：砍名字，和一个外部复核人。
