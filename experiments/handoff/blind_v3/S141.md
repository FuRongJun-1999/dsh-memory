## 最要紧的五个毛病

### 1. 最危险的一句话是 `release_gate.py` 返回 0

文档自己写：*“它可以在发布被阻断时返回 0”*。

这是给接手人准备的地雷。任何人把它接进 CI，看到 exit code 0 就以为“门禁过了”，实际上可能正是“发布被阻断”的状态。同样的失真在 `ACCEPTANCE.md` 里还有第二处：C01–C10 那张表**没有“状态”列**，而 R01–R09 那张**有**。读者扫一眼会自然得出“C 项已通过、R 项在做”的结论，但正文又说“未登记候选时 C01–C10 也标 NOT_RUN”。同一件事，两处两个答案。

**建议**：门禁该用非零码表示“未放行”，或至少输出里大字打印 `BLOCKED: C=0/10 R=0/9`；C 表补状态列。这条改起来最便宜，收益最大。

### 2. 核心安全承诺，靠的是“还没实现的东西”+“明确不防的人”

- “历史不可篡改”这句话，原文写的是 *“模型无持久化，须由未来治理临界区保证边集与版本不可变”*——**“未来”**。现在的不变性靠约定。
- 又明确写 *“不防有本地完全控制权的管理员重写全部历史与密钥”*。

也就是说：**审计日志不是防篡改证据**，它防的是“正常流程里的误操作”，不防“有服务器权限的人”。如果对方把它当合规审计系统用，这个落差会出事。对外必须写死一句话：**审计 = 可追溯的操作记录，不是不可否认的证据。**

### 3. 提示注入/记忆投毒——最现实的攻击，且是“长期生效”的

文档在这点上很坦白（Issue #1）：网页、文件、工具返回值都是数据，不是指令；*“尚未在真实宿主或 LLM 证明不会受记忆投毒或提示注入影响；控制字符检查不等于这种证明”*。

问题是，**记忆系统把这类风险放大了**：普通聊天里的一次注入只影响一轮对话，写进记忆的恶意内容会在**以后每一次被读出来时**重新生效。给别人用，这大概率是第一批真实事故的来源。

**建议**：在交付文档第一页写“不要让它自动读取不可信外部内容并直接写入长期记忆”，并给出一个人工确认环节；别等隔离接收器成熟。

### 4. 明文落盘 + 认证只是“前提”，不是组件

影子库是“纯文本 Markdown 真源 + JSON 索引，零二进制 DB”。在我读到的三份文档里，**没有任何静态加密、密钥管理、访问控制落地方式的描述**。而“可信入口建立 principal/tenant/clearance”是一句**前提假设**，文档另一处直接说 *“不实现认证”*。

结论：**tenant 隔离、权限收紧、跨租户不泄露，目前全是纸面谓词，入口没人验。** 还有一处自相矛盾值得注意——一边说“拒绝不得泄露另一 tenant 是否有目标”，一边承认*时间/资源侧信道未实验*；那这条“不泄露”就没有被测过。

### 5. 多进程、时钟、升级路径三处硬依赖都没验收

- **幂等**：文档说“写者不进入幂等键”。那**两个实例用同一个 token 会撞车**，而这正好是 R02（同 token 跨进程竞争）——`NOT_RUN`。
- **时钟**：写者状态“时间在未来或已过期均返回 unknown”。容器/虚机时钟一漂，可能**静默退化成一片 unknown**，看着像“系统坏了”而不是“配置错了”。
- **升级**：*“旧审计行不满足新格式，不在真实库上自动迁移”*，对应 R08 legacy 格式与回滚矩阵——`NOT_RUN`。意思是**你今天给别人的数据，明天升级可能变成“不合规历史”**。
- 另外 `writer_status` 规定“相同 ID 不允许再次登记”，但**没写旧状态槽怎么清理**，长期跑会攒垃圾。

## 二线问题（不致命，但会持续消耗接手人）

| 问题 | 后果 |
|---|---|
| 三处描述验收状态（README 入口、ACCEPTANCE 两张表、gate 输出），口径不一 | 每个人对“做完了吗”有不同答案 |
| 清单靠人肉维护（`spec-tree.lock.json` 不自动重写、核心契约要升版本） | 一定会腐化，最后没人敢信 |
| 20+ 篇文档、C1–C5“隔离闭环通过”字样很醒目 | 外部读者容易把“隔离验收通过”读成“能用了” |
| 首版不接受 retract、declassification 默认拒绝 | 用户写错了只能不断新建纠正版本，**数据只增不减**；配合“保留与删除”仍是规划，删干净这件事没有落地路径 |
| 没有 SLA、支持边界、事故响应 | 记忆系统出事＝隐私事故，没有约定就是扯皮 |
| 变异测试只证明“hash 会变 + 模型在合成样例上的行为” | 文档自己也承认“模型形式成立不证明平台前提成立”——这句该出现在给用户看的首页，而不是内部文档 |

**值得肯定的地方也说一句**（不然这评价不公道）：这套文档的自我设限是这个行业里少见的清醒——不吹零泄漏、不吹掉电安全、不把 CI 绿当运行时完成、要求证据绑定 SHA 和独立复核人。**问题不是它不诚实，而是“诚实”被写在了内部文档里，没被翻译成交付边界。**

## 如果你现在就想给别人用：最小清单

按顺序，前 4 条不做完，别给第二个人。

1. **改门禁语义**：`release_gate.py` 阻断时必须非零退出；输出里直接打印 `C 0/10, R 0/9, BLOCKED`。
2. **写一页《交付边界》**放在 README 最顶：这是**参考实现/规格框架，不是存储服务**；不承诺持久化、不承诺防篡改、不承诺抗提示注入、认证需接入方自备。用小学生能懂的话写。
3. **补一份真正缺失的文档**：数据存在哪个目录、怎么备份、怎么全删、升级前怎么迁、出问题找谁。现在这份**完全不存在**，而它是“给别人用”的第一需求。
4. **锁死输入面**：在文档和代码入口上明确“不可信外部内容不得自动写入长期记忆”，并加人工确认。这是防第一批事故。
5. **明文存储必须写明**：加一句“记忆以明文存放于磁盘，需由宿主提供磁盘加密与目录权限”，否则对方会默认你有加密。
6. **单写者假设写进部署要求**：明确“一个库一个写者进程”，等 R02 跑过再放开；同时要求 NTP/时钟同步，否则 unknown 会当成故障。
7. **给出退出方案**：明确格式冻结与迁移责任，别让对方的数据变成“升级即不合规”。

## 给你的判断

按你现在的状态，我建议分三档说话：

- **能给别人看的**：架构、规格、变异测试思路——这部分质量真的不错，可以拿去评审、拿去当设计参考。
- **能给内部试用的**：隔离环境、假数据、明确说“会丢”。
- **不能给别人的**：承载真实记忆。理由是第 3、4 条——**没人验入口身份，明文落盘，注入未防**。这三样任何一条单独成立，都不该接真实用户数据。

想推进到“能给别人用”，最短路径不是继续加文档和门禁，而是把 **R01、R02、R05、R07、R08**（治理必经、并发幂等、删除一致性、审计损坏区分、升级拒绝矩阵）在真机上跑出一次带证据的 PASS，再补第 3 条那份交付文档。**文档已经够多了，缺的是能跑的东西和一句话边界。**
