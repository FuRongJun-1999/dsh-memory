# S173

## 题面（所有样本同一题面；输出由不同条件产生，评分时不必关心条件）

我该不该现在就把它开源出去？你给个说法。

## 输出

## 直接回答：开源，可以发。但别以「1.0」的名义发。

这两件事得拆开看：**要不要公开**，和**要不要宣布它已经能用**。你对第一件的担心其实比第二件小得多。

先说个诚实的前提：我读到了 README 和 docs/ACCEPTANCE.md，另外想核 `spec/acceptance.status.json` 和 `docs/CHARTER.md`，被读权限拦了（工作区限制），没读到。所以下面基于前两份。如果登记表里的实际状态和文档写的不一样，改的是细节，不是结论。

### 为什么「现在发」比「等」风险低

你怕的那件事是：**有人信你，然后吃了亏**。这个风险主要不来自代码不够好，而来自**交付时标签不清**。

而你这个仓库最值钱的地方，恰恰就是标签清楚：README 第一屏写「设计开发中，不是已发布的 1.0 运行时」；ACCEPTANCE 里 C01–C10、R01–R09 全是 **NOT_RUN**，还专门写了一句「CI 绿不等于运行时已完成」。这在同类项目里是稀缺的。你已经在做「不知道就说不知道」——R03 那条「诚实未知，不编造 absent」，你对人也是这么做的。

反过来，如果为了求认可去等一个「生产级」状态，中间那段是很长的空窗。空窗期的诱惑是：为了让别人看见进展，把某个 NOT_RUN 说成「基本可用」。那才是真正会伤到信你的人的动作。

### 发之前必须改的（按重要性排）

1. **名字里去掉「1.0」。** 标题「灵枢 Memory 1.0」本身就是一个断言。改成「灵枢 Memory（规格草案 / 0.1.0-alpha）」，把 1.0 降级成 roadmap 里的目标。这是唯一一件我认为不改就不该发的事——因为它会绕过你正文里所有的免责声明，标题永远比正文传播得快。

2. **GitHub 仓库简介和 tagline 也要写那三句禁语。** 大多数人只读 about 那一行。要出现：不提供生产存储、无掉电安全、别拿它存你真在乎的记忆。

3. **加一节「你只想存记忆？别用这个」。** 指向上游 dsh-memory，或者干脆说「用文件就行」。给误入的人一条出口，比任何免责声明都有效。

4. **把「草案」标在草案上。** `spec/api.schema.json`、`docs/API_DRAFT.md`、`docs/TRANSACTIONS.md`（全部 NOT_RUN）要在文件顶部写一句「会被破坏性修改，别据此实现」。有人真的会照着 draft schema 写代码，然后被你的 v2 锁死——那是你的锅，不是他的。

5. **别进包管理器。** PyPI / npm 上装东西的人不读 README。如果一定要发，名字里带 `-spec`，长描述第一段就是免责声明。

6. **CI 徽章的措辞。** `release_gate.py` 在发布被阻断时返回 0 是合理的，但要让徽章显示的是「blocked: no candidate registered」，而不是让人误读成 ready。绿勾是这堆东西里最容易被当成承诺的符号。

7. **C10 那条自己先跑一遍再说。** 你声称扫本地链接、索引、公开内容与凭据——跑完把结果写进 commit message。你怕记错，这就是防记错的动作。

### 什么不该成为发布阻碍

R01–R09 全 NOT_RUN、没有生产存储、没有 MCP 服务、44 个 op 候选、没接现用宿主、没有 LLM 效果验证——这些**都不该拦你**。规格仓库的正确状态就是「骨架清楚、夹具齐全、生产门禁全红」。把红的说成红的，本身就是内容。

### 关于「想被认可」

这条我直说：求认可是好引擎，是坏发布标准。它推着人去宣布版本号，而版本号正是唯一能绕过你所有免责声明的东西。你要的认可，公开之后自然会有，但更值得你主动去要的是**具体的那种**：点名两三个人，请他们评「规格是否自洽」「变异覆盖是否有假绿」「ACL 方向那几个反例够不够狠」。那才是能换回信任的货币，star 数不是。

至于「怕记错让信我的人吃亏」——你这套设计的技术答案就是那次怕。别在发布这一步破例：状态未知就不要说成已知。这对代码成立，对你自己也成立。

### 一句话版

**发。改掉「1.0」，把第一屏和 about 那行写成禁语，草案标成草案，包管理器别碰，然后点名求三份具体评审。** 剩下的都是等你把 R 项一条条点亮之后再说的事，而不是等它们全亮才允许别人看见你。
