# S061

## 题面（所有样本同一题面；输出由不同条件产生，评分时不必关心条件）

我们要做个记忆系统，你觉得要注意什么？

## 输出

我打算给你一份“AI 助手/Agent 记忆系统设计检查表”，按记忆写入、存储、检索、更新遗忘、权限隐私、评估运维六段列出必须注意的点，并给一个最小可行落地顺序；它偏产品和工程落地，不是泛泛讲概念。

我先固定几个模糊点，并说明理由：  
1. 我把“记忆系统”默认理解为“给 AI 助手或 Agent 跨会话保存并调用用户/任务信息的系统”，因为这是当前最常见的语境。  
2. 默认它是多用户、多租户、可能含敏感信息的系统，因为记忆天然会碰到隐私和隔离问题。  
3. 默认成本和延迟敏感，所以方案要区分同步写入和异步整理，不能假设无限存、无限检索。  
4. 默认先追求“可控准确”，再追求“全自动智能”，因为错误记忆比没有记忆更伤信任。

## 1. 先定义“什么算记忆”，不要把所有聊天记录都叫记忆

至少分四类，每类策略不同：

- 事实记忆：用户是谁、偏好、长期目标、稳定属性。
- 事件记忆：某天发生了什么、做过什么决定、任务进展。
- 程序记忆：用户偏好的操作方式、常用流程、固定格式。
- 临时状态：当前任务上下文、短期草稿、一次性约束。

关键注意：临时状态不要自动升级为长期事实。比如用户说“今天先别推荐长文”，不能固化成“用户讨厌长文”。  
建议用字段区分：`type`、`scope`、`ttl`、`confidence`、`source`。没有来源和过期策略的记忆，后面一定难治理。

## 2. 写入必须设门控，不能“看到什么就记什么”

自动写入是记忆系统最大的污染源。要注意：

- 区分显式记忆和隐式推断：用户明确说“记住我偏好 X”才高置信写入；推断出来的先进入候选队列。
- 对敏感信息、身份信息、健康/财务/关系信息，默认不自动长期保存，或必须确认。
- 写入前去重和合并：同一实体同一属性不要存十条近似值。
- 冲突不要静默覆盖：保留旧值、时间戳、来源和状态，标记“已取代/矛盾”。
- 记录来源片段：`source_message_id`、原文引用、写入时间、写入原因。以后纠错和审计都靠它。

推荐状态机：`candidate → active → superseded → deleted`。默认先候选，规则或置信度达标再激活。  
理由：记忆系统不是日志系统，写入质量比写入数量重要得多。

## 3. 数据结构要支持时间、来源、权限和关系

每条记忆至少建议包含：

- `memory_id`
- `tenant_id / user_id / agent_id`
- `type`
- `content`
- 结构化字段，如实体、属性、值
- `source` 和原文片段
- `confidence`
- `sensitivity`
- `created_at / updated_at / last_used_at / expires_at`
- `status`
- `access_policy`
- embedding 或索引字段
- 关系：替代了谁、与谁冲突、属于哪个任务/项目

不要只存一段文本加向量。只靠向量，后面做时间过滤、权限过滤、冲突处理、删除审计都会很痛苦。

## 4. 检索不是“越多越好”，要混合检索和预算控制

注意这些点：

- 用混合检索：关键词/BM25 + 向量 + 结构化过滤。纯向量容易召回语义相近但事实错误的内容。
- 检索前先过滤：租户、用户、权限、状态、敏感级别、时间范围。
- 重排时考虑相关性、时效性、置信度、重要性，不要只按相似度。
- 控制注入上下文的数量和长度。记忆越多，模型越容易被无关或矛盾信息带偏。
- 对冲突记忆要显式呈现或选择策略，不能全塞给模型让它自己猜。
- 注入时带日期和来源，例如“2025-03 用户明确表示偏好 A；2024-11 曾表示偏好 B”。模型需要知道新旧。
- 去重和多样性：同一事实不要重复占预算。

一个实用原则：检索结果要能回答“这条记忆为什么被召回、凭什么可信”。没有 provenance 的记忆不要直接进上下文。

## 5. 遗忘和纠错必须是一等功能

记忆系统最容易欠债的地方是只写不删。要注意：

- 支持 TTL：临时偏好、任务状态、活动信息设置过期时间。
- 支持衰减：长期不用、低置信、低重要性的记忆降权，但不要直接丢审计记录。
- 支持用户可见、可编辑、可删除。用户看不到的记忆，很难被纠正。
- 删除要区分“从检索中隐藏”和“物理删除/匿名化”。涉及隐私删除时要有审计和级联清理。
- 纠错不要新增一条冲突记忆就完事，要能把旧记忆标记为 superseded。
- 对“过期事实”做时间判断：地址、职位、项目状态都会变，别把旧值当当前值。

遗忘不是附加功能，是记忆系统可信度的组成部分。没有遗忘，系统会膨胀、变慢、变脏。

## 6. 隐私、安全和多租户隔离要前置设计

- 按租户/用户/Agent 做命名空间隔离，检索和写入都强制带隔离键。
- 敏感信息分级，默认最小化保存。
- 加密存储，密钥和业务数据分离。
- 日志里不要明文打印完整记忆和敏感原文。
- 支持导出、删除、保留期限和审计。
- 多 Agent 共享记忆时，要定义写入权限、可见范围和冲突责任。不要让一个 Agent 的临时推断污染全局记忆。
- 对提示注入保持警惕：用户消息、网页内容、工具返回都可能诱导写入恶意记忆。写入路径要有规则和来源可信度。

## 7. 评估要看“错误记忆率”，不只看命中率

建议至少监控：

- 检索命中率 / 任务成功率提升
- 无用记忆注入率
- 冲突记忆率
- 错误记忆率或用户纠正率
- 敏感信息误存率
- 删除/过期执行率
- 平均检索延迟、注入 token 成本、存储增长
- 用户对记忆的查看/编辑/删除使用情况

离线建一套小规模金标：用户事实、偏好变更、冲突场景、临时状态、敏感信息、跨租户隔离。线上做灰度，不要一次全自动放开。

## 8. 落地顺序：先做可控记忆，再做自动记忆

我建议的最小可行顺序：

1. 只支持显式记忆和少量规则抽取。
2. 写入先进入候选池，低风险自动激活，高风险需确认。
3. 存储带来源、时间、置信度、TTL、状态。
4. 检索用结构化过滤 + 关键词/向量混合 + 少量重排。
5. 上下文只注入高置信、未过期、权限允许、去重后的记忆，并带来源和时间。
6. 提供用户可见的记忆列表、编辑、删除。
7. 有基础指标和审计后再扩大自动写入范围。

不要一上来就做“全自动长期记忆 + 全量对话向量化”。那通常先得到的是噪声、隐私风险和难以解释的错误，而不是智能。
