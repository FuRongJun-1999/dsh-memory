# S077

## 题面（所有样本同一题面；输出由不同条件产生，评分时不必关心条件）

我们要做个记忆系统，你觉得要注意什么？

## 输出

我打算给你一份面向可落地 AI 记忆系统的注意事项清单：默认你要做的是给助手/Agent 用的长期记忆，而不是纯缓存、日志或普通知识库；我会按“先定边界—再定数据与生命周期—重点处理写入、检索、更新、遗忘、安全、评估”的顺序，指出最容易踩坑的判断点，并把我自行设定的模糊假设和理由放在前面。

## 我自行确定的模糊假设与理由

1. **默认场景是 AI 助手/Agent 的长期记忆，多租户 SaaS，个人与团队混合使用。**  
   理由：这是目前最常见、也最容易暴露权限和删除问题的场景。纯个人玩具系统可以简化，但若一开始不按多租户设计，后面很难补。

2. **默认记忆必须可查看、可纠正、可删除、可审计。**  
   理由：记忆系统一旦影响模型输出，就必须能回答“它为什么记得这句话”“记错了怎么改”“删了是否真删干净”。

3. **默认模型提炼出的摘要不是事实本身，只是派生数据。**  
   理由：摘要会丢证据、会幻觉、会过期。原始事件和派生记忆必须分开，派生记忆要能追溯到原始来源。

4. **默认先做中文、文本为主，检索采用关键词+向量+时间/实体过滤的混合方式。**  
   理由：纯向量检索在精确实体、否定、时间、权限上不够稳，混合检索更接近工程可用。

5. **默认遗忘是一等公民，不是最后再加的 TTL。**  
   理由：记忆系统的成本、隐私风险和错误传播都来自“记得太多、记得太久、删不干净”。

## 1. 先定义“什么不是记忆”

很多记忆系统做坏，是因为把日志、缓存、知识库、用户画像、对话历史全塞进一个“记忆库”。要先区分：

- **工作记忆**：当前任务上下文，生命周期短，通常不进长期库。
- **情景记忆**：某次对话、某次操作、某个事件，强调时间和来源。
- **语义记忆**：从多次事件中提炼出的稳定事实、偏好、关系。
- **程序记忆**：做某类任务的步骤、策略、工具使用习惯。

建议存储上至少分两层：**原始事件不可变层** + **提炼记忆可版本化层**。原始事件是证据，提炼记忆是索引和判断。不要把模型摘要直接当唯一真相。

## 2. 每条记忆必须带“元数据”，否则后面没法治理

最小字段建议包括：

- 租户/用户/团队 ID，访问范围；
- 记忆类型：情景/语义/偏好/程序；
- 内容与结构化键值；
- 来源事件 ID、来源角色、来源时间；
- 置信度、敏感级别；
- 生效时间、失效时间、TTL；
- 版本号、状态：候选/生效/冲突/已删除/已归档；
- 实体、主题、embedding、关键词；
- 创建者：用户明确说、系统推断、管理员导入。

其中最重要的不是 embedding，而是**来源、权限、时效、置信度**。没有这些，检索越强，错误传播越快。

## 3. 写入比存储难：先做门控，不要有对话就写

写入管线建议是“抽取—判定—去重/冲突—审核/落库”，不要直接异步写向量库。

重点注意：

- **是否值得记**：临时口令、一次性的任务参数、闲聊不应长期记。
- **是否已有**：按实体+关系+时间做去重，不能只靠向量相似度。
- **是否冲突**：用户说“我现在住上海”，旧记忆是“住北京”，不要静默覆盖。保留版本，标记冲突，按时间和来源决定优先级，必要时让用户确认。
- **是否敏感**：健康、财务、身份、他人信息要单独标记，默认更短 TTL、更严格访问。
- **是否可推断**：模型推断出的偏好要低置信度，不能和用户明确陈述同级。
- **是否有证据链**：每条语义记忆要能指回原始事件，否则无法纠错和审计。

写入失败要幂等、可重试、可重放。原始事件先落库，派生记忆允许重建，这是系统可恢复的关键。

## 4. 检索不是“相似度 top-k”，而是任务驱动的受控取用

检索时最容易犯的错是：先按向量召回，再补权限过滤。正确顺序应是：

1. 按租户/用户/任务限定权限范围；
2. 按记忆类型、时效、状态过滤；
3. 关键词+向量+实体+时间混合召回；
4. 重排时考虑置信度、新鲜度、来源权威性、与当前任务相关性；
5. 在上下文预算内返回少量高价值记忆，并附来源和置信度。

还要注意：

- **时间衰减要按记忆类型不同**：偏好衰减慢，位置/职位/项目状态衰减快。
- **否定和条件要保留**：“不喜欢咖啡”不能检索成“喜欢咖啡”。
- **不要把低置信度记忆写成确定事实注入提示词**。应在提示中标注“可能”“来自历史推断”。
- **上下文预算要硬限制**。记忆不是越多越好，错误记忆会挤掉正确指令。

## 5. 更新与遗忘：追加日志优先，删除要级联

更新不要直接改覆盖。推荐追加版本或状态变更日志，保留“曾经是什么、为什么改、谁改的”。

遗忘至少分三类：

- **过期归档**：不再参与检索，但保留审计；
- **压缩摘要**：多个情景记忆合并成低敏语义记忆，原始事件按策略保留；
- **彻底删除**：用户删除、合规删除，要级联删除派生记忆、索引、缓存、备份中的可删除副本，并记录删除审计。

删除最难的是派生数据：摘要、embedding、缓存、模型上下文、分析报表。设计时就要给每条派生数据打来源 ID，否则无法级联。

## 6. 权限与安全要继承到记忆，不是只放在 API 层

记忆系统天然会跨会话、跨设备、跨时间聚合信息，权限问题会被放大。

重点：

- **权限随源**：一条记忆的访问范围不能大于其来源事件。团队共享记忆要明确谁能读、谁能改。
- **租户隔离**：向量库、缓存、日志、备份都要隔离，不能只靠查询条件。
- **最小化存储**：能不存原文就不存，敏感字段加密或令牌化。
- **防记忆投毒**：外部网页、邮件、文档中的内容可能诱导写入恶意记忆。写入前要区分“用户明确指令”和“外部内容中的指令”，后者默认低信任。
- **审计**：谁在什么时候写入、读取、修改、删除了哪条记忆。
- **导出与删除权**：用户要能导出自己的记忆，也要能一键关闭记忆功能。

## 7. 一致性和可重建性

建议把系统设计成“原始事件是源，记忆是可重建索引”。这样模型升级、抽取规则变化、索引损坏时还能重跑。

注意：

- 写入队列要幂等，避免重复事件生成重复记忆；
- 失败要有死信队列和补偿；
- 向量索引和元数据库要有版本与重建流程；
- 多设备同步要定义冲突策略，不能简单最后写入赢；
- 记忆删除后，检索缓存和会话上下文中的副本也要失效。

## 8. 评估不能只看“回答像不像”

至少监控这些指标：

- 写入精确率：写进去的记忆有多少是真正该记的；
- 检索召回率/精确率：该用的记忆有没有被取到，取到的是否相关；
- 冲突率与解决延迟；
- 错误记忆传播率：错误记忆被模型使用并输出给用户的频率；
- 用户纠正后的生效延迟；
- 删除完成率与残留检查；
- 每次请求的记忆检索延迟和 token 成本；
- 记忆带来的任务成功率提升，而不是单纯“回答更个性化”。

最好有离线评估集：构造多轮对话、冲突更新、过期信息、权限隔离、敏感信息、恶意注入等场景。上线后保留用户“这记错了/删掉”的反馈闭环。

## 9. 产品交互要透明可控

用户需要看到：

- 系统记得我什么；
- 每条记忆来自哪次对话或哪个来源；
- 哪些是系统推断，哪些是我明确说的；
- 我可以改、可以删、可以关闭某类记忆；
- 敏感记忆写入前是否要确认。

没有这些，记忆系统会从“贴心”变成“不可控”。

## 10. 最容易被忽略的几点

- **把遗忘当一等公民**：先设计怎么过期、怎么删除、怎么归档，再设计怎么存。
- **把摘要当事实**：摘要只能作为派生索引，必须可回溯。
- **冲突静默覆盖**：旧记忆不能直接盖掉，要版本化和可解释。
- **权限只做在查询层**：派生索引、缓存、日志也要继承权限。
- **只评估回答质量，不评估记忆质量**：记忆写错会长期污染系统。
- **没有重建能力**：模型或规则一变，旧记忆无法重算。
- **上下文塞太多记忆**：检索预算和重排比“记得多”更重要。

如果只让我压成一句话：**记忆系统的核心不是“存下来并向量检索”，而是“有来源、有权限、有时效、可冲突、可纠正、可删除、可重建”的生命周期管理。**
