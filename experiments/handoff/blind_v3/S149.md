## 二、最要紧的问题（按风险排序）

### A 级：会直接造成"别人用了出事"

**A1. 它还不是能交付的东西，但名字叫"Memory 1.0"**
README 第一句自己写着"**设计开发中，不是已发布的1.0运行时**"。风险不在代码，在**沟通**：别人看到 1.0 + CI 全绿，会默认可用。建议：在产物里加醒目标识（版本字符串、命令行启动横幅都打 `NOT FOR PRODUCTION`），不能只写在 README 里——因为转手的人不看 README。

**A2. 19 项发布门禁，当前 0 项通过**
ACCEPTANCE 原文："未登记候选及其证据时，C01–C10、R01–R09 均标 NOT_RUN"。这 19 项覆盖的正是"重复键拒绝、跨租户血缘、原地改写拒绝、真实持久化、审计损坏区分、legacy 回滚拒绝矩阵"这些要命的东西。**别把"有测试在跑"当成"门禁过了"**，文档自己也在防这个误解。

**A3. 租户隔离靠人，不靠代码**
原话："调用方负责分配目录，当前入口未强制绑定根目录与租户。恢复时发现其他租户的审计行会报告完整性异常。"
意思是：A 客户的数据和 B 客户的数据混在一个目录里，系统不会在写入时拦你，只会在**以后恢复的时候**报"完整性异常"。这是**事后发现，不是事前阻止**。交付给多租户使用前，这条必须变成代码里的硬校验。

**A4. 发布门禁脚本会在"该拦"的时候返回成功**
原话："它可以在发布被阻断时返回 0。"返回 0 的含义是"登记表自身一致"，**不是**"准予发布"。如果谁写了 `python scripts/release_gate.py && deploy`，就会在该拦的时候把东西发布出去。建议：把这两种语义拆成不同退出码，或改名，别叫 gate。

### B 级：交付前必须处理的"承诺没兑现"

**B1. 安全模型的核心不变量，现在只是文字承诺**
原话："模型无持久化，须由**未来**治理临界区保证边集与版本不可变。"
整套"边不可原地改写、revision 不降密、前提版本绑定"的安全论证，建立在一个**还不存在的组件**上。规格成立 ≠ 平台成立，这正是 ACCEPTANCE 最后那句"模型形式成立不证明平台前提成立"。

**B2. 一条坏边可能让节点永久读不出来，而且 v1 没有清理通道**
规则是：任一条来源边 unknown，或目标缺失/遗忘，就"使当前节点MAX并隔离拒读"；而且"unknown/悬空旁证**不能靠清理移出**安全计算"；同时"首版不接受retract事件"、禁止原地改写。
连起来看：**坏边只能靠 Govern 新建纠正版本来修**，而前面 B1 说了，保证这套机制的东西还没实现。
**[推断，请核实]** 如果一个普通写入者就能造出一条悬空边，那他就能让指定节点长期失效——这是个可用性/低成本骚扰的口子。需要你确认：写边需要什么权限？一条坏边从产生到被清除，现在有可执行的流程吗？超时多久？

**B3. 记忆投毒/提示注入，文档明说没证明**
原话："尚未在真实宿主或 LLM 证明不会受记忆投毒或提示注入影响；控制字符检查不等于这种证明。"
对你这行尤其要紧：**网页、文件、工具返回值写进记忆后，永远只能当数据，不能当指令**。这条现在只是架构约定 + 测试夹具（`FixtureReceiver`），不是真实宿主里的保证。

**B4. "生产档"这个词比实际强**
常规生产档要求"全部 C 项和**除 R04 外**的 R 项"，power 档才要求 R04。而 R04 是"strict 文件/目录/审计/轮转**真实持久化**"。
也就是说：**一份"生产档通过"的登记，可以不包含真实持久化与轮转的验证**，而 README 又明说不提供掉电安全承诺。对外别用"持久化可靠"这类词。

**B5. 证据链靠人，哈希不能自证现场**
原话："输出与复核身份须由**可信外部采集**，哈希不能认证生产现场。**临时合成证据只测试判定逻辑**。"
意思是：登记表能证明"有人填了一份格式正确的证据"，不能证明"这份证据是在真实生产环境采的"。这类控制只对**诚实的人 + 有纪律的流程**有效。别把它当技术保证卖.

### C 级：用起来会持续困扰你的

**C1. 多写者状态永远只能说"unknown"**
"它只证明该实例在指定时刻报告过此状态，不证明实例此刻仍然存活。"且未建立可信实例身份前，不允许用共享状态戳判断单个写者健康。
后果：运维界面上会长期出现大量 unknown。**当 unknown 变成常态，人就不再读它了**——这是这种诚实设计最大的实际风险，需要单独设计一个"unknown 比例"告警，否则诚实会退化成噪音。

**C2. 降密流程尚未实现，默认拒绝**
"declassification独立授权流程尚未实现，默认拒绝。"
好事（安全默认），但意味着**写进去的敏感东西没有官方出口**。实际业务里，人会绕过制度，而不是绕过代码。要提前给一个合规的申请路径。

**C3. 时钟与文件系统被信任**
写者状态依赖本地时钟（未来时间即 unknown）。多机、容器、时钟漂移场景下会误报。部署前要确认 NTP 与时钟漂移预算。

**C4. 规格锁是"人造闸门"，不是控制**
每个文件名字+字节摘要都锁在 `spec-tree.lock.json`，改任何字都要人工更新清单，而"CI 不会自动重写清单"。好处是防悄悄漂移；风险是**久而久之会有人为了变绿直接刷清单**。文档自己写了"一致不等于获准发布""不得修改测试来掩盖语义漂移"——这两句是纪律，代码不强制。
