## 先说结论

**这套东西本身并没有失控；真正的问题是，它现在还不适合给别人用，但文档写得太像能用了。**

你要交付的其实是三类东西，风险差别极大：

| 你给出去的是什么 | 风险 |
|---|---|
| 一套架构思路 + 验收清单（让人读、借鉴） | 低，甚至值得给 |
| 一个参考实现，让别人跑 `check_all.py` 验证规格 | 中，主要风险是别人会误读“绿了” |

README 自己写得很清楚：“设计开发中，不是已发布的1.0运行时”“不提供生产存储/MCP服务或掉电安全承诺”“CI绿不等于运行时已完成”。ACCEPTANCE 里 C01–C10、R01–R09 **全部 NOT_RUN**。

## 最该担心的三件事

### 1. 安全模型的地基依赖一个“还没造出来的部件”

SECURITY_MODEL 一边说“首个核心版本禁止原地改写已提交 revision 的边”，一边自己承认：**“模型无持久化，须由未来治理临界区保证边集与版本不可变。”**

也就是说：“只能追加、不能篡改历史”这个承诺，目前只是**约定**，并没有对应机制。真正防止篡改的东西，是“未来的治理临界区”。谁要在那之前拿它存真数据，“历史不可篡改”就只是一句话。

同类问题还有“declassification 独立授权流程尚未实现，默认拒绝”。默认拒绝是正确做法，但后果是：一旦某条记忆被标记为敏感度偏高，就没有正常通道来解除。用户只会看到“这条记忆读不出来”。

### 2. 失败关闭策略在运维中容易变成“把用户记忆锁死”

这套设计的核心安全策略是 MAX 隔离：**只要有一条来源边是 unknown，或者目标缺失/遗忘/不可解析，整条记忆就会被隔离、拒绝读取，直到治理确认**；而且“unknown/悬空旁证不能靠清理移出安全计算”。

从安全上看这是对的（宁可读不出来，也不要读错）。但从产品上看：

- 普通用户会体验到“我的记忆突然消失了”；
- 唯一的解法是走治理流程，而文档里没有给运维人员一份“怎么解除隔离”的操作手册（RECOVERY.md 我没读到，不确定有没有）；
- 现实里运维压力一大，最省事的做法就是**把这道检查关掉**，于是整套安全属性一次性失效。

这是“安全设计很好、但会被运营现实反向压垮”的典型形态。要么补一份解除隔离的 runbook，要么把隔离做成受限的“以低权限+显式告警读出来”，让别人没必要砸墙。

### 3. 最现实的攻击面，明确不在保证范围内

这是记忆系统给外人用最该紧张的一条，文档自己也承认：

- **“尚未在真实宿主或 LLM 证明不会受记忆投毒或提示注入影响；控制字符检查不等于这种证明。”**
- 隔离接收器（source_boundary）：**“同进程受信代码及其他消费端不在保证范围内”**；“FixtureReceiver 不是宿主、模型或认证系统”。
- 边界：**“不防有本地完全控制权的管理员重写全部历史与密钥”**；“时间/资源侧信道、平台级权限、真实认证和并发策略快照未实验，不声称零泄漏”。

翻译成大白话：**别人往记忆里塞一段恶意文本，再让模型读出来照着做，这件事没有被证明防住。** 而这恰恰是“记忆系统给别人用”最容易出事的场景。文档写了“检索数据不授予指令权限”的原则，但原则和证明之间还差一个真实宿主的对抗测试。

## 其他具体问题（按“会不会真出事”排）

| 问题 | 依据 | 后果 | 建议 |
|---|---|---|---|
| **发布闸门 exit code 0 可能表示“正在阻断发布”** | ACCEPTANCE：`release_gate.py` “可以在发布被阻断时返回 0” | 任何人把它接进 CI、只看退出码，就会把本该阻断的版本放出去 | 改成 0=通过、非0=不通过；或 CI 里强制解析 JSON，不看退出码 |
| **“真实持久化/轮转”（R04）在常规生产档不是必需** | 仅 power 档要求 R04 | 掉电、磁盘满、日志轮转这类**最常见的数据损坏原因**，在最宽松的发布档里可以不做 | 建议把 R04 提为常规必需。持久化不该是可选加分项 |
| **证据链可以自己证明自己** | “输出与复核身份须由可信外部采集，哈希不能认证生产现场”；登记表“是对候选的事后审阅，不要求其自身的 Git SHA 等于候选”；“临时合成证据只测试判定逻辑” | 谁准备证据，谁就能让闸门变绿。这不是漏洞，但是**审计叙事容易被高估** | 对外说明白：这套哈希证明的是“文件没被改”，不是“事情真的发生过” |
| **删除/保留只有规划，没有实现** | CONTEXT_OUTPUT/RETENTION：“提供纯谓词与反例，不实现认证、原子发送或清理” | 用户要求“删掉我的数据”时，没有可交付的实现。对外供人使用会有合规问题 | 交给别人前，写清“本系统不承诺可删除”，或补最小删除实现 |
| **多实例/共享盘部署会悄悄失去保证** | “未建立可信的实例身份…不支持由共享状态戳判断单个写者是否健康”；writer_status 信任本地文件系统与时钟 | 别人把它放到 NFS / 多容器 / 跨主机，异常时是“静默失效”，不是报错 | 部署文档里硬性写死“单写者、本地盘”，并在启动时检测共享盘直接拒绝启动 |
| **旧数据没有升级路径** | “无写者的旧回执不补签，旧审计行不满足新格式，不在真实库上自动迁移”；R08 NOT_RUN | 已经存了记忆的人升级时会卡住，或者新旧混在一起 | 发布前给一条“旧数据 → 新格式”的明确说法，哪怕结论是“不支持” |
| **别人要对接的 API 还是草案** | README：“四应用字段草案”“输入 schema 提案”；COMPATIBILITY “仅 44 个顶层 op 候选”；事务协议“仍全部 NOT_RUN” | 别人照草案写代码，正式版一改就返工 | 明确标版本号与“破坏性变更不预告”，或者干脆先不给接口 |
| **验收矩阵读不出信息量** | C01–C10、R01–R09 全 NOT_RUN | 全是 NOT_RUN 的表格，等于“没信息”。分不清“没跑”和“跑了没过” | 加第三态（FAIL）和日期、负责人，让矩阵能反映进展 |
| **术语墙太高** | MAX、旁证/矛盾边、M1/M2 kill 点、C1–C5 与 C01–C10 与 R01–R09 三套编号并存 | 外人读三页就放弃，于是只记住“这是个记忆系统” → 正好是最危险的误解 | 每个文档顶部加一行状态标签：`规格` / `仅参考实现` / `隔离已跑` / `生产已验证` |
| **一套编号三种含义** | 文档里 C1/C2/C3（上下文闭环）与 C01/C02（验收判据）极易混 | 评审时互相引用会指错对象 | 换掉其中一套前缀 |

## 别人接手时会遇到的情况（按角色）

- **架构读者**：会被文档的诚实打动，但也会被密集的限定语淹没，最后只记住功能列表。**这是当前最大的交付风险：诚实被稀释成了噪音。**
- **想跑一下的开发者**：会跑 `check_all.py`，看到绿色，然后以为系统可用。文档里“CI绿不等于运行时已完成”这句话，抵不过终端里那一片绿。
- **想接进去用的团队**：会撞上草案 API、NOT_RUN 的运行时门禁、以及“默认拒绝且无解除通道”的隔离策略。大概率会在第三周自己动手把安全检查绕开。

## 如果一定要给出去，我的最小条件清单

1. 交付物改名：从“记忆系统”改成“**记忆系统规格 + 参考模型 + 验收清单**”，标题里就写明。
2. 在 README **第一行**放一句不带修饰的话：“当前不可用于存放真实数据。”现在这句藏在第三段。
3. 修掉 `release_gate.py` 的退出码语义，或至少在 CI 模板里写死“不准只看 exit code”。
4. 每个文档加状态标签，让人一眼看出哪些是规格、哪些跑过、哪些没跑。
5. 补一份《解除隔离运维手册》，否则那条安全设计一定会被运营压力拆掉。
6. 对外明确三条**不做**的承诺：不防本地管理员、不承诺可删除、不证明能防提示注入。
7. 如果对方真要存数据：单写者、本地盘、只存可重建的派生数据，且先做一次“故意拔电源”的演练。
