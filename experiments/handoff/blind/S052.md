## 三个会被误用的地方，先说清

1. **单测绿 ≠ 发布绿。** 文档开头就切断了两者：登记的是候选提交的发布证据，不是最近一次单测计数。任何人拿 CI 绿条当验收，都是把矩阵读反了。
2. **`release_gate.py` 返回 0 ≠ 可发布。** 无参数模式只检查登记表自身一致性，**在发布被阻断时也返回 0**。真正的判定是 `--profile production --candidate <40位SHA>`：0 才是证据齐全，3 是缺必需 PASS，2 是登记/证据/参数无效。所以"能不能说做完"有一个可执行的答案：跑这条命令。除此之外的一切绿灯都不算。
3. **哈希不认证现场。** 文档明写"输出与复核身份须由可信外部采集，哈希不能认证生产现场"，并禁止把临时合成证据当验收（"只测试判定逻辑"）。意思是：判定器验的是**台账自洽**，不是事实。你能对外说"我们有证据"，不能说"我们的证据已被机器证明为真"。

## 到"能说做完"还差什么（按成本排）

1. **定档。** 常规生产档要全部 C + 除 R04 外的全部 R；power 档还要 R04。**这一步是纯决策，却决定后面差 1 项还是 2 项**，先定。
2. **补 C01–C10 的逐项锚点**（哪个测试、哪条用例、哪次变异变红）。文档缺口，成本最低。
3. **补 API 边界、44 op 兼容面、事务**的对外口径：要么做成"已知不支持"，要么补实现。前者便宜，但必须写进对外材料。
4. **每个 PASS 备一份证据包**：文件字节、项目 ID、提交、环境范围、数据/策略摘要、命令、输出、退出码、一次故障注入 FAIL + 一次撤销 PASS、**两名不同复核人**。19 项各自独立，"双人复核"是纯人力——这大概率是真正的长杆，不是技术。
5. **R01–R09 生产实跑**，每项都要有 FAIL 与 PASS 对照。
6. **若走 power 档，R04 是硬骨头。** "strict 文件/目录/审计/轮转真实持久化"与"纯文本 Markdown 真源、零二进制 DB"这个架构取向正面冲突——明文真源上做严格权限、审计轮转和防篡改，正是最难的一项。文档把 R04 从常规档摘出来，我判断这不是随手，而是架构决定的现实。**建议对外明确只承诺常规档**，否则客户会按 power 档读 R04。

按这个顺序，3 天能做 1–3，4–5 以周计且取决于复核人排期。
