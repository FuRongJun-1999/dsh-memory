# S047

## 题面（所有样本同一题面；输出由不同条件产生，评分时不必关心条件）

我该不该现在就把它开源出去？你给个说法。

## 输出

我打算给你一个直接可执行的判断：在当前信息下，我建议你**不要现在就“全量、永久、不可逆地开源”**，而是先做一次开源前审计；审计通过就尽快全量开源，不通过就只开放外围层或延后。下面我把判断依据、硬门槛、红线、许可证选择和今天就能做的动作写清楚，你照着决策即可。

## 我的说法

**默认答案：现在别全量开源。**  
今天最多做“可逆动作”：私有仓库补齐 README/LICENSE、跑密钥和依赖扫描、划清开源边界、发一个不含核心的 SDK/CLI/示例层。除非你满足下面“立即全量开源清单”，否则不要把核心仓库直接推公开。

## 我替你定的前提

你把“它”说得很模糊，我按以下默认情况判断：**这是一个有真实用户或潜在商业价值、包含你自有代码和第三方依赖的软件项目，不是周末玩具。**  
理由：开源发布对已发布版本不可逆，而你没有给项目性质、权属、依赖、商业模式。我不能把不可逆动作建立在“应该没事”上，所以默认走最保守路径。

例外：如果它只是无用户数据、无商业计划、无第三方许可证限制、无密钥的玩具项目，那今天就 MIT 开源，不用纠结。下面内容不适用于这种玩具。

## 为什么不是“想开源就开源”

开源释放的是修改权和分发权，不是发一篇博客。你已经发布的版本，别人可以永久使用、fork、商用，具体取决于许可证；你可以停止维护新版本，但不能收回已发布版本。  
所以真正的问题不是“我愿不愿意让人看代码”，而是：

1. 你的价值是不是主要在代码秘密本身？
2. 你有没有托管、服务、集成、数据、品牌、标准这类护城河？
3. 你能不能承受竞争对手直接拿走核心代码做产品？
4. 你有没有法律权属和第三方许可证风险？
5. 你有没有准备好接 issue、安全报告和用户预期？

如果价值在代码秘密本身，且没有服务/生态/数据/品牌护城河，现在全量开源是自削议价。如果价值在托管、支持、集成和生态，开源可以加速获客。这个判断比“开源社区很美好”重要得多。

## 立即全量开源的硬门槛

以下每一条都要过，不是差不多就行：

1. **权属清晰**：代码不是前雇主、客户、外包方或联合创始人的争议资产；没有“下班时间写的但用了公司电脑”的模糊地带。
2. **第三方依赖许可证兼容**：没有把 GPL/AGPL 依赖混进你想用 MIT/Apache 发布的核心；生成 SBOM，检查传递依赖。
3. **密钥和敏感信息干净**：不仅查当前文件，还要查 git 历史。token、私钥、内网地址、云账号、数据库连接串、客户数据、个人数据都要清掉。
4. **安全基线过一遍**：依赖漏洞扫描、静态扫描、基本威胁建模。至少知道哪些接口不能公开。
5. **专利和商标想清楚**：项目名、logo、域名是否可公开使用；有专利顾虑就用带专利授权的许可证，比如 Apache-2.0。
6. **开源边界明确**：哪些目录开源、哪些企业功能闭源、哪些配置和运营数据永不进公开仓库。不要同一仓库里混着“核心闭源模块”。
7. **许可证和治理文件定了**：LICENSE、README、SECURITY.md、CONTRIBUTING.md；个人项目用 DCO 就够，公司项目再考虑 CLA。
8. **发布包能独立构建**：在干净环境 clone 下来能跑，不依赖你本机私有路径和内网服务。
9. **支持负担可承受**：你愿意接 issue 吗？不愿意就明确“best effort”，并关掉不合理的支持预期。
10. **商业模式不被误伤**：如果你靠卖核心功能，先确认开源后你卖的是托管、支持、合规、企业集成还是别的，而不是“把唯一值钱的东西送出去再想”。

## 红线：碰到就别现在全量开源

- 有权属争议或前雇主/客户资产混入。
- git 历史里有密钥、客户数据、个人数据，且没清理。
- 核心依赖是 AGPL/GPL 且你的许可证策略没想清楚。
- 项目唯一价值就是那套算法/规则，且没有服务或数据护城河。
- 你还没想清楚靠什么赚钱，但指望开源后自然有商业模式。
- 你准备用“禁止商用”之类的自定义许可证，却对外说“开源”。那不是开源，会引发社区预期错位。

## 今天就能做的执行顺序

**今天：**
1. 冻结当前版本，打 tag，别在公开前继续大改。
2. 跑密钥扫描和依赖扫描，重点查 git 历史。
3. 列出“公开层”和“私有层”：CLI、SDK、协议、插件接口、示例可以公开；服务端核心、训练数据、运营配置、客户集成不要公开。
4. 补 README：项目做什么、不做什么、状态是 alpha/beta、如何构建、如何报安全漏洞。
5. 选许可证，先放草案，不急着推公开。

**48 小时内：**
1. 在干净目录 clone 私有仓库，按 README 从零构建一次。
2. 建一个私有“公开候选仓库”，只放拟开源内容，再跑一次扫描。
3. 决定许可证和商标策略。
4. 如果通过，发 alpha，明确“接口可能变”；如果不通过，只发外围层或继续私有。

**2 到 4 周：**
全量开源或放弃全量开源。不要拖成“永远准备中”，但也不要今天裸发核心。

## 许可证怎么选

- **默认推荐 Apache-2.0**：适合工具、基础设施、SDK，带专利授权，企业更容易接受。
- **想极简就用 MIT**：适合小库和示例，但专利保护弱。
- **想强制网络服务回馈就用 AGPL-3.0**：但你要接受它劝退一部分企业用户。
- **开放核心**：核心用 Apache-2.0/MIT，企业功能放独立私有仓库，边界写清楚，别在同一仓库里混许可证。
- **不要用“源码可见但禁止商用”然后自称开源**。你可以做 source-available，但要说清楚它不是 OSI 开源。

## 如果你今天非发不可

只发**剥离核心的最小层**：CLI、SDK、协议定义、插件接口、示例、文档。不要发服务端核心、训练数据、运营配置、客户集成、内部密钥。标注 alpha，保留私有核心继续开发。这样你获得曝光和反馈，但不把不可逆的核心资产一次性交出去。

## 最终说法

**现在不要全量开源核心。今天做开源前审计；通过就尽快发，不通过就只发外围层或延后。**  
如果你问我“就现在，全量，核心仓库直接公开”——我的回答是：**不建议。** 除非上面十条硬门槛你已逐条过完，并且你清楚自己开源后靠什么活。
