这里有两道不同的检查，别混为一谈：

1. 核心版本锁 —— 盯的是核心契约。改动它必须升版本号，并写清为什么改。
2. 目录清单 —— scripts/spec-tree.lock.json 记录规格目录下每个文件的名称和内容摘要（样例和已生成报告也算在内），scripts/spec_tree.py 是只读检查器，负责逐文件比对。

清单只做比对，不会自己更新：增删改任何文件都得人来审阅，CI 不会帮你重写清单。
清单一致只说明"没被意外改动"，不代表获准发布。

## 我做的判断和理由

**1. 只依据 README 改写，没有补内容。** 我本想打开 `WORKSPACE_INDEX.md` 和 `docs/BASELINE_ACCEPTANCE.md` 核对“哪些已验收”，被权限拦了。既然核对不了，我就不替它们编简介，宁可字段少一点：所有链接后面的括号说明，都是从原 README 里原有的短语搬过来的，没有一个是我新写的推测。

**2. 把“能/不能”提到最前面。** 原文的三条免责是分散的（开头引用块、定位段末尾、验证段末尾），读者读完三十个链接才知道不能部署。我合并成一张“能/不能”清单放在最前，因为对这类仓库来说，“它现在能不能用”是唯一的首要问题。重复风险我也认了：结尾“三条底线”和开头有重叠，但第 2、3 条（CI 绿不等于完成、不许改测试）原文放在最后，是防止误用的硬规则，值得留两处。

**3. C1–C5 加了“五个递进的隔离验证阶段”这句。** 原文只列了 `C1隔离存储`、`C2可运行动作环` 这种名字，没解释 C 是什么。不解释的话，新人无法判断这是一套方法论还是五个模块。我没有解释每个 C 具体做了什么——那要读文档，我读不到。

**4. rev12 原样保留，没解释。** “旧 rev12 五项问题”这句话对外部读者等于没有信息。但 ADR-0001 我打不开，五项问题具体是什么我不知道，编一个解释比留着更糟。我只把它挪到“和上游的关系”里（它本来讲的是历史遗留处置，不属于使用入口）。

**5. 术语替换。** 这几处原文是行话，我换成具体行为：

| 原文 | 改成 | 理由 |
|---|---|---|
| 规范化核心契约 / 核心版本锁 | 核心契约的改动要升版本号并写原因 | “锁”在原文里没定义，读者不知道它锁什么 |
| 字节摘要 | 内容摘要（哈希） | 我不知道脚本用哪种算法，不写死 SHA-256 之类 |
| 掉电安全承诺 | 不承诺掉电不丢数据 | 后者是前者的直白说法 |
| 可执行契约框架 | 能跑通的规格检查工具 | 原文这个词组同时指文档和工具，容易误解为“可执行的运行时” |
| 方案基线验收单等中性名 | 保留原名 + 说明它在回答什么问题 | 中文文件名本身不含信息，加“看清楚哪些已经过、哪些没有”才有用 |

**6. 组织结构改了，但没删链接。** 原文 30 条链接我逐条搬进分组表格，一条没删、地址一字未改（含相对路径的 `<>` 写法我改成了纯路径，因为分组表格里 `<...>` 没法包）。`~~~text` 代码块保留原样，避免命令被误读成其他东西。

**7. 我加的两处“黏合剂”句子**，是解释性而非事实性的：「一句话：现在交付的是定义和自检，不是做好的东西」和「清单一致只说明没被意外改动，不代表获准发布」。后者的意思原文有（“一致不等于获准发布”），我只是展开成人话；前者是从三条免责里归纳的，没有新增事实。如果你想严格零新增表述，删掉第一句即可，其余不受影响。
